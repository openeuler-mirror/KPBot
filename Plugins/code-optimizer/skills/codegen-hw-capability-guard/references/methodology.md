# 硬件能力的探测与拒绝 — 方法细节

> 来源与适用范围：本文整理自原始工程实践记录（`SKILLS_ALL.md` 汇编稿），未提供可公开引用的上游文档，也未经独立复现。文中阈值、收益倍数与机器相关数据绑定当时的生成器版本、硬件与配置，迁移到其他环境前必须重新测量。置信度：中；未覆盖范围与平台差异见正文。

## 适用背景

生成器把硬件参数写进产物：向量长度决定一次处理多少个元素，流式模式决定寄存器与内存的访问方式，线程规模决定分区。这些参数一旦写死，产物就只能在与写入时相同的机器上工作。

把常量改为探测值，会引入两类新问题。第一类是换算：探测接口给出的单位未必是生成器需要的单位。第二类是失败方式：探测不到、探测到不支持的值、环境变量覆盖为非法值，这三种情况都必须在生成阶段处理完，不能留给运行期。

## 1. 探测来源与优先级

探测按三级取值，优先级从高到低。

第一级是显式覆盖，通常是一个环境变量。它存在的理由不是方便，而是可控：当探测接口在容器、虚拟化或新平台上不可用时，使用者需要一条不依赖探测结果的路径。

第二级是运行时接口，例如系统的 ABI 参数文件或架构特性寄存器。这一级的读数代表当前机器的真实配置。

第三级是默认值。默认值应当取最常见且最保守的那个值，并在文档中写明它是默认值而非探测结果。默认值存在的意义是让未支持的平台上仍能完成生成，但它不能掩盖探测失败：若走了默认值，应当记录一条日志，说明未探测到。

三级的顺序不可颠倒。把默认值放在探测之前，等于关掉了探测；把运行时接口放在覆盖之前，等于取消了使用者的控制权。

## 2. 单位与精度的换算

探测接口给出的单位与生成器需要的单位经常不同，换算错了不会报错，只会让产物按错误的宽度工作。

以参考实现为例，ABI 参数文件记录的是字节数，而生成器需要的是浮点车道数。单精度下每车道四字节，因此车道数等于字节数除以四；双精度下每车道八字节，除数随之改变。

由此得到一条要求：车道数不能独立于精度计算。生成状态里应当保存字节数与精度两个量，车道数由二者推导，并在精度改变时重新推导。若把车道数当作独立常量缓存，切换精度后它会保持旧值，产物按错误的宽度生成。

推导顺序同样重要：精度必须在生成汇编之前设定完成，因为许多宽度相关的量在生成过程中被读取。先设精度再生成，与先读宽度再设精度，结果不同。

## 3. 拒绝点的位置

不支持的硬件参数必须在生成入口拒绝，而不是在产物运行时失败。

位置的理由是信息完整性。生成阶段持有全部信息：探测到的值、支持范围、以及请求的组合。运行阶段只知道自己崩了，无法判断是编译选项、内存对齐还是宽度不符。把拒绝点放在运行时，等于把一条本可以说清的诊断降级成一次崩溃。

拒绝时的错误信息应包含三个要素：实际探测到的值及其单位，支持的取值范围，以及一两条可行的处理办法。缺少实际值，使用者无法判断是自己机器特殊还是探测写错了；缺少单位，数值会引发歧义，这在历史上真实发生过。

单位歧义有一个确定的症状：报错里的数值相差四倍或八倍。看到这种量级的偏差，应当先怀疑单位，而不是怀疑探测接口。

## 4. 失败形态与静默降级

需要防范三种失败形态。

第一种是探测失败后静默使用默认值。产物生成成功，但因为默认值与实际不符，产物在本机就不对；若产物被拷贝到另一台机器，错误会以“在别人机器上错、在我机器上对”的形式出现，排查方向会被引向环境差异。

第二种是探测到不支持的值后截断到最近的支持值。这与静默降级同类：产物能生成、能运行，计算结果却在语义上不等价。硬件参数的语义通常不可近似，宽度差一档意味着累加顺序改变。

第三种是覆盖值非法时回落到默认。使用者显式设置了值，说明他有理由；把它替换成默认值而不告知，会让使用者以为设置生效了。

这三种情况的共同处理方式是：拒绝，或接受并在日志中明确记录降级事实。选择哪一种取决于该参数是否影响数值语义。影响语义的必须拒绝；只影响性能的可以接受并记录。

## 5. 测试纪律

为“不支持就必须失败”这类契约写测试，顺序比覆盖率更重要。

先写一条断言失败行为的测试，确认它在当前实现上失败，再提交实现。这条纪律的价值在于排除假通过：若先写实现再补测试，测试可能只是描述了实现的现状，而不能证明契约被建立。

测试应当断言错误信息的内容，而不只是断言抛出了异常。只断言抛出，会让单位错误这类缺陷穿透：实现确实拒绝了，但报错里的数值相差八倍，使用者按这个数值排查会走错方向。

失败路径的测试需要两类环境：支持该参数的机器，与不支持的机器。若只有一类环境，至少要用覆盖机制构造出两类情形，例如把覆盖值设为一个不支持的值，验证拒绝逻辑与错误信息。

覆盖路径本身也要有测试：设置覆盖值后，产物应当按覆盖值生成，而不是忽略覆盖继续探测。这条路径最容易被漏，因为默认路径覆盖了绝大多数执行。

## 6. 验证

验证按四组组织。

第一组是探测正确性。在已知配置的机器上，探测结果应当与配置一致，并记录来源，说明走的是覆盖、探测还是默认值。

第二组是拒绝正确性。对每个不支持的值，验证生成被拒绝、错误信息含实际值与支持范围、单位正确。

第三组是换算正确性。对每种支持的精度，验证车道数由字节数正确推导，且精度切换后重新推导。

第四组是产物一致性。用探测值生成的产物，其汇编文本中与宽度相关的部分应当与手工指定同一宽度时的产物一致。

## 7. 约束

验证范围是单机、单进程、单一线程团队。以下情形未经验证：跨节点参数不同；容器内探测接口不可读；同一进程内混用多种宽度；运行期改变硬件参数。

上述情形下探测来源的优先级与默认值的取值需要重新确定，不能直接沿用本文结论。
