# 模型精度分析

手头有两份（或多份）**同一批题目**的推理结果 JSON，来自 torch / torch_npu 精度评测工具。
任务不是复述模型输出，而是回答一句话：**这次优化让模型变差了吗？**

## 快速开始

```bash
python3 scripts/analyze_precision.py <before_run_dir> <after_run_dir> \
    [--dataset-name aime2024.json] [--fail-on-regression]
```

脚本只读文件，不修改任何数据。报告含两次准确率、未答/截断数、逐题明细、回归项和改善项。
退出码语义（CI/脚本化调用一律按此判断，**退出码 0 才是达标**）：

| 退出码 | 含义 |
|--------|------|
| 0 | 两次运行可比，且没有回归 |
| 1 | 两次运行可比，但存在“对→错”回归（`--fail-on-regression` 时抛出） |
| 2 | 两次运行**不可比**（gold 或题号不一致），结论为“不可判定”，不是达标 |

`--dataset-name` 指定的 json 不存在、或 `merge/` 下有多个 json 却没指定时，脚本直接报错退出，
不会静默换成别的文件——否则会跨数据集比较，结论完全无效。

## 为什么不能直接比文本

推理是非确定性的：同一个正确答案，模型的措辞每次都不一样。直接 diff 原文或做字符串比较，
会把大量“答案对、写法不同”的题判成错误，得出假回归。所以流程永远是：

1. 从每条 `prediction` 里**抽取最终答案**（数值 / 选项字母 / 文本），容错处理单位、`\text{}` 包装、千分位、标点；
2. 拿抽取结果和 `gold` 比；
3. 再看“优化前对、优化后错”的题——**回归数为 0 才叫精度达标**，准确率的绝对高低是次要信息。

脚本已经把 1~3 做完了，不要自己重写抽取逻辑。

## 输入长什么样

```
opendatas/output/
└── <dataset_name>/                       aime2024_gen, aime2025_gen, gpqa_gen_diamond ...
    └── <run_dir>/                        目录名 = 标签 + 时间戳, 例如 20260523-gpqa-16k_2026-11-04-05-06_dsv4pro
        ├── merge/
        │   └── <dataset>.json            合并后的推理结果, 例如 aime2024.json / GPQA_diamond.json
        └── tmp_*.json                    分片中间结果, 分析不需要
```

合并后的 JSON 是以整数下标为 key 的 dict，每一项：

```json
{"origin_prompt": "...", "prediction": "<推理过程 + 最终答案>", "gold": "127", "exec_times": 1}
```

`gold` 的类型决定抽取方式：AIME 是数字（模型通常写成 `\boxed{...}`），GPQA-Diamond 是
`A`~`D` 的选项字母（模型被要求以 `ANSWER: X` 结尾）。不确定时先读一份 JSON 的第 0 项看清
`gold` 形态，比猜数据集类型可靠。

## 工作流

1. **确定两个目录**：优化前（基线）和优化后。用户可能给出完整路径、数据集名 + 实验标签，
   或只说“刚才那两次”。只在 `opendatas/output/` 下按目录名时间戳或 mtime 找，找到后**把两个路径
   回显给用户确认**再跑——基线找错，后面所有结论都是错的。只查到一次运行就先问清基线是哪次，
   不要拿别的数据集凑数。
2. **跑脚本**：见「快速开始」。自动在 `<run_dir>/merge/` 下找结果 JSON，找不到时退化为
   `<run_dir>/*.json`；`merge/` 里有多个 JSON 时必须用 `--dataset-name` 指定（不指定直接报错），
   指定的名字找不到也直接报错，不会静默回退到别的数据集。
3. **读结果**，重点看四个数：两次准确率、`未答/截断` 计数、`回归` 数、`改善` 数。
4. **对可疑回归做人工确认**（见下节），再给结论。

## 怎么读结果 / 怎么判断

- **回归题（对→错）是唯一的一票否决项。** 有回归就说明这次改动破坏了原本正确的题目，
  报告里要逐题列出 ID、gold、优化前后抽取到的答案，方便定位。
- **未答/截断数突增**通常是输出被截断（max tokens、EOS、模板变化），不是推理能力退化。
  对比两次的未答数：如果优化后从 0 涨到十几，优先怀疑截断，并在结论里明确指出这是截断问题，
  不要笼统说“精度下降”。
- **逐题明细里“答案不同但都判对”**是正常的非确定性，不需要在结论里逐条解释。
- **改善题**是加分信息，不能抵消回归：判定达标与否只看回归数。
- 纯时间表达式（`1.4 hours`、`3 hours 24 minutes`）和 `1,000` 这类写法由脚本按数值换算，
  报告中直接判对即可，不要再把它们列成“人工判定为格式差异”；只有脚本确实抽出数值不对时
  才需要人工复核。
- 若两次的题数或 `gold` 序列不一致（比如数据集版本不同），脚本会打出 `⚠️ gold 不一致` /
  `⚠️ 只出现在其中一次运行` 并跳过这些题的翻转判定，结论变成“不可判定”，**退出码 2**；
  这时先让用户确认两次跑的是不是同一份数据集，不要硬给达标结论，也不要把退出码 2 当成通过。
- 输出尾部有**未闭合的 `\boxed{`**（如 `...\boxed{21`、`...\boxed{\frac{1}{2`，即使前面已有完整 box）
  会被判为“未答/截断”，不会被当成数字算对或算错；这正是想区分“答案对但写法不同”和“根本没算完”的边界。
  唯一的例外是已经写出完整 `ANSWER: X` 的字母题，那本身就是完整答案。

## 抽取容差与人工兜底

| gold 类型 | 抽取方式 |
|-----------|----------|
| 数字 | 最后一个非空 `\boxed{}` 里的数值（长 CoT 里靠前的中间结果会被忽略）；无 box 时退化为全文最后一个数字；纯时间表达式按 gold 的单位换算（`1.4\text{ hours}`→84、`3\text{ hours and }24\text{ minutes}`→204、`204\text{ minutes}`→204，小时/分钟/秒都支持）；`1,000`/`1{,}000` 与 `1000`、`90\%` 与 `90%`、`5.0` 与 `5` 视为相等 |
| 选项字母 | 全文最后一个 `ANSWER: X`；没有时取最后一个 `\boxed{}` 里的字母，再退化为最后一个 A~D 字母（首个字母通常只是推理里的干扰项） |
| 其他文本 | 先取最后一个非空 `\boxed{}` 内容，去掉首尾标点后比较 |

仍然会有脚本抽不准的情况，例如 box 里是未求值的表达式（`\boxed{\frac{1}{3}}`，gold 是小数）、
box 里混着多个不相关数字、或模型用的单位与 gold 不同但数值确实不等（gold=4 小时，模型答 3.8 hours）。
遇到被判错但看起来明显的题，去 JSON 里读那一题的 `prediction` 原文：

- 如果正确答案确实写在里面，只是格式问题 → 按正确计，在结论里注明“该题属格式差异，非真实回归”；
- 如果答案是空的或被截断 → 按“截断”归类，不要归因到推理质量。

这一步很重要：把格式差异当成回归上报，会让用户回滚一个本来正确的优化。

## 结论输出模板

先给一句话结论，再给表和细节。控制篇幅，不要贴推理过程。

```markdown
**结论**：精度<达标 / 未达标>。准确率 X% → Y%（a/n → b/n），回归 k 题，改善 m 题。

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 准确率 | X% | Y% |
| 未答/截断 | i | j |
| 回归 / 改善 | — | k / m |

（有回归时）回归明细：
- 题 <ID>：gold=...，优化前 `...`（对）→ 优化后 `...`（错）
```

若有回归，补一句可能原因（截断 / 抽取格式 / 真实的数值偏差），并指出可以继续看哪几道题。

## 与 kpbot-app-tuner 流程的衔接

本技能是**验证类skill**，不参与候选优化列表，也不修改环境。典型用法是在
`accelerator-optimization`（NPU/GPU 推理优化）、`application-config-optimization`（batch/量化配置）
或 `compiler-optimization`（重编译、混合精度）完成一轮真实变更、并做完性能 A/B 之后调用：
用同一批题目跑基线版与优化版，确认优化没有把原本正确的题弄坏，再把结论回填该轮结果的
`validation_plan` / review 章节。性能收益为正但出现回归时，结论是回退或改用更保守的精度策略，
不能只按吞吐放行。

## 自检

改动抽取规则或报告格式后，先跑本目录自带的两组测试：

```bash
python3 tests/test_extraction.py   # 31 条抽取用例（含多 \boxed{} 与各类截断）
python3 tests/test_pipeline.py     # 8 组端到端（准确率/回归题号/退出码 0/1/2/dataset-name 门禁）
```

`evals/evals.json` 中的用例覆盖数字题、字母题、混合格式与干扰项场景，可直接用于技能效果对比。

## 边界情况

- **多组对比**：用户要比较 3 次以上运行时，按“基线 vs 每次”逐对跑脚本，再汇总成一张表。
- **只看单次准确率**：把同一个目录同时当作 before 和 after 传入即可，回归数必然为 0。
- **目录里没有 `merge/`**：脚本会自动退化到 `*.json`；同一层有多个 json 时必须 `--dataset-name` 指定，
  不会猜。若只有分片文件（`tmp_*.json`）说明结果还没合并，先让用户用评测工具完成合并，不要手工拼接。
- **路径含中文或空格**：命令里加引号。
- 报告里的数字必须来自脚本输出，不要凭印象改写；脚本没有覆盖的判断题，明确标注“人工确认”。
