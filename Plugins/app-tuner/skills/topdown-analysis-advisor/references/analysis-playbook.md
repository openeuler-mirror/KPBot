# 分析与建议规则

## 证据层次

用四种措辞区分证据强度：

- 观测：原始文件直接支持的指标、计数或调用路径。
- 解释：在已核实指标定义下，该观测代表什么机制。
- 假设：一种可能原因，仍需要补证或对照实验。
- 验证结果：执行可比实验后实际观察到的变化。

不要用“已定位”包装单个较大的百分比。
格式检查通过与根因成立是两个独立状态。
报告里的置信度来自来源、范围、窗口和交叉证据，不由解析器自动赋值。

## 阅读顺序

1. 先确认对象是否活跃，计数是否有效，是否为预期业务阶段。
2. 检查完整 Level1 结果和工具警告。
3. 阅读主要类别的下钻项，不把父子项累计排序。
4. 将机制与热点路径关联，保留范围差异。
5. 检查业务瓶颈是否确实落在这些 CPU 路径。
6. 形成候选动作或补采计划。

## 指标口径

相同名称不保证不同 CPU 或工具版本采用相同公式。
未核实的百分比分母记录为 tool-defined/unverified。
保留工具原始名称，避免把厂商指标强行改名成另一平台的指标。
只有明确采用同一分母且互斥完备的项才可检查总和。
解析器的 Level1 总和检查是格式合理性提示，不是公式认证。
允许显示舍入造成的小误差；明显偏差先查工具说明和缺测。
子项总和与父项不一致可能涉及覆盖范围、公式或舍入，应解释而非修数。

不要自动把分项重新归一化到 100%。
不要将 cache miss 百分比填入 Frontend Bound 或 Memory Bound。
不要用 stall 周期比例替代槽位比例。
IPC 不是独立性能目标；更高 IPC 可能伴随更多无用工作。
Retiring 也不等于业务有效工作，忙等和冗余计算可能退休大量指令。

## Frontend Bound

检查 Fetch Latency 与 Fetch Bandwidth 等实际存在的子项。
若有 L1I Cache/TLB 证据，关联热点代码布局、代码规模或指令页行为。
区分采样期间的启动代码与稳定热路径。
候选动作可以包括冷热代码分离、减少热路径体积或评估 PGO/LTO。
但需要构建条件、热点路径和可比性能测试支持。
不要仅凭 Frontend Bound 高就确定编译优化一定有效。

验证同时观察：

- 指令获取相关机制指标。
- 目标路径耗时或每工作单位 CPU 成本。
- 吞吐/延迟与正确性。

机制指标下降而业务目标不变时，检查关键路径占比和其他限制。

## Bad Speculation

区分实际输出中的 Branch Mispredicts 和 Machine Clears。
只有分支相关证据时才优先检查分支行为。
Machine Clears 不应统一解释为分支预测失败。
结合热点和输入分布判断是否值得调整算法或条件路径。
likely/unlikely、无分支化和数据重排都应作为候选实验。
无分支化可能增加计算量或数据访问，需实测权衡。
历史数据上的收益不能直接推广到当前输入分布。

## Backend / Core Bound

先区分实际存在的 Core、Memory 和 Resource 子项。
Core Bound 较高不自动意味着所有执行单元都饱和。
执行依赖、指令组合或可用并行度需要热点和指令证据区分。
不要仅按“0 ports non serialize”名称推导“减少序列化指令”。
先查该平台事件定义，未核实则保留原名称和待解释状态。
候选动作包括减少重复计算、缩短依赖链或评估向量化。
向量化需验证语义、精度、尾部处理和部署平台能力。

## Backend / Memory Bound

Memory Bound 反映工具定义下的数据访问受限贡献。
它本身不足以区分带宽饱和、依赖延迟、缓存问题或远端访问。
L1 Bound 也不直接等价于“L1 cache miss 高”。
继续读取 DTLB、Forward hazard、Pipeline 等已有子项。
子项缺失时明确缺失，不依据名称补造数值。

| 待区分机制 | 有帮助的证据 | 可测试动作 |
| --- | --- | --- |
| 带宽压力 | 实测带宽、可持续基准、每工作单位搬运量 | 减少复制、分块、缓冲复用 |
| 依赖访存延迟 | 热点访问链、延迟采样 | 数据布局、批处理或预取实验 |
| TLB 压力 | TLB/walk 证据、工作集 | 页面策略或减少离散访问 |
| 远端访问 | NUMA 流量、线程与内存归属 | 放置策略实验 |
| load/store 冲突 | 对应事件定义、热点指令 | 调整重叠访问或布局 |

单凭 LLC miss 比率不能确认带宽饱和。
预取是否有效取决于访问可预测性、时机及额外带宽成本。
大页、绑核等动作可能涉及系统配置，建议与执行分开。

## Retiring 占比较高或较低

较高时仍需检查每单位业务是否做了冗余工作。
较低时先解释其他受限类别，不直接断言算法有问题。
若目标是减少成本，可考虑指令数/请求或 CPU 时间/请求。
只有已知业务工作量时才计算每单位工作指标。
不要用采集秒数替代未知请求数。

## CPU 之外的限制

topdown 不能完整解释 I/O 等待、网络、锁等待和外部依赖。
低 CPU 活跃度或尾延迟问题应结合系统及请求链路证据。
不要为了给出 topdown 结论而忽略业务主要时间花在 CPU 之外。
交付可以是“当前证据不足以用 CPU 微架构解释主要延迟”。
随后提供范围明确的下一步测量，而不是强行生成代码优化动作。

## 建议条目

每条建议写明：

1. 动作名称和唯一 action_id。
2. 关联 finding_id 和原始证据位置。
3. 机制假设与成立条件。
4. 变更对象及单次实验变量。
5. 需要固定的业务与环境条件。
6. 机制指标、业务指标和正确性检查。
7. 有收益、无收益、退化三种结果的下一步。
8. 停止或恢复原配置的条件。

机制成立但动作无效时不要抹去原诊断，应记录实验结果。
局部指标改善但业务目标无变化时，不标记端到端优化成功。
建议状态使用 proposed / tested / rejected / reverted 等明确值。
默认新建议是 proposed，收益为未知。

## 优先级

优先考虑在关键路径、证据较强、实施成本合理的动作。
候选百分比相近时可先选择更容易证伪或风险更小的实验。
未知业务目标时给出条件优先级，例如“若目标是 CPU 成本”。
不要用任意固定阈值替代业务上下文。
历史案例可以提供候选方向，不能充当本次测量证据。

## 停止分析的合理结果

- 关键证据不足且当前环境无法补采。
- 工具输出格式或公式未知，需要版本资料。
- 预算已用完，可交付带边界的初步诊断。
- 当前主要问题超出 CPU 微架构范围。

上述情况仍应交付已知事实、限制和最有价值的下一步。
