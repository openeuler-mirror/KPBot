# 摊销条件

## setup 分解

LUT 侧 setup 分三段，摊销性质不同：

| 段 | 发生频率 | 摊销对象 |
| --- | --- | --- |
| 表构建（量化/归一化/偏置） | 每查询 | 该查询全部 probe 的列表 |
| 表构建（量化/归一化/偏置） | 每 (查询, probe) | 仅该 probe 实际扫描的码数（列表） |
| 打包/memset | 每列表 | 该列表的扫描时间 |
| 分发/指针准备 | 每列表 | 同上 |

每 (查询, probe) 建表只服务对应 probe，不得把单张表的成本摊到该查询访问的全部列表上，否则会低估多 probe 的建表成本。

先分段计时再谈消除：只有实际占比高的段才值得改。

## 成本口径与交叉点

- 收益判定比较两方案的实测总成本：「打包准备 + 打包路径扫描」vs「行指针准备 + 行指针路径扫描」，取两成本曲线的交叉点导出列表长度与查询数门槛。只看"被消除的 setup 占比"会误判：消除 20 μs 打包、扫描 200 μs 时占比 0.1 像不划算，若行指针准备与额外寻址只增加 2 μs，总成本实际从 220 μs 降到 202 μs。
- 行指针布局的间接寻址成本按"每内核调用一次"计，长列表下可忽略，短列表下与原拷贝同量级——短列表场景要实测而非假设。
- 启用条件写成显式 guard（nc 阈值、列表长度阈值），阈值来自总成本交叉点。

## 复用与生命周期

- 单 LUT（每查询）可在该查询的全部 probe 间复用；3D LUT（每查询×probe）语义不同，不得借复用改变。
- 复用表的有效期必须覆盖消费者执行全程；并发查询下表区共享只读，写回与统计不得落在表区。
- 索引缓存（保存索引复用）与 LUT 复用是两层：前者属基线冻结字段，后者属实现布局，分别记录。

## 验证

- 摊销条件两侧（满足/不满足）行为与结果一致；guard 命中率记录进实验。
- 表身份（构建参数、偏置）与冻结字段一致；改布局不改表内容，逐表哈希可证。
