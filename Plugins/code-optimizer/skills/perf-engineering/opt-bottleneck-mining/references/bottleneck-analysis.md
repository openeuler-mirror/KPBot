## 2. 分层结论
### 组件级
- milvus 是唯一 CPU 飙到 165%–186% 的组件；mem0 的 Python 81% 叶级时间停在 `_blocking`（等 gRPC 返回），真实业务 CPU <3% → **mem0 是等待者**。
  - **"<3%" 的口径**：py-spy 默认只采样运行中线程（不单独采空闲线程，空闲 worker 的等待不直接折算成 CPU 占比）；
    "81% 叶级 `_blocking`"的分母是**被采到样本数**。业务 CPU 占比要另用同窗口口径算：统计非 `_blocking` 帧的
    CPU 时间（分子）÷ 该进程同窗口总 CPU 时间（进程 CPU% × 墙钟，分母），两口径不可直接互推。
- mock 容器 CPU ~1%（LLM/embedding 已 mock），minio/etcd/runner 非目标。

### base 模式（优化前）
- 热点：`metadata["user_id"]` 的 **simdjson JSON 全量扫描**，stage1 累计 ~46%（45.88%）。
- 每请求在 20 万候选上做 JSON 过滤。
  （口径：20 万 = 20 用户 × 10000 的 flatidx 标定配置；系列里 81592→82480 是**另一套**分组基线 golden
  volume 的 8 用户 × 10000 数据池行数，两套配置不同、勿混用。）

### flatidx 模式（优化后）
- JSON 扫描消失，瓶颈迁移为 **faiss L2 距离内核** `fvec_L2sqr_sve_pf`（self ~52%）。
- 候选集收窄到每用户 ~1 万。

## 3. 量化归因链
| 量 | 值 | 计算 |
|---|---|---|
| 每请求 CPU 成本 | 67.7 → 21.5 ms-core/req | 优化前后 |
| 每查询浮点量 | ~31 MFLOP | 1 万候选 × 1024 dim × 3 flop（sub+mul+add） |
| 每秒浮点量 | ~2.4 GFLOP/s | 31 MFLOP × 76.8 req/s |
| 核当量 | ~0.86 核 | self 占比 × CPU 使用率 |
| 单核算力 | ~2.7 GFLOP/s/核 | 2.4 ÷ 0.86 |
| 理论峰值 | ~36 GFLOP/s（SVE-256） | 鲲鹏 950 |
| 利用率 | **~8%** | 2.7 ÷ 36 |
| 每查询 DRAM 流量（**推算**，非实测） | ~41 MB | 1万 × 1024 × 4B |

**结论修正：低利用率只能"不能排除"带宽受限，不等于"就是"带宽受限。** 单核浮点吞吐只有峰值 8%，
指令依赖 / 访存延迟 / 单累加器依赖链都能产生同样现象；41 MB/query 是按向量大小**推算**的，不是实测。
要下"带宽受限"结论并据此动降精度/降召回，必须先补：① **实测同一窗口 DRAM 带宽**（`perf stat` 带宽
PMU 计数器 ÷ 墙钟）；② **对照平台可持续带宽**（STREAM/规格值）。实测贴近可持续带宽 → 才判带宽受限、
才动降流量；否则标"待验证假设"，转向依赖链/延迟方向。加线程/加位宽/双累加器不减少 DRAM 流量 → 吞吐≈0
这一句只在"确为带宽受限"时才成立。

## 4. 四类瓶颈与杠杆
| 类型 | 判据 | 有效 | 无效 |
|---|---|---|---|
| 算力受限 | 利用率≈峰值 | 加线程/位宽/SIMD | — |
| 带宽受限 | 利用率远低（~8%）**+ 实测带宽贴近可持续带宽** | 降流量（量化/降精度/降召回，动正确性） | 加线程/双累加器 |
| 分配 churn | growSlice/分配器占比高 | 预分配/复用 | 改算法 |
| I/O 等待 | 阻塞在往返 | 减往返/批量化 | 加算力 |

## 5. 多源交叉验证（"瓶颈在 milvus 向量检索"的 5 条证据）
1. py-spy：mem0 在等（`_blocking` 81%→53%）。
2. mock 容器 CPU ~1%（上游已桩替代）。
3. milvus 是唯一 CPU 飙高组件（165%–186%）。
4. 候选集 ~1 万 × 1024 维算术量推算。
5. 机制切分：base 瓶颈 JSON 解析 → flatidx 瓶颈向量距离。

## 6. 测量偏置
- gomem 采样每秒轮询堆，`pprof.writeHeap` 自身占 10%–20% CPU。
- 靠"采集/计时分离"让该偏置在基线与候选中公平抵消。
