# CPU 型号白名单缺口

你负责判断一个库或接口是否存在这样一类缺口：**目标 ISA 的最优实现已经编入、硬件能力已经探测到，但运行时被一道按 CPU 型号写的经验白名单挡在门外**。存在时给出最小改动与可复现的验证结论；不存在时给出不适用依据并停止。

本 skill 属经验/方法类，聚焦单一问题：只处理「型号白名单」这一道门。不承担编译期缺失（要改构建）、硬件能力缺失（无解）、跨版本补丁移植（另一类工作）、实现改写或通用性能分析。判断不绑定具体负载：只要目标库的派发满足三层门中的结构条件，方法就成立；负载差异只改变接口追踪、等价验证和测量空间的定义。

## 判断模型：三层门

运行时选择哪条实现，按三层叠加判断：

| 层 | 检查什么 | 典型证据 | 不命中的含义 |
|---|---|---|---|
| 编译期 | 目标的 asm/intrinsics 实现是否已编入二进制 | 符号、构建宏、构建日志、反汇编 | 要改构建或配置，超出本 skill |
| 能力探测 | 硬件是否真支持目标指令集 | HWCAP/getauxval/sysctl/库自己的 probe | 硬件不支持，无解 |
| 型号启发式 | 能力位之上是否还有按 CPU 型号/微架构写的白名单 | 型号列表、`*_WORTH_USING` 标志、MIDR 比较、ifunc 比较 | **本 skill 的缺口：能力命中但型号不命中** |

候选条件需要四项同时满足：**能力位命中 && 型号白名单不命中 && 对应实现已编入 && perf 显示瓶颈在这条路径**。四项缺一，结论就不是本 skill 能解决的缺口。

## 适用范围与泛化条件

本 skill 面向 AArch64（Kunpeng/ARM）库，其它架构不在范围内。在此前提下不绑定具体负载：目标库只要满足三条结构条件，方法就成立；不满足则不属于本 skill：

1. 同一语义存在多个可选实现，运行时通过派发选择。
2. 派发条件包含 CPU 型号/微架构启发式，而不只是能力位。
3. 最优实现已编入二进制，且能力位可探测。

换负载时变的只是四个参数，流程本身不变：

| 参数 | 换负载时要确定的内容 |
|---|---|
| 语义单元 | 被加速的计算是什么，输出等价的定义是什么 |
| 内核入口 | 从公开接口追到实际计算循环的调用链与符号 |
| 等价验证 | 用哪些测试向量、逐字节比对或容差证明输出不变 |
| 测量空间 | 哪些尺寸、方向、数据分布会改变派发或收益 |

「跨负载」不是准备一套新步骤，而是把这套三层门和验证流程按新的四个参数重新实例化。不要预设某类负载一定适用或一定不适用，用上面三条结构条件判定；案例只作为实例，不作为适用清单。

## 输入

```text
库与版本         源码树或二进制、构建选项、目标 ISA
接口与场景       哪个 API、数据规模、调用方向（同一接口的不同分支）
目标机器         CPU 标识（以 MIDR 实读 implementer/part 为准）、内核、频率与绑核条件
已有证据         perf/火焰图、库日志、能力位输出、上游 issue 或注释
验证授权         只读判定 / 允许改分支 / 允许上目标机 / 允许跑基准
约束             FIPS 或合规要求、不能改系统库、不能长时间占用机器
```

缺项时不要猜，按「受阻与交回」处理。

## 输出：一页结论

| 项 | 内容 |
|---|---|
| 接口与热点算子 | API → 实际计算内核，数据规模与方向 |
| 实现等级 | 编译期是否编入、存在哪些实现 |
| 三层门 | 每层 pass/fail/unknown 及证据 |
| 候选判定 | `whitelist_gap` / `not_applicable` / `needs_evidence` |
| 实机 probe | CPU 标识、能力位、派发标志或命中的实现符号 |
| 最小改动 | 只加型号常量/列表项，保留能力位前置条件 |
| 正确性 | 库自带测试/向量集结果 |
| 性能 | 尺寸×方向、均值、波动、跨轮复现；内核级与端到端分开 |
| 结论与边界 | 采纳/不采纳、已知负收益、未验证项 |

## 受阻与交回

| 受阻情形 | 交回 |
|---|---|
| 拿不到目标机器或不能 probe | `needs_evidence` + 需在目标机执行的 probe 清单 |
| 不能改代码或不能重编译 | 只读判定 + 最小 diff 草案 + 预期收益形态 |
| 没有性能测量授权 | 静态结论 + 待测项，不承诺收益 |
| FIPS/合规禁止改动 | 说明模块哈希/校验影响，给出上游提交路径 |
| 运行时无法确定实际派发 | 保留 probe 方案与备选证据，标 `unknown` |

交回至少包含：缺什么、已确认什么、下一步需要谁提供什么。

## 流程

### Step 0：接口反推热点算子

从公开 API 追到真正做计算的内核，记录调用链和内核符号。同时记录数据规模分档与方向，尺寸至少覆盖小、中、大三档；同一接口的不同分支要分别确认派发。

### Step 1：盘点实现等级

列出库内该算子的实现层级（`asm/`、`*_armv8*`、`*_neon*`、`*_sve*` 等），确认目标平台构建是否把这些实现编入。证据用完整符号表、构建宏、构建日志或反汇编；`nm -D` 只覆盖动态导出的公开符号，内部 asm 内核要用 `nm`/`readelf -sW`/`objdump -t` 或反汇编确认。不要只看源码目录存在。编译期没编入时停止，这属于构建问题。

### Step 2：定位运行时派发

用关键字搜派发点：`getauxval`、`HWCAP`、`MIDR`、`cpuinfo`、`sysctl`、`armcap`、`*_probe`、`is_.*_supported`、`*_CAPABLE`、`*_WORTH_USING`、`ifunc`、`isa_traits`、`cpu_features`。

从能力位定义反查消费点，画出「位定义 → 探测 → 条件 → 实现选择」的路径，把每个条件归入三层门。注意能力位和型号名单可能分散在不同文件，消费点才是关键。

### Step 3：静态判定候选

出现「能力位命中 && 型号白名单不命中」时是候选。随后核对三件事：

- 上游是否已在注释、提交记录或 issue 中说明为什么排除该型号；有可复现的排除理由时停止。
- 型号命名：用 `grep` 列出目标树中该 part 的全部常量与别名，确认新增或复用哪一个，避免两套常量。
- 改动是否触达 FIPS/合规模块源码清单或校验和；触达时先确认提交路径。

结论只有三种：`whitelist_gap`、`not_applicable`、`needs_evidence`。

### Step 4：实机 probe

不要只读代码，到目标机器确认实际派发：

- 读 CPU 标识：先确认内核暴露 `HWCAP_CPUID`（`getauxval(AT_HWCAP)` 或 `/proc/cpuinfo` 的 `Features`）；库内缓存 MIDR 只在 `HWCAP_CPUID` 置位时填充，未置位时白名单比较对象为 0。确认后再用内联汇编读 `MIDR_EL1` 或 `/proc/cpuinfo` 的 implementer/part，与目标库实际使用的匹配字段对齐，以实读值为准。
- dump 能力位与派发标志：链接库写一个小 probe，或使用库自带诊断；若库以派发标志暴露选择，确认补丁前能力位为真、目标派发位为假（型号白名单未命中），补丁后目标派发位为真。
- 确认实际实现：用 `perf record -g` 看热点落在哪个内核符号，或用断点/回调确认走进了慢路径；对 ifunc、函数指针等直接派发、没有可读标志的库，记录两版在相同输入下命中的实现符号或入口断点，以实际实现切换作为证据。
- 做一次最小 A/B：同一台机器上，原文件与带改动的版本分别 probe；有派发标志时确认只有目标位翻转，没有标志时确认命中的实现符号切换，其他可观测项不变。

若 `perf` 显示瓶颈不在该路径，即使白名单缺口存在也不值得改，回到 Step 0 重新确认。

### Step 5：最小改动

只加型号常量与白名单列表项，保留能力位前置条件，不改实现、不改算法、不扩大启用范围。改动应能用一句话说明：为哪个能力位、在哪个白名单里、加哪个型号。记录原始文件与回退方式；涉及 FIPS/校验和时同步评估。

### Step 6：正确性

跑库自带的测试与向量集，覆盖相关模式、参数组合、数据尺寸与方向；有对照实现时做逐字节比对。确认补丁只影响派发、不改变输出。不要用性能数字替代正确性结论。

### Step 7：性能验证

按 `references/shared-machine-ab.md` 执行：固定一个核、A/B 逐轮交替、尺寸分档、污染守卫、跨轮复现。验收门槛与不可比条件见下节。若目标机器是共享环境且无法保证干净，明确标注测量限制。

### Step 8：一页结论

按「输出」表交付：门禁证据、probe 值、最小改动、正确性、尺寸×方向性能、结论与未验证项。结论必须是可执行的：采纳、不采纳、或需要补哪项证据。

## 验证的基线与通过条件

### 基线

原版与候选使用同一份源码、同一编译器与构建选项、同一库路径与运行环境；两边只差白名单改动。固定同一个核与频率策略，记录绑核、NUMA、负载与内核版本。

### 指标

按系列（尺寸×方向×实现）汇总 n、均值、CV、最小值/最大值；每个变体每轮一次 invocation，原始逐轮数据单独保留。正确性单独记录通过项。内核级与端到端分开，不把内核级收益直接当成业务收益。

### 通过条件

正确性全部通过、probe 确认实际走了目标实现、大尺寸收益达到测量前登记的唯一阈值且在轮间与跨次运行可复现；阈值必须高于测量噪声下限，不能事后在区间内挑选。小尺寸允许落在噪声内或小幅负收益，但要明说。收益低于噪声、方向不一致或代价不可接受时，结论为不采纳。

### 不可比条件

构建选项/编译器/库版本不同、机器或内核不同、绑核/NUMA/频率策略不同、测量窗口内有其它负载、尺寸或方向不同、一次用单次对比另一次用交替测量，均不可比。保留原始数字与原因，标 `inconclusive`，不计算收益比。

## 停止条件

出现以下任一情况直接停止，不硬凑补丁：

- 编译期未编入目标实现。
- 硬件能力位缺失。
- 白名单已包含该型号（含别名）。
- `perf` 显示瓶颈不在该路径。
- 实测收益低于噪声或稳定为负。
- 上游已有可复现的排除理由。
- FIPS/合规或授权不允许改动。

## 常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 只看 CPU 名称，不读 MIDR | 把补丁加到错误型号上 | 实读 MIDR，按 implementer/part 对齐常量 |
| 同一 part 多个常量名 | 两套命名并存或漏加 | 先盘点头文件里的别名，再改 |
| 只看能力位不看消费点 | 改错位或改完无效 | 从消费点反查位定义与白名单 |
| 能力位与加速对象混淆 | 改错位或改完无效 | 逐个确认位控制哪条实现 |
| 补丁没真正编入 | 现象不变却以为无收益 | probe 确认位翻转/符号变化，清理构建缓存 |
| 增量构建 mtime 跳过重编 | 测的是旧库 | 校验库文件时间与符号，必要时完整重建 |
| FIPS 模块校验和变化 | 合规失败 | 提前确认模块源码清单与校验流程 |
| 小尺寸固定开销 | 小包略慢，被误判为无效 | 按尺寸报告，说明大尺寸收益与小尺寸代价 |
| 共享机污染 | 数字失真 | 固定核、等待重跑、用兄弟核与切换守卫 |
| 只报总平均 | 掩盖分尺寸差异 | 按尺寸×方向报告，给出波动与复现性 |

## 安全与授权

- 默认只读：统计、probe、`perf` 不需要改代码；改分支、重编译、上目标机、跑基准都需要对应授权。
- 改动限定在库源码分支，不直接改系统安装的库；记录原始文件、构建选项与回退步骤。
- 涉及 FIPS 或其它认证/合规要求时，先确认模块源码清单、校验和与重新认证要求，再决定是否提交。
- 目标机器上只占用授权范围的核与时间；测完恢复绑核、频率与后台进程，清理临时源码包与构建目录。
- 报告中保留机器型号、内核、构建选项与测量条件；不写主机名、IP、凭据或与结论无关的客户数据。
