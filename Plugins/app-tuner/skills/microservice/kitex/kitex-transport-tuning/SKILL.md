# Kitex 传输与连接调优

本 skill 只处理"请求如何获得传输能力"：事件循环线程数、连接形态、连接池参数、以及与网卡中断的 NUMA 对齐。编解码、内存分配、协议选型分别在 `kitex-thrift-codec-selection`、`kitex-allocation-hotspot-tuning`、`kitex-transport-protocol-selection`。

## 何时触发

- QPS 随核数增加不线性增长，但 CPU 未打满。
- 火焰图中系统调用（readv/sendmsg/epoll）占比高，或事件循环线程负载不均。
- 连接数或 fd 暴涨；连接获取出现明显锁等待；dial 次数异常。
- 启用复用连接后吞吐上升但 P99 变差，或出现超时/重试语义变化。

## 范围

- 覆盖：事件循环线程数、独占/复用连接形态、连接池参数、事件循环与网卡中断的节点关系。
- 不覆盖：协议与编解码选型、GC 与并行度、框架源码改造、绑核与内核参数的执行。
- 环境与工具：服务端需支持 `netpoll.Configure`（建连前设置）；观测用 `ss`、`/proc`、pprof；绑核与 IRQ 需要系统权限，由系统层技能执行。

## 出处

- 事件循环默认值与配置入口：netpoll 仓库的全局配置与事件循环实现。
- 独占连接池与连接获取/归还：`pkg/remote/connpool/`、`pkg/remote/remotecli/client.go`（版本以现场读取为准）。
- 复用连接与协议的绑定关系：`client.WithMuxConnection` 的实现。

## 命中验证与越界验证

- 命中：问"加核后 QPS 不涨、fd 很多，先看什么"，应答"先看系统调用占比与事件循环负载，再决定线程数与连接形态"。
- 越界：问"该不该换 codec"，应答属于编解码选型，转 `kitex-thrift-codec-selection`，不在此给结论。

## 安全与资源上限

- 连接数与空闲连接数必须设上限，避免 fd 耗尽；改前记录原值。
- 单轮只改一项，压测并发与时长设上限；结束或中断后核对实际配置并恢复。

## 输入

- 当前配置：事件循环线程数（含是否显式设置）、连接形态（独占/复用）、空闲连接数与超时、并发度。
- 证据：CPU profile、mutex/block profile、fd 与连接数、dial 计数。
- 基线：本轮同口径的基线数据（见 `microservice-ab-testing`）。

## 判定

| 证据 | 结论 | 动作 |
|---|---|---|
| 系统调用占比明显偏高，且事件循环数为默认值 | 事件循环线程不足 | 调整事件循环线程数（见下） |
| 事件循环间负载明显倾斜 | 连接分布不均 | 调整负载均衡策略 / 增加线程数 |
| 锁等待集中在连接获取 | 独占连接池竞争 | 评估复用连接或调整池参数 |
| fd/连接数随并发线性增长 | 连接模型不合适 | 评估复用连接 |
| 复用后 P99 显著变差 | 队头阻塞或分片锁 | 调整复用连接数，或回到独占池 |

## 执行步骤

1. **固定基线**：记录 QPS/P50/P99、服务端 CPU、fd 数、dial 次数；口径统一走 `microservice-ab-testing`。
2. **先调事件循环线程数**：默认由并行度推算（`GOMAXPROCS/20+1`），高核数机器通常偏少；必须在建立连接前设置。取值从 `max(NUMA 节点数, GOMAXPROCS/16)` 起步，在 8/16/32 上做单变量对比。线程过多会增加空闲开销。
3. **再评估连接形态**：独占连接池适合低并发、需要隔离的场景；复用连接适合高并发、连接数受限的场景。切换前确认超时、重试、单向调用、流式语义的回归。
4. **最后调池参数**：空闲连接数与最大空闲时间要和并发度匹配；过小会把锁竞争转成 dial 系统调用，过大会占用 fd 与内核内存。
5. **NUMA 对齐**：事件循环线程应尽量与接收网卡中断在同一节点；实际绑核与 IRQ 设置移交 `cpu-affinity-optimization` / `network-optimization`。
6. **单变量验证**：每轮只改一项，3 次取中位；吞吐提升但 P99 变差时必须同时报告两个指标。

## 判断要点

- 事件循环线程数是最先应该确认的一项：数量不足时，其它调优的收益都会被串行的事件处理吃掉。
- 复用连接通常换来更高吞吐、更少连接，但可能牺牲长尾；是否采用取决于业务对 P99 与连接数的约束，不能只看吞吐。
- 服务端锁等待通常来自请求派发而不是业务锁，不要把派发开销误判成连接池问题。
- 跨节点部署会同时抬高延迟与波动；先确认服务端与压测端/上游的节点位置，再谈参数。

## 回退

- 事件循环：移除 `netpoll.Configure` 调用，恢复默认推导。
- 连接形态：移除复用连接选项，恢复独占连接池与默认池参数。
- 池参数：恢复改动前的空闲连接数与超时。

## 输出

- 输出分析结论：事件循环与连接形态的调整建议、判定依据、验证指标与回退方式；不产出文件。

## 与相邻技能的边界

- 协议优先：先按业务需求定传输协议（`kitex-transport-protocol-selection`）。若启用复用连接，协议必须是 TTHeader，需回到该 skill 确认兼容性检查项。
- GC 与并行度：参数只在 `go-runtime-tuning` 调整，本 skill 不出现具体值。
- 编解码：实现选择在 `kitex-thrift-codec-selection`，本 skill 只关心连接与事件循环。
- 绑核、IRQ、sysctl：移交系统层技能，本 skill 只输出"应放在哪个节点"的结论。
- 本 skill 可独立调用，不依赖 `WORKFLOW.md` 的中间产物。
