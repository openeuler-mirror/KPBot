# 接手 + 锁定基线（阶段 0→1）

## 何时使用

- 刚拿到一台共享执行机 / 一个没文档的组件，还没开始改任何代码。
- 需要一份"优化前"数字，作为之后所有对比的唯一锚点。
- 需要判断内存规格、NUMA 绑核、磁盘落点、外部负载等环境约束。

## 核心原则

1. **先预检，别急着动手。** 最大的风险不是"不会做"，而是"误伤了别人正在跑的东西"、或"测错了对象"。
2. **每条预检事实都必须回答"它约束了后面哪个决定"**；回答不了的就是白收集的噪音。
3. **先问"这个基准到底测什么"，再问"哪里慢"。** 上游不确定开销（LLM/embedding/模型服务）必须已被回放或桩替代，否则你测的是混合体。
4. **基线不是一句"约 27 req/s"，而是：规格表 + 逐轮原始值 + N 轮中位口径 + 单轮产物完整性校验。**
5. **接近临界值的资源规格是定时炸弹**：有时侥幸通过、有时确定性失败，会让你误以为是代码问题。

## 步骤

### 1. 环境预检六张表（一次性抓全）

```bash
docker ps -a                     # ① 分清「别人的」vs「本任务的」容器
docker images && docker volume ls # ② 镜像/卷清单（识别悬挂镜像与历史 tag）
ss -lntp                          # ③ 端口占用
df -h && docker info | grep "Docker Root Dir"  # ④ 哪个分区快满、Docker 根在哪
lscpu                             # ⑤ 架构 + 指令集标志(sve/sve2) + 缓存
numactl -H                        # ⑥ NUMA 拓扑：逐节点看 size！
```

**NUMA 必看每个 node 的 `size` 和 `cpus`，并区分「CPU 亲和」与「内存绑定」**：
- `size=0` 的无内存节点：**CPU 可以绑**（那些核仍能跑线程），但 **`cpuset-mems`/内存绑定必须避开**——仅绑这些节点的
  CPU 时，默认内存策略会从**别的有内存节点**分配，产生**远端内存访问**（跨 NUMA 读写的延迟/带宽代价）。
- 所以预检要**分别记录**：① 各节点的可用 CPU 区间；② 各节点的内存大小；③ 「绑 CPU 到空节点、内存落到远端」时的
  **远端访存代价**。别把"不可绑 CPU"和"不可绑内存"混成一句"不可绑定"。
- 真实案例：某 4 节点机器里 node2/node3 有 CPU 但无内存，凭直觉"绑 node2"会把线程绑过去、内存却远端分配，性能反降。

### 2. 事实 → 决策映射表

把每条预检发现写成"事实 → 它约束了什么决定"。例：

| 预检事实 | 约束的决策 |
|---|---|
| 存在无内存 NUMA 节点（有 CPU 无内存） | mem0 绑有内存节点 A、milvus 绑有内存节点 B；CPU 亲和与内存绑定分别列出，空节点 CPU 不绑或绑后注明远端访存代价 |
| 系统盘接近满 | 红线：禁止写系统盘，一切落 `<workdir>` 与 `<docker-root>` |
| 他方常驻容器在跑 | 红线：禁止 kill/stop/restart 非本任务容器 |
| CPU 有 `sve`/`sve2` | 选 SVE 加速版向量库而非标量版 |

回答不了下游决策的事实 → 删掉，别堆。

### 3. 画请求路径图 + 确认上游已桩替代

- 画出：客户端 → 被测组件 → 依赖服务。
- 确认昂贵/不确定的上游调用（LLM、embedding、外部模型）已被 **offline replay 或 mock** 替代，真实压测路径只剩你要优化的那一段。

### 4. 按"恒定开销 vs 可变开销"切相位

- 把一次完整运行切成有名字的相位（如 seed → 索引构建 → ingestion → qa）。
- **只有随代码改动变化的相位才参与对比**；恒定开销（seed/索引，常占 10–20 分钟）必须排除，否则几分钟的真实信号会被十几分钟固定开销的噪声淹没。
- 用阶段标记或逐请求事件定界（契约见 `opt-measurement-infra`，独立 PR 待合入）。

### 5. 锁定基线四件套

1. **规格表**：资源（CPU/内存/NUMA，CPU 亲和与内存绑定分列）、规模（用户数/并发/预热条数）、镜像 tag、轮数——全部写死。
2. **逐轮原始值**：把波动暴露出来，不要只报中位；**每个对比口径都要有逐轮原始值**（如"QA 吞吐"就要三轮 QA
   请求数与对应时长，让调用方能复算中位数，而不是只给一个中位值）。
3. **N 轮取中位**的口径（通常 3 轮）：规避单轮偶发。
4. **单轮产物完整性校验**：一轮 = 一组能相互印证的产物文件，缺任一文件该轮作废。

### 6. 资源规格做"临界判定"

- 对内存/CPU 规格做"够不够"的量化判断，留安全余量。
- 用机器真实可用资源证明没有挤占别人。
- 遇到"有时能跑有时确定死"的规格，直接上调到安全值并记录原因（真实案例：4G → 8G 解决 `predictMemUsage≈4.3G > 4G` 预测超限的确定性拒载 + 就绪超时）。

### 7. 决策记录用三元组

`事实（可复现数字/字节级来源） → 结论（含明确生效范围） → 为什么不会回头再改`。
记录"冲突/版本歧义"比记录"共识"更有价值。

## 门禁

- [ ] 预检六表齐全，且每条事实都有下游决策；CPU 亲和与内存绑定已分列、无内存节点 CPU 绑定的远端访存代价已记录
- [ ] 请求路径图画完，上游不确定开销已桩替代
- [ ] 相位已切分，明确哪些相位参与对比
- [ ] 基线规格表锁死（单一事实源），逐轮原始值已落盘（每个对比口径都有逐轮值可复算中位）
- [ ] 内存/CPU 规格做过临界判定；资源超限事件按观测记录（拒载/超时），不把"拒载"直接写成"OOM"除非有内核/容器事件
- [ ] 外部负载已写进安全红线

## 产物

- `预检快照文档` 式预检快照
- 基线规格表 + 逐轮原始值 + 中位值
- 决策记录（三元组）
