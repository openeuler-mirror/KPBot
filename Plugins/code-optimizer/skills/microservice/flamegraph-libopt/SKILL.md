# 生产火焰图驱动的第三方库优化（通用工作流）

本 skill 从两次完整的库优化闭环（protobuf 序列化库在解析/合并负载、folly
异步链路在回调负载，均为生产火焰图驱动、aarch64 实测）提炼**不随目标库变化**
的工作流层。目标库可替换，具体库的深入路径（热点函数清单、形态核对表、语义
判据、A/B 脚本）由专项 skill 承载：

- 命中 protobuf → 先读 `protobuf-optimization`（含画像对齐验收双条件、形态
  前提核对表、5 轮交替 A/B 协议、SPE 确证分级）
- 命中 folly futures/then 链路 → 先读 `folly-future-optimization`
- 其他库（abseil、json 库、自研公共库……）→ 本 skill 全程自足

## 输入

| 字段 | 必填 | 说明 |
|------|------|------|
| `service_flamegraph` | 是 | 生产服务火焰图 SVG（perf + flamegraph.pl 产物；倒置冰柱或标准布局均可） |
| `lib_name` | 是 | 目标库标识（用于帧定位：命名空间/前缀/返回类型） |
| `lib_repo` | 是 | 目标库可构建源码树（生产所用 fork/版本） |
| `upstream_ref_repo` | 建议 | 上游新版本源码树，用于 diff 找"官方已做的优化" |
| `build_env` | 建议 | 远程构建机（变体构建脚本 + taskset 固定核能力） |

## 工作流

### Step 1：火焰图解析（先自检，再引用任何数字）

用 `scripts/parse_flamegraph_svg.py` 解析 SVG（详细算法与坑见
[火焰图解析参考](references/flamegraph-parsing.md)）：

```bash
# 安装布局（主形态）
python3 scripts/parse_flamegraph_svg.py <火焰图.svg> --lib <库名模式>
# 自检：Σ(self)==100%（树构建回归的必要条件）+ 结构门禁（负 self、同父兄弟帧
# 重叠——子帧挂错祖先在此拦截）。任一门禁失败禁止引用任何数字。
# 聚合：--denest 开启同名帧去嵌套（每条调用栈同名帧只计一次，见下）
```

两条铁律：

1. **方向先验**：SVG 的 y=0 在画面顶部——root 在底部 = root 帧 y 值全图最大，
   root 在顶部 = y 值最小。flamegraph.pl **默认输出**的火焰图 root 在底部；
   `--inverted` 输出冰柱图 root 在顶部（坐标真实翻转，非视觉倒挂）。脚本按
   root 的 y 值自动判定，人工分析时同样先实测 root 位置再用树算法，不要按
   工具印象假设方向。
2. **同名帧去嵌套**：递归/模板实例化的同名帧在全树多处出现，直接求和会把
   递归深度算进占比（实测案例：某解析循环 9 个实例中 5 个递归，naive 求和
   10.85%，去嵌套后 ≈3.0%——3.6 倍虚高）。任何"库占比/路径天花板"结论
   必须基于去嵌户口径。

self 口径的定义与边界：`self = 帧样本 − 直接子帧样本和`。它回答"哪里热"，
**不回答"该处是否已最优"**——隐形收益类型（指令选择/CPI/调用开销）在采样图
上完全不可见（实测案例：某 fork 自带的 SVE 编译选项、arena 对齐、varint 快
路径全是采样不可见的既有优化）。因此"self% 小"永远不能单独作为关闭方向的
依据，需配合指令级证据（见专项 skill 或 perf 反汇编）。

### Step 2：库帧定位与类别分解

- 命名空间匹配要含"返回类型前缀"帧（如 `void ns::lib::func`），用包含匹配
  不锚定行首；**参数列表里出现的库名会误命中**（生成代码签名含库类型），
  先按第一个 `(` 截断再匹配
- 按函数名语义分类别（构造/析构/拷贝/序列化/查找……），类别和 ≈ 库总 self；
  与"库占总进程比例"分开报数
- 类别构成 + 关键函数集合 → 后续画像对齐微基的**验收基准**（对齐协议见
  `protobuf-optimization` 步骤 2：类别构成差 <5pp + 生产上榜函数全出现）

### Step 3：测量可信度三件套（微基报数前必做）

1. 计时开销实测：`steady_clock::now()` 单次开销（vDSO 约 20-30ns 量级才
   允许 5 段分计时）
2. 段和交叉验证：各段计时之和 vs 程序墙钟，差 <0.5%
3. 方差 vs 效应量：多轮间方差应低于预期效应量的 1/5，否则报数无效
4. A/B 两变体走相同代码路径 → 系统偏差在差值中相消，**相对结论比绝对值稳**

### Step 4：优化点挖掘路由

按性价比顺序，前一项做完才进下一项：

1. **上游参照 diff（第一优先）**：对热点函数逐一 diff 目标库 vs 上游参照。
   "上游有没有做 X"永远用 diff 回答，禁止凭"高版本见过这个文件名"假设
   （实测教训：被误判为"上游新增"的预取 API 其实本地版本早已含同度实现）。
2. **形态前提检查**：上游优化普遍自带形态前提（arena/heap、大消息/小消息、
   miss-bound 与否），不匹配就是负优化（实测：批量分配类优化在 heap 形态
   -22%）。核对表见 `protobuf-optimization` 的 references。
3. **miss-bound 判定（cache 类优化的前置实验）**：污染实验——目标路径间
   touch 一块远超 L3 的 buffer（如 64MB）；若污染本身只让该段 +1.5%，则
   该段非 miss 主导，预取/对齐/局部性类优化全部关闭。
4. **自研方向**：找"库代码结构性冗余"而非"上游有什么"；每提候选先给先验
   收益估算，实测后对比——估算偏差一个量级是常态（实测案例：预估 25-35%、
   实测 0.46%），估算不可作裁决。

### Step 5：变体构建与验证（安全模式）

远程变体构建照抄安全模板（完整模板与坑清单见
[变体构建安全参考](references/variant-build-safety.md)）：文件备份 + trap
还原 + 前后 marker 校验 + CRLF 树先洗行尾 + patch 用 `git diff` 生成。

**链接指纹验证（性能归因前的前置门禁）**：变体 bench 构建必须验证实际链接
对象——cmake `find_package` 类工程漏传 `CMAKE_PREFIX_PATH` 时会**静默落到
系统库**，构建照常成功、数字全废（实测案例：曾据此误判"优化劣化 886%"，
实为链接错库）。验证手段：ldd 确认目标库路径、二进制体积对比、protoc 等
生成物 md5。**构建产物检查前置于一切性能结论。**

A/B 协议：单变量、5 轮 base/opt 交替（绝不先跑完所有 base 再跑 opt）、
taskset 固定核、checksum 两变体一致、语义矩阵独立测试——协议细则与脚本见
`protobuf-optimization`（alternating_ab.sh）。

### Step 6：负结果固化

无收益/负收益的尝试连同数字、根因、"何时可重试的前提"固化进 patch 头注
或负结果档案——找齐根因的负结果常翻转出正设计（实测：批量移植 -22% 的
根因分析直接产出 +5.6% 的单遍历自设计）。本 skill 不提供统一负结果库
（负结果与库强相关），归档格式见 `protobuf-optimization` 的
references/negative-results.md。

### Step 7：换目标库参数核对

从一个库换到另一个库时，逐项核对（完整 10 项参数表见
[变体构建安全参考](references/variant-build-safety.md) 第 3 节），其中
三项最常翻车：

| # | 项 | 换库时必须重新确认 |
|---|---|---|
| 1 | 帧定位模式 | 命名空间前缀、模板实例化帧、lambda 帧；模板名含逗号空格的解析 |
| 2 | 生产传导模型 | 预编译库（.a 重链即传导）vs header-only 模板（内联固化在业务二进制，换库必须业务重编） |
| 3 | 语义判据 | 是否存在等价 DebugString 的全量比对手段；无则按对象类型设计行为断言 |

## 脚本用法

```bash
# SVG 火焰图解析 + 自检 + 库帧聚合（纯标准库，Python >= 3.8）
python3 scripts/parse_flamegraph_svg.py graph.svg --lib "google::protobuf"
python3 scripts/parse_flamegraph_svg.py graph.svg --lib "folly" --denest --top 20
# 输出：Σself 自检结果 / 库总 self / 类别分解 / 热点函数排行（去嵌套口径可选）
```

脚本依赖与边界见 `scripts/README.md`。

## 常见误区

| 误区 | 真相 |
|------|------|
| "库帧 10%，优化它 E2E 就能涨 10%" | 递归同名帧不去嵌套的占比是虚的；去嵌套后才是真天花板 |
| "self% 低的函数没有优化价值" | self 只回答"哪里热"；隐形收益（指令选择/CPI）采样不可见 |
| "构建成功 = 测的是新代码" | find_package 静默回退系统库时构建照常成功；链接指纹验证必须前置 |
| "上游新版本的优化抄过来就好" | 上游优化自带形态前提；核对表见专项 skill |
| "微基快 X%，生产也快 X%" | 微基 % × 生产占比才是生产预期，且要封顶换算 |

## 验收清单

- [ ] Σ(self) 自检 = 100.000%（防树构建回归）且结构门禁通过（负 self / 兄弟重叠——挂错祖先在此拦截；否则全部数字作废）
- [ ] 库占比与路径天花板基于去嵌户口径
- [ ] 微基画像对齐验收通过（类别构成差 <5pp + 关键函数全出现）
- [ ] 测量三件套通过（clock 开销 / 段和交叉验证 / 方差 vs 效应量）
- [ ] 链接指纹验证前置（ldd / 体积 / 生成物 md5）
- [ ] A/B 5 轮交替 + checksum 一致 + 语义矩阵
- [ ] 负结果连同根因归档
