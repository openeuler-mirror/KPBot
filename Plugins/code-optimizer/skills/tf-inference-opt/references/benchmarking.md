# 基准与剖析方法学（贯穿所有层）

> **何时读**：为优化建基线、定位瓶颈、验证路径命中、设计压测或输出 A/B 结论。

**没有可信的测量，就没有优化。** 先定义模型、负载与成功标准，再用分段计时和执行证据定位，最后通过可复现对照判断收益。历史案例中的倍率、线程数和验收阈值不能直接移作当前目标。

## 1. 服务端剖析（profiling）

### 1.1 分段计时（第一优先）

把请求拆成：**接收 → 排队/等待 batch → 反序列化 → 预处理/输入构造 → session.run → 后处理 → 序列化 → 返回**。根据服务实际执行顺序设打点，避免把排队时间漏掉或重复计入；客户端端到端时延另报。

用请求 ID 关联单调时钟时间戳，输出 `SERVER_TIMING queue_us=.. prepare_inputs_us=.. session_run_us=.. output_proto_us=.. total_us=..` 等结构化字段。日志限流；只采启动期前 N 条不能代表稳态，应允许 warmup 后采样。

### 1.2 图执行级 timeline

- 先确认执行模式和版本。C++ Session 路径可用 `RunOptions FULL_TRACE`、`output_partition_graphs=true` 与 RunMetadata；TF2 函数执行使用对应版本 profiler。RunMetadata/StepStats 与 XPlane 是不同产物，转换工具须与格式及 TF 版本匹配。
- **采样限流**：限制全局导出次数、设置采样间隔，并为冷启动与稳态分别标记。并发抢占导出名额用原子计数，避免大量文件同时落盘。
- **落原始格式，离线转换**：服务侧只保存必要原始数据（如 `*.runmeta.pb`），Chrome trace 转换离线做。采集脚本记录自身 server PID、配置与输出目录，只回收自己启动的进程。
- **诊断轮与性能轮分开**：trace 和详细日志自身有成本，正式 A/B 关闭它们；若生产必须保留采样，两侧保持同配置并测量其开销。

### 1.3 读 timeline 与验证实际命中

- 看 kernel 数量、张量搬运、热点算子及依赖关键路径；并行 kernel 耗时相加不等于请求墙钟时间。
- 对照分段计时确认 session.run 内外的占比，再判断是图重写、算子实现还是调度问题。
- 保留**配置解析值 → pass 注册/平台拒绝原因 → 匹配和重写节点数 → 实际 kernel/后端 → prepack hit/miss/回退原因**。优先复用日志、图 dump 和采样调用栈，必要时添加低开销计数。
- 开关开启、符号存在或重写成功都不能单独证明整条路径生效。历史“全开”实验曾因平台门控导致 `_FusedMatMul` 节点数为零；见 [消融报告 §2.7–2.9](../ablation_report.md)。
- **命中证据可能是惰性的**：grappler 图优化等机制在**首个推理请求**后才触发（不是模型加载时）——取证前先发至少一个真实请求再 grep 日志，否则会把正常路径误判为零命中。
- **门控要审整条链**：打开一个 gate 后，同路径上其它 gate（平台 part 号、shape/布局守卫、build 裁剪、flag 默认值）可能仍关闭。逐环取证据链（见上条），不要验证完第一环就下结论。

以下服务压测条目仅用于服务负载；局部算子或离线推理选用适用指标，不要求 RPC、超时与容量扫描。

## 2. 压测工具设计

1. **阶段与计时**：warmup 和测量阶段共用请求路径，稳态开始前确认延迟/缓存趋稳；使用单调时钟。固定测量窗口，区分窗口内发送、完成及窗口后 drain，说明吞吐分母与延迟样本归属。
2. **负载模型**：open-loop 按计划到达率发请求，closed-loop 在请求完成后补发以维持并发。前者用于观察给定到达率下的排队，后者用于指定并发下的性能；不可把两种口径直接混比。`max_qps=0` 是否表示固定并发全速，以工具实现为准。
3. **调度与迟发**：票号制可统一计划时刻 `start + k/max_qps`，但线程调度、阻塞 RPC 和 in-flight 上限会使实际发送偏离计划。记录计划发送、实际发送和完成时刻，分别报发送迟延、发出后 RPC 时延及计划到完成时延，避免漏掉迟发等待（coordinated omission）。超载时明确迟发、丢弃或补发策略，不能悄悄突发补票。
4. **流控与失败**：显式设置 in-flight 上限及 timeout；达到上限时记录未发出的 dropped，已发出的超时和失败分别计数。`QPS×timeout` 仅可估算极端在途规模，不是通用容量配置。检查压测机 CPU、连接、网络及实际发送率，排除客户端先饱和。
5. **统计口径**：报告计划/实际发送/成功完成 request/s，以及错误、超时、丢弃数与各自分母。成功请求的 p50/p99 必须标注样本集合；超时是截尾观测，不能从成功 p99 推断全部请求满足 SLO。request/s 与 sample/s 分开，后者累加实际成功 batch 样本数。
6. **分位数与内存**：小规模可保存样本，按 nearest-rank 取 `ceil(n*p)-1`；长时高 QPS 可用具有明确精度的直方图/摘要，报告精度、样本数与聚合方式。不能平均各线程/各窗口 p99 作为全局 p99，也不能无限保存样本耗尽内存。
7. **进度与 batching**：定期输出 QPS/in-flight/失败率等进度，正式测量限制日志成本。客户端每 RPC 捆多条样本只模拟请求 batch；服务端动态 batching 还需记录等待超时、队列长度及实际形成的 batch 分布。

## 3. 输入真实性

- **签名驱动 mock**：SignatureDef 的 dtype/shape 只能生成候选输入；动态维、字符串编码、稀疏索引与关联输入须满足模型语义。不能保证任意模型仅凭随机填充就能跑通。
- **代表性回放**：优先用有授权的业务样本；不可获得时使用经验证的合成分布，明确结论适用范围。覆盖稀疏度、重复 ID 比例、序列/字符串长度及 batch 分布，避免均匀随机数据掩盖真实瓶颈。
- **输入映射**：依据模型签名和服务协议构造所有关联输入，不把 `model_input` 字段名或 TSV 格式作为通用约定。固定回放顺序/随机种子，A/B 使用相同样本。

## 4. A/B 方法论

### 4.1 对照设计

- **可复现身份**：保存源码 commit 与未提交 diff、二进制哈希、模型/checkpoint 身份、依赖/编译配置和完整启动参数；记录机器拓扑、quota/cpuset/亲和性、各线程池与库线程上限、batch/并发/QPS、输入集和负载模型。
- **单变量与交互互补**：固定配置逐项切换做归因；依赖联合实现的候选可先测整体原型，再消融可分离部分。对相关候选项补小规模交互矩阵，不必穷举全部开关。例如融合×后端用下表判断融合收益是否随后端改变。

  | | 原生后端 | 库后端 |
  |---|---|---|
  | 融合关闭 | 基准 | 库路由效果 |
  | 融合开启 | 原生融合效果 | 组合效果与交互 |

  历史 hmv 实验中 FM 在 Eigen 下为 +1.7%、KDNN 下为 −6.0%，说明不能默认各层收益相加；该有限轮次结果用于说明交互，不代表其他负载的收益保证。prepack×库线程数同理。
- **基线含义**：同时区分生产现状基线与为归因关闭优化的参考路径；“baseline/lib/opt”三模式可做初筛，但不是完整交互矩阵，原生实现也不是性能下限。
- **重复与噪声**：同机隔离资源，交替或随机化 A/B 顺序；从多轮配对结果报告中位数与离散度，需要时给置信区间。预先定义有效轮条件，保留失败轮及原因，不因结果慢而删轮。小于波动范围的变化标为证据不足；机器负载漂移时不跨轮拼接绝对数字。
- **归因与最优值分开**：固定配置 A/B 回答“改动是否有效”；双方分别扫参回答“各自最优性能”。保存逐模型/batch/并发配置，不能把线程变化的收益归给代码，也不能把模型 A 的负结果直接推广到模型 B。
- **产物**：逐轮原始日志、有效配置、命中证据、逐秒 CSV 和汇总表关联同一 run ID，记录采样/测量窗口与 CPU 归一化公式。

### 4.2 验收与指标纪律

- **正确性优先**：先对拍参考与优化路径，再做性能结论。固定 dtype 对应的 atol/rtol，报告最大绝对/相对误差与不匹配数；整数/字符串精确比较，NaN/Inf 单独定义规则。覆盖空/边界 shape、转置/广播、稀疏重复/乱序、回退、并发首调及模型重载等与改动相关的语义。
- **冷启动与稳态分开**：分别记录模型加载、首次请求（JIT/预打包/图优化）及 warmup 后测量；测内存时保留启动峰值、稳态 RSS 和重载后的旧缓存占用。
- **完整指标**：p50/p99/吞吐/RSS 与错误/超时/丢弃齐报。按用户的延迟 SLO 和失败预算判定容量；成功吞吐升高但 dropped 上升不能直接判为改进。
- **CPU 口径**：同时给 CPU 时间/占用核数和按有效预算归一化的比例，说明 quota 是否无限制，并记录节流。归一化只统一口径，不消除跨机型性能差异。
- **micro-benchmark**：用于定位 shape×transpose×dtype 路由收益和 pack 成本，最终以服务 E2E 验证。Google Benchmark 的 `Threads(...)` 通常控制基准调用线程数，不等于单个 GEMM 内部线程数；两者分别配置，避免误读伸缩结果。

## 4.3 按目标负载验证适用范围

固定并发结论对该负载有效；目标覆盖多档并发时再扫代表性梯度，不强制所有任务跑 1/2/4/8/16/32。

低负载常受关键路径和调度影响，高负载还需检查计算、带宽、缓存、排队及节流。这些是诊断视角，不预先指定融合或 prepack 谁会获胜。历史案例出现过并发升高后排名反转，但曲线不一定交叉，交叉点也不一定等于线程池饱和点。

按观察到的瓶颈解释结果；有交叉点时记录其区间，无交叉时如实报告。局部结论不外推到未测负载，也不因缺少全范围扫描而否认它在已测条件下的价值。

## 5. 瓶颈定位决策树

```text
1. 定义负载/SLO，固定环境与产物身份 → 基线（分段计时 + 稳态压测）
2. 客户端迟发、服务端排队或节流明显 → 先查负载生成、容量与 CPU 预算
3. 序列化/输入构造占比高 → L4；session_run 占比高：
   3a. 上下文切换高/扩核无收益 → L3 线程与调度
   3b. 小 kernel 海量/搬运多 → L1 融合
   3c. 少数大算子主导 → L2 后端与路由
4. 已改却无收益 → 查配置→注册→重写→实际后端→缓存命中；必要时查 L5 产物
5. 正确性通过 → 单变量 A/B → 关键交互消融 → 按模型/batch/并发保存配置
6. 报告完整指标与噪声；未满足 SLO 或证据不足时明确保留结论
```

## 6. 反模式

- **只看开关不看命中**：平台门控、注册顺序或 shape 守卫可能挡住整条优化路径。
- **只看成功请求 p99**：迟发、超时与丢弃被排除后，服务超载也可能显示“更快”。
- **把设定 QPS 当实际负载**：记录真实发送率与迟发，检查客户端容量。
- **剖析与性能混测**：详细 trace/日志会改变调度、CPU 和 I/O。
- **同时开多项只报总收益**：缺归因；反之只测单变量也可能漏掉后端/融合交互。
- **跨线程/并发/机器泛化**：固定配置收益和各自最优性能必须分开报告。
- **分位数口径不明**：明确样本集合、样本数、精度与聚合方式，不平均 p99。

## 实战案例摘要

历史工具采用 RunMetadata 限流采样、离线 trace 转换、票号调度和 TSV 回放，这些是可选实现。更可复用的教训是：环境开关与实际路径要逐段取证；线程配置会改变收益大小甚至方向；同一融合在不同后端上可反号；冷启动、失败率和并发档位不能从结论里省略。详细背景按需读 [消融报告](../ablation_report.md) 与 [三方对比分析](../agent_vs_manual_analysis.md)。
