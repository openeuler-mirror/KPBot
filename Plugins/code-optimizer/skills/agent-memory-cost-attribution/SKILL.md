# 三段归因：框架 / 驱动 / 服务端

## 步骤

1. **串行执行**（`concurrency=1`），避免并发互相模糊每条查询的归因。
2. **定位协议边界**，在边界两侧计时：
   - `框架` = 框架检索入口外层墙钟 − DB 调用区间**并集**
   - `驱动` = 驱动调用区间并集 − 服务端时间
   - `服务端` = 协议响应里的服务端耗时字段
3. **区间取并集，不要求和**：一次查询常发多路并发调用（全文 + 向量），区间重叠，求和会双计。
4. **自证拆分正确性**：客户端优化前后，服务端绝对毫秒应基本不变（实测 7.7→8.5 ms / 3.3→3.6 ms）。
   若服务端时间跟着客户端一起变，说明口径有误——典型原因是用"服务端开始返回"的时间当总时间，
   它只说明开始得快，慢在消费完。
5. **同机代理/日志兜底**：协议不暴露服务端耗时时，用服务端日志耗时、或同机代理前后差值，并标注口径。

## 各协议的服务端耗时来源

| 协议 | 取值方式 |
|---|---|
| 二进制图协议（Bolt 等） | 响应 SUCCESS 元数据里的消费完成时间字段 |
| gRPC | 响应头 / 服务端拦截器 |
| pg wire | `log_min_duration_statement` 或代理计时 |
| RESP / HTTP | 服务端日志，或客户端"首字节 − 末字节"差额 |

## 实测参考（每查询一段，串行）

| 架构 | 版本 | 总时间 ms | 框架 ms(%) | 驱动 ms(%) | 服务端 ms(%) |
|---|---|---|---|---|---|
| 鲲鹏 | 基线 | 59.60 | 1.15 (1.9%) | 49.93 (83.8%) | 8.52 (14.3%) |
| 鲲鹏 | 优化 | 21.06 | 0.96 (4.6%) | 12.40 (58.9%) | 7.70 (36.6%) |
| x86_64 | 基线 | 39.64 | 0.80 (2.0%) | 35.28 (89.0%) | 3.56 (9.0%) |
| x86_64 | 优化 | 11.74 | 0.58 (4.9%) | 7.85 (66.9%) | 3.31 (28.2%) |

同一批优化的服务端占比从 14.3% 升到 36.6%（x86_64 从 9.0% 升到 28.2%）。
这不是服务端变慢，而是客户端被削掉后暴露了新瓶颈——所以每轮都要重跑拆分。

## 封闭轴（必须写）

明确列出"已用证据排除的方向"，避免下游重复尝试：模型网络、GC、磁盘、锁、带宽、解释器启动。
每条要给证据（如"服务端 CPU 未饱和 + 延迟集中在客户端 CPU"）。

## 输出

- 三段占比表（绝对值 + 百分比，优化前 vs 优化后）
- 拆分自证记录（服务端绝对毫秒前后对比）
- 封闭轴清单
