# 决策矩阵、负结果与停止条件

本文件是优化的“刹车与方向盘”：什么时候该做什么、什么时候必须停、负结果如何归档。

## 1. 决策矩阵

| 证据 | 首选 | 次选 | 不要做 |
| --- | --- | --- | --- |
| 物理读高、命中率低 | 增大 buffer pool、覆盖索引 | 分实例、预热 | 加 CPU |
| `Innodb_log_waits`/写抖动 | 先查 `innodb_log_buffer_size` 与刷出速率，再按 checkpoint 压力决定扩 redo；提高 io_capacity | 分盘、组提交 | 只加 buffer pool；未查 log buffer 就扩 redo |
| 脏页高、checkpoint 频繁 | 提高刷脏/换盘 | 调 page_cleaners（仅 10.5.1 及更早的功能版本；10.5.2 起弃用并忽略，10.6.0 起移除） | 盲目调大 redo |
| 行锁等待高 | 缩短事务、改索引 | 隔离级别评估 | 加线程 |
| `futex`/latch 高 | 减少共享写、绑核、线程池 | LSE/分配器 | 加 worker |
| 跨 NUMA | `numactl --membind` + 绑核 | 分实例 | 跨片部署 |
| 临时表/排序 | 索引/改写 SQL、tmpdir | 缓冲参数 | 只调 sort_buffer |
| MDL 等待 | 避免长事务与 DDL 撞车 | 在线 DDL 工具 | 强杀 DDL |
| 客户端先瓶颈 | 加压测进程/核、减结果集 | 连接池 | 改数据库 |
| 综合 OLTP 无单点 | 部署/配置 | 编译/三方 | 直接改源码 |

## 2. 停止条件（硬规则）

遇到以下任一情况，立即停止优化并回到正确性/归因：

- 功能门禁失败（mtr/冒烟/对账/复制/备份）。
- 两腿环境/数据/配置不一致，无法比较。
- 多变量同时改，无法归因。
- 轮间波动 >5% 且无法消除。
- 需要降低持久性（`flush_log_at_trx_commit`/`sync_binlog`/双写）才能“提升”。
- 需要修改数据格式/复制协议且没有回滚方案。
- 生产环境未获授权/未安排窗口。

## 3. 负结果清单

| 尝试 | 结果 | 原因 | 教训 |
| --- | --- | --- | --- |
| 所有场景默认 LSE | 部分场景退化 | 原子竞争不是唯一瓶颈 | 必须分场景 A/B |
| jemalloc + tcmalloc 同时启用 | 行为不确定 | 分配器冲突 | 只选一种 |
| 10.3 顺序锁/lock_word 补丁套 10.11 | 编译失败/无效 | `rw_lock` 已重写 | 版本校准 |
| 只加大 buffer pool 解决写抖动 | 无效/更差 | 瓶颈在 redo/刷脏 | 先归因 |
| `Innodb_log_waits` 高就扩 redo | 无效、抖动仍在 | 真正原因是日志缓冲不足/刷出滞后 | 先查 `innodb_log_buffer_size` 与刷出速率 |
| 10.11 my.cnf 写 `innodb_buffer_pool_instances`/`innodb_page_cleaners` | 启动失败 | 10.6.0 起移除（10.5.2 起弃用并忽略，仅 10.5.1 及更早功能版本有效） | 版本校准，区分“未知变量”与“查询失败” |
| 不重置数据连续压测 | “提升”虚高 | 数据/缓存变化 | 每轮重置 |
| 多变量一起改 | 无法归因 | 违反单变量 | 拆开重测 |
| 关闭 doublewrite 提升写 TPS | 数字上升但风险不可接受 | 崩溃恢复受损 | 不作为默认优化 |
| `-O3` 替换 `-O2` | 无稳定收益 | 热点不在编译优化 | 不做无证据变更 |

> 负结果与正结果同样重要：写入团队台账，避免重复试验。

## 4. 反模式

- **参数堆砌**：一次改十几个参数，最后不知道哪个有效。
- **抄配置**：把别人的 my.cnf 直接用于不同工作集/内存/盘。
- **只看均值**：忽略 p99 与错误率。
- **只看 QPS**：忽略 CPU 饱和、IO 排队、客户端瓶颈。
- **用生产做试验**：没有备份/窗口/回滚。
- **把测试机调优结论直接上生产**：数据量、并发、盘、网络都不同。
- **迷信版本升级**：不定位机制就升级，可能引入新问题。

## 6. 复盘问题

- 瓶颈是否在优化前后发生了迁移？迁移到哪？
- 收益是否可复现？换一轮/换一天是否仍在？
- 是否有更简单的杠杆（索引/绑核/参数）被忽略？
- 变更是否增加了运维复杂度/升级成本？
- 是否引入了新的长尾/错误/资源风险？
- 文档与回滚是否足以让同事独立复现？

## 7. 交接

优化结束后把以下内容交给 `mariadb-test-verification` 做最终验收，并归档：

- 变更清单与二进制 md5；
- 逐轮 A/B 原始数据；
- 功能证据；
- 回滚脚本/命令；
- 已证伪清单。
