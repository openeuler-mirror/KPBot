# 网络边序列化机制与拷贝计数对账

本文是 `flink-native-stateful-operator-tuning` 的网络边参考：**跨算子链顶点
（vertex）的数据边为什么必须序列化、怎么数拷贝、批的生死边界在哪**。传输税的
消除方法在姊妹 skill `flink-native-jni-transport-tax`；本文管机制与对账方法。

## 网络边是绝对切线

同一 vertex 内：向量化算子之间整批向量直通（真零拷贝），批不拆不还原。

跨 vertex（网络边）：JVM 壳算子的输出必须经 Flink 网络栈（ResultPartition 类
机制）序列化传输，下游再反序列化回向量批。**不存在跨 vertex 零拷贝**——两个
native 计划段之间的网络边就是序列化边界。keyed 语义的网络边（KEY-GROUP 分发）
同理：key 分组是网络边属性，不是算子属性。

推论：**"把中间算子合并成一个 native 计划"能消灭 vertex 内边，但消灭不了 keyed
网络边**——分区/分组分发是拓扑层的，合并计划只影响 vertex 内部的执行段。评估
"合并优化"收益时先数还剩几条网络边。

## 拷贝计数对账方法

网络边开销 = 序列化（向量批 → wire 字节流）+ 网络传输 + 反序列化（wire 字节流
→ 向量批）。对账步骤：

1. **数原生栈的拷贝**：原生 Flink 网络边是 RowData 序列化器（含跨内存段拷贝与
   写缓冲）——以"每行几次拷贝"计；
2. **数向量化栈的拷贝**：以"每批序列化字节量（wire bytes）+ 每行摊薄拷贝次数"计；
3. **对账双端**：同查询、同数据下，比较每行摊薄的 wire 字节数与拷贝次数——差值
   即网络边归因量；序列化格式差异（行式 wire vs 列式 Arrow）单独立账。

经验口径（自测）：向量化栈早期在 wire 格式上使用 Base64 编码 + 多次字符串拷贝
（一条记录九次拷贝的实测案例见姊妹 skill 的案例实录），行摊薄 wire 成本可数倍
于原生序列化——这是"算子已对齐仍残余数倍差距"的典型归属。

## 批的生死边界

判定一条批什么时候"活"什么时候"死"：

- **生**：source 整批到达 / 桥上攒批配置触发（preferred_output_batch_rows 类配置键
  决定输出批行数）；
- **死**：跨出 native 段（经序列化出网络边）——下游收到的是新批（反序列化产物），
  上游批的生命周期结束；
- **跨出再回来的形态**：出 native 段再回来 = 序列化→反序列化往返，批形态重建；
  同段内传递 = 引用直通。

判定口诀：**凡过网络边批必重建，凡同段内批必直通**。评估任何"零拷贝"声明时，
先问这段路径过了几条网络边。

## 出/入桥的 rowKind 契约

changelog 标记（row kind：insert/update-before/update-after/delete）在向量化批上
以尾列（$row_kind 列契约）承载：出桥写尾列、入桥读尾列。**跨算子的 row kind 保真
依赖这个契约**——语义对照矩阵中"rowKind 保真"回归项的验证对象就是它（丢 row kind
= changelog 折叠不一致 = 行为冻结失败）。

## 调用本参考的判定

- 疑似传输层差距 → 先数网络边条数与每行 wire 成本（本文件对账法），再进姊妹
  skill 的税种消除；
- "合并算子/消灭序列化"提案 → 先用"KEY-GROUP 是网络边"推论核收益边界；
- changelog 不一致 → 先查 rowKind 尾列契约两端。
