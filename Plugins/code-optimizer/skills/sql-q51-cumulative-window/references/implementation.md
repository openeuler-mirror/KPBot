# 前缀窗口与排序复用

两个分支分别按商品分区，在每个商品内按 `d_date` 升序计算累计 `SUM`。仅按商品排序不能保证分区内日期升序，不能据此跳过窗口前的日期排序。全外连接后的两列累计 `MAX` 使用同一窗口规格，核对物理计划是否已经由一个窗口算子共享分区和排序。用运行计划确认关联的 `Exchange`、`Sort` 和窗口是否发生回退及 spill。

1. 写明输入的分区键、排序键、升降序、NULL 排序和证明该属性成立的算子。普通哈希连接、Shuffle 和全外连接后的键投影均可能使原顺序失效。相同的列名或表达式文本不足以满足有序输入契约。
2. 复用当前已保证的排序并检查更紧凑的流式窗口构建。当前 Velox 的 `Window.cpp` 根据 `inputsSorted()` 与窗口函数和 frame 的实现条件选择行级流式、分区级流式或排序路径。准入沿用引擎校验。
3. 检查窗口状态在商品边界重置、跨批次延续、NULL 不参与聚合及全 NULL 输出。样本覆盖累计销售下降的情况。后置的 `MAX` 表达历史峰值，缺失渠道行的原始累计值仍是 NULL。相同 item/date 的排序并列按原计划语义处理，证明无并列时才能依赖唯一总序。

## 源码定位

### 可复用属性的记录表

逐边记录 `生产节点 → 消费窗口`、商品分区范围、全部排序字段/方向/NULL 规则、frame、函数类型及中间节点。哈希连接或 Exchange 后若没有新的顺序保证，就按排序属性失效处理。两列 MAX 只有完整规格兼容时共享构建，不共享各自的值和 NULL 状态。

| 条件 | 允许评估 | 回退 |
| --- | --- | --- |
| 已证明有序、分区有效、函数/frame 支持 | 目标版本已有的流式路径 | 原排序窗口 |
| 原计划已共用两列 MAX 的排序 | 继续定位状态、内存或长分区成本 | 不重复“省一次排序” |
| ROWS 逐行前缀与 RANGE peers 不同 | 仅用支持当前 frame 的实现 | 保留原窗口 |

### 跨批次与 peers 例子

商品 1 的日金额 100、NULL、-70 分两批输入，第一批结束不能清空 sum/max。第二批最后结果是 sum=30、peak=100。接着商品 2 若全 NULL，应输出 NULL/NULL，不继承商品 1 的状态。用例把同一个逻辑分区拆成不同批次并与 SQLite 的完整窗口比较。

对同日两个金额 10、20，ROWS 的首行前缀可以是 10，而 RANGE 当前日的两行都可得到 30。不要为了使用逐行实现把 RANGE 改为 ROWS，也不能以样本没有 peers 代替约束证明。检验中的排序扫描只用于小数据 oracle；生产路由依赖已有计划属性。

### 验收分层

本地结果比对涵盖前缀、全 NULL、分区重置和 peers 反例，不能证明原生窗口选择。目标验收须记录真实分派、回退原因、实际排序构建次数及输入行、窗口行、内存和 spill。别把一个批量输入调用计为处理一行，也不按窗口表达式数量推算排序次数。

按 `WindowExecTransformer.scala`、`SubstraitToVeloxPlan.cc` 和 `Window.cpp` 检查窗口下推、输入排序标记及实现选择。原生实现应能定位到 `SortWindowBuild.cpp`、`RowsStreamingWindowBuild.cpp` 或 `PartitionStreamingWindowBuild.cpp`。
