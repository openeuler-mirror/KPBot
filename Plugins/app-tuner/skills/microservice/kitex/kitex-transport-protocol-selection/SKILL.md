# Kitex 传输协议与元信息开销

本 skill 回答"用哪种传输协议、以及为它付多少额外开销"，不改编解码实现（见 `kitex-thrift-codec-selection`），也不做连接与事件循环调优（见 `kitex-transport-tuning`）。

## 何时触发

- 在 Framed、TTHeader、gRPC 之间选型或评估迁移。
- 已用 TTHeader，但透传元信息导致分配与延迟上升。
- 在 ARM64 上使用泛化调用，或看到动态编解码库的降级告警。
- 需要流式、跨语言、服务网格透传等能力，必须确认协议侧成本。

## 范围

- 覆盖：Framed / TTHeader / gRPC 选型、元信息开销、ARM64 泛化调用可用性。
- 不覆盖：编解码实现、连接容量、框架改造。

## 出处

- 协议实现与默认值：`pkg/rpcinfo/rpcconfig.go`、`pkg/remote/codec/header_codec.go`、`pkg/remote/trans/nphttp2/`（版本以现场读取为准）。
- 元信息解析：`gopkg/protocol/ttheader/`。

## 命中验证与越界验证

- 命中：问"启用透传后分配和延迟都涨了，值不值"，应答"按 header 数量与长度评估，再决定精简还是换协议"。
- 越界：问"事件循环线程数设多少"，应答属于连接容量，转 `kitex-transport-tuning`。

## 协议对比

| 协议 | 结构 | 适合 | 主要成本 |
|---|---|---|---|
| Framed | 长度前缀 + 纯 payload | 同语言、无需透传 | 最低 |
| TTHeader | 长度 + 头 + 键值元信息 + payload | 需要透传、跨语言路由、服务治理 | 每请求解析头部并构造键值容器，字符串需拷贝 |
| gRPC | HTTP/2 帧 + 头部压缩 + 流控 | 跨语言、流式、生态互通 | 头部构造与压缩、控制帧队列、流控状态机 |

## 关键事实

- 新版本默认传输协议已从"带缓冲"改为 Framed；升级前先确认默认值变化。
- TTHeader 的元信息解析会按需创建键值容器，并对每个值做字符串拷贝；键值越多、越长，成本越高。
- gRPC 的成本是协议固有的，不是实现缺陷；能用 Framed/TTHeader 满足需求时不要选 gRPC。
- ARM64 上部分动态编解码/泛化调用库只对 x86 提供加速路径，启动时会打印降级告警，性能可能明显低于静态生成代码。

## 执行步骤

1. **列需求**：是否需要跨语言、透传、流式、服务网格；不需要就不要为协议付成本。
2. **看现状**：确认两侧协议与版本默认值；升级过版本的要重新确认。
3. **量成本**：对比 Framed 与目标协议的 QPS/P99/每请求分配；TTHeader 还要看透传键值数量。
4. **压元信息**：能不放 header 的就不放；必须放的合并同类项、缩短值长度。
5. **泛化调用**：在 ARM64 上单独压测；能用静态生成代码就不要用泛化调用。
6. **回归**：协议切换后验证超时、重试、错误码、流式与半包处理。

## 判断要点

- Framed 是默认且最省成本的选项；只有当确实需要透传或跨语言能力时才升级协议。
- TTHeader 的成本随 header 数量与长度线性上升，且会体现在分配侧；先精简再换协议。
- gRPC 的额外成本集中在头部构造、头部压缩、控制帧与流控，不能靠调参消除；必要时评估改回 Thrift 路径。
- ARM64 上的泛化调用是已知的降级点；优先使用静态生成代码。

## 回退

- 恢复原协议与两侧选项。
- 保留原 header 集合与版本配置，避免回退后下游解析失败。

## 输出

- 输出协议选择结论、元信息精简清单与回归项；不产出文件。

## 与相邻技能的边界

- 连接形态：独占/复用与池参数在 `kitex-transport-tuning`。若决定启用复用连接，协议必须是 TTHeader；本 skill 负责确认该约束下的兼容性与回归项。
- 元信息精简：本 skill 决定"要不要传、传哪些键"；"传了之后如何减少分配"由 `kitex-allocation-hotspot-tuning` 评估。
- 编解码实现：在 `kitex-thrift-codec-selection`，与线路协议是两个独立决策。
- 本 skill 可独立调用，不依赖 `WORKFLOW.md` 的中间产物。
