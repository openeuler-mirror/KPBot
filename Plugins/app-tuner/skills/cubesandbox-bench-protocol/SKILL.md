# CubeSandbox 生命周期性能基准协议

为 CubeSandbox 创建/恢复性能工作提供可信测量：**同一纪元、同一模板、同一清理口径**
下的吞吐与延迟，以及供归因用的轮内分布形态。本 skill 是 CubeSandbox 调优类工作的
测量底座——没有可信的测量，任何优化结论都是空中楼阁。

## 场景与口径

| 用例 | 负载 | 主指标 | 说明 |
|---|---|---|---|
| 吞吐 | `cube-bench -c 50 -n 500 -m create-only` | total_time / avg | 高并发大批量，看系统吞吐与稳定性 |
| 延迟 | `cube-bench -c 100 -n 100 -m create-only` | **Total Time** | 官方口径以一轮总时长为准；p50/p99 辅助 |
| 暂停/恢复 | pause/resume 基准（c10n5） | pause_avg / resume_avg | 恢复路径专项 |

口径纪律：

1. **各跑 ≥3 轮取中位数**，不取单轮，更不取最好轮；
2. warmup 阶段不计入计时（bench 二进制行为）；不同版本的 bench 二进制计时口径可能
   不同，跨版本数字不可直接对比；
3. `-o <file>.json` 落盘报告（config + summary + create/delete 统计块 + **raw 逐请求
   明细**），判读用 raw 而不只是 summary；
4. 绑核基线：按官方口径不额外 numactl 绑核（实测绑核与否无差异的场合以不绑为准，
   保持与基线可比）。

## 纪元纪律（最重要）

**跨重启纪元的数字不可比**。实测同版本组件栈，仅宿主机重启一项即可造成同指标
+50% 左右的系统性漂移（且多轮不收敛）；对比必须同纪元同窗口。详见
[epoch-discipline.md](references/epoch-discipline.md)。要点：

1. 以下任一变化即开启**新纪元**，必须重测基线：宿主机重启、内核/内核参数变更、
   沙箱组件版本/二进制替换、模板变更；
2. 单实例健康度（如 c1 创建延迟）是纪元锚点：先确认单实例健康，再谈并发数字——
   罚金只在并发时出现说明是争用，单实例就慢说明环境本身有问题；
3. 报告结论必须注明纪元（组件版本 + 关键环境标识），跨纪元结论无效。

## 多轮纪律（防冷窗口）

同步类问题的失败/成功具有**热/冷窗口竞态**：后台状态同步恰好落在测量窗口内才显现，
单轮可能全过或全败。因此：

1. 验证修复（尤其并发错误类）：**连跑 ≥6 轮**（历史上 6 轮 × 500 = 3000 次创建
   零错误才算闭环）；
2. 单轮全过不能宣布修好，单轮全败不能宣布退步；
3. 轮与轮之间做完整清理（见下节），否则容量耗尽会把"退步"伪装成"错误"。

## 轮间清理清单

每轮之间按序清理，缺一会产生假信号：

1. **沙箱实例**：单节点并发容量有上限（数量级 ~600+，受 IP 池与资源配额约束），
   超限报"no more resource"——这是容量错误不是性能退步；
2. **TAP 接口**：残留 TAP 会拖垮后续轮（严重时服务重启都会卡死）；v0.7.x 的 TAP 以
   IP 命名（`192.168.x.x`），清理命令要匹配实际命名规则，别用旧版本命名（`z192.*`）
   白跑一场；
3. **网络代理状态文件**（如有）：清空 state 目录下的运行时记录。

bench 脚本族通常自带清理模式（如无参/0 参调用只执行清理），优先用自带模式。

## 结果判读纪律

1. **看轮内分布，不只看均值**：`create` 块的 min/avg/p50/p90/p95/p99/max 一行排开，
   分布形态本身是根因线索：
   - `uniform-lift`（min/max 同步抬高，极差比小）→ 共享资源争用（内存带宽/缓存行/
     串行化路径），加核无效，找共享点；
   - `staircase`（max ≫ min，分层）→ 串行化排队（锁/单点服务），数台阶可估并发度；
   - `quantized-tail`（少量样本聚在窄带高值，如精确 601-602ms）→ 量化效应：某个
     轮询周期/超时参数在睡大觉，找周期值反推组件（601 ≈ 500ms 轮询 + 100ms 首查）；
2. 多轮趋势：轮间中位数波动大（CV > 10%）说明环境不稳，先稳环境再下结论；
3. **时间戳考古**：结果文件名/内部 timestamp 通常是脚本**启动**时间（含 pre-run
   清理 ~30s），定位真实测量窗口用文件 mtime 反推结束点；
4. 跑没跑完看日志收尾标志（`Done!`/`Summary`）或持 PID 判断；**不要 `pgrep -f <脚本名>`**
   （命令串含关键词会自匹配，永远误判"还在运行"）。

脚本 `scripts/analyze_bench_results.py` 自动完成上述判读（形态分类 + **按场景分组的轮次聚合** + 纪元提示）。轮次聚合按 `(concurrency, total, mode, template)` 分组——c1 锚点、吞吐、延迟、**模板 A/B 对照**混在同一目录时各自成组，永不并算（并算会使 median/CV 失真并伪造 "≥3 轮" 信号）；每组携带 `n` 与 `rounds_sufficient`——**引用某组结论前必须确认该组 n ≥ 3**，n < 3 的组（如单轮 c1 锚点、模板 A/B 对照的各 1 轮）stability 标记为 "insufficient rounds"，只能作为单轮参考，不得当作已验证结论：

```sh
python3 scripts/analyze_bench_results.py --files run1.json run2.json run3.json
python3 scripts/analyze_bench_results.py --dir results/          # 按 mtime 排序全量
python3 scripts/analyze_bench_results.py --dir results/ --output verdict.json
```

## 执行纪律

1. **逐轮分步执行**：不要在一条远程命令里串多轮（bench+清理），长命令超时被掐断后
   状态不明，清理与计时全部作废；
2. 每轮启动前确认上轮清理完成（实例数归零/TAP 归零）；
3. 报告文件按轮次归档，判读时全量送入脚本。

## Anti-patterns

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 单轮下结论 | ≥3 轮中位数；修错验证 ≥6 轮连跑 |
| 2 | 跨重启/跨环境变更比数字 | 同纪元同窗口；新纪元重测基线 |
| 3 | 只看均值 | 轮内分布 + 形态分类（uniform/staircase/quantized-tail） |
| 4 | 不清理跑下一轮 | 每轮完整清理（实例/TAP/状态文件） |
| 5 | 容量错误当性能退步 | "no more resource" 先查容量上限 |
| 6 | 拿文件名时间戳当测量窗口 | mtime 反推；文件名含 pre-run 清理时间 |
| 7 | `pgrep -f` 判跑完 | 日志收尾标志或 PID |
| 8 | 一条命令串多轮 | 逐轮分步，轮间人工确认 |
| 9 | 跨机器直接比数字 | 先对齐 sysctl/内核开关（单个开关可差 10 倍） |
| 10 | 跨版本 bench 二进制比数字 | 确认计时口径一致再比 |
