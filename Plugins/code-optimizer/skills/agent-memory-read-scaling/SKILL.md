# L4 读路径多进程扩展

> 前置：扩展曲线已测、拐点已确认（见 `agent-memory-read-scale-curve`）。本 skill 只负责实施。

## 前置条件

- 前三项做完，单副本仍单核 99%，服务端未饱和；
- 先验证"多线程无效"（GIL 下 4 线程与单线程等速），别把预算花在 GIL 上。

## 做法

**串行写入（单队列）+ N 个查询副本进程**：

- 每个副本独立解释器、事件循环、连接池；
- 副本内用信号量控并发（本例 20）；
- 副本 0 幂等建索引，其余错峰启动（0.3 s）避免建连惊群；
- 副本数与服务端核预算一起规划。

## 实测（标定案例）

- 固定核预算下 5 副本达到 **3.08×**；
- 容量模型 **容量 ≈ 核数 / 1.45**（客户端与服务端分摊同一预算）；
- 副本继续加时吞吐反降、连接重试激增（线程饿死）。

## 风险

- **写入不可并行**：实体在会话间共享，判重依赖并发交错顺序 → 缓存键不确定 → 命中率崩塌；
- 内存按副本数预留：每副本常驻内存随客户端缓存与索引规模增长；
- 加副本若未同步服务端核预算，只是在制造重试。

## 不适用于

运行时没有 GIL/单线程约束（C++/Go/JVM 原生线程池）——那边先查锁竞争、线程池利用率与 GC；
多副本仍可用于分片读，但上限由服务端预算决定。判据：单副本 CPU% 未到 100% 时加副本只是排队。
