# 案例：仅元数据对象的分配下限

本案例是 `allocation-path-optimization` 的证据来源：一个事件缓冲区库中，引用型数据块的元数据对象被通用分配下限放大了 16 倍，导致清理路径被内核回收主导。库名与函数名只作为证据，配方本身不依赖它们。

## 现象

清理接口（依次释放缓冲区里的链）在 Kunpeng 目标机上约 77 ns/op，而同轮对照平台约 32 ns/op。链本身很小，清理的算法复杂度是 O(链数)，却出现这么大的差距。

profiler 的调用链给出了明确答案：

```
drain -> free -> systrim -> brk -> unmap/zap/page/memcg
```

即耗时不在清理逻辑，而在 `free` 触发堆顶收缩、内核回收页表与物理页。单个批次的堆顶收缩量约 5.02 MiB，耗时约 231 µs，折算到每操作约 56 ns——与默认环境和关闭 trim 后的差值（77.1 → 27.3 ns/op）吻合。

## 根因

每个引用型链只需：

```
链头结构体          48 B
引用元数据          16 B
合计                64 B
```

但通用分配 helper 对小于 1024 B 的请求一律提升到 1024 B（该下限原本是为"拥有内部数据区"的链设计的，用来把元数据开销压到 5% 以下）。引用型链的 `buffer` 字段在创建后立即被外部数据地址覆盖，内部数据区永远不用——于是每个 64 B 的对象占 1024 B，通胀 16 倍。

一个批次约 5119 个这样的对象，占用从约 5.08 MiB 变成约 0.39 MiB，直接决定了堆顶能否被 trim、内核要做多少回收工作。

## 改动

只在引用型链的创建点增加紧凑分配：按 `链头 + 引用元数据` 的精确尺寸申请，其余字段初始化保持与通用 helper 一致（清零、refcnt=1、extra 区紧邻链头）。通用 helper 与数据型链的分配保持不变。

同时保持：锁协议不变、引用计数不变、cleanup 回调语义不变、允许跨线程释放（每个链仍独立申请与释放）、自定义分配器下 malloc/free 仍同源成对。

## 实测

分配口径（`alloc_probe`，20 万次操作；该比值由数据结构与分配下限决定，在 64 位目标上与平台无关；32 位下 `MIN_BUFFER_SIZE` 为 512，比值随之下移）：

| 指标 | 基线 | 改动后 | 倍数 |
|---|---|---|---|
| 申请字节总数 | 256,008,712 | 16,010,632 | 16.0x |
| 峰值活字节 | 5,249,160 | 332,040 | 15.8x |
| 每操作申请字节 | 1280.0 | 80.1 | 16.0x |

时间口径（Kunpeng 目标机，上游验收记录）：清理接口从约 77.2 ns/op 降到 17.89 ns/op（7 次中位数），约 4.3 倍；同时 `brk` 收缩从约 40003 次降到 6 次，minor page fault 从约 127 万降到 168。这与"内核回收主导"的因果判断一致。对应的上游改动是 `4319044c`（buffer: compact AArch64 reference metadata）。

这些是上游在目标机上取得的测量记录，未随本仓库提供，也未在仓库内复测；用例的验收以运行时断言为准。

## 免费得到的第二个接口

该库的"读一行"接口在内部会清理已消费的链，因此同一改动让它也加快了约 17%（70.8 → 59.3 ns/op）。这提示一个重要经验：分配类改动的收益面常常比目标函数更宽，验证时要扫一遍共用该分配点的所有接口。

## 一个被拒绝的相邻候选

同一轮实验里，把分配下限本身从 1024 调小以"顺便帮到所有链"被拒绝。原因：下限对拥有内部数据区的链仍然正确，全局调低会让所有小数据块的数据区变小、重对齐与分配次数上升，收益与风险不成比例。正确做法是**只在用途明确的调用点做精确分配**。

## 复现命令

```bash
# 1) 确定性字节口径
cc -O2 bench.c <skill>/scripts/alloc_probe.c \
   -Wl,--wrap=malloc -Wl,--wrap=calloc -Wl,--wrap=realloc -Wl,--wrap=free \
   <objects> -o bench_alloc
./bench_alloc -n 200000

# 2) 尺寸类审计（与实测交叉验证）
python3 <skill>/scripts/alloc_size_audit.py --sizes sizes.txt --floor 1024 \
    --op-count 200000 --actual-bytes-per-op 1280.04 --actual-peak-live 5249160

# 3) 因果对照
MALLOC_TRIM_THRESHOLD_=-1 ./bench_alloc -n 200000
```

## 该案例给出的通用经验

1. 高频、极小、短生命周期对象的成本通常不在 CPU，而在"申请了多少字节"以及内核为此做的回收工作。
2. 通用分配 helper 的最小尺寸对数据型对象正确，对仅元数据对象是浪费；修复点在调用点，不在 helper。
3. 峰值活字节与工作集比"每次申请多大"更能解释时间收益。
4. 用确定性口径（申请字节、峰值、brk 次数）做门禁，wall-clock 只作参考。
5. 改动命中一个分配点时，要主动检查共用该分配点的其它接口，收益往往是复数的。
