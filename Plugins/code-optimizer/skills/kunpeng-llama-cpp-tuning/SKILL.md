# Kunpeng llama.cpp Embedding 端到端性能优化

当目标是在鲲鹏服务器上获得可合入、可复现且正确性通过的 llama.cpp Embedding 性能提升时，使用本 Skill。优化有三条路径：接入新的高性能算子库、修复或优化已有后端的接入层、优化 llama.cpp/ggml 自身实现。配置搜索和 profiling 只用于建立强基线与选择代码修改，不能作为优化任务的最终产物。用户已授权优化或允许探索后直接修改时，应让高收益候选在同一正确性预算下进行有界竞争，选出最快的通过项，再应用到目标源码树并重新构建复测；第一个成功候选不是默认终点。

本 Skill 沉淀的是可迁移的决策与验证方法，不是某台服务器的固定参数。CPU 编号、NUMA 节点、线程数、batch、算子库线程数、路由阈值和收益百分比都必须在目标服务器重新测量。

## When to use

满足以下任一条件时进入本 Skill 流程：

1. **需要接入新的 CPU 算子库**：候选库支持热点算子、数据类型和形状，需要完成构建检测、ggml 注册、张量映射、执行与 fallback。
2. **算子库已经接入但没有获得预期收益**：库已编译或加载，但计算图未实际路由，或转换、打包、线程、缓存、同步和 shape 阈值吞噬了收益。
3. **热点位于 llama.cpp/ggml native 路径**：需要优化 ISA 选择、向量内核、循环依赖、分块、归约、融合、内存访问或调度。
4. **需要比较 native/KDNN/KleidiAI/OpenBLAS**：目标是选择并落地最快的正确实现，而不是证明预设后端优胜。
5. **更换鲲鹏服务器、编译器、模型或关键运行库**：历史补丁可作为候选，但机器配置与历史收益必须重新校准。

不适用的情况：

- 只要求诊断、解释或基准报告：保持只读，不自动修改源码。
- 用户明确只允许配置调优：可以交付配置结果，但不能称为源码优化。
- GPU/CUDA/NPU 是主要执行设备，或目标不是 llama.cpp：不要套用本 Skill。
- 没有代表性模型、工作负载或正确性参考，且无法合理构造代理：先报告缺口，不能凭单个随意 prompt 宣称优化成功。

## Core findings

Core findings 只记录性能为什么变化、收益属于哪一层以及结论的适用边界；执行步骤和交付规则放在后续章节。

1. **端到端收益受热点占比限制。** 先把 Embedding 延迟拆成算子计算、转换/打包、调度/同步和服务开销，再用热点占比估算候选的理论收益上限。只优化占比很小的阶段，即使该阶段完全消失，端到端收益也有限；因此优先处理占比高且调用频繁的路径。

2. **配置收益与代码收益必须分开归因。** NUMA、绑核、线程、batch 和并发优化决定代码对比的强基线，但不能计入源码加速。代码收益只能来自冻结同一运行配置后的 matched control/candidate；否则无法判断变快来自配置还是实现。

3. **新算子库的真实收益是“计算节省减去接入成本”。** 算子库内核加速只是毛收益，张量转换、权重打包、workspace、线程启动、同步、缓存失效和 fallback 都属于接入成本。库覆盖主导热点且净收益为正时才值得接入；小 shape 或短请求可能更适合 native 路径。

4. **接入层性能由覆盖率和每次调用开销共同决定。** `supports_op`、shape/type/stride 映射和路由阈值决定热点覆盖率；缓存生命周期、转换复用和线程协调决定单次接入成本。库已构建或已加载但图节点没有实际进入，收益归零；过度路由到不合适形状也可能产生回退。

5. **native 优化首先归因于快路径是否生效，其次才是内核细节。** feature detection、编译 flags、dispatch 和运行时路由决定 SVE/SVE2/NEON 快路径是否存在并被选择；向量化、独立累加器、分块、归约、融合和预取决定快路径内部效率。若目标指令没有生成，先修复构建或 dispatch，避免在未执行的内核上优化。

6. **微内核收益具有工具链和微架构边界。** 编译器、优化级别、ISA、向量长度、核心流水线和库版本会改变指令调度、寄存器压力与访存行为。同一补丁在不同构建上可能方向相反，所以性能归因必须同时记录生成指令和环境指纹；迁移的是机制假设，不是历史收益数字。

7. **调度与内存收益不能错误归因给计算内核。** barrier、任务粒度、嵌套并行、false sharing、NUMA first-touch、重复复制和缓存局部性都可能改变端到端性能。应结合计数器、调用栈和分阶段计时区分“计算更快”“等待更少”“数据移动更少”，避免仅凭热点函数名称归因。

8. **性能归因需要执行证据和反事实对照。** 新后端至少证明构建/注册、正确库加载、热点节点实际执行；源码候选保持同源、同工具链、同资源且只改变一个主要机制。AB/BA 方向不一致的小收益优先归因为系统噪声，而不是候选效果。

9. **正确性阈值同时定义了可用的数值优化空间。** 精度不是只能“完全不变”或“任意降低”两种选择。用户给出 cosine、最大绝对误差、输出维度和有限值门禁时，可比较保持原累加精度、混合精度和降低累加精度等实现，但每个精度候选都必须独立通过完整代表性负载与边界输入；不能因某个保守候选先通过，就放弃仍在明确误差预算内且理论上更快的实现。

10. **获得提升不等于找到当前预算内的最好实现。** 热点仍占主导且理论上还有明显余量时，至少让两个不同的高收益代码机制完成低成本筛选，例如“修复 ISA/dispatch”与“优化内核数据路径”，或“减少转换”与“缓存转换结果”。首个候选只有在接近 Amdahl 上界、剩余候选被证据排除或实现预算确实耗尽时才能直接结束。

## Methodology

按以下 6 步执行，每一步都有明确产物；探索达到能够决定下一项代码修改的程度就停止，不追求工具覆盖率。

1. **冻结真实目标与正确性。** 记录模型哈希、真实或代表性请求、token 数、请求权重、延迟/吞吐指标、当前生产配置、正确性阈值和分桶回退上限。产物：工作负载清单、指标公式和正确性参考。
2. **审计环境并建立强配置基线。** 首次运行或服务器变化时，用系统工具采集 CPU/NUMA、ISA、编译器、运行库和当前负载；根据实际拓扑生成有界候选，比较物理/逻辑核、线程数、NUMA、batch 线程、并发和库内部线程。配置搜索只占完成可信基线所需的预算。产物：机器/构建指纹、生产基线、强配置基线和原始样本。
3. **确认路由并定位主导热点。** 用构建日志、maps、图日志/计数器/采样栈确认实际执行路径；用 `perf stat` 和调用图定位主导算子、shape、type、stride、转换、同步和调度开销。产物：后端三层证据、热点表和理论收益上界。
4. **选择路径并进行有界候选竞争。** 先检查 ISA 实际生成和路由问题，再在“新算子库、接入层、native 实现”中按理论收益选择候选。读取调用者、所有权、对齐、alias、tail、累加精度和 fallback 语义后，在隔离副本实施最小 C/C++ 修改。若首个候选通过但热点仍占主导且离理论上界较远，继续筛选至少一个不同机制的高收益候选；同一微内核还应以少量离散值比较独立累加器或展开深度，避免把未经测量的单一实现误当成最优。产物：候选排名、可证伪假设、补丁和预期观测变化。
5. **选择最快正确候选并直接落地。** 所有入围 candidate 与 control 使用相同源码基线、工具链、参数和资源；先用少量重复执行专项测试、Embedding 正确性和完整端到端负载，仅让通过门禁且无关键分桶回退的候选进入正式 AB/BA。按目标函数选择最快项后，三方检查目标树与候选差异，直接应用补丁，并在目标树的新构建目录复验。产物：匹配对比、正确性结果、候选拒绝理由、目标树修改和最终复测。
6. **交付与归因。** 分开报告配置收益、算子库/接入层收益和 llama.cpp 自身代码收益；给出可提交 diff、适用边界、复现命令与回退方式。没有代码候选通过时，状态是“优化未完成/受阻”，并给出下一项具体实现，不能用探索完成代替。

## Operator and llama.cpp integration checklist

### 新算子库接入

1. 核对版本、许可证、AArch64/鲲鹏支持、ISA 要求、线程模型和稳定 API。
2. 映射 ggml 张量语义：type、shape、stride、transpose、alignment、batch、broadcast、tail 和累加精度。
3. 增加可选构建检测与显式开关；依赖缺失或形状不支持时保留 native fallback。
4. 实现严格的 `supports_op`、后端注册、执行路径和错误回退，不能改变其他架构的默认行为。
5. 管理句柄、workspace、常量权重打包和缓存生命周期，避免每请求重复初始化或转换。
6. 协调 llama.cpp 外层线程与库内线程，避免嵌套并行和隐式跨 NUMA 扩散。
7. 测量支持/不支持形状、阈值两侧、短/长输入；端到端时间包含转换、打包、同步和调度。

### 已有接入层优化

1. 检查 `supports_op` 是否过严导致 fallback，或过宽导致低效/错误路由。
2. 检查 shape/type/stride/transpose 映射是否触发隐藏复制或通用慢路径。
3. 比较小矩阵 native fallback 与大矩阵算子库路径，按目标机器实测 shape-aware 阈值。
4. 检查权重打包、布局转换、句柄和 workspace 能否跨请求安全复用。
5. 检查 backend buffer、线程、调度、同步、锁和缓存是否引入额外移动或栅栏。

### llama.cpp/ggml 自身优化

1. 检查热点函数反汇编与 ISA feature probe，确认 SVE/SVE2/NEON 指令实际生成。
2. 根据热点机制选择向量化、独立累加器、分块、归约树、预取、融合或内存布局修改；对独立累加器数和展开深度只搜索少量有依据的离散值。
3. 当用户给出明确数值门禁时，把累加精度列为候选维度：分别验证保持精度、混合精度或较低精度的实现，保存每个分桶的 cosine 和最大绝对误差；没有明确门禁时不得自行降低精度。
4. 保留不支持 ISA、类型、shape 和 tail 的原路径；不得为了单一模型破坏通用 fallback。
5. 检查 barrier、任务粒度、false sharing、NUMA first-touch 和 oversubscription。
6. 用专项微基准解释机制，用完整 Embedding 请求决定候选排名；只要主导热点仍存在且预算允许，不因首个候选提速就提前停止。

## Anti-patterns

以下反模式遇到即拒绝：

| # | 反模式 | 为什么错 | 正确做法 |
|---|---|---|---|
| 1 | 只找到最佳线程/绑核就结束 | 只是配置调优，没有代码交付 | 冻结强基线后进入源码优化 |
| 2 | 无限 profiling 或遍历所有后端 | 消耗实现和复验预算，没有上线产物 | 证据足以选择候选后立即修改 |
| 3 | 看到库被链接/加载就归因 | 不代表热点图节点实际执行 | 保存构建、加载、执行三层证据 |
| 4 | 先优化低占比锁或日志 | 理论收益上限低，容易落入噪声 | 按收益上界和证据排序 |
| 5 | 只看微基准或单一 GEMM | 忽略转换、路由、同步和 HTTP/调度开销 | 用端到端加权负载验收 |
| 6 | control/candidate 使用不同编译器或 flags | 无法把收益归因于源码修改 | 同源、同工具链、单机制差异 |
| 7 | 从干净 Git revision 构造 control，遗漏本地修改 | 候选与用户真实源码不匹配 | 隔离复制完整目标源码状态 |
| 8 | 复用构建目录或只检查可执行文件路径 | 可能加载错误的 `libggml-cpu` | 独立构建并校验 maps、RPATH 和哈希 |
| 9 | 把另一台服务器的 CPU 列表和阈值写死 | 拓扑、NUMA、缓存和编译器均可能不同 | 目标服务器重新检测和搜索 |
| 10 | 两个候选失败就称为优化完成 | 负面探索没有产生可合入性能提升 | 标记未完成并继续下一高优先级实现 |
| 11 | 候选通过后只交付实验目录 patch | 用户目标树没有得到优化 | 应用到目标树并从目标树复验 |
| 12 | 覆盖、清理或回退用户已有修改 | 破坏工作区且使结果不可追溯 | 三方差异检查，只应用本次最小补丁 |
| 13 | 第一个正确且提速的候选通过后立即停止 | 证明了“可优化”，没有证明预算内已选到更快实现 | 热点仍主导时再筛一个不同机制，并按统一目标函数择优 |
| 14 | 未经门禁就降低精度，或完全忽略用户允许的误差预算 | 前者可能破坏结果，后者可能错过大幅收益 | 将累加精度作为显式候选，并逐桶执行完整正确性验证 |

## Benchmark protocol

所有性能结论必须遵守以下协议：

- **统一目标函数**：默认使用各请求中位延迟按生产权重加权；吞吐任务固定或显式搜索并发和槽位。报告真实 token 数。
- **强基线但分开归因**：生产配置、强配置基线和代码候选分别重放；配置收益不能计入代码收益。
- **预热与重复**：明确冷启动、首次请求和预热稳定态；重复次数在实验前固定，保留全部原始样本和异常值。
- **反顺序复测**：执行 AB/BA 或等价交错顺序。方向不一致的小收益默认视为噪声，除非统计与系统证据能够解释。
- **完全匹配的 control/candidate**：模型、请求、环境、CPU/NUMA、server flags、compiler、build flags 和动态库身份一致，只改变一个主要代码机制。
- **正确性先于排名**：验证 cosine、最大绝对误差、输出维度、token 数和非有限值；失败候选不参与性能排名。
- **分桶回退约束**：总体加权收益不能掩盖关键短/中/长请求回退；使用用户阈值，未给出时先声明保守阈值。
- **后端归因门禁**：只有三层执行证据完整时，才能声称收益来自新算子库或接入层。
- **目标树最终复测**：隔离候选的收益只是准入条件，最终数字必须来自已应用修改的目标源码树构建。

环境采集、候选生成、统计、正确性和构建指纹可以直接使用目标服务器已有的系统工具；需要自动化时，将一次性工具放入实验证据目录，不要混入目标源码补丁。任何测量工具都必须对 control/candidate 使用同一实现与参数，并保存原始输出以便复核。
