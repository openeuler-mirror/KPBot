# Lance BP NEON 解码优化

先确认 Lance 当前如何读取和解包 BP 数据，再实现保持原有文件格式与解码结果的 NEON 路径。先验证正确性和真实执行，再分别判断解包、完整 BP 解码和业务查询是否变快。

## 与现有技能配合

本技能负责 BP 布局和 NEON 适用条件。Rust intrinsics 或 C ABI 接入需要时参考同插件的 `rust-native-simd-integration`；短内核配对测量可参考 `kernel-paired-benchmark`，查询归因可参考 `kernel-business-performance-validation`。这些是可选辅助，本技能不依赖源包中未导入的 Lance 编排技能。

移植前读取[接入检查](references/integration-checklist.md)，补齐本次版本的位宽分派表、物理读写范围和逐层验证状态。本文中的历史路径及 benchmark 名称均需在目标提交重新核对。

## 输入

开始前核对以下信息。能够从源码、构建记录和已有结果查到的内容直接读取；缺少目标机器时先完成源码分析和方案，明确哪些结论没有实机证据。

```text
源码基线      仓库地址、分支、提交、未提交修改、Lance版本、目录规范
优化对象      InlineBitpacking入口、现有解包函数、候选实现、启用方式
数据条件      输出类型、压缩位宽、物理块大小、逻辑值数、排列与对齐
运行环境      CPU/指令集、工具链、构建特性、CPU/NUMA、线程和缓存策略
测试依据      官方用例源码及名称、自建扩展、压缩字节和独立预期结果
已有证据      正确性结果、命中计数、原始耗时、汇编、火焰图和业务结果
优化目标      需要改善的类型、位宽、计时范围及可接受的退化条件
```

版本号不能单独确定源码。记录实际执行程序或加载库的路径和摘要，防止修改的是一份源码、测量的却是另一份构建。

## 执行步骤

### 1. 确认原版实现和本次修改范围

读取仓库及 Rust 子目录的开发规范，使用该版本规定的工具链、依赖和 Cargo profile。基线以本次约定的 Lance 实现为准，不能把先前试验中的中间候选称为官方原版。

优先检查下列位置，再按实际版本追踪重命名、模块拆分和调用关系：

```text
rust/lance-encoding/src/encodings/physical/bitpacking.rs
rust/compression/bitpacking/src/
rust/lance-encoding/benches/decoder.rs
```

检查原版 Rust 解包的生成代码，确认是否已经自动向量化。不能仅因它用 Rust 编写，就称为纯标量实现。

本次默认只优化读取端，不改变写入规则、稳定文件格式、位宽含义和对外返回值。

### 2. 明确完整解码与解包的调用边界

沿实际代码标出下列工作，不能仅凭函数名称推测计时范围：

```text
BP完整解码入口
  +-- 头部、位宽、输入长度和请求值数检查
  +-- 建立输入类型视图
  +-- 分配输出
  +-- 选择原版或NEON实现
  +-- 解包：移位、拼接、掩码及输出写入
  +-- 按逻辑值数截断
  +-- 构造DataBlock并返回
```

分别定义“BP完整解码”和“BP解包”。计时若从输出分配之后、内核选择之前开始，就包含选择逻辑，不能称为只有 NEON 指令的纯内核时间。另行写明结果释放是否计时。

### 3. 核对位宽、FastLanes排列与块长度

先区分输出类型和压缩位宽。u32 值用 12 位保存，解码后仍需还原为原来的 u32 值，并不产生一种 12 位输出类型。

读取原版的通道排列、压缩字布局和跨字拼接规则。数值提取正确但写错位置仍是解码错误；不能用普通连续位流的展开规则替代 FastLanes 排列。

区分逻辑值数与内核实际读写范围。一次写满 1024 个值的内核，即使逻辑尾块只需要 1 个值，也必须先有容纳全部物理写入的空间，再截断为 1 个值。先越界写入、随后截断不能保证安全。

单块入口若只允许最多 1024 个值，应拒绝 1025；上层多块入口则需要正确处理跨块请求。零值请求是否提前返回，也按当前入口分别核对。

### 4. 定义候选适用条件和回退

列出候选覆盖的数据类型、压缩位宽、块长、缓冲要求和平台。历史候选主要覆盖 u32/u64 的中间位宽，零位宽、满位宽及其他类型保留原路径；新增覆盖要单独实现和验证。

```text
编译条件      候选对象是否编入，其他平台是否仍能构建
执行条件      CPU和系统是否支持实际使用的指令
数据条件      类型、位宽、输入长度和输出空间是否符合要求
回退条件      不适用时是否在任何候选写入之前选择原实现
```

外层开关为真或候选已编译，不等于实际执行 NEON。检查全局 target-cpu、target-feature 和原生编译参数：它们可能使分派函数之外也出现特定指令，有回退分支不代表整个二进制可移植。

### 5. 实现NEON解包

围绕原有布局，将独立的取位、移位、掩码、跨字拼接和输出写入改为向量操作。保持输出次序及数值，不通过改变磁盘排列来简化本次读取优化。

逐项检查：

- 零位宽、满位宽和跨字位置的移位、掩码，不产生按字长移位等未定义行为或错误结果。
- 向量加载与存储均处于已验证的可访问范围，不依赖额外越界字节“通常可读”。
- 指针转换、元素数量、对齐、输入输出不重叠等条件在进入 unsafe 或原生函数前成立。
- 未初始化输出通过原有原始指针或 MaybeUninit 方式写入，不提前形成覆盖未写区域的已初始化类型切片。
- 内核完整写入后才发布相应 Vec 长度，再执行逻辑截断。
- 不适用分支符合无写入回退约定，部分写入后的失败作为独立错误处理。

查看生成汇编，检查寄存器溢出、额外打乱、重复加载和函数调用成本。不能只因出现向量指令就认定优化有效。

### 6. 建立正确性和边界测试

将相同压缩字节交给原版和候选，逐值核对独立预期。随机测试固定种子，同时准备能辨认位置、跨字边界和高位处理的确定性数据。

不能只让新写的编码器和解码器互相往返验证，两者可能共享同一个排列错误。至少加入已有写入器生成的数据或独立指定的压缩字节和预期值。

```text
测试类别      覆盖要求
类型/位宽     u32的0～32、u64的0～64；其他类型检查原有回退
特殊路径      零位宽、满位宽及候选中的特殊分支
值分布        全零、位宽内最大值、边界位、位置可辨数据、固定随机值
逻辑长度      合法零长度、1、1023、1024和上层跨块的1025等长度
异常输入      无头部、无效位宽、截断数据、非法长度和缓冲条件
执行层次      直接内核、真实入口、候选关闭、不适用回退和非目标平台
内存边界      输出容量、完整初始化、尾块、对齐和可能的越界访问
```

所有位宽正确，不代表所有位宽都走 NEON；解码正确性覆盖与 SIMD 实际覆盖分别统计。完成修改后运行目标目录要求的针对性测试、格式和必要检查；准备提交代码时执行仓库要求的完整 lint。

### 7. 审计实际NEON命中

独立执行不计入正式性能成绩的审计运行，分别记录完整入口次数、实际 NEON 次数、原版次数、处理值数及回退原因。计数放在真正能够确认实现执行的位置。

确认候选关闭时使用原版，开启且适用时执行 NEON，不适用时执行约定回退。原版与候选处理值数和请求范围应一致；不一致时先定位原因。

正式计时关闭审计计数，确认源码、二进制和算法开关与审计时一致。阶段计时开关和算法开关分别控制。

### 8. 核对官方用例与自建扩展

扫描固定提交下的 benchmark 注册、辅助生成器和性能脚本，记录 target、group、实际完整用例名、输入生成及计时闭包。不只搜索 decoder.rs 就宣称不存在其他测试。

已核查版本中的官方组和两个基础用例为：

```text
target    decoder
group     decode_inline_bitpacking_unchunk
case      u32_bw12_1024
case      u64_bw23_1024
```

完整名称可能再带 legacy_copy、typed_view、compressed_bytes 等后缀，以当前源码和实际列出的名称为准。compressed_bytes 表示吞吐率字节口径，不说明计时只有内核。

先核对 Cargo.toml 中的 target 和特性。若该版本提供 bitpacking 特性，可从仓库根目录用下面的入口列出用例；原版和候选的启用特性仍按第 4 步核对，不凭这个命令认定已进入 NEON。

```sh
cargo bench --locked -p lance-encoding --bench decoder --profile release-with-debug --features bitpacking -- 'decode_inline_bitpacking_unchunk/' --list
cargo bench --locked -p lance-encoding --bench decoder --profile release-with-debug --features bitpacking -- 'decode_inline_bitpacking_unchunk/'
```

确认列出的用例非空，且不是表示特性关闭的占位用例后再测量。预热和测量参数按第 9 步的协议设置，原版与候选都通过相同的测试入口运行。

比较候选时，两侧包装路径必须一致，例如 typed_view 对 typed_view。legacy_copy 对 typed_view 还改变了分配或复制，不能把全部差异当作 NEON 收益。

扩展全位宽、更多类型或块数时保持生成规则和计时范围一致，并明确标记“基于官方结构的自建扩展”，不能写成官方现成用例。

### 9. 固定环境，执行配对测试

沿用用户确认的 CPU/NUMA、线程、缓存和频率策略。先检查目标核心空闲与真实拓扑，不能把历史 CPU8、CPU9 的关系当作所有机器的条件。

使用仓库规定的 release-with-debug。尽量在同一构建中切换实现；不同构建要保存补丁、编译参数和加载库差异。保持相同输入、工作量、包装逻辑和计时范围，不混入行布局或其他算法改动。

看到结果前确定预热、采样、轮次和顺序。各轮交替或平衡原版与候选顺序，保留原始样本、异常和运行状态。数据生成、独立结果检查放在约定计时范围外。

Criterion 样本通常包含多次迭代。轮次、样本、解码调用和 NEON 调用分别记录，不能把 10 个样本写成只执行 10 次解码。

### 10. 计算和解释收益

先核对正确性、命中、工作量和成对样本完整，再计算原版耗时除以候选耗时。保留前后耗时、每轮比值和离散情况，不只给最终倍数。

跨轮使用预先约定的几何平均等汇总方法。全位宽汇总明确权重，单独保留退化位宽。1.25 倍加速表示耗时减少 20%，不能写成减少 25%。

```text
观察结果                  后续检查
没有实际NEON调用          查构建、加载版本、类型、位宽和分派
解包没有稳定收益          查生成指令、寄存器、重排及小块调用成本
解包变快、完整解码变化小  查解析、类型视图、分配、截断和结果构造
完整解码变快、查询变化小  查阶段占比及其他环节，独立测完整查询
```

需要业务验证时，保持同一数据和 SQL，等待完整结果取回后结束计时。局部解码倍数不能替代查询倍数；与 RLE 联合启用时实测联合效果，嵌套计时先去重。

## 输出

- 原版提交、候选补丁、工具链、编译特性、程序或库摘要及实际加载路径。
- 调用链、具体优化点、适用类型和位宽、回退条件及内存安全说明。
- 官方用例与自建扩展清单、输入生成、物理/逻辑长度和预期值来源。
- 逐值正确性、异常输入、尾块、平台回退和真实内核命中的记录。
- CPU/NUMA、线程、缓存、预热、采样、轮次及顺序等复现条件。
- 各场景前后耗时、解包与完整 BP 加速比、波动和退化项。
- 若测业务，另列完整查询结果；未测时写明未验证业务收益。

时间表先说明单位、汇总方法和计时范围，采用空格对齐：

```text
输出类型  压缩位宽  原版耗时  候选耗时  加速比  实际路径  正确性状态
```

缺少目标机器时交付方案、已有证据和待执行检查，标记 awaiting_target_evidence，不给出虚构的实机收益。

## 约束

- 保持稳定文件格式、FastLanes 排列、返回值及原有错误语义，不删除必要检查换成绩。
- 原版使用本次固定基线，不把不同提交或历史中间候选混为一谈。
- 满足类型、长度、指令集和内存条件后才进入候选。
- 逻辑截断不能补救物理越界，未写容量不能作为已初始化数据读取。
- 解码全位宽覆盖和实际 NEON 位宽覆盖分别报告。
- 不适用回退和执行失败分别处理，不能用成功回退掩盖候选错误。
- 包装层、解包、完整解码和 SQL 收益分别命名，不互相替代。
- 开关、编译成功、汇编或文档格式通过，都不能代替真实运行审计。
- 新编码器与候选的往返结果不能作为唯一正确性依据。
- 保留失败、退化和离群样本；缺失样本及未测平台不自动补为通过。
- 不搬用历史机器、其他位宽或其他数据集的加速比作为当前结论。
- 仅要求分析时不自行执行远端压测或发布修改；执行范围以当前任务授权为准。
- 本文正文定义完整流程；evals/evals.json 的代理场景不等于 ARM 正确性或性能已经验证。
