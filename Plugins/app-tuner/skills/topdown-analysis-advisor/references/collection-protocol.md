# 采集协议

## 输入最小集

开始采集前需要确认：

| 项目 | 用途 | 缺失时 |
| --- | --- | --- |
| 主机和目标 PID/CPU/cgroup | 确定测量边界 | 询问目标，不默认采全机 |
| 业务阶段 | 避免启动、空闲混入稳态 | 记录未知，先观察负载 |
| 业务目标 | 决定建议优先级 | 可先做描述分析 |
| 时间预算 | 限制生产采样成本 | 提议有界的短窗口 |
| 输出位置 | 保存可追溯证据 | 使用新的可写运行目录 |

已有文件分析允许以上信息不全，但在报告中列出影响。
记录采集对象实际命令或服务名时注意凭据和个人数据。
需要脱敏时保留本地受控原件，发布脱敏副本并说明变换。

## 环境检查

1. 确认目标是 Linux aarch64，记录 CPU 型号、核数与 NUMA 拓扑。
2. 读取现有 kptools-devkit 的版本约束和使用说明。
3. 用 discover_devkit.sh 检查工具及 top-down 子任务。
4. 用当前工具帮助核对参数，不以本 skill 示例覆盖真实帮助。
5. 验证目标 PID 存活，记录其服务身份和实际工作线程范围。
6. 核对 perf/PMU 可用性；权限不足时记录错误和可行方案。

不要自动设置 perf_event_paranoid 或 kptr_restrict。
这些设置是主机安全策略的一部分，安装授权也不等于权限修改授权。
宿主机、虚拟机和容器的 PMU 暴露情况可能不同。
即使 discover 成功，也要检查实际采集是否有有效计数。

## 范围选择

### 进程

PID 模式适合持续运行的单服务实例。
确认工具对线程、子进程和退出后 PID 重用的处理方式。
短任务中 PID 可能在采集完成前退出；记录这种情况，不当作稳定窗口。
多进程服务可能需要多个 PID 或 cgroup，避免只覆盖管理进程。
脚本支持逗号分隔的正整数 PID；ALL 不作为隐式默认值。

### CPU 核

核模式测量这些核上的所有活动，不等价于某个进程。
记录业务线程是否绑定、是否迁移，以及同核是否有其他负载。
不要仅为采集便利自动修改绑核配置。
将核级结果和进程级结果比较前说明范围差异。

### cgroup / 系统 / workload

这三种模式通过已核实的 DevKit 原生入口采集。
本 skill 的采集器有意不接受任意 shell 字符串。
保存参数数组或原始命令以及 cgroup 版本、名称和业务边界。
运行 workload 前确认它会产生的负载和外部副作用在授权内。
使用 shell 重定向时分别保存 stdout 和 stderr，不吞掉退出码。

## 窗口设计

采样应覆盖有代表性的业务阶段。
持续服务优先在已知稳定负载中采样；短任务围绕目标阶段设计。
没有通用“30 秒就足够”的保证，示例时长只是起点。
记录请求率、并发、输入规模、吞吐、延迟或完成工作量。
若这些业务指标不可取得，不把采样结果直接推广到端到端收益。

多个窗口有明显差异时，先检查业务阶段与负载变化。
稳定性不够时可以增加同条件重复，但应遵守时间预算。
对重复结果保留每次分布和范围，不只报最佳一次。
不要把重复窗口数量当作统计可信度的充分条件。

## 分层采集

先采 Level1，决定是否需要更多维度。
已知需要完整树且采样成本可接受时可使用 -L 0。
`-L 2..6` 是工具 profile 选择，不是通用树深度参数。
不同 profile 的计数可能来自不同运行，不能拼接为同窗完整树。
跨轮下钻需要记录窗口和负载一致性。

## 补采决策

| 当前问题 | 可选补充证据 | 目的 |
| --- | --- | --- |
| 不知道哪个代码路径贡献主要成本 | hotspot、调用栈 | 将机制关联到候选路径 |
| 怀疑访存带宽 | memory、工作量 | 检查实际带宽与每工作单位数据量 |
| 怀疑长延迟访存 | miss、SPE | 区分访问位置和延迟分布 |
| 怀疑远端访存 | numafast、NUMA 放置 | 检查目标线程与内存归属 |
| 怀疑分支或执行依赖 | 热点源码、反汇编 | 构建可测试的代码机制假设 |

miss 和 numafast 依赖 SPE，按现有工具说明和真实环境检查。
不可用时明确降级，不把不存在的补采结果写进报告。
多个 PMU 采集器可能竞争资源；默认顺序采集并记录不同窗口。
确需并行时先检查事件调度与采集干扰，不默认等价于单独采集。

## 失败与停止

- 权限不足：保存错误，说明需要的环境条件，停止相关硬件分析。
- 不支持事件：保留已有可用数据，缺失维度标记未知。
- 全零计数：检查目标活动、采集范围和工具支持，不判定无瓶颈。
- 超时：结束本次工具进程，保留部分输出，标记 timeout。
- 业务负载改变：将该窗口分离，不混进同条件比较。
- 用户时间预算耗尽：交付现有证据及下一步建议。

重试仅针对可解释的暂时性问题，并限制在原采集预算内。
相同错误没有新的环境信息时不重复运行。
采集器超时会终止自己的进程组，不会主动终止目标 PID。
由用户原生命令启动 workload 的生命周期需另行管理。

## 前后对比

固定业务输入、并发、编译版本、关键配置与资源条件。
记录所有有意改变的变量，以及无法固定的环境差异。
比较百分比的同时比较业务指标和绝对工作成本。
百分比下降可能是其他类别增加，不能独立证明收益。
不同 scope、不同 profile 或不同工具公式不直接相减。
没有可比条件时分别描述，明确不作收益归因。
