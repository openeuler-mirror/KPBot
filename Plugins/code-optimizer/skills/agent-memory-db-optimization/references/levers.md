# 杠杆库：载荷、解码、水合、并发模型、服务端读路径（levers）

> 供 agent-memory-db-optimization 在阶段 4 按需 Read：每条杠杆先看前置条件与不适用面，再看收益数字；实施顺序随客户端运行时分档（见文末）。

按类别排列（L1→L7）。每条给出：**前置条件 → 做法 → 实测收益 → 风险/约束 → 不适用面**；
实施顺序不固定，见文末「实施顺序建议」，随客户端运行时分档。
收益数字是 Graphiti + Neo4j 标定案例在鲲鹏 / x86_64 两类架构的实测，客户端与服务端共享同一组核。

---

## L1 载荷瘦身：不用的字段不上行

**前置条件**：端到端追踪确认某字段"传上来就被丢弃"。
查法：在结果解析处下断点/打印，看 `attributes` 里哪些键被构造后又 `pop` 掉；
再看代码里是否真的从不从该 map 读它（本例：向量只通过专用 loader / MMR 查询按需加载）。

**做法（不改 schema，只改查询投影）**：
Cypher 没有"删键"，但 map 投影可以用常量覆盖：

```cypher
-- 之前：properties(n)  -> 每行带 1024 维向量（约 8 KB）
-- 之后：
WITH n{.*, name_embedding: []} AS attributes
```

关系同理（`e{.*, fact_embedding: []}`）。保留 map 类型与全部动态属性，只把大字段
置空列表；解析端本来就会 `pop` 它，行为不变。用环境变量开关（默认关）便于 A/B。

**实测**：检索 6.46 → 5.54 s（x86_64，−14%）、7.32 → 6.01（鲲鹏，−18%）；
写入 4.80 → 4.22（−12%）、4.91 → 4.40（−10%）。
结果指纹与图规模逐字节不变。

**风险**：若有某条冷路径真的从 `attributes` 读向量，会拿到 `[]` → 报错或静默降级。
上线前必须全仓搜索该键的读取点；开关化 + 全量对拍。

**不适用于**：客户端与服务端同进程/共享内存（不存在"上行"）——此时改做"少物化、
复用缓冲、视图替代拷贝"，量化口径从"线上字节"换成"每行拷贝字节数"。

## L2 解码下沉：把协议反序列化交给编译语言实现

**前置条件**：客户端火焰图里驱动层反序列化 ≥40%（实测 86.5% 的自耗时）。
先确认官方/社区是否已有同版本编译实现，不要自己写。

**做法（以 Neo4j 为例）**：安装与驱动版本严格匹配的 `neo4j-rust-ext`，
确认导入路径生效（踩坑：wheel 把 `_rust*.so` 装到 `lib64` 站点目录而驱动在 `lib`，
表现为 `RUST_AVAILABLE=False`——把 `.so` 复制进驱动包目录即可）。

**实测**：检索 21.86 → 9.80 s（x86_64，−55%）、24.97 → 11.31（鲲鹏，−55%）；
写入 15.65 → 6.37（−59%）、16.33 → 6.87（−58%）。单一杠杆收益最大的一项。

**风险**：版本错配会静默回退 Python 实现（必须用 `RUST_AVAILABLE`/导入路径自证）；
不同架构 wheel 不可混用。

**不适用于**：客户端已是 C++/Go/Rust——除非它当前走的是通用反射/动态序列化
（如 Python 风格 map、protobuf 反射解析），否则"再换一门编译语言"收益接近 0。
判据：驱动/反序列化在火焰图里 < 15%。此时预算转到 L1、L7 与 L5。

## L3 水合下沉：存储类型 → 领域对象的转换

**前置条件**：L2 之后客户端仍钉满单核，且火焰图里"时序/向量/JSON 转换"占 20%+。
本例热点是把 `neo4j.time.DateTime` 等时序类型转成 Python 对象——纯 Python
实现里每一步都要建对象、走属性协议。

**做法**：把"结果行 → 领域对象"的字段级水合挪到原生扩展（本例写了
`neo4j-time-ext`：Rust 侧解析时序类型并直接构造目标对象），Python 侧只保留
一个薄入口；用 `sitecustomize.py` + 环境变量激活，便于与基线版本切换。

**实测**：检索 9.80 → 6.46 s（−34%）、11.31 → 7.32（−35%）；
写入 6.37 → 4.80（−25%）、6.87 → 4.91（−29%）。

**风险**：类型语义必须逐字段对拍（时区、精度、None）；扩展与驱动 ABI 绑定，
升级驱动要重编译；必须保留"关闭开关"回到纯 Python 路径。

**不适用于**：编译型客户端（C++/Rust/Go）的类型转换本来就零拷贝。那边要看的是
"是否把缓冲区拷贝进了中间结构"——如果是，收益来自删除中间层，而不是"下沉"。

## L4 并发模型：单事件循环 + GIL 下只有多进程有效

**前置条件**：前三项做完，单副本仍单核 99%，且服务端未饱和。
先验证"多线程无效"（本例 4 线程与单线程等速），别把预算花在 GIL 上。

**做法**：**串行写入（单队列）+ N 个查询副本进程**（独立解释器、事件循环、
连接池）；副本内用信号量控并发（本例 20）；副本 0 幂等建索引，其余错峰启动
（0.3 s）避免建连惊群。

**实测**：固定核预算下 5 副本达到 **3.08×**；容量约等于 **核数 / 1.45**
（客户端与服务端分摊同一预算）；副本继续加时吞吐反降、连接重试激增（线程饿死）。

**风险**：
- **写入不可并行**：实体在会话间共享，判重 prompt 依赖并发交错顺序 → 缓存键不确定
  → 命中率崩塌。上游也要求串行 `add_episode`。
- 副本数与服务端核预算必须一起规划；否则"加副本"只是在制造重试。
- 内存：每副本常驻内存随客户端缓存与索引规模增长，需按副本数预留。

**不适用于**：运行时没有 GIL/单线程事件循环约束（C++/Go/JVM 原生线程池）。那边先查
锁竞争、线程池利用率、GC 停顿；多副本仍可用（分片读），但收益上限由服务端核预算决定。
判据：单副本 CPU% 未到 100% 时，加副本只是增加排队。

## L5 服务端读路径补丁（累积、源码级）

**前置条件**：服务端 JVM 火焰图里"每行必走"的解码/相似度例程合计 ≥5%，
且客户端已优化到位（否则测不出）。必须能重建 jar。

**做法**：按火焰图逐个打，每项单独成版本，累积保留（`v0_orig → v1 → v2 → …`），
每版记录 4 个 jar 的 md5。本例四项：

| 版本 | 补丁 | 目标 |
|---|---|---|
| v1 | 数组位桶解码快路径（bit-buffer array decode fastpath） | 属性数组解码按常见位宽走直线 |
| v2 | 属性存储浮点快路径（propertystore float fastpath） | float 数组解码免通用路径 |
| v3 | 向量查询记忆化（vector-query memo） | 同一查询内重复的向量转换/校验只做一次 |
| v4 | 向量相似度单遍就地（single-pass in place） | 省一趟扫描 + 一份拷贝 |

**实测（在最优客户端之上，累积）**：
检索 5.54 → 3.86（v1，−30%）→ 3.32（v2，−14%）→ 3.15（v3，−5%）→ 3.22（v4，持平）；
鲲鹏 6.01 → 4.60（−24%）→ 4.15（−10%）→ 3.81（−4%）→ 3.81（0）。
服务端累计 −42%（x86_64）/ −37%（鲲鹏）；**写入 ±0.1 s（无收益，符合预期）**。

**风险**：
- 收益强烈依赖并发度与架构：同一套补丁在 5 副本 x86_64 上让 search 15.59 → 8.12 s
  （−48%），在鲲鹏只有 2~4%。
- 只改读路径就断言"整体提升"是错的：写路径占比高的场景会被稀释。
- 版本管理与回滚必须做扎实，否则"优化后不知道基线是哪份二进制"。

**不适用于**：服务端是封闭二进制（无法重建）；或客户端尚未优化到位——此时服务端
耗时被客户端噪声淹没，测不出真实收益，结论必须标注"待客户端优化后复测"。

## L6 运行配置（不改代码，常被当成优化）

| 配置 | 结论 | 代价 |
|---|---|---|
| 服务端全线程绑核 | 只绑主线程等于没绑；`taskset -a -pc` | 需按核预算规划 |
| 连接池 | **不要缩**（本例 96/192）；缩到 8/32 时排队 → 判饥饿 → 连接被重置 → 重试雪崩（冷对冷慢 1.65×，重试 34×） | 内存 |
| JVM/JDK | 新 JDK 与旧版性能相当（~2%）但重试显著更少；重启会回退系统 JDK，需显式 `JAVA_HOME` | 升级风险 |
| 预热 | 重启后 2 轮完整负载才稳态（首轮慢 40~80%）；基准必须丢这两轮 | 时间 |

## L7 检索配方层（在框架内改）

- 候选倍数（`2×limit`）与返回字段：先量化"每行字节 × 候选行数"再决定砍哪一项。
- 多路召回（全文 + 向量）本来就并发，**测拆分时取区间并集**；串行化会平白多一倍时间。
- rerank：确认它是否真的被调用、命中缓存比例多少；未命中时会成为新的长尾。

## 实施顺序建议

顺序由**客户端运行时**决定，不是固定公式：

```
解释型客户端（Python/TS/Node）：
    L1 载荷瘦身 → L2 解码下沉 → L3 水合下沉 → L4 多进程 → L5 服务端补丁 → L6 配置 → L7 配方

编译型客户端（C++/Go/Rust）：
    L1 载荷瘦身 → L7 配方（候选数/字段）→ L5 服务端/存储引擎 → L4 线程与分片 → 分配/拷贝消除 → L6
    （L2/L3 基本跳过：换编译语言或"下沉"本身没有可削的空间）

无网络边界（同进程/嵌入式存储）：
    L7 查询计划与配方 → 少物化/复用缓冲/视图 → L5 引擎内部 → L4 → L6
```

理由：L1 是"少干活"，收益大且不改语义，凡有边界都该先做；L2/L3 只在解释型客户端
有肉（判据是驱动/水合层占比）；L4 只有在单副本钉满且服务端未饱和时才该上；
L5 必须在客户端之后测，收益才不被 Amdahl 吃掉；L6/L7 用来消除误判与长尾，
不要当主收益报。
