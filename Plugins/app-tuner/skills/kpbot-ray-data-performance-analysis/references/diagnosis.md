# 证据驱动诊断

这些是候选解释，不是自动分类规则。每个判断写明证据文件与行号/时间窗口，区分观测和推断。只使用当前任务的公开资料与用户允许使用的材料。

| 方向 | 需要交叉核对的证据 | 容易误判之处 | 最小区分实验示例 |
|---|---|---|---|
| 读取 / I/O | reader 产出、下游是否缺输入、存储或网络服务指标、请求延迟 | CPU 低也可能因为调度等待、初始化、限流 | 相同输入和资源下独立测读，注明缓存状态与是否包含解码 |
| CPU 处理 | worker 栈、CPU 时间、实际配额/节流、阶段输入输出率 | 主机平均 CPU 低可掩盖单 worker 饱和；线程数不等于活跃线程 | 选代表性数据测阶段，核对并发与库内线程的实际占用 |
| 调度 / 并发 | pending/running 任务、actor 资源请求、block 数、时间线 | Ray num_cpus 是逻辑资源；增加它不等于增加实际 CPU | 保持物理资源不变，小范围比较并发，记录是否挤占其他阶段 |
| 内存 / 背压 | object store、heap、spill/restore、队列随时间变化、上下游速率 | spill 是现象，不证明内存是主因；下游慢可导致上游积压 | 同时观察生产与消费速率，测试有界 batch/并发候选 |
| 数据表示 / 序列化 | 实际 batch 类型、dtype/shape/布局、转换/复制栈和耗时 | explain 中融合不代表没有转换；热点函数名不等于可删除成本 | 用独立输入验证接口和格式成本，包含转换及所有消费者 |
| GPU 批推理 | 输入等待、设备利用率、传输/计算时间、batch 分布 | CPU/GPU 异步时间不能直接相加；利用率低不证明供数不足 | 明确同步计时，分开观察设备计算与端到端，保持模型与输出契约 |
| 输出 / sink | writer 活跃时间、文件数与大小、flush、存储吞吐 | 计算结束不代表端到端结束，cache 可掩盖持久化成本 | 同一输出语义与持久化范围下测写出 |

## 归因纪律

- 流式阶段会重叠，累计 task 时间可超过墙钟。没有时间线时描述“累计成本”，不伪造关键路径占比。
- task、block 和行数先逐 operator 列出，再说明汇总口径。两个 operator 各执行 4 个 task，表示 8 次 operator-task 执行，不是全流程只有 4 个任务；同一批 256 行经过两个算子也不是 512 行唯一输入。比较融合与未融合计划时尤其要区分这些层次。
- 首轮异常仍保留在原始样本和正式对比中。可将初始化列为候选解释，但不要事后剔除首轮再把余下样本当成已约定的热运行实验；需要热运行结论时，先定义预热阶段再重新测量。
- 最大耗时 operator 可受上游饥饿或下游背压影响；结合队列、输入输出率与运行状态确定原因。
- 微基准只能支持局部结论；模拟推理不支持真实模型服务收益；单节点不支持集群扩展性结论。
- 多个候选相关时记录依赖关系，通过配对/消融实验区分贡献，不把顺序叠加收益当独立收益。
- 正确性按业务定义：ETL 的 filter/expand、文本 token 数、图像 shape/dtype、模型输出误差可能不同。不以行数相同替代结果一致性。
- 缺少实际栈或持续指标时，用“待验证”及下一项采集建议结束该判断，不强行给出主因。

方法依据为 Ray 官方的性能、监控及资源说明，链接见 [sources.md](sources.md)。这里的实验设计是本 skill 的建议，不是 Ray 的固定运行要求。
