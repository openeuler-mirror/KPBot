# 差异分类学与盘点方法

> 配套 SKILL.md 第 2 步：全量枚举架构差异后按本表分类，再进入第 3 步考古。
> 分类决定后续处理路径：A/B/C 类进入考古 + 量化，D 类直接归档。

## 两个差异面

本审计方法与门槛对两个差异面通用：

1. **架构间**（主差异面）：同一代码树里 x86_64 与 aarch64 的分支/默认值差异，
   "成熟侧 vs 移植侧"；
2. **基线间**：定制/发行版构建与上游 vanilla 的默认值漂移（典型：同版本内核的
   定制 config 与上游 config 差异），上游 vanilla 为基准。基线间没有"移植侧"，
   每项差异逐个问"为什么改、改了谁受益、上游为什么保持默认"。

## 语言覆盖矩阵（盘点完整性）

| 语言/构建系统 | 差异载体 | 盘点方法 |
|---|---|---|
| Rust | `cfg(target_arch)` / `cfg!(...)` / `cfg(any/all(...))` | arch_diff_scan.py |
| C/C++ | `#ifdef __x86_64__` / `#if defined(...)` / per-arch `.S` | arch_diff_scan.py |
| Go | `//go:build` tag / `runtime.GOARCH` 行为分支 | grep 人工（脚本盲区） |
| 汇编 | `.arch` 指令 / per-arch 文件命名 | 目录对比 |
| CMake/Make | per-arch 开关、源文件选择、toolchain | 构建脚本 diff |
| 内核/平台 config | 默认值漂移 | 两份 config normalized diff |
| 运行时拼装 | cmdline/启动参数按架构拼装（常藏在通用函数里） | `--keyword` 定位 + 读代码 |

**注意**：通用参数里的架构特异语义（如 `earlyprintk=ttyS0` 两架构通用但对其中一侧
无意义）不会出现在任何 `cfg`/`ifdef` 分支里——这正是 `--keyword` 扫描的价值，选词
从启动参数、设备名、子系统关键词入手。

## 差异分类学

| 类 | 名称 | 定义 | 移植侧风险 | 处理 |
|---|------|------|-----------|------|
| A | 架构默认值差异 | 同一逻辑开关/参数在两架构取不同默认值（console、调度参数、预读策略、超时） | 高——默认值无人质疑，影响全局 | 考古 + 量化 |
| B | 模拟/交互机制差异 | 同一功能两架构用不同实现机制（模拟设备 vs 半虚拟化设备、PIO vs MMIO、同步 vs 线程化处理） | 高——成本差可达数量级 | 考古 + 量化 |
| C | 能力假设差异 | 代码假设的 ISA/微架构能力不同（缓存行、原子指令、内存模型、TLB 粒度、SIMD 宽度） | 中——常是合理适配，但错误的"能力降级"是隐性退化 | 考古 + 量化 |
| D | 合理差异 | 有明确 stated reason 且仍成立的差异（页大小选择、指令集专属实现、平台拓扑） | 无 | 归档记录理由 |

判定顺序：先问"是不是 D 类"（考古出理由即归档），再对 A/B/C 类做成本量化。
**A、B 类是本审计的主力产出区**——它们改的是"选择"而不是"实现"，向成熟侧对齐的
改动小、风险低、收益可期。

## A 类：架构默认值差异

### 盘点方法

1. `arch_diff_scan.py --keyword` 辅助定位（console、earlyprintk、earlycon、hz、
   prealloc、flush 等本项目高频默认值词）；
2. 找 per-arch 常量表/匹配分支：`match arch`、`cfg(target_arch)` 里返回字面量的分支；
3. 对照构建产物或运行时状态（`/proc/cmdline`、`dmesg`）确认默认值实际生效。

### 高发位置

- guest 启动参数拼装（console=、earlycon=、init=）；
- 内核构建默认配置（发行版 patch 与上游 vanilla 的默认值漂移属于同类问题）；
- 框架层的 per-arch 参数预设（线程数、缓冲大小、对齐策略）。

### 判定要点

- 默认值差异**必须看运行时生效证据**：参数出现在源码或 cmdline 里不等于内核识别并
  启用了对应功能；
- 成熟侧默认值也可能过时——考古理由时同时考古成熟侧的选择依据。

## B 类：模拟/交互机制差异

### 盘点方法

1. 列出两侧各自的设备清单（模拟设备 + 半虚拟化设备）与交互通道；
2. 对每个高频交互路径数 exit 次数：`perf kvm stat`、KVM debugfs
   （`mmio_exit_user` / `mmio_exit_kernel` / `pio` 计数）、trace 点；
3. 找"成熟侧批量化、移植侧逐次化"的路径——批量化（virtqueue + ioeventfd，KVM 内
   处理）与逐次化（每字节/每次访问用户态 exit）的成本差是数量级的。

### 判定要点

- 每字节 N 次 exit × 热点路径字节数 = 可数成本下界，这是 B 类最有力的证据形式；
- 注意**输出量本身**也是放大器：一行日志走模拟串口就是上千次 exit，日志量与 exit
  数成正比；
- 线程模型也算 B 类：同一设备在 vCPU 线程同步处理 vs 独立设备线程排空，吞吐差异巨大。

## C 类：能力假设差异

### 盘点方法

1. `grep` 缓存行大小、原子内建、内存序、页大小相关常量与 `#[cfg]` 分支；
2. 对照 `kunpeng_microarch` 微架构知识库判断"能力降级"是否真的必要；
3. 典型隐性退化：把本可用的批量/宽向量路径降级为逐元素路径"以防万一"。

### 判定要点

- C 类常与 D 类混淆：区分"平台确实没有该能力"（D）与"懒得确认就当没有"（C）；
- 量化时用 `analyze-hotspot` 的产物（IPC、缓存 miss、原子指令占比）做证据。

## D 类：合理差异（归档区）

考古出 stated reason 且理由仍成立的差异。归档时记录：

| 记录项 | 说明 |
|---|---|
| 差异位置 | 文件 + 行号 + 两侧取值 |
| stated reason | commit/注释/issue 原文出处 |
| 理由现状 | 仍成立 / 已过时（过时的转候选池） |

常见合理差异：页大小与硬件规格绑定、指令集专属优化（NEON/SVE vs AVX）、平台拓扑
（NUMA/GIC/中断控制器）、编译器与 ABI 差异。

## 盘点完整性自查

- [ ] 语言覆盖矩阵逐行过完（Rust/C 脚本扫、Go/汇编/构建/config 人工）；
- [ ] 双侧代码都读过（只看单侧看不见差异）；
- [ ] 覆盖源码 cfg/ifdef、构建配置、运行时参数拼装三个层面；
- [ ] 通用参数里的架构特异语义用 `--keyword` 过了一遍；
- [ ] 基线间差异面（如适用）做了 config normalized diff；
- [ ] 每条差异都有分类与考古结论，无"未分类"残留。
