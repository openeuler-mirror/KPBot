# 标定案例：同机 proxy/datanode 服务的 UDS 迁移

本案例用于说明收益形态、失败路径和边界。具体项目、环境、配置与测量数字已按内部数据规范脱敏；案例**不是收益承诺**，换环境后必须重新验证。

## 1. 背景

- 形态：某 KV 服务，proxy 与 datanode 分离部署，单机、同一文件系统。
- 原链路：proxy 经 loopback TCP 连接 datanode，承载小消息、高频、每请求一次往返的同步协议。
- 瓶颈背景：proxy 接近饱和，perf 中可见 TCP/IP 栈路径的固定开销，优化前已确认瓶颈不在存储引擎。

## 2. 实现演进

| 阶段 | 做法 | 结果 |
|---|---|---|
| 1 | 在服务端额外起一个 UDS listener，TCP 继续监听 | 能工作，但出现双 listener 的清理与就绪判定问题 |
| 2 | 改为优先 UDS、失败回退 TCP | 回退路径难以验证，且会把配置错误静默掩盖 |
| 3 | 改为 TCP + UDS 双 listener | 连接归属不明确，排障与监控双份复杂度 |
| 4 | 回退为只监听 TCP，再恢复可选 UDS，并补停止清理 | 解决残留文件问题 |
| 5 | 补 socket 清理测试（启动、停止、文件消失） | 清理行为有回归保护 |
| 6 | 删除 UDS 专用代码，改为纯配置驱动 | 最终形态：只有一条 listener 路径，TCP/UDS 由 endpoint 字符串决定 |

最终形态：

```text
# 服务端
bind  unix:/tmp/<service>.sock

# 客户端
backend-addrs  unix:/tmp/<service>.sock
```

关键事实：

- 框架的 Endpoint 原生支持 `unix:` 前缀，server 与 channel 复用同一套解析，因此不需要在业务代码里区分 TCP/UDS。
- 最终只监听 `bind` 指定的一个 endpoint，不存在并行 UDS server。
- socket 文件在框架停止路径中清理；早期版本由应用层在启动前/停止后 `unlink` 兜底。
- 压测脚本的就绪与端口检查必须感知 endpoint 类型：TCP 用 `ss -ltn`，UDS 用 `ss -xl`，并解析 `bind` 判断当前是哪种。

## 3. 测量与口径（已脱敏）

- 采用 TCP/UDS/TCP 交替测量：UDS 吞吐高于两轮 TCP 的均值，尾延迟基本持平，收益主要体现在吞吐。
- 两轮 TCP 之间本身存在可见波动，说明单次前后对比不可信，只有同时间窗内的配对比值可信。
- 不同优化组的百分比不能相加或混用；只报告同一时间窗内的配对比值。
- 该次验证只覆盖单机、单 datanode 的吞吐与尾延迟，没有覆盖多实例、容器、混合版本发布等场景。

## 4. 机制证据

- 换 UDS 后，perf 中 TCP/IP 栈路径消失；但 UDS 仍经过 socket/epoll/数据拷贝，收益上限是链路中内核网络路径的占比。
- 后续 profile 结论：TCP 前端和 UDS 后端都仍会经过 socket/epoll，因此继续优化要靠减少调用频率和协议开销，而不是继续更换传输方式。

## 5. 边界与风险

- **仅同机**：两个进程在同一台机器、文件系统可见；跨机、跨容器无共享卷时不适用。
- **单 datanode**：该验证不涉及多 datanode 路由与一致性；多副本场景要单独评估路径唯一性与故障切换。
- **监控与探活**：端口消失后，依赖 TCP 端口的健康检查、服务发现、防火墙规则需要替代方案。
- **清理**：崩溃后残留 socket 会导致下次 bind 失败；清理必须在确认无 listener 时进行。
- **配置一致性**：两端 endpoint 写错或不一致时表现为「连不上」，容易被误判为 UDS 无收益。
- **收益边界**：大消息、低 QPS、长连接低频请求、瓶颈在存储/业务/锁时，收益会落在噪声内甚至变差。

## 6. 可复用的教训

1. 双 listener / 双 server 是错误方向：最终形态一定是单 listener + 配置驱动。
2. 「失败自动回退 TCP」会掩盖配置错误，生产上应显式失败或显式切换。
3. socket 文件生命周期必须纳入设计：启动清理、停止清理、崩溃兜底、清理前检查 live listener。
4. 就绪与监控要感知 endpoint 类型，不能沿用端口探测。
5. 先证明内核路径占比，再决定是否切换；切换后仍要回到「减少每请求开销」这条主线上。
