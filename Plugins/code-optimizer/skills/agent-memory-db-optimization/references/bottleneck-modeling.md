# 瓶颈建模：客户端 top-down、缓存缺失率、服务端火焰图、判定树（bottleneck-modeling）

> 供 agent-memory-db-optimization 在阶段 3 按需 Read：从"哪一层慢"落到"哪条指令/哪次访存慢"，并给出杠杆类别。

本文件解决一个问题：**阶段 2 说"某层慢"，这里回答"慢在哪条指令/哪次访存，
下一步该选哪类杠杆"。**

## 0. 全景：这类负载的典型形态

Graphiti + Neo4j 实测（客户端优化前后）：

| 指标 | 优化前 | 优化后 | 读法 |
|---|---|---|---|
| IPC | 2.60 | 1.53 | 变"低"不是退化，是剩下的活更像在等内存 |
| Memory Bound | 24% | 40~47% | 同上；后端占比上升是预期 |
| 单副本 CPU 利用率 | 99% | 99% | 客户端始终把单核钉满，直到并发模型改变 |
| 服务端 CPU 利用率 | 低 | 低 | 客户端没优化前服务端远未饱和 |

结论模板：**客户端单核饱和 + 服务端未饱和 = 瓶颈在客户端**；此时服务端优化最多
贡献个位数百分比。反过来，客户端压下去后服务端占比从 14% 升到 37%，
下一轮才有服务端的事。

## 1. 采集入口

| 目的 | 命令要点 |
|---|---|
| 客户端 top-down L1 | `top-down -L 1 -d 10 -p <真身 PID>`（不是 `taskset` 父壳） |
| 分层 L2/L3 | `top-down -L 2/-L 3`，注意部分平台 L3 无法区分 L3-bound / DRAM-bound |
| 热点调用链 | `perf record -g --call-graph fp -p <PID> -- sleep 20` |
| SPE 行级归因 | `miss -m 1`（源行）、`memory -m 2`（L3 miss 计数）、`memory -m 3`（DDR 带宽） |
| 服务端 | JVM: JFR/async-profiler；Go: pprof；C++: perf；Python: py-spy（产出火焰图） |
| 上下文切换 | 自研 `/proc/<pid>/task/*` 统计（`pidstat -w` 对多线程 JVM 失效） |

采样区间要**门控**：只在稳态（缓存已载入、JVM 已预热）采，机器空闲度 ≥98%。

## 2. 缓存缺失率表（跨级 + 指令侧）

这是本方法的"体检单"。不追求平台相关事件的精确名字，追求**同一口径跨配置可比**。

### 2.1 口径

| 平台 | 口径 |
|---|---|
| AArch64（这类 PMU 有分级 refill/access） | 每级 = `REFILL / ACCESS`；DRAM 归因 = `L3D_REFILL / L1D_REFILL`（L1 每个 fill 追到最终来源） |
| x86_64（PMU 分级不齐） | L1D 用 `L1-dcache-load-misses / loads`；L2 用 `l2_request_g1.*`/L2 访问计数比；L3 不一定可测；DRAM 用 uncore 内存控制器（PCM 之类） |
| 指令侧 | `L1I` / `L2I` 的 `refill/access`，并额外算 **每千条指令的 L1I miss 数**（密度），比百分比更能反映代码足迹 |

**不要混用口径**：AArch64 的 `L3D_REFILL/L3D_ACCESS` 与 x86_64 的 LLC miss 有不同含义。

### 2.2 参考值（同一 8 组矩阵的四种配置）

列：未优检索 / 未优写入 / 全优检索 / 全优写入；每格三台机器，按机器 A / 机器 B / 机器 C 排列
（两台 AArch64、一台 x86_64），不记录具体机型。


### 2.3 怎么读

1. **数据侧随优化"上移"**：检索 L2D 14.2% → 26.0%，DRAM 归因 13.6% → 30.5%。
   原因不是变差，而是每行载荷变小后，原本被大对象连续访问"顺带命中"的行变散了。
   → 接下来该看**访问局部性与并发度**，不要继续抠单行解码。
2. **指令侧是最容易被忽略的一层**：客户端优化后 L1I 百分比 1.18% → 2.30%（翻倍），
   每千指令 miss 2.03 → 5.13（2.5×）。含义：总指令数大幅下降，剩下的代码足迹
   相对更分散。→ 信号是"该把剩余热路径继续下沉到编译语言/减少解释器分派"，
   而不是在 Python 里继续微调。
3. **x86_64 与 AArch64 的绝对值不可比**（x86_64 L1I/1k instr 9.2 vs AArch64 2.0），只比趋势：
   x86_64 的 DRAM 归因 3.3% → 8.5%，同样在"上移"。
4. **L3 不可测时不要造数**：某平台上 L3 相关事件可能 not supported；此时只报
   "L3 不可测"，用 DRAM 归因与带宽替代，不要用 PMC 的"fill 来源"反推 miss rate
   （那是**最初来源**归属，会与 DRAM 行重复计数）。

## 3. 服务端火焰图（JVM / Go / C++ / Python）

服务端只优化**读路径**，所以火焰图要按"每行数据都要走一遍"的通用例程看。
采集工具按服务端运行时选：JVM → async-profiler / JFR；Go → `pprof`；
C++ → `perf record`；Python 服务 → `py-spy`。判读口径与工具无关。

| 类别 | 典型符号（Neo4j 为例） | 实测占比变化 |
|---|---|---|
| 属性/数组解码 | `PropertyStore.readArrayFromBuffer` | 7.4~10.0% → 4.7~4.9%（−2.6~−5.3 pp） |
| 向量合法性/拷贝 | `VectorSimilarityFunctions$*.maybeToValidVector` | 8.0~10.3%（补丁目标） |
| 查询执行/规划 | `...cypher...` | 大但不可改（框架成本） |

判读规则：

- 单行解码类函数占比 ≥5% 且"每行必走" → 值得改（快路径/批量/避免临时对象）。
- 向量相似度类 → 优先看"是否多次遍历/是否拷贝"，单遍就地通常可省一份拷贝 + 一趟扫描。
- 写路径（ingest）不看这些函数 —— 实测服务端补丁对写入 ±0.1 s，符合预期。

## 4. 判定树

```
客户端 CPU 99%（单核钉满）？
├── 是 → 看客户端 top-down / 火焰图
│        ├── 驱动层反序列化占比高（>40%）→ 杠杆：解码下沉编译语言（阶段 4 L2）
│        ├── 领域对象水合占比高（时间/向量/JSON 转换）→ 杠杆：水合下沉（L3）
│        ├── 载荷字节数大（字段多/向量大）→ 杠杆：投影瘦身（L1，先做）
│        └── 以上都压完仍 99% → 杠杆：并发模型（L4，多进程）
└── 否 → 看服务端
         ├── 服务端 CPU 未饱和 且 逐查询服务端时间稳定 → 瓶颈在客户端并发/等待
         ├── 服务端 CPU 饱和 + 火焰图解码热点 → 服务端读路径补丁（L5）
         └── CPU 高但吞吐下降 + 连接重试暴涨 → 线程饿死/池过小（配置层，转 app-tuner）

多副本下吞吐不再涨？
├── 重试数暴涨 → 副本超额订阅（容量 ≈ 核数/1.45），减副本或给服务端独立核
└── 重试平稳 → 存储端单点（锁/页缓存/网络），看服务端扩展性
```

### 4.1 封闭轴（必须有证据再排除）

| 轴 | 排除方式 |
|---|---|
| LLM/网络 | 缓存回放后 misses==0，且客户端无 socket 出网 |
| 磁盘 | pagecache 命中、`iostat` 无持续读 |
| GC | JVM 日志无长暂停；客户端 RSS 稳定 |
| 带宽 | DDR 实测带宽 < 峰值 50% |
| TLB | `L1D_TLB/L2D_TLB` miss 率与优化前后无相关性 |
| 锁 | 客户端无等待堆积；服务端上下文切换平稳 |

## 5. 常见误判

| 现象 | 误判 | 实际 |
|---|---|---|
| 优化后 IPC 下降 | "性能退化" | 剩余工作在等内存，属预期 |
| 服务端补丁收益 2% | "补丁没用" | 客户端才是瓶颈，Amdahl；换架构/并发度后可能 −48% |
| L2/L3 miss 率上升 | "优化把缓存搞坏了" | 载荷变小导致空间局部性变差，属正常迁移 |
| PMC 的 "fill 来源" 当 L3 miss rate | 数字自洽但重复计 DRAM | 那是最初来源归属，不是本层 miss |
| 图 235/720 时查询更快 | "这是优化效果" | 脏库/候选集异常，数据作废 |
