# 应用代码层：未定义行为与静态可查项

## A-1 何时才动代码

代码层差异**最难定位**。顺序：选项层（L2）→ 库层（L3）→ 归约层（L4）都排除后，才进代码层（L1）。
先做两件低成本动作：
1. 用 `-O0` / `-O1` 对照跑一次：**优化一关差异就消失 ⇒ 强烈指向 UB**。
2. 查历史已知代码差异（版本间修过的越界、值域、维度不匹配）。

## A-2 值域越界（案例一）

- 现场：WRF 中 `i_cos` / `i_tau` 的注释声明取值范围 **1..10**。
- 触发：`cosz(i)` 与 `cld_alb` 同时为 **1** 时，算出的 `i_cos` / `i_tau` 为 **11**。
- 后果：越界取值 → 不同编译器拿到不同结果。
- 修复：WRF **4.1.2** 已加钳制；旧版本需自行加边界限制。

判据：**注释里的值域就是契约**；越界即 UB，任何「编译器对齐」都救不了。

## A-3 数组越界（案例二）

- 现场：地形数据有 **33** 类（`num_land_cat = 33`），而 WRF 的 `MPTABLE.TBL` 只配了 **27** 类，相关变量（如 `SLA`）只有 27 维。
- 后果：访问 27 维之外 → 越界，`SLA` 在不同编译器下取到不同值。
- 修复（`phys/module_sf_noahmpdrv.F`）：当 `IVGTYP` 为 **31/32/33** 时，`SLA` 下标改用 `ISURBAN_TABLE`（**13**）。

判据：维度不匹配（33 vs 27）是**静态可查**的，优先静态检查，不要靠跑崩了再猜。

## A-4 静态检查清单（迁移前必做）

| 检查 | 方法 | 典型问题 |
|---|---|---|
| 数组维度 vs 配置表 | 对比数据表维度与配置项维度 | 地形/植被/土壤类型表不一致 |
| 注释值域 vs 实际取值 | 在越界点加断言后跑一次 | 索引上限差 1 |
| 未初始化变量 | 编译期告警 + `-finit-*` 对照 | 结果随栈内容变 |
| 越界读写 | AddressSanitizer / 边界检查版编译 | 隐藏的越界访问 |
| 依赖求值顺序 | 静态扫描 + `-O0` 对照 | 换编译器才变 |

## A-5 工具选型

- 商业/平台侧通常有专门的精度分析工具（如鲲鹏生态的 Hawkeye 鹰眼、Cruiser 悟合、DBI 玄武），用于「差异点未知、代码量大」的场景。
- 选型原则：能静态查出来的（A-2/A-3 类）先用静态检查，一天内解决；工具留给「跑得出来但说不出在哪」的情况。
- 工具输出必须给出「文件 + 行 + 变量 + 两侧取值」，否则只是噪声；拿不到这四项就换方法（插桩更可靠）。

## A-6 归档

调优成功后归档：改了哪些文件、加了哪些选项/参数、四指标前后值、验收等级与规模。
下一个版本遇到同样问题，这份归档就是最短路径。

## 反模式

- 靠注释约定值域却不加断言：迁移必踩。
- 用「改数据表让它刚好能跑」绕过维度不匹配：把错误藏进数据。
- 直接改代码而不先做 O0/O1 对照：很可能改错层。
