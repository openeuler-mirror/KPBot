# Kitex 组件级分析与诊断流程

本流程是 `kitex` 专题的推荐入口，把专题内的 skill 串成一条可执行链路。它不替代 app-tuner 主流程的候选机制：主流程把 Kitex 作为候选时，进入本流程；单个 skill 仍可被独立调用。

## 独立使用契约

- 本流程是**可选编排**：任何 skill 都可以被单独调用，不要求先走这里。
- skill 被单独调用时，按它自己的"输入"节准备最小输入；流程中的 `kitex_profile`、`baseline`、`evidence` 只是约定名，不是前置条件。
- 本流程不改变任何 skill 的门控、拒绝条件与回退方式；两者冲突时以 skill 自身边界为准。
- skill 的输出应自包含，不把流程产物写成强依赖。

## 适用与不适用

**适用**

- 现象已知（慢、抖、连接多、内存涨）但方向不明，需要一条从证据到动作的固定路径。
- 已完成若干零散调优，需要重新确认瓶颈并做单变量归因。
- 准备做一次完整的 Kitex 专项优化，需要产出可复现的过程记录。

**不适用**

- 只是判断"该用哪种 codec/协议"这类单点问题 → 直接调用对应 skill。
- 需要改框架源码或业务代码 → 本流程只输出候选，落地交 `code-optimizer`。
- 没有可复现负载与基线 → 先补基线，流程不能跳过阶段 1。

## 总览

```text
阶段 0 识别与边界确认
   └─ 产出 kitex_profile（版本/协议/codec/连接形态/埋点/部署形态）
阶段 1 基线（委派 microservice-ab-testing）
   └─ 产出 baseline（吞吐/延迟/CPU/RSS/GC/fd）
阶段 2 证据（kitex-profiling）
   └─ 产出 evidence（CPU/堆/锁/阻塞/系统调用/硬件计数）
阶段 3 分诊（kitex-troubleshooting）
   └─ 产出 suspect_skills[]（按证据给候选技能与顺序）
阶段 4 单变量调优（按 suspect_skills 逐项执行）
   └─ 产出 rounds[]（每轮：变更、前后指标、保留/回退）
阶段 5 验证与收尾
   └─ 产出 final_config、rollback_plan、handoff[]
```

## 阶段 0：识别与边界确认

**目标**：把后续所有判断所需的形态固定下来，避免拿不同形态的数据做对比。

**必查项**

| 项 | 取值来源 |
|---|---|
| Kitex 版本、Go 版本 | 现场读取版本文件或启动日志 |
| 传输协议 | 服务端/客户端选项或配置 |
| 编解码实现 | 默认实现还是自定义 |
| 连接形态 | 独占连接池还是复用连接 |
| 埋点级别 | 是否注册链路追踪 |
| 部署形态 | 物理机 / 容器 / 跨机；服务端与压测端是否同节点 |
| 目标 | 吞吐、长尾、内存，三者哪个优先 |

**门控**

- 形态未固定时，不得进入阶段 1；否则后续数字不可比。
- 目标未明确时，默认以"吞吐优先、长尾不劣化"为准，并写入记录。

**产出**：`kitex_profile`。

## 阶段 1：基线

**目标**：得到一组可复现、可对照的数字。

**执行**

1. 按 `microservice-ab-testing` 固定负载、预热、时长、重复次数与判定规则。
2. 用 `assets/` 的 demo 与运行器搭建，服务端与压测端分开绑核。
3. 记录：QPS、P50/P99、服务端 CPU、RSS、GC 次数、fd 数与 dial 次数。

**门控**：基线重复性不达标（波动过大）时，先排查环境与压测端瓶颈，不得进入阶段 2。

**产出**：`baseline`。

## 阶段 2：证据

**目标**：判断瓶颈类别，而不是直接猜参数。

**执行**：调用 `kitex-profiling`，按该 skill 的采集清单执行；至少覆盖"系统调用 / 锁 / 分配"三类中的两类。

**门控**：证据充分性判定不通过时，回到本阶段补采；不得用单次采样直接进入阶段 3。

**产出**：`evidence`，包含主导类别与热点位置。

## 阶段 3：分诊

**目标**：把证据映射为"先做哪个技能"。

**执行**：调用 `kitex-troubleshooting`，使用其症状表；本流程只消费其输出，不重复判据。

**输出**：`suspect_skills[]`，每项包含：技能名、命中证据、优先顺序、预期验证指标。

**门控**：无法判定时，输出"证据不足 + 最小补采清单"，回到阶段 2；不得直接给参数。

## 阶段 4：单变量调优

**目标**：一次只验证一个方向，收益可归因。

**默认顺序**（按"改动风险从低到高、依赖从底到顶"排）

| 顺序 | 技能 | 为什么在这个位置 |
|---|---|---|
| 1 | `go-runtime-tuning` | 并行度与容器配额是环境正确性问题，错了会污染后续所有测量 |
| 2 | `kitex-transport-protocol-selection` | 协议是形态选型，会约束连接形态与元信息成本 |
| 3 | `kitex-thrift-codec-selection` | 编解码实现依赖协议已定 |
| 4 | `kitex-transport-tuning` | 连接形态与事件循环容量，受协议约束（复用连接要求 TTHeader） |
| 5 | `kitex-allocation-hotspot-tuning` | 分配来源在形态固定后再削，避免白改 |
| 6 | `kitex-version-upgrade-audit` | 版本变化会改变默认值与热路径，独立成轮 |
| 7 | `kitex-hot-path-analysis` | 配置层见顶后才评估框架改造，且只输出候选 |

**每轮规则**

1. 只改一个技能给出的一组绑定动作；跨技能合并必须标记为不可归因。
2. 每轮 3 次重复取中位，同时记录吞吐、长尾、CPU、内存。
3. 相对上一轮有效配置：收益高于判定阈值则保留，否则回退并记录。
4. 出现"吞吐上升但长尾明显变差"时，按阶段 0 的目标决定去留，并写入记录。
5. 任一轮回退后，下一轮必须从上一轮有效配置出发，不得静默回退到初始基线。

**门控**：`suspect_skills[]` 中的项未全部得到"执行/拒绝/阻塞"结论时，不得进入阶段 5。

## 阶段 5：验证与收尾

**目标**：给出可审计的结论与可执行的移交。

**执行**

1. 用最终有效配置重跑一次完整基线，与阶段 1 对照。
2. 汇总每轮收益与累计收益，标注归因方式。
3. 输出回退计划：每项变更的恢复方式。
4. 列出未采纳的候选及原因。

**产出**：`final_config`、`rollback_plan`、`handoff[]`。

## 移交边界

| 方向 | 交给 |
|---|---|
| 绑核、IRQ 亲和、大页、内核参数 | app-tuner 主流程的 `cpu-affinity-optimization` / `network-optimization` / `os-optimization` |
| 框架源码改造 | `code-optimizer`（由 `kitex-hot-path-analysis` 输出候选） |
| 业务代码与算法 | `code-optimizer` |
| 通用 Go profiling 方法 | `code-optimizer` 侧 `microservice/go-pprof-analysis` |
| cache miss、跨核迁移或伪共享/真共享怀疑 | `go-cacheline-optimization`（先识别优化点，方案落地再分流） |

## 产物与交回契约

| 阶段 | 产物 | 关键字段 | 下游读取 |
|---|---|---|---|
| 0 识别 | `kitex_profile` | 版本、协议、codec、连接形态、埋点级别、部署形态、目标 | 全部阶段 |
| 1 基线 | `baseline` | QPS、P50/P99、服务端 CPU、RSS、GC 次数、fd、dial | 阶段 4/5 |
| 2 证据 | `evidence` | 主导类别、热点位置、采样窗口、观测方式 | 阶段 3 |
| 3 分诊 | `suspect_skills` | 技能名、命中证据、优先顺序、预期验证指标 | 阶段 4 |
| 4 调优 | `rounds[]` | 技能名、动作、前后指标、保留/回退、归因方式 | 阶段 5 |
| 5 收尾 | `final_config`、`rollback_plan`、`handoff` | 最终配置、每项回退命令、移交对象与待办 | 父任务 |

**分支条件**

- `suspect_skills` 为空或证据不足 → 回阶段 2 补采，不进入阶段 4。
- 某轮收益未达判定阈值 → 回退并记录，继续下一项。
- 出现"吞吐上升但长尾明显变差" → 按阶段 0 的目标取舍，并在 `rounds[]` 注明。
- 达到目标或全部候选有结论 → 进入阶段 5。

**交回**

- 交回父任务时至少包含：`final_config`、`rollback_plan`、`handoff[]`、每个候选的结论（执行/拒绝/阻塞）与未采纳原因。
- 直接给用户时返回同样内容，并注明证据窗口与测量口径。

## 常见最短路径

**编号为流程阶段（0–5）；阶段 4 的具体 skill 以分诊结果为准。**

| 只出现 | 最短路径 |
|---|---|
| 吞吐上不去、CPU 未打满 | 0 → 1 → 2 → 3 → 4（按分诊结果逐项）→ 5 |
| 只有长尾变差 | 0 → 1 → 2（锁/阻塞优先）→ 3 → 4（`kitex-transport-tuning` 或 `go-runtime-tuning`）→ 5 |
| 内存/GC 偏高 | 0 → 1 → 2（堆采样）→ 3 → 4（`kitex-allocation-hotspot-tuning` 或 `go-runtime-tuning`）→ 5 |
| cache miss 高或怀疑伪共享 | 0 → 1 → 2（缓存事件/字段归属）→ 3 → 4（`go-cacheline-optimization`）→ 5 |
| 连接数或 fd 异常 | 0 → 1 → 2 → 3 → 4（`kitex-transport-tuning`）→ 5 |
| 计划升级 | 0 → 1 → 2 → 3 → 4（`kitex-version-upgrade-audit`）→ 5；升级后再按需进入 2 |

## 异常处理

| 情况 | 处理 |
|---|---|
| 缺少基线或形态不明 | 停在阶段 0/1，不进入证据与调优 |
| 证据不足或采样无权限 | 输出 `blocked` 与最小补采清单，保留已有证据 |
| 单轮收益为负 | 回退该轮，记录原因，继续下一候选 |
| 观测器导致负载失真 | 结束观测，按无观测口径重测 |
| 配置被外部改动 | 核对实际生效值，重建基线后再继续 |
| 超时或部分失败 | 保留已完成产物，标注未完成阶段，不给出收益结论 |

## 停止条件

满足任一即停止并输出结论：

- 达到阶段 0 设定的目标。
- `suspect_skills[]` 全部得到结论且无新的可测收益。
- 证据始终不足，或受权限/环境限制无法继续（输出阻塞原因与最小补采清单）。
- 后续动作超出已授权的变更边界。

## 记录要求

- 每个阶段都记录输入、产出与门控结论。
- 每轮记录：技能名、动作、前后指标、保留或回退、归因方式。
- 不引用其他环境或历史版本的性能数字作为本轮结论。
