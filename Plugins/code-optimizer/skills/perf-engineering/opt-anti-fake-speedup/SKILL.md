# 防假提速：两层铁证

## 何时使用

- 优化后吞吐涨了、时延降了，但不确定是"真快"还是"少干活"。
- 等价重构（submodule 化、路径迁移）后要实跑复验，而不是靠"应该等价"。
- 需要一个单一稳定的硬指标当锚，排除"收益其实来自少干活"。

## 核心原则

1. **提速只有两种可能**：真快了，或"少干活了"。防假提速就是排除后一种。
2. **两层铁证缺一不可**：① 量——干了一样多的活；② 质——每个请求干得一样重。
3. **单一稳定硬指标当锚**：请求计数是跨重构最稳的锚，能一次戳穿"少干活"。
4. **等价重构也必须实跑复验**：任何"应该等价"的重构，都要实跑 + 请求计数对照。

## 步骤速览

详细判据、假提速来源表与坑点**只在 `references/anti-fake-speedup.md` 一处维护**，本节给步骤名与去向：

1. **第 1 层：量**——请求计数与基线逐位一致、错误请求为 0 → references §2。
2. **第 2 层：质**——过滤命中数按同一快照拆两项（全库行数 + 相同过滤条件基线命中数），逐查询核对结果 ID
   （及必要顺序）+ 租户归属/主键 → references §3。
3. **把锚固化进复验**——运行容器镜像 ID/摘要与预期构建比对，匹配后才采用结果 → references §4。

## 门禁

- [ ] 请求总数逐位一致（或对等的资源/字节量一致）
- [ ] 过滤命中数按同一快照拆两项：全库行数 + 相同过滤条件基线命中数（非只测全库行数）
- [ ] 逐查询核对结果 ID（及必要顺序）；近似检索约定 top-k 召回率阈值
- [ ] 对齐同一批查询核对返回记录的租户归属与主键（防"跳过排序直接返前 k 条"）
- [ ] 错误请求全为 0
- [ ] 结果条数 / 候选集规模一致
- [ ] 运行容器镜像 ID / 摘要与预期构建比对一致后才采用结果
- [ ] 等价重构经实跑 + 请求计数对照

## 结果（标定案例形态）

flatidx 优化后请求计数与基线逐位一致、命中数 = 10000 / 空值 = 0，两层铁证排除"少干活"，增益 +179.6% 才站得住；
重组引入的版本转发失效靠"实跑 + 请求计数一致 + 镜像 ID 核对"才确认修复。细节与数字口径见
`references/anti-fake-speedup.md` §1/§2。
