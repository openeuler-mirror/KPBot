# 机制开销族的取证与验收方法

本文是 `hot-path-overhead-elimination` 的方法论依据。它回答三个问题：什么时候该怀疑"成本在机制上"、怎么把怀疑变成证据、改动之后怎么证明收益真实且没有回归。

## 一、成本位置的判定

同一个热点函数，成本可能来自三个完全不同的层次：

| 层次 | 表现 | 归属 |
|---|---|---|
| 算法与数据 | 循环迭代、访存、算术 | 向量化、访存优化、算法替换 |
| 调用与分派机制 | 序言/保存寄存器、间接调用、重复分类、被丢弃的记账 | 本 Skill |
| 分配与回收 | 每操作的 malloc/free、堆增长、内核回收 | 分配路径优化 |

判定顺序建议从"函数本身有多大"开始。当反汇编显示目标函数只有几十条指令、其中相当比例是序言与调用准备，而profiler 又把它列为热点时，成本大概率在机制层。反之，函数体里有长循环或大量访存指令时，先按算法层处理。

一个容易误判的情形：热点符号是"外层入口"，而真实工作在它调用的内层函数里。此时应当先按内层函数归属，除非可以证明内层函数在主导输入下几乎不做事（例如立即返回）。这个证明正好是 `dominant_outcome_inline` 的准入条件。

## 二、证据三件套

机制类改动必须同时拿到三类证据中的至少两类，缺一类只能作为假设：

1. **分布证据**：主导结果或主导取值占调用/样本的比例。必须来自实测——instrumentation 计数、采样 trace 的分布、或 benchmark 内的分类计数。`scripts/value_distribution.py` 负责把样本变成覆盖率与 top-k。经验阈值是主导覆盖 ≥ 0.8；覆盖率越低，特化的收益上界越低，低于阈值应直接拒绝而不要"先改再看"。
2. **生成代码证据**：`scripts/codegen_overhead_probe.py` 给出的指令数、调用点、栈帧字节、callee-saved 保存数量、是否叶子、入口附近是否有廉价条件早退。它同时是"编译器已经替我们做了"的判据——如果通用例程调用已经被内联成等价常量宽度代码，再改就是负收益改造。
3. **调用计数证据**：该函数在取样区间被调用了多少次。分布再集中，调用次数不够就不构成热点；调用次数很高但每次都很便宜时，才轮到机制层。

三类证据都能量化，所以都可以写进输出的 `evidence_used`，也都能被下游验证阶段机械复核。

## 三、guard 完备性

把一条路径从通用实现里拆出来，唯一的安全依据是：拆出来的快路径条件，覆盖了通用实现里所有会导致不同行为的条件。

做法是**枚举通用实现的慢分支**，而不是枚举想象中的快路径场景。以"短追加"为例，通用实现里可能有这些分支：缓冲区被冻结、长度溢出、观察者非空、末尾链不可写、剩余容量不足、需要加锁。快路径的 guard 集合必须与这个枚举一一对应；只要有一条没有对应的 guard，就会在某些输入上产生与通用实现不同的行为。

输出里的 `guard_completeness` 就是这份对照表：

- `general_slow_branches`：从通用实现读出来的完整枚举；
- `covered_by`：每条对应的 guard；
- `uncovered`：没有覆盖到的条目，非空即拒绝执行。

这条约束还有一个维护维度：快路径与通用实现是"同一份语义的两处表达"，通用实现的 guard 变化时快路径必须同步。改动交付时应当在代码注释里写明这一依赖，否则下一次维护会静默失配。

## 四、最小改动与代码放置

机制类改动最容易失控的地方是把"挪一段代码"做成"重构一个模块"。约束如下：

- 一次只应用一族配方，不做混合变换；
- 原实现必须保留为 fallback；`leaf_entry_split` 把它改成不可内联的独立符号，`dominant_outcome_inline` 把它留在 out-of-line 符号中；
- 内联的只放"判定 + 廉价动作"，重体一律 out-of-line；把重体一起内联会推高调用方的寄存器压力，抵消收益；
- 对外符号保持兼容：需要保留旧符号时用薄封装转发，不改调用方可见的签名。

`codegen_expectation` 是对这些要求的机械化表达。它写清楚"预期消失哪些调用、预期在调用方出现哪个谓词、预期哪个符号被 out-of-line"，验证阶段逐条核对，避免"改了但没生效"或"生效了但方向不对"。

## 五、A/B 协议

微秒级的机制改动对测量噪声极其敏感。实测中同一二进制在同一台机器上的单次结果可以相差数倍，所以必须按下面的协议取值：

1. **预热**：每侧先跑 1–2 次丢弃，避免首次运行的缺页与缓存冷启动进入样本。
2. **交替采样**：基线与候选交替执行（A、B、A、B……），而不是先跑完 A 再跑完 B。交替可以把缓慢漂移（温度、调度、页缓存增长）平均到两侧。
3. **样本量与统计量**：至少 7 对，推荐 11 对；同时报告均值与中位。均值对离群值敏感，中位对系统性漂移不敏感，两者严重不一致时说明噪声未受控，应加大样本或换测量口径。
4. **绑核**：固定 CPU（`taskset`），两侧一致。
5. **验收阈值**：主指标改进需超过 2%；其余同类接口的回归不得超过 1%。这两个数字来自微基准的可复现噪声水平，用它避免把噪声当收益。
6. **口径区分**：合成基准只能证明该代码路径的成本下降；端到端吞吐必须另有实测。

当墙钟噪声无法压到可接受范围时（虚拟化环境、共享机器），改用**确定性口径**做主判据：每操作的分配字节数、调用次数、指令数、分支命中数。这些量在相同输入下完全可复现，适合做门禁；墙钟仍要测，但只作为方向性参考。

## 六、因果验证

"改完变快了"不等于"因为推断的原因变快了"。机制类改动尤其容易把其它因素算到自己头上，所以要设计对照实验：

- 若推断是"通用例程调用"造成，可在不改代码的前提下用对照构建（例如强制内联同一函数）观察指标是否同样下降；
- 若推断是"分配与内核回收"造成，可用分配器层面的对照（关闭 trim、限制 arena）估计上界，再与源码改动的实测收益比较；
- 若推断是"记账被下游丢弃"，可在下游加一次计数断言，证明快路径确实不消费该记账。

对照结果与推断方向不一致时，应当重新假设而不是调整结论措辞。

## 七、跨平台与"编译器已经做了"

- 同一份配方在不同调用约定和指令集上收益不同：在目标机上明显的调用开销，可能在其它平台的编译器上已经被优化掉。落地前必须用目标机的反汇编确认通用调用或慢分支仍然存在。
- 平台限定允许，但要在 `risk_notes` 写明；语义等价与 fallback 要求不因平台降低。
- 反汇编显示编译器已经产出等价代码时，正确动作是返回 `success=false`，把它记进拒绝台账，而不是为了"有产出"制造改动。

## 八、拒绝台账

被拒绝的候选必须记录：假设、实测数字、拒绝原因。理由有三条：避免下一轮重复试验同一方向；避免把噪声当成"未验证的潜在收益"重新提起；让后来者知道哪些方向已经被证伪。

推荐的最小记录格式：

```
candidate: <配方> @ <函数>
hypothesis: <预期机制>
measured: <主指标前后值 / 覆盖率>
rejected_because: <低于阈值 | 编译器已内联 | guard 不完备 | 回归超限>
```

负结果与正结果一样是交付物的一部分。
