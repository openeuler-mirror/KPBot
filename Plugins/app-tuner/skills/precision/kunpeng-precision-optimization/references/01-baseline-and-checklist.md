# 基线与一致性 CheckList

## 验收等级先定（S-1~S-4）

调优的第一件事不是改参数，是决定「要什么级别的一致」：

| 等级 | 判据 | 现实性 |
|---|---|---|
| L0 | 单线程、同机、同配置多次跑结果**位模式相同**（按位比较，`+0.0` 与 `-0.0` 视为不同） | 必须达到，否则测量本身无效 |
| L1 | 同平台、多进程结果一致 | 排查并行干扰的中间目标 |
| L2 | 跨平台、同配置结果一致 | 客户常提，需要锁死编译器/库/选项版本 |
| L3 | 跨平台、跨规模统计等价 | 多数生产迁移的真实目标 |

四个指标全为 0（RMSE=ME=MAE=0、相关系数=1）**不等于** L0 达标：`+0.0` 与 `-0.0` 的差在这套指标里看不见，
但位模式不同。验收时按等级分开口径：L0 比位模式，L1/L2 比数值（可设 ULP 容差），L3 才用统计阈值。

- S-1：三项指标冲突时按 **准确性 > 稳定性 > 性能** 排序，任何以性能换精度的改动都要先证明前两项没被破坏。
- S-4：以「完全一致」为验收等于无限投入；先设等级与阈值，再开工。
- 附加事实：某些差异物理上不可消除（如 x86 的 80 位扩展精度路径），对应场景只能走 L3。

## 基线要固定什么（S-2/S-3）

| 维度 | 必须记录 | 为什么 |
|---|---|---|
| 硬件 | CPU 型号、核数/频率策略、NUMA 拓扑 | 频率与核数影响可选路径 |
| 编译器 | 厂商与**具体版本** | 不同版本浮点处理不同，关键指标会飘 |
| 数学库 | 库名与版本（含是否走扩展精度实现） | 同一函数不同实现差在末几位 |
| MPI | 实现与版本、归约相关环境变量 | 归约顺序随算法与规模变 |
| 算例 | 输入数据、进程/线程数、网格切分 | 切分变了结果就变 |
| 目标 | 验收等级 + 四指标阈值 | 没有阈值就没有“达标”

- S-3：对照侧若用激进优化（如 `-O3` + 快数学）编译，其精度损失是不透明账，只能缩小差距、不可能完全对齐。

## 一致性 CheckList（S-7）

开工前从上到下逐项核对，任一项不过先修它，不要跳过：

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 代码指纹 | 两平台代码摘要一致（同 commit / 同 patch 集） |
| 2 | 算例与配置 | 输入数据与配置摘要一致 |
| 3 | 编译器版本 | 使用双方约定的版本；不自行升级 |
| 4 | O0–O1 对照 | 先固定库版本、运行环境与并行规模，再两侧都把 `O3`/`Ofast` 改为 `O0` 跑一次、`O1` 跑一次；**只有单独改优化选项后才出现的差异**才算编译器优化层嫌疑 |
| 5 | 单线程一致 | 进程数一致，先保证单线程一致，再开多线程/多进程 |
| 6 | 选项集 | 精度相关选项显式写出，不依赖默认值 |

两个用法要点：
- 第 4 项是**分层手段**而非最终配置：它把「优化器引入的差异」（L2）与「库/架构引入的差异」（L1/L3）切开。
- 第 5 项是隔离手段：多线程归约顺序不稳定，单线程不一致就别指望并行下能对齐。

## 反模式

- 一上手就调 `-fp-model`，而两边编译器版本、库版本都不同——变量太多，结论不可信。
- 用「上次某项目改了这个选项就好了」直接套——选项语义随版本变，必须重验。
- 不记基线就跑两轮对比，第二轮环境已变，数字不可比。
