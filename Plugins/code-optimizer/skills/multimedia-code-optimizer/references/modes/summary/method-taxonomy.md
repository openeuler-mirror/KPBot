# 方法分类与命名

方法库的价值取决于“同一种手法只出现一次，且下一次还能认出来”。本文件给出一套稳定的命名、合并和拆分规则，以及常见方法族的识别线索。它不是必须逐条填满的清单：只用项目里真实出现的方法，类别只是帮助你对齐命名。

## 1. 一个方法是什么

一个方法 = **一种可复用的代码变换 + 它解决的向量化问题**。

它应该满足：

- 换一个项目、换一组变量名，仍然能照着做；
- 能指出“修改前为什么这样做”“修改后为什么能向量化”；
- 有一个最小的代码切片能说明差异；
- 不依赖某个库、某个文件、某次 commit 才能理解。

反例：

- “在 `pixel_sad_4x4_neon` 里把循环改成 8 路展开”——这是函数名，不是方法。
- “用 NEON 优化 SAD”——太宽，无法指导下一次改写。
- “把 `for` 改成 `vld1q`”——只说了指令，没有说数据布局和循环怎么变。

正例：

- “用多累加器拆分隐藏归约依赖”
- “用滑窗复用避免逐行重复加载”
- “用谓词化尾部把主体和收尾合并成一个循环”
- “用扩宽累加避免 16 位中间结果溢出”

## 2. 标题、场景、slug

### 标题

格式建议：`用<手段>处理/替换/合并<对象或问题>`。一句话说清手段，不要写“优化 xxx 函数”。

- 好：`用多累加器拆分隐藏归约依赖`
- 好：`用谓词化尾部合并标量收尾`
- 好：`用滑窗复用减少相邻行的重复加载`
- 差：`优化 SAD 函数`
- 差：`使用 NEON intrinsic`
- 差：`把 C 改成 NEON`

### 场景

一句话说明“这段代码在做什么、原实现受什么限制”，要通用，不要出现项目名/函数名。可以包含适用条件（数据类型、块尺寸、边界、内存布局）。

- 好：`逐元素计算两个块的绝对差并累加，元素数不是向量宽度整数倍，尾部需要单独处理`
- 好：`多抽头滤波的相邻输出共享输入窗口，逐点加载会重复读取同一批像素`
- 差：`优化 pixel_sad_4x4`
- 差：`这个函数很慢`

同一个方法可以有多个场景；合并时用 `；` 连接，不要为每个调用点新建方法。

### slug

- kebab-case，只用小写字母、数字、连字符；
- 语义化，稳定，不带项目名、版本号、函数名；
- 同一方法在不同批次必须复用同一 slug，否则合并脚本会生成两个 pattern。

示例：`multi-accumulator`、`predicated-tail`、`sliding-window-reuse`、`widening-accumulate`、`deinterleave-transpose`、`table-lookup-select`、`vla-strip-mine`、`gather-scatter`、`narrowing-pack`。

## 3. 合并还是拆分

先问三个问题：

1. **代码骨架能复用吗？** 换一个内核，改动点仍然是同一处（例如“把归约变量拆成 4 份，最后合并”），合并。
2. **变的只是数据宽度/类型/尺寸吗？** 合并。例如 8 位和 16 位版本的同一套扩宽累加，属于同一方法，用不同代码示例说明。
3. **循环变换或数据布局不同吗？** 拆分。例如“多累加器”和“滑窗复用”解决的是不同问题，即使都出现在同一个滤波函数里，也应是两个方法。

其他规则：

- 同一方法在三个模式里出现时，**按模式分文件**：`summary/auto/C_NEON/patterns/<slug>.md` 与 `summary/auto/C_SVE/patterns/<slug>.md` 是两份，因为目标指令和约束不同；slug 可以相同。
- 同一模式内，NEON 和 SVE 的“同名方法”不要合并到一份 pattern；模式目录已经表达了目标 ISA。
- 只是把一种指令换成另一种、思路完全相同的（例如 `vaddvq` → `svaddv`），放在 `NEON_SVE`，不要重复写进 `C_SVE`。
- 不要按函数数量建方法。一个方法可以有 1 个或 10 个代码示例；示例多说明复用广，不是拆分的理由。

## 4. 常见方法族

下面是提炼时常用的类别，用来对齐命名，不是必须覆盖的清单。真实方法可能组合其中几项；以代码里实际发生的变化为准。

### C → NEON

| 方法族 | 识别线索 | 典型标题 | 合并提示 |
| --- | --- | --- | --- |
| 定长分块 | 标量循环按 8/16 个元素切块，块内用 `vld1q`/`vst1q` | 用定长分块把逐元素循环改成向量循环 | 不同块宽通常合并，用示例说明 |
| 多累加器 | 多个 `vdupq` 累加变量、循环后 `vaddq` 合并 | 用多累加器拆分隐藏归约依赖 | 与“横向归约”区分：这里重点是拆依赖 |
| 横向归约 | `vaddvq_*`、`vmaxvq_*`、`vpadd` 收尾 | 用向量横向归约替代标量累加 | 归约指令不同可合并 |
| 扩宽/窄化 | `vmull`、`vmlal`、`vaddl`、`vmovn`、`vqmovn` | 用扩宽累加避免中间结果溢出 | 扩宽和窄化是两个方向，按实际改写拆 |
| 交错/转置 | `vzip`、`vuzp`、`vtrn`、`vrev`、`vtbl` 重排 | 用转置/交错重排匹配多抽头访问 | 与查表区分：这里是固定 permutation |
| 查表/选择 | `vtbl`、`vqtbl`、`vbsl`、`vbit` | 用查表或位选择替代分支 | 查表和掩码选择可分开 |
| 滑窗复用 | 相邻输出复用上一轮的加载结果，寄存器轮转 | 用滑窗复用减少相邻输出的重复加载 | 与定长分块区分：重点是跨迭代复用 |
| 饱和/掩码 | `vqadd`、`vqsub`、`vmaxq`/`vminq` 组合、比较掩码 | 用饱和/掩码运算替代标量 clip | 与查表选择区分 |
| 尾部重叠加载 | 最后一次加载向前重叠，避免标量收尾 | 用重叠加载消除尾部标量循环 | 需要说明越界安全条件 |
| 布局转换 | AoS→SoA、分离平面、预转置 | 用数据布局转换把跨步访问变成连续访问 | 与转置区分：这里是整体布局 |
| 点积/矩阵指令 | `vdotq`、`vmmla`、`bfdot` | 用点积指令合并乘加与归约 | 只在目标 CPU 支持时使用 |

### C → SVE

| 方法族 | 识别线索 | 典型标题 | 合并提示 |
| --- | --- | --- | --- |
| VLA 分段循环 | `svcnt*()` 作为步长，循环次数由运行时向量长度决定 | 用向量长度无关循环替代定长分块 | 与谓词尾部可组合，但仍是两个手段 |
| 谓词化尾部 | `svwhilelt` 生成 `pg`，同一循环体处理余数 | 用谓词化尾部合并标量收尾 | 与 VLA 循环区分：这里解决余数 |
| 谓词化访存 | `svld1(pg, ...)`、`svst1(pg, ...)` | 用谓词化加载/存储消除尾部越界判断 | 与尾部处理合并时说明 |
| 谓词归约 | `svaddv`、`svmaxv`、`svminv` + `pg` | 用谓词化归约替代标量收尾累加 | 与 NEON 横向归约对应 |
| gather/scatter | `svld1_gather_*`、`svst1_scatter_*` | 用 gather/scatter 处理非连续访问 | 需要说明索引生成方式 |
| 表查找/复制 | `svtbl`、`svdup`、`svindex` | 用 SVE 表查找/索引生成替代分支或常量表 | 固定 permutation 与查表可分开 |
| 多向量展开 | 一次处理多个 `svcnt*()` 宽度的块 | 用多向量展开提高 SVE 流水并行 | 与多累加器区分：这里拆的是数据块 |
| NEON 桥接 | SVE 主路径 + NEON 处理 128-bit 或特殊指令 | 用 NEON 桥接补齐 SVE 缺失的窄操作 | 只在确有桥接代码时总结，不要泛化 |

### NEON → SVE

| 方法族 | 识别线索 | 典型标题 | 合并提示 |
| --- | --- | --- | --- |
| 定长→VLA | `vld1q` 的固定 128-bit 循环改成 `svcnt*` 步长 | 用向量长度无关循环替换定长 NEON 循环 | 与谓词尾部区分 |
| 标量尾部→谓词 | NEON 的 `for (; i < n; i++)` 收尾改成 `svwhilelt` | 用谓词化尾部替换 NEON 的标量收尾 | 与 VLA 循环可组合 |
| 归约映射 | `vaddvq_*` → `svaddv`，`vmaxvq_*` → `svmaxv` | 用 SVE 谓词归约替换 NEON 横向归约 | 只换指令时合并为一个方法 |
| 掩码→谓词 | `vbslq`/比较掩码改成 `svsel` + `pg` | 用谓词选择替换 NEON 位掩码选择 | 与查表选择区分 |
| 转置/交织映射 | `vzip/vuzp/vtrn` → `svzip/svuzp/svtrn` | 用 SVE 重排指令替换 NEON 交织 | 数据布局不变时合并 |
| 窄化/饱和映射 | `vqmovn`、`vqxtn` → SVE 窄化 | 用 SVE 窄化/饱和指令替换 NEON 打包 | 与扩宽区分 |
| 点积映射 | `vdotq` → `svdot` | 用 SVE 点积替换 NEON 点积 | 只换指令时合并 |
| 多累加器扩展 | NEON 的 2/4 份累加器改成更宽的 SVE 向量或多份 SVE 累加器 | 用更宽向量扩展 NEON 多累加器 | 与多累加器区分：这里重点是宽度变化 |

## 5. 场景与方法的对应

- `场景` 回答“什么代码、什么限制”，`手法` 回答“用了什么变换”。不要把指令名堆在场景里。
- 同一个方法可以有多个场景（例如“块尺寸不是向量宽度整数倍”和“行尾需要越界保护”），合并到同一 scene 行，用 `；` 分隔。
- 如果两个场景需要不同的前置条件（例如一个要求可越界读、一个要求严格边界），在要点里写清，不要假装是同一套代码。

## 6. 写 pattern 时的取舍

- `# 修改要点`：3～6 条，每条是一个可执行的动作或约束，不是代码复述。
- `# 修改代码示例`：每对“修改前/修改后”只保留说明该方法的必要代码；同一个方法有多个函数时逐个举例，不要只放最漂亮的那个。
- 示例说明（`## 示例 N：...`）写“这段代码在做什么”，不要写函数名、文件、项目。
- 如果修改后代码依赖某个宏/类型别名，在要点里说明“类型别名按项目定义”，不要把宏定义整段抄进来。
