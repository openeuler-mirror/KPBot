# SQL72 连接探测前的数量上界预筛

## 说明与范围

SQL72 按商品键连接 `catalog_sales` 和 `inventory`，再检查 `inv_quantity_on_hand < cs_quantity`。如果销售建表侧最大的有效销售量是 `10`，库存探测侧数量为 `10` 或 `11` 的行与任何建表行配对都无法通过。把这些行从探测选择集删掉，可以省去哈希探测和重复键配对。库存量低于 `10` 的行仍须按商品查表，并对每个配对执行原条件。[实施细节](references/implementation.md)

## 与相邻技能的分工

本 skill 在常规哈希探测之前应用数量上界，只淘汰不可能通过严格比较的探测行。[过滤位图压缩](../sql-q72-join-filter-bitmask/SKILL.md) 在原探测和谓词求值之后搬运行映射；本 skill 必须保留这些后续精确步骤，不能将预筛当作最终匹配。

[split 提交前剪枝](../sql-q72-parquet-split-pruning/SKILL.md) 依据分区 Bloom 淘汰读取任务，与这里依赖完整哈希表的数值上界不同。分别计量跳过 split、减少探测行及减少候选配对，再通过单项开关归因。

## 实施步骤

### 1. 从最终计划定位商品键和数量条件

```text
销售量随商品键建表 → 得到当前完整哈希表 → 计算销售量最大值
库存批次 → 预筛不可能匹配的库存行 → 商品键探测 → 候选配对 → 原数量条件
```

SQL 文本中的左右顺序与物理 build/probe 方向可能不同。对照最终 Spark 计划、Gluten 的连接转换和 Velox `HashJoinNode`，记录 `cs_quantity` 是建表列、`inv_quantity_on_hand` 是探测列的证据。

### 2. 用连接类型、函数身份和列绑定把准入收窄

只给内连接的原生 `INTEGER` 严格小于比较增加这条路径。确认比较的左输入是直接引用的探测列，右输入是直接引用的建表列，名称在两个 schema 间无歧义。校验编译后的函数身份及默认 NULL 语义。组合条件、用户自定义函数、隐式转换或无法确认的列绑定沿用原路径。

### 3. 在哈希表就绪后计算可证明的上界

从当前完整建表结果的所有相关行容器读取有效销售数量，用原 `int32` 域取最大值。空表仍走引擎原有空表处理。若存在未恢复或仍待处理的 spill，停用上界，避免用仅含部分建表行的数据误删。重新接收哈希表时清除旧上界，再按当时的状态重新判断。

### 4. 在常规探测之前更新当前选择集

适用批次使用 flat、可证明无 NULL 的 `INTEGER` 探测列。对于 `probe_value >= max_build_value` 的行清除选择位，把原选择集与新掩码相交。向量化实现按位图字长处理完整块，余下各行使用标量比较，并更新选择集范围。若所有活动行都被淘汰，按原输入状态协议结束当前批次。

### 5. 保留探测和剩余条件，设置成本门槛

全表最大值只提供淘汰证据。库存量低于最大值的行可能属于另一个商品，仍要按原键查表、生成所有重复键配对并评估原谓词。SQL72 的实现只在建表键有重复时计算上界，输入前 32 个值至少有 8 个达到上界才继续预筛。迁移时将这些数值视为成本策略，结合目标分布复核。

### 6. 从真实入口核对结果和分派

覆盖等于上界、跨商品、重复销售行、全 NULL/空建表、NULL 连接键、`INT32_MIN/MAX`、混合选择集、无命中、SIMD 尾部以及 spill 回退。普通 `=` 连接的两个 NULL 键不能匹配；不要用 Python 的 `None == None` 代替 SQL 语义。用完整候选配对及输出重数做精确对照，记录准入、实际运行和回退原因。确认旧上界不会穿过新的建表实例。

### 7. 按重复键和淘汰比例测收益

分开记录计算上界的次数与耗时、预筛输入行、实际淘汰行、提交探测行和过滤前配对数。比较低淘汰、无淘汰及高重复度的成本。固定 SQL、库、资源和计时边界交错运行，按需要只启用这一项做配对复测。

## 约束

- 只淘汰严格小于条件能证明失败的探测行。用 `>= max` 保留正确的等值边界，避免通过 `max - 1` 引入溢出。
- 上界的生命周期跟随当前完整哈希表。构建未完成、部分 spill、绑定不确定或比较行为不明时沿用原探测路径。
- 保留内连接的 SQL 三值逻辑、重复键配对与输出映射。其他连接类型或向量编码需要单独证明后才能扩展。
- 记录完整查询实测与算子局部证据。阶段性计时可以定位主收益，单项贡献需对应版本的配对实验。
