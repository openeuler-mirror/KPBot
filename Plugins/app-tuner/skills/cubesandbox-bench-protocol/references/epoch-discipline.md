# 纪元纪律（Epoch Discipline）

> 配套 SKILL.md「纪元纪律」节。这是本协议最核心的纪律：**跨纪元的数字不可比**。

## 什么是纪元

纪元 = 一组影响性能数字的底层状态。同纪元内的对比才有意义；跨纪元的差异可能全部
来自纪元本身，而不是被测的改动。

## 新纪元触发条件（任一发生即重测基线）

| 触发 | 说明 |
|---|---|
| 宿主机重启 | 实测同组件栈仅重启即可造成同指标 +50% 左右的系统性漂移，多轮不收敛；怀疑页缓存/调度器/组件初始化差异 |
| 内核或内核参数变更 | sysctl、启动参数、内核版本；单个开关（如 RCU 模式）可造成 10 倍级差异 |
| 沙箱组件版本/二进制替换 | VMM/agent/编排组件任一替换；同版本重编译不必然新纪元，但替换即新纪元 |
| 模板变更 | 模板重建、探针参数修改、镜像内容变化 |
| 硬件/拓扑变更 | CPU 热插拔、NUMA 绑定策略变更、频率策略变更 |

## 漂移案例（一线记录）

同版本组件栈（虚拟化组件含内核适配补丁），重启前后同场景同口径测量：

- 重启前：轮总时延中位数稳定在 ~150-170ms 段
- 重启后：稳定在 ~230-260ms 段（多轮不收敛回旧水平）

阶段分解显示各阶段同步抬高 ~96ms（非某单阶段劣化）；单实例创建延迟完全健康（与
历史锚点一致）→ 罚金只在并发出现 → 共享资源路径问题。此案例证明：**跨纪元对比
会得出"优化无效"或"性能退化"的错误结论**，排障一天后确认纪元不可比才是正解。

## 单实例健康锚点

并发数字之前先看单实例（c1）：

1. c1 延迟 ≈ 历史健康锚点 → 环境健康，并发劣化是争用/排队问题；
2. c1 显著高于锚点 → 环境本身出问题（组件状态/内核参数/磁盘），先修环境再测并发，
   否则测的全是环境噪声。

c1 分解参考（健康数量级）：API 处理 ~几 ms、VM 恢复 ~十几 ms、探针等待 ~十 ms
量级、杂项 ~几 ms。

## 结论标注模板

每个性能结论必须带纪元标识，否则不可复查：

```markdown
### <结论标题>

- 纪元：<组件版本标识> / <内核版本+关键参数> / <模板标识> / <是否重启后>
- 场景与轮次：<用例> × N 轮（中位数口径）
- 数字：<指标值列表>
- 对比基准：<同纪元基线的获取时间与值>
```

## 跨机器对比前置检查

1. 内核版本与关键 sysctl（RCU 模式、调度器、THP/预读类）逐项对齐——先确认开关的
   **存在性**再谈取值（有的内核根本不暴露某开关，默认行为也不同）；
2. bench 二进制版本与计时口径一致；
3. 模板一致（同 ID 或同内容指纹）；
4. 磁盘类型与页缓存状态尽量对齐（冷/热盘差异可达数量级）。
