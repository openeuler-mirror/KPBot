# Go 运行时与容器适配调优

本 skill 只处理 Go 运行时层面的参数与容器适配。组件内部的分配热点由对应组件专题负责（如 `kitex-allocation-hotspot-tuning`）；`sync.Pool` 参数见 `go-syncpool-optimization`；打补丁与重编译见 `go-runtime-patch-build`。

## 何时触发

- 容器 CPU 配额小于宿主核数，进程线程数异常或出现 CPU throttling。
- GC 频率偏高、停顿影响 P99，堆增长快但内存预算有限。
- 压测结果随部署环境漂移，怀疑并行度设置不当。

## 范围

- 覆盖：并行度与容器配额、GC 参数与内存上限、分配速率判断、容量兜底与回退。
- 不覆盖：组件分配点定位、`sync.Pool` 参数、运行时补丁。
- 环境与工具：Linux cgroup v2（`cpu.max`、`cpu.stat`）；观测用 `/proc`、pprof 或运行时指标；改参数通常需要重启或重新部署，按授权执行。

## 出处

- 并行度语义与 GC 参数：Go 官方运行时文档与 `runtime` 包文档。
- 容器配额与限流计数：cgroup v2 文档（`cpu.max`、`cpu.stat`）。

## 命中验证与越界验证

- 命中：问"容器里线程数比配额多，怎么办"，应答"读配额 → 对齐并行度 → 看限流计数"。
- 越界：问"Kitex 每请求为什么分配这么多"，应答属于组件分配点，转 `kitex-allocation-hotspot-tuning`。

## 安全与资源上限

- 压测并发、时长与重复次数设上限；改参数前记录原值，结束后核对生效值并保留回退配置。
- 内存上限必须预留余量，避免 OOM。

## 判定

| 证据 | 结论 | 动作 |
|---|---|---|
| 容器配额 < 宿主核数，且并行度取宿主核数 | 并行度过大 | 按配额设置并行度 |
| `cpu.stat` 出现明显 throttled | 时间片被打断 | 并行度与配额对齐，必要时留余量 |
| GC 次数高且堆很小 | GC 过于频繁 | 放宽 GC 或用内存上限约束 |
| GC 次数低但 RSS 持续上涨 | 放宽过度 | 收紧 GC 或加内存上限 |
| 分配速率高 | 组件分配问题 | 移交组件专题，不靠调 GC 解决 |

## 执行步骤

1. **读配额**：确认 CPU 配额、cpuset、实际可用核数三者关系；注意配额限制的是时间片，不是核数。
2. **定并行度**：旧版本 Go 需显式设置或引入自动适配库；新版本默认感知容器配额，但仍要确认实际取值。并行度应与配额一致，并留出少量余量给系统与 sidecar。
3. **看 GC**：记录 GC 次数、停顿、堆大小、分配速率；先判断是"分配太多"还是"阈值太紧"。
4. **调 GC**：优先用内存上限约束（软上限），其次放宽 GC 百分比；不要用"关闭 GC"作为生产配置。
5. **容量兜底**：设置内存上限时预留安全余量；监控 RSS 与 OOM 风险。
6. **验证**：QPS/P50/P99 + CPU + RSS + GC 次数，四项同时看；口径走 `microservice-ab-testing`。

## 判断要点

- 并行度不是越大越好：超过配额会带来时间片打断与调度开销，低于配额则浪费算力。以 `nr_throttled` 是否增长作为主要判据。
- "关闭 GC 更快"只在小堆短跑中成立，代价是内存成倍增长；生产必须给内存上限并保留回退。
- GC 频繁但分配速率正常，说明阈值过紧；分配速率高则说明问题在组件代码，调 GC 只是掩盖。
- 内存上限设置得过低会让 GC 变成新的热点，必须结合真实内存画像。

## 回退

- 并行度：恢复环境变量或移除自动适配库。
- GC：恢复原环境变量；保留一份原配置用于回滚。
- 内存上限：去掉上限或调高，并观察 RSS 回落。

## 输出

- 输出参数取舍结论、判定依据与回退配置；不产出文件。

## 与相邻技能的边界

- 唯一归属：并行度与 GC 参数只在本 skill 调整；其他组件 skill 提到 GC 时只做委派，不得给出具体值。
- 组件分配点：字符串解码、上下文链、元信息、请求/响应结构等分配来源由对应组件专题定位（如 `kitex-allocation-hotspot-tuning`），本 skill 只根据分配速率判断"是否该调 GC"。
- `sync.Pool` 参数与运行时补丁：分别在 `go-syncpool-optimization` 与 `go-runtime-patch-build`。
- 缓存行争用识别：cache miss、跨核迁移或伪共享/真共享证据不在本 skill 内判断，转 `go-cacheline-optimization`。
- 本 skill 可独立调用，不依赖 `WORKFLOW.md` 的中间产物。
