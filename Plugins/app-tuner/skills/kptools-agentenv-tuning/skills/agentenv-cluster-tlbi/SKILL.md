# AgentENV TLBI / DVMBM 广播优化

## 输入与共享约定

需要实际 CPU cluster 拓扑、目标任务/vCPU 的有效 cpuset、运行内核、
硬件及 TLBI 范围控制实现、页表失效路径证据、AgentENV 并发测试。
另需实现的使能/禁用接口、位图更新策略与控制粒度、基准材料及测试授权。
通用流程见 `references/optimization-process.md`；源码布局下为
`../../references/optimization-process.md`。
读取共享 `references/validation.md`；源码布局下为 `../../references/validation.md`。
补采使用共享 `scripts/collect_environment.sh`，源码布局为
`../../scripts/collect_environment.sh`。
离线 UnixBench、快照制作、脚本复用与指标口径见 `references/tlbi-benchmark.md`；
源码布局下为 `../../references/tlbi-benchmark.md`。规格、并发和采样预算按当前项目确定。

## 诊断

1. 区分 NUMA node、socket、die、cluster、core。优先读取平台实际拓扑和说明，
   不根据连续 CPU 编号、NUMA node 或相同 L3 自动推定 TLBI 广播域。
   某个拓扑文件缺失时保留 unknown，不能当成 ID=0。cluster_id 可能只在某层级内
   唯一，应联合 package/die 和平台说明解释，不能按单一 ID 跨 socket 合并 CPU。
2. 记录目标进程/线程或 vCPU 的 CPU 允许集合及实际运行分布，检查 cgroup
   有效约束；不能用 cgroup 根目录的 cpuset 代替目标任务所在层级。
   先区分 cgroup v1/v2，再按目标 membership 和实际 mount root 解析路径；
   status 中允许集合可用时保留它，但不能据此推断 CPU quota 或 vCPU 线程绑定。
3. 分析 TLBI/shootdown 或页表失效路径开销。普通 TLB miss 较高不足以证明
   广播开销较大，仍需对应路径的测量证据。
4. 核实平台是否存在与此方案匹配的硬件能力、内核补丁、接口和运行时生效证据。
5. 明确操作的是哪个地址空间、Host/Guest 哪一级页表，以及硬件/软件如何跟踪
   需要接收失效的 CPU。

## 核对 DVMBM 接口和位图策略

- 对提供该接口的实现，以 Host 内核参数 `kvm-arm.dvmbm_enabled=1` 作为使能入口。
  在实际源码中核对参数类型、默认值、所需补丁、硬件能力和生效范围；
  参数名存在于文档或 `/proc/cmdline` 不证明当前内核识别或启用了功能。
- 从实现确认禁用方法；只有核实支持时才使用关闭值，不把删除参数等同于关闭，
  也不将启动参数当作可在线写入的通用 sysctl。
- 区分按 vCPU 亲和性生成允许范围位图，和按实际运行/迁移更新位图的策略。
  记录所测策略版本，不能只用“开 TLBI”描述不同实现。
- 核对逐 vCPU 与 cluster 粒度的实际能力和映射编码。不同平台可能不同：
  920C/E 的逐 vCPU 更新与 920G 的 cluster 更新是待对照实现的能力线索，
  不能仅凭型号名保证支持或直接把 Linux CPU 编号当硬件位图编号。

cpuset 只约束任务可运行 CPU。仅配置 cpuset 不能保证 TLBI 广播范围缩小。
跨 cluster 迁移后可能存在旧 TLB 项，不能简单按当前 cpuset 省略失效目标。
未证明一致性覆盖时，仅输出布局建议或 `blocked`，不生成省略必要 TLBI 的补丁。

## 实施

1. 准备可恢复的测试节点，保存原启动项、机制状态、cpuset 与线程绑定；
   需要构建、部署或重启时分别核对授权。
2. 审查项目现有的 `make_ub_image.sh`、`ub_bench.sh` 或同类脚本，
   核对参数、基础镜像、快照选择、资源开销及清理范围后再复用，不默认执行硬编码路径。
   无脚本时按共享测试指南完成材料校验、后台启动、推包、自检和快照制作。
3. 固定镜像/快照、Guest 内核、VMM、规格、工作量、并发、预热及统计规则。
   根据当前可用内存、CPU 与 Host 预留资源确定并发，不套用其他单板的容量上限。
4. 通过沙箱 ID、API/日志或串口 FD 核对实际 VMM PID，再识别 vCPU TID。
   不照抄查找 QEMU 的命令来定位 Firecracker；主线程和 API 线程不是 vCPU。
   每次重新启动/恢复后重查 PID/TID，不复用旧标识。
5. 根据真实拓扑设计映射，可复用 `cpu-affinity-optimization` 的方法。
   若要求物理核一对一，排除 SMT sibling 共享；不同沙箱的 CPU 列表不重叠，
   也不自动等于物理核不共享或 cluster 隔离。

   ```bash
   ps -T -p "$VMM_PID" -o pid,tid,comm
   taskset -cp "$PCPU" "$VCPU_TID"
   taskset -pc "$VCPU_TID"
   ```

   变量必须来自已确认的实例和分配方案；查询参数是线程 TID，不是 pCPU 编号。
   只修改本轮测试线程，同时核查有效 cpuset 和实际运行分布。
6. 按已核实的方式切换 Host 功能。重启后重新关联 boot_id、运行内核、
   `/proc/cmdline`、实现对应的参数值/日志与范围控制证据，确认开关真正生效。
7. 单板重启后先校验可信时间源、时区和时钟同步，再开始测量。
   校时需单独核对授权并使用真实当前时间，不能照抄教程日期；耗时采用单调时钟。

没有厂商/内核实现资料时，不把 NUMA 绑定、`taskset` 或 TLBI 指令名称
包装成已实现的广播范围控制。

## 性能对照与策略消融

- 先在同一布局、同一负载下比较功能关闭/开启；若要衡量布局贡献，
  再在相同功能状态下比较绑定/不绑定，不能把绑核收益全归给 DVMBM。
- 覆盖单沙箱与业务代表性的并发场景，比较每沙箱 Process Creation 的 lps/INDEX
  及并发保留率。它们不是沙箱创建/恢复延迟，后者需要另外的真实生命周期用例。
- 比较亲和性驱动与迁移驱动补丁时，固定开关和其他设置，仅改变更新策略。
  若要测试放宽绑定的能力，将布局变化与策略变化分开对照。
- 为新策略加入受控迁移或允许集合大于实际驻留集合的场景，观察安全目标位图
  与广播域的变化。一直固定绑核、没有迁移的结果不足以判断动态跟踪价值。
- 核实并发任务有共同运行窗口；CPU 范围错开与负载启动错开不是一回事。
  保留每沙箱原始输出、绑定映射、开始/结束时间、失败与重复轮次，不只留均值。

## 迁移驱动位图的正确性门控

“当前运行在某个 pCPU”不等于“只有这个 pCPU 可能持有该 VM 的 TLB 项”。
核对迁入新域、迁出旧域与 vCPU 执行之间的同步/屏障，以及历史驻留状态的回收条件。
旧 CPU 上的条目失效或其上下文被安全退休前，不能仅因 vCPU 已迁走就从目标集合删除。

验证迁移与失效并发、亲和性/cpuset 扩缩、vCPU 阻塞/恢复及快照恢复等适用场景，
并检查上下文标识复用及恢复后位图初始化，不能沿用旧实例的 pCPU 映射。
新策略若尚无匹配补丁，只输出验证计划，
不凭“实时监控”描述生成省略必要 TLBI 的代码。

## 验证与回退

- 正确性：真实沙箱创建/恢复、并发 map/unmap、地址空间共享及迁移场景。
  如果实现禁止跨 cluster 迁移，应验证约束被强制执行，以及变更 cpuset 时
  必要的失效/同步处理；不是强行执行其不支持的迁移。
- 性能：相同规格和背景负载下比较业务指标、失效路径耗时及调度分布，
  并发和负载水平由当前项目确定。
- 范围：用实现提供的跟踪、计数或其他可核实证据确认机制生效；
  绑核生效不等于范围广播生效。
- 回退：按实现规定的依赖顺序关闭范围优化、完成所需同步，再恢复调度范围；
  不能在仍依赖限制 cpuset 的机制运行时先放宽绑定。必要时回到旧内核复验。

按共享结果契约输出实际结果，附机制开关、位图策略/粒度、生效证据、线程映射、
基准与快照标识、逐沙箱指标及回退结果。只有绑定或 cmdline 验证时明确限制结论，
不能宣称范围机制或性能收益已验证；未实测时 `gain_pct=null`。
