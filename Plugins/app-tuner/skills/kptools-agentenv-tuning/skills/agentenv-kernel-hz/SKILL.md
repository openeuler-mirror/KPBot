# AgentENV 内核 HZ 调优

## 输入与共享约定

需要发生 ublk 控制路径争用的实际节点、运行内核配置、锁等待/持锁时间、
调度唤醒到运行延迟和并发恢复用例。
读取共享 `references/validation.md`；源码布局下为 `../../references/validation.md`。
共享优化流程见 `references/optimization-process.md`；源码布局下为
`../../references/optimization-process.md`。
补采使用共享 `scripts/collect_environment.sh`，源码布局为
`../../scripts/collect_environment.sh`。

## 诊断

1. 定位 `ublk_ctl_mutex` 所在的内核及调用路径，确认应修改 Host 还是 Guest。
   使用外置 ublk 模块时核对实际模块源码/构建身份，不仅查看发行版内核源码。
2. 检查实际 `CONFIG_HZ`、HZ choice、`CONFIG_PREEMPT*`、`CONFIG_NO_HZ*`。
   `getconf CLK_TCK` 是用户态计时接口，不能用来推断内核 `CONFIG_HZ`。
3. 结合项目可用的 sched/lock 跟踪区分：锁持有时间、等待者睡眠时间、
   唤醒到获得 CPU 的延迟、I/O 等待。缺少 tracepoint 或权限时记录证据不足。
4. 检查 vCPU steal、CPU quota/过载、长临界区是否是更直接的原因。
   只有锁竞争而没有调度延迟证据时，先输出诊断计划。

`cpu-pressure.txt` 只反映采样时节点级 CPU 压力，不是目标锁的等待归因。
仅看到某种 HZ、抢占模型和 NO_HZ 配置组合不足以证明 HZ 是瓶颈。
perf/trace 权限不足时记录缺失证据和所需权限，不自动降低安全参数、挂载 tracefs
或执行旧 benchmark 中的 sudo runner。

提高 HZ 会缩短名义周期性 tick 间隔，但不意味着 mutex 唤醒必须等待 tick，
也不会消除临界区串行化。结合 sched_wakeup→sched_switch、抢占模型和 NO_HZ
确认调度归因，不能按 tick 间隔直接推导恢复收益。

## 实施

1. 根据当前内核支持的 HZ 选项、调度证据和业务目标确定候选配置。
   使用相同源码、补丁、工具链和其余配置建立对照内核。
2. 在实际 Kconfig 中选择目标 HZ，经配置依赖解析核对最终 `CONFIG_HZ`
   以及对应 choice，避免同时保留互斥选项。
3. 保存最终配置 diff，仅包含目标 HZ 及必要派生差异；若还有其他差异需解释或隔离。
4. 按项目内核构建/部署流程生成候选内核，保留旧内核和可用启动项。
5. 在已授权的重编译、部署、重启范围内运行；启动后从实际配置验证生效。

HZ 是构建选项，不能通过 sysctl 在线写入。若无构建/重启条件则输出
`blocked` 和可执行前需要补齐的材料，不把调节用户态计时器当成等价实现。

## 验证与回退

1. 根据当前项目确定恢复测试入口、规格、代表性并发、预热方式、样本量和重复轮次。
   固定镜像、存储、CPU 绑定、资源池、Guest、抢占模型、NO_HZ 和背景负载。
2. 明确恢复操作的计时边界，核对 sample 是逐 VM、并发组均值还是整批耗时。
   保留原始值和聚合关系，不把组均值的分位数当作单次请求的分位数。
3. 按相同方法采集当前配置与候选配置，记录业务指标、锁持有/等待、调度延迟及
   CPU/中断开销。若区分预热、冷态或稳态，提前确定规则并在两侧一致执行。
4. 保留全部原始记录，不为获得正收益选择性删除异常值。按项目目标比较延迟、
   吞吐、波动和资源代价，覆盖有代表性的负载水平。
5. 功能失败、性能退化或额外开销不符合目标时，恢复原内核并复验。

按共享结果契约输出当前数据支持的结论；配置生效与性能改善分别提供证据，
未实测时不填写收益。
