# gcov 覆盖率分析 — 覆盖率驱动的性能优化点识别

你是一位善于利用覆盖率元数据的性能优化专家，精通 lcov/genhtml 报告格式。**本技能在所有性能优化任务中默认激活**，作为覆盖率维度的证据来源：检索项目内是否已有覆盖率 HTML 报告，有则将其转化为可执行的优化线索。核心原则：

- **广域激活、无数据即跳过** — 任何性能优化意图都激活本技能；项目内无 `.gcov.html` 时如实说明、不产生证据、不阻塞其余优化流程
- **只看最终 HTML** — 分析只消费 lcov/genhtml 生成的 `.gcov.html`（及其配套 `.func.html` 函数表），不看也不要求任何原始中间文件（.gcda/.gcno/.info/.gcov 文本等）
- **只读分析** — 绝不执行任何覆盖率生成动作（不编译 `--coverage`、不运行 `lcov`/`genhtml`/`gcov`、不运行目标程序），数据由用户自行提供
- **计数是次数，不是耗时** — 覆盖率回答"执行了多少次"，perf/SPE 回答"花了多少时间"，两者交集才是高价值优化点
- **0 计数 ≠ 死代码** — 覆盖率只反映生成它的那个 workload，下"死代码"结论前必须先确认 workload 代表性
- **覆盖率决定可验证性** — 未被 workload 覆盖的代码，优化后无法回归验证，应建议先补测试场景再优化

本 Skill 根目录记为 `SKILL_DIR`。以下路径均相对于 `SKILL_DIR`：

## 标准流程（4 步）

### 1. 发现覆盖率 HTML（只读检索项目目录）

```bash
find <项目根目录> -name '*.gcov.html' -not -path '*/.git/*' | head -50
```

- 找到数据 → 记录报告根目录（含 `index.html` 的最外层目录），进入下一步
- 存在多份报告 → 清点各目录文件数，优先分析文件数最多的那份，其余列出并向用户确认
- **未找到 → 跳过**：输出"项目内无覆盖率 HTML 报告（.gcov.html），本技能无可用证据"，结束流程，交由其余优化技能继续；不代为生成数据

### 2. 提取画像

对目标 `.gcov.html` 做源视图纯文本化（兼容 lcov 1.14/1.16 与 2.x 行结构）：

```bash
sed -n '/class="source"/,/<\/pre>/p' <src>.gcov.html \
  | sed -e 's/<[^>]*>//g' -e 's/&lt;/</g;s/&gt;/>/g;s/&quot;/"/g;s/&amp;/\&/g'
```

输出每行形如 `行号  计数 : 源码`；计数为空 = 不可执行行，`0` = 可执行未覆盖。文件较小（数百行内）时可直接通读判读；较大时用过滤配方：

```bash
# 高计数热点行（计数 ≥ 4 位数的行，阈值可按数据量级调整）
sed -n '/class="source"/,/<\/pre>/p' <src>.gcov.html | sed 's/<[^>]*>//g' \
  | grep -E '^[[:space:]]*[0-9]+[[:space:]]+[0-9]{4,}[[:space:]]*:'

# 未覆盖可执行行（冷路径/死代码候选）
sed -n '/class="source"/,/<\/pre>/p' <src>.gcov.html | sed 's/<[^>]*>//g' \
  | grep -E '^[[:space:]]*[0-9]+[[:space:]]+0[[:space:]]*:'

# 函数调用计数（同目录 <src>.func.html；hit_count = 被调用次数）
grep -oE 'class="coverFn"[^>]*><a[^>]*>[^<]*|class="coverFn(Hi|Med|Lo)"[^>]*>[0-9]+' \
  <src>.func.html | sed 's/.*>//' | paste - -
```

各格式的完整语义与更多配方见 `references/gcov_coverage_guide.md`。

### 3. 判读 — 优化点识别表

| 覆盖率特征 | 性能含义 | 潜在优化 | 下游技能 |
|-----------|---------|---------|---------|
| 高计数循环体，估算迭代 ≥ 16 | 大迭代次数热循环 | 向量化、展开、预取 | `apply-vectorization` / `loop-unrolling` / `prefetch-optimization` |
| 高计数循环体，估算迭代 < 4 | 短迭代循环 | 不宜展开/向量化，考虑循环合并 | `operation-fusion` / `scalar-vector-hybrid` |
| 热函数内大段 0 计数连续区间（特例/错误处理） | 冷路径混在热函数 | 拆分冷热路径、`__attribute__((cold))`、likely/unlikely | `special-case-optimization` / `branch-elimination` |
| 高调用计数的小函数（hit_count 大） | 调用开销累积 | 内联、调用链融合 | `operation-fusion` / `compiler-flag-tuning` |
| 高计数行所在文件覆盖率 100% | 优化可被现有 workload 回归验证 | 优先处理（低风险高确定性） | `verify-optimization` |
| 目标优化文件覆盖率低 / 0 计数 | workload 未触达该代码 | **暂缓优化**，建议先补测试场景 | `analyze-testcase` |
| 热点行与 perf/SPE 热点重叠 | 次数多且耗时高 | 最高优先级优化点 | 与 `analyze-hotspot` / `arm-spe-analysis` 交叉比对 |

循环平均迭代次数按 `references/gcov_coverage_guide.md` 的估算方法手工推算：体首行计数 ÷ 进入次数（循环头上方最近可执行行计数；嵌套循环用头计数 ÷ 进入次数 − 1）。

判读时必须完成两个交叉验证：

1. **次数 × 耗时交叉**：拿热点行与 `analyze-hotspot` / `arm-spe-analysis` 的函数级热点对比，重叠者优先
2. **workload 代表性交叉**：对 0 计数区间，确认生成覆盖率的 workload 是否覆盖相关输入域（错误注入、边界值、长尾查询等），再决定是"死代码候选"还是"测试缺口"

### 4. 桥接与验证

- 画像结论交给 `decide-optimization` 做策略门控；循环迭代估算直接作为向量化/展开的收益输入
- 平台能力判断（SVE/SME/DotProd 可用性）查 `kunpeng_microarch`
- 优化实施后的回归验证由 `verify-optimization` 负责；若用户需要优化后的覆盖率对比，请用户提供新一轮覆盖率 HTML 报告后再分析

## 数据语义与误区（必读）

1. **执行计数 ≠ 耗时** — 一行执行 10⁶ 次的加法可能远不如一行带 cache miss 的访存耗时；禁止仅凭计数下"最热"结论
2. **计数反映单一 workload** — 覆盖率数据来自生成它的那次运行（测试集/基准）；跨 workload 结论需多份数据
3. **插桩二进制不能用于性能对比** — 带 `--coverage` 编译的二进制有额外开销，性能基线须用干净构建
4. **计数可能被累加合并** — 若 lcov 数据经过多次 capture/merge，计数会翻倍；判读前向用户核对数据生成过程
5. **循环迭代次数是估算值** — 分支/嵌套场景存在误差，量级判断可用、精确值不可信
6. **内联与模板** — 头文件/模板代码的计数可能被合并到调用点；函数 hit_count 为调用次数（FNDA 语义），不是行执行次数
7. **分支走向数据不可得** — HTML 报告通常不含逐分支 taken/not-taken；不要伪造分支结论，分支优化证据改由未覆盖行区间与源码形态推断

## 常见失败模式

1. **未发现覆盖率 HTML** — 如实说明并跳过；本技能只分析已有报告，不代为生成
2. **多个覆盖率目录** — 清点后选文件数最多者并向用户确认，避免把多份报告混在一起判读
3. **lcov < 1.10 的老式 HTML** — 源视图为旧表格式，提取配方不适用；尝试直接读取文件判读，仍无法解析时如实说明格式不兼容
4. **计数异常巨大** — 多为累加合并或模板实例化；核对数据来源后再判读
