## 案例 1（A+B 类，全链模板）：guest console 逐字节模拟串口

**公开记录**：[CubeSandbox PR #21](https://gitcode.com/boostkit/CubeSandbox/pull/21)
（perf(shim): use virtio-console as the aarch64 guest console，已合入 v0.7.1）。

### 现象与差异

aarch64 上沙箱创建比 x86_64 慢数倍，单实例热点集中在 guest 内 create/start 步骤。
差异：x86_64 guest 默认 `console=hvc0`（virtio-console，批量化、ioeventfd 在 KVM 内
处理），aarch64 默认 `console=ttyAMA0,115200`（模拟 PL011 UART）。guest agent 作为
PID 1 把日志写到 `/dev/console`。

### 证据链

1. **机制成本**（B 类）：模拟 PL011 每输出一字节 = 1 次 flag 寄存器读 + 1 次数据寄存器
   写，都是用户态 exit，且 VMM 在 vCPU 线程上同步写冲——单次 create 实测 1651 字节
   agent 日志 × 2 = ~3300 次 exit，全部落在 agent 的同步请求路径上；
2. **考古**：aarch64 的 ttyAMA0 选择随移植带入，无 stated reason；guest 内核已启用
   `CONFIG_VIRTIO_CONSOLE`/`CONFIG_HVC_DRIVER`，VMM 两架构都创建 virtio-console
   设备——移植侧"顺手"选了纯模拟路径；
3. **量化**（c1，KVM debugfs + `kvm:kvm_mmio`）：`mmio_exit_user` 1811 → 2，PL011
   数据寄存器写 1651 → 0，vCPU 线程 `write(1)` 1651 → 0，console TX notify（KVM 内）
   0 → 26；create 延迟 58.5 → 51.7 ms；
4. **A/B**（c100×n100，900/900 成功，交错 3 轮取中位）：轮总时延 307.2 → 188.3 ms
   （**-38.7%**），create p50 220.4 → 137.0 ms，guest 内 start 步骤 ~23 → ~4 ms；
5. **防回归**：新增单测断言默认 cmdline 恰好一个 `console=` 且为 `hvc0`，防止 UART
   再次静默成为 `/dev/console`。

### 教训

- 输出字节数是放大器：模拟串口路径上"一行日志"就是几十次 exit，日志量与成本线性相关；
- 修复不是删功能而是**对齐成熟机制**：early boot 输出仍走已有 earlycon，设备模型与
   快照布局零改动，单文件 diff；
- 改 cmdline 只影响新构建模板，老模板继续可恢复——对齐改造可以做到零迁移成本。

## 案例 2（A 类，默认值漂移）：RCU 模式开关的 100 倍劣化

### 现象与差异

某基于 Linux 6.x 的定制内核上，虚拟机恢复路径比同源 vanilla 内核慢两个数量级
（单 VM 恢复 ~20 ms → ~2 s），无 IO 无 CPU 占用、纯等待。

### 证据链

1. **差异定位**（A 类默认值）：定制内核 `rcu_normal` 默认置 1，vanilla 默认 0——
   一次"无人复核"的默认值漂移；
2. **机制成本**：`rcu_normal=1` 使 `synchronize_srcu_expedited()` 降级为普通模式，
   单次宽限期从 ~30 µs 退化为 10-12 ms（对照机 kprobe 实测）；
3. **量化**：VM 恢复要注册数十个 KVM ioeventfd，每个注册 2 次宽限期 × 24 ms ≈
   累积 1.9 s——最小复现器（裸调 `KVM_IOEVENTFD` 的 50 行 C 程序）把"全链路 2 s"
   压成"单 ioctl 24 ms"后根因即现形；
4. **修复**：运行时 `sysctl` 置回 0（`/sys/kernel/rcu_normal`），单 ioctl 24 ms → 0 ms。

### 教训

- 默认值审计不只发生在 x86 vs arm 之间，**定制内核/发行版 vs 上游 vanilla** 是同等
  高发的差异面：排查系统性劣化时先 diff 默认值配置；
- "排除一切用户态后，优先翻内核运行时开关"——`rcu_*`/`sched_*` 这类开关一个就能
  造成 10 倍全局劣化；
- 最小复现器是把多因素问题压成单变量的最短路径。

## 案例 3（C 类，能力假设冲突）：预读大 folio 与并发随机访问

### 现象与差异

多 vCPU 并发恢复快照场景出现均匀的耗时抬高（非阶梯排队），单实例完全正常——
共享资源争用形态。

### 证据链

1. **差异/假设**：内核默认 folio 预读把映射文件的小页访问聚合为大 folio——隐含
   假设"预读总是好的"；该假设在"多线程共享同一映射、访问模式随机"的场景失效：
2. **机制成本**：大 folio 单一 refcount 缓存行被多个 vCPU 线程并发命中，缓存行乒乓，
   页引用操作串行化；
3. **量化**：并发/单实例耗时比异常，锁与缓存行争用证据在 `/proc/<pid>/task/*/stat`
   的内核时间分布中可见；
4. **修复**：对相应映射 `MADV_RANDOM` 关闭预读，恢复 4K folio 粒度，争用消失。

### 教训

- C 类差异常以"合理的通用默认值 + 特定负载"形式出现：默认值本身没有 arch 差异，
  但两侧负载形态差异（并发度/访问模式）使其成本只在一侧显形；
- 能力假设审计要问的是"这个默认假设在当前负载下成立吗"，而不只是"两架构一样吗"。

## 案例 4（负样本）：无害死参数

### 现象与差异

x86 的 `earlyprintk=ttyS0` 启动参数被原样带到 aarch64 内核 cmdline。aarch64 上
该参数无对应实现（arm 用 earlycon + 平台地址），属于**死参数**：无功能、无成本、
无风险。

### 判定

- 考古：随 x86 配置模板复制而来，无理由；
- 量化：冷路径（仅启动早期）、零成本——**门槛二不通过**，判 `observed` 观察项，
  不报优化点。

### 教训

- 不是所有无理由差异都值得修：死参数修了零收益；
- 但它是**移植未做架构审查的信号**——同一批复制粘贴的改动里往往藏着真正的 A/B 类
  问题（见案例 1 的 console），值得作为审计线索追查相邻差异。
