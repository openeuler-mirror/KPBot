# 从内核收益查到业务收益

检查业务是否实际使用候选、内核与完整操作是否变快，再结合阶段占比解释完整查询或请求的收益。

## 输入

```text
优化实现    原版、候选、开关、适用条件、源码和构建身份
业务入口    命令、SQL或请求负载，完整结果的完成条件
数据        内容、布局、类型、块大小、分布和正确性参照
环境        机器、加载库、线程池、CPU/NUMA、缓存和频率设置
已有证据    微基准、调用审计、阶段记录和业务样本
```

按用户请求选择方案设计、采集或已有结果分析。缺少目标环境或记录时，指出哪些结论暂时无法验证，按当前授权范围补充。

## 执行步骤

### 1. 从真实业务入口核对调用链

读取当前查询或服务的实际路径，找到原版与候选的分派点。核对业务中的类型、块大小、输入分布、线程和并发是否与微基准一致。

记录实际加载的扩展或库、二进制摘要、源码和编译选项。尽量在同一个构建中用开关比较，使用不同构建时写明差异并核对计时边界。

冻结数据、SQL 或请求、线程、亲和性和缓存策略。为了触发某种编码而改变行序或分布时，把新布局列为独立场景，算法比较在同一布局内部进行。

### 2. 审计候选是否真正执行

独立运行正确性校验和调用计数。检查启用候选时实际进入内核，关闭时使用原版，参数不适用时按约定回退。记录调用次数、逻辑值数和实际内核工作量。

编解码器包装函数被调用，不能证明内部已经使用 SIMD。临时计数放在能够确认实际实现的位置。正式性能采集关闭审计计数，并核对当前程序与审计时的身份。

### 3. 选择算法模式和比较

两个可独立启用的优化可以使用以下四模式，BP/RLE 是具体实例。

```text
模式        BP实现    RLE实现
original    原版      原版
bp          候选      原版
rle         原版      候选
both        候选      候选
```

```text
比较                 要回答的问题
original → rle       单独开启RLE的影响
original → bp        单独开启BP的影响
original → both      两项优化共同使用的总体影响
bp → both            已开启BP后，再开启RLE的额外收益
```

RLE 内部可能调用 BP，因此 bp 模式也可能改变 RLE 完整时间。两项优化可能相互作用，both 的收益使用实际测量，不能将两项独立加速比相乘代替。

单项优化只需要原版和候选两种模式，按当前问题选比较即可。

### 4. 定义阶段边界

通常记录业务总时间、外层完整操作和内部目标内核。以 BP/RLE 为例，先把各层包含的工作列清楚。

```text
整条查询        SQL规划、扫描读取、解码、过滤聚合排序、取回结果
BP完整解码      头部检查、类型视图、输出分配、解包、截断及结果构造
BP解包          选择并执行原版或NEON解包
RLE完整解码     子编码解码、检查、输出分配、展开及结果构造
RLE展开         展开入口的检查、输出分配、Rust或SVE展开及结果构造
合计完整解码    两类完整解码区间去掉嵌套重复后的时间
```

按实际代码放置计时器，并记录返回后的释放是否计入。内层结束更新计数会增加外层开销，不能把名称写成比实际范围更窄的“纯 C 内核”。

### 5. 建立独立统计会话

串行诊断每次只执行目标请求，等待前一个会话及其子任务结束，再初始化本次计数。

并发诊断为每个请求分配独立 session_id 和统计存储，子任务显式继承归属。结束一个请求只停止该会话，不能清零或关闭其他请求使用的全局计数。

异常、取消、跨线程和跨 await 的任务也要维持会话归属。停止后检查未完成区间及晚到记录，快照保持不可变。线程局部嵌套深度适用于同步同线程调用，不能直接追踪跨线程迁移。

### 6. 处理父子嵌套和并行重叠

以下计时关系需要保留。

```text
RLE完整解码
    子编码解码
        BP完整解码
            BP解包
    RLE展开
```

BP 子调用已经包含在 RLE 完整时间中。各阶段分别统计，合计可只累计执行上下文最外层的目标调用，或从可比较的起止区间计算并集。

计算“合计完整解码”时，区间并集只选 BP 完整、RLE 完整两类。BP 解包、RLE 展开仍分别统计，不用仅有的内层记录冒充完整解码。某类完整阶段没有记录时，先结合调用审计区分没有调用和漏采，不能自动补零。

例如合成查询 100ms，RLE 完整 12ms，BP 共 5ms，其中 3ms 在 RLE 内，去重合计为 14ms，占查询 14%。

多线程累计墙钟时间可能超过查询时长。即使逐线程消除了嵌套，也不能将相加结果直接解释为串行业务占比。有完整区间时，可以计算活动时间并集；这个比例表示窗口内有目标阶段活动的时间，不等于关键路径贡献。

### 7. 执行统计关闭和开启两组

每种算法模式分别运行两种统计设置，使用同一构建、数据、负载和预热策略。

```text
统计状态    业务总时间    内部阶段时间    主要用途
关闭        记录          未采集          比较业务性能
开启        记录          记录            分析阶段收益及占比
```

在看结果前确定预热、重复次数和运行顺序。各轮调整模式顺序及统计开关先后，减少固定顺序造成的偏差。

BP/RLE 历史场景采用每进程 2 次预热、10 次正式查询、每查询 6 轮，参数按当前任务调整。沿用四模式与两种统计设置时，每查询有 48 个测量进程、480 个正式样本和 96 次预热，进程依次运行。

每个正式样本按下面的边界采集。

```text
创建本次会话，初始化专用计数
    ↓
开始记录业务总时间
    SQL规划、读取及扫描
    每次目标解码或算子调用
        开始完整操作计时
            检查、分配或子编码解码
            开始内层计时
                内层入口工作及原版或候选内核
            结束内层计时并累计
            完成结果构造
        结束完整操作计时并累计
    完成过滤、聚合、排序等业务操作
    等待并取回全部结果
结束记录业务总时间
    ↓
停止本次会话，核对未完成区间
    ↓
读取快照、校验结果、保存样本
```

提交异步任务后立即返回的时刻，通常还不是业务完成时刻。异常路径同样关闭统计，并保留失败样本及原因。

上图展示层次关系，具体边界按第 4 步定义。例如 RLE 展开计时从展开入口开始，包含该入口内的检查和分配；BP 解包计时则围绕解包选择与执行，不能统一缩成一段纯内核时间。

### 8. 检查样本和统计干扰

核对正确性、候选命中、身份、工作量、会话归属和窗口完整性。处理值数不同先查原因；算法确实改变工作量时，在收益解释中说明。

```text
统计开关影响 = 开启统计的业务耗时中位数 / 关闭统计的业务耗时中位数
```

逐模式、逐轮报告。这个比值包含统计成本与运行波动，不能由此推出每次时钟读取的精确开销。

业务总时间受影响小，也不能保证几十纳秒的内层阶段准确。干扰明显时降低采集频率、扩大计时边界或使用适合该问题的采样。不要从所有样本里机械扣除固定开销。

缺少区间、混入其他会话、未完成任务或目标未采到时，先处理数据问题，再给阶段归因。

### 9. 计算阶段、占比和业务加速比

每轮、每模式先对约定次数的累计耗时取中位数。同轮、相同统计状态下比较，时间指标统一用比较前除以比较后。

```text
内核加速比       = 比较前内核累计时间 / 比较后内核累计时间
完整操作加速比   = 比较前完整操作累计时间 / 比较后完整操作累计时间
合计解码加速比   = 比较前去重合计时间 / 比较后去重合计时间
业务加速比       = 比较前关闭统计的业务时间 / 比较后关闭统计的业务时间
```

阶段比值使用统计开启组，业务比值使用关闭组。跨轮可采用预声明的几何平均，同时保留各轮结果及离散程度。

对于有效的串行累计时间，每次样本先算阶段时间除以同次业务时间，再汇总占比。阶段中位数除以业务中位数是另一种统计量。并行样本若采用区间并集，明确标注活动时间比例，不能混成串行贡献。

### 10. 根据数据解释收益

```text
观察结果                          下一步判断
候选未命中                        查分派、类型、布局及加载版本
内核没有稳定收益                  查真实块大小、分布和计时干扰
内核变快，完整操作收益较小        查分配、解析、子调用及封装
完整操作变快，原占比较低          检查整体收益是否符合数量级
占比与阶段收益明显，业务不吻合    查其他阶段变化、并行关系与测量干扰
```

假设原版目标阶段占业务时间 f，阶段加速 s 倍，其他部分耗时相同且没有重叠，可作以下估算。

```text
优化后业务时间 / 原业务时间 = (1 - f) + f/s
业务耗时减少比例           = f × (1 - 1/s)
业务加速比                 = 1 / ((1 - f) + f/s)
```

例如阶段原占 2%，阶段快两倍，业务耗时预计减少 1%，加速约 1.0101 倍。这个估算用于核对数量级，业务实测仍单独报告。

外层减内层的差值可以缩小调查范围，但不能直接命名为尚未单独测量的分配或子编码时间。已有分段仍解释不了表现时，围绕未解释的部分增加分段、火焰图或时间线。

## 输出

- 入口、构建、数据、运行条件、模式和计时边界。
- 正确性及命中审计、调用量和样本有效性。
- 比较前后逐轮的阶段耗时、阶段加速比、业务加速比、有效占比及开关影响。
- 原始记录、汇总方法、失败原因、收益解释和待验证范围。

两个优化的结果可按下列字段列出，每种比较同时保留前后耗时。用户只关心单项时，保留相应字段。

```text
查询    比较    RLE完整加速比    BP完整加速比    去重合计加速比    RLE展开加速比    BP解包加速比    查询加速比
```

## 约束

- 候选未命中时，不把查询波动归因于候选；正确性失败不由性能收益覆盖。
- 算法模式、统计开关和审计计数分别控制，记录实际配置。
- 并发请求使用隔离会话，停止和读取一个会话不能干扰其他请求。
- 父子累计时间不能直接相加，并行累计、区间并集和关键路径贡献不能混用。
- 关闭统计的零值表示未采集；空区间还需区分未命中和漏采。
- 统计成本和极短阶段分辨能力要结合实际测量判断，不机械扣除假定开销。
- 重排行序、线程或构建变化单独记录；局部诊断与完整业务验收分别给结论。

## 脚本工具

由项目采集器生成 session.json，再从本 skill 目录运行。分析脚本只依赖 Python 标准库，配套用例要求 Python 3.9 或更高版本。

```sh
python3 scripts/analyze_session.py session.json > session-summary.json
python3 cases/protocol-contract/run.py
```

用例结果写入 `cases/protocol-contract/results/result.json`。通过 `case.yaml` 执行时，从该 YAML 所在的用例目录运行入口并解析断言路径。

分析工具核对一个已结束会话的起止区间，输出各阶段累计时间、重叠标记和区间并集。它不安装计时器，也不自动汇总多个模式的加速比。

工具对输入的全部阶段求并集，不按阶段名称自动筛选。要得到合计完整解码，另生成只含 BP/RLE 完整区间的分析输入，并保留原始记录。含内外层的总并集只有在确认内层都被对应完整区间包含时，才与完整解码并集相同。

非法输入退出码为 2。有效输入退出码为 0，空区间仍会返回 `no_target_spans`，读取结果时要同时检查状态。输入字段和输出口径见 [会话数据格式](references/stage-measurement.md)。
