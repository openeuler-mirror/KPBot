# 异常诊断手册

## 诊断记录

每轮记录原始观测、假设、区分实验、固定条件、实际结果和下一步。
没有执行的实验标为计划，不写成事实。
先排范围与完整性，再讨论真实瓶颈。

## Bad Speculation 偏高

1. 确认“偏高”相对于哪个同口径对照。
2. 阅读进程和阶段范围，检查框架、初始化和验证。
3. 在同配置另采分支热点，保存事件总量和调用栈。
4. 定位符号与对应 ELF；UNKNOWN 保持未归属。
5. 有分支机制证据后，设计业务正确性和性能对照。

不以 5%、10% 或案例的 13.03% 作为通用错误阈值。
不从热点份额推算“扣除框架后的 Top-down”。

## 窗口过短

区分目标正常提前完成、工具错误、负载崩溃、配置单位错误。
读取实际时长，不使用请求时长替代。
正常完成但不足目标窗口：可增加持续工作量或缩小结论。
崩溃：保留报告用于故障分析，禁止正式 A/B。
窗口完整但含预热：改变边界方案，不只增加重复次数。

## 采集期间崩溃

保存工具和目标日志、信号、构建、配置及可用现场。
用户已授权的情况下设计无采集/附加采集对照。
对照用于定位触发条件，不直接证明工具缺陷。
不同故障指令或寄存器不全时，不合并根因。
不要自动修改业务实现、关闭检查或忽略失败继续算收益。
把最小复现及缺失证据交给故障诊断任务。

## 负值或非有限值

先看原始文本，确认不是解析器丢负号或列错位。
检查指标模型、事件支持与调度情况。
保留 raw、value、status，不裁剪到零。
缩小事件组或单层采集可以是区分实验，不能宣称必然修复。
缺少公式时，不自创归一化修正。

## 参数被忽略

保存具体版本、模式、帮助与警告。
requested 与 effective 分开记。
若参数不影响当前目标，可有依据地说明限制。
若影响目标范围，改用支持模式或明确无法完成该目标。
忽略警告不等于问题已解决。

## 波动与开销

检查是否进入不同阶段、发生线程迁移或竞争负载变化。
记录频率和温度证据，避免用推测补齐。
必要时对比采集开/关的业务指标，评估观察开销。
采集开销的测量也需要正确性与重复性。
若无法隔离，报告可观察范围并降低结论强度。

## 建议格式

采集建议：证据 → 调整变量 → 预期区分结果 → 停止条件。
性能建议：可信机制证据 → 候选动作 → 正确性与业务指标验证。
每项标记已验证、待验证或受限。
已有高值但没有来源证据时，建议进一步定位，不能直接下优化结论。
