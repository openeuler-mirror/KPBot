# 分配路径的取证、建模与验收方法

本文是 `allocation-path-optimization` 的方法论依据。它回答：怎么证明成本在分配器、怎么把"申请字节"算清楚、改完之后怎么保证所有权与生命周期没被破坏。

## 一、先区分两种成本

分配相关的开销有两种，处理方式完全不同：

| 形态 | 特征 | 主判据 | 对应配方 |
|---|---|---|---|
| 字节型 | 每操作的申请字节数大，堆增长快，内核回收频繁 | 每操作申请字节、峰值活字节、brk/trim 次数 | 精确申请、尺寸类审计 |
| 次数型 | 每操作申请/释放次数多，对象很小 | 每操作分配次数、分配延迟占比 | 分配抖动合并、成对释放 |

两者经常同时存在。测量时要把它们分开：`alloc_probe` 同时给出 `bytes`、`calls`、`peak_live`，三个数一起看才知道该走哪条路。只看 wall-clock 无法区分。

## 二、通用分配 helper 的"下限"是常见根因

库为了抑制元数据开销，常给通用分配 helper 设置一个最小尺寸：小于该尺寸的请求一律提升到最小尺寸。这个策略对**拥有内部数据区**的对象是合理的——它保证数据区占比不至于太低。但对**仅承载元数据**的对象，它会造成纯粹的浪费：

- 对象结构体 + 少量元数据只需要几十字节；
- 数据指针在创建后立即被外部地址覆盖，内部数据区永远不会被使用；
- 于是每次申请都按最小尺寸付费，而实际用量只有几十分之一。

识别方法是看三件事：通用 helper 是否有下限；目标对象的数据字段是否在创建后立即被覆盖；该对象是否从不以内部数据区作为数据源。三者同时成立时，`exact_size_allocation` 成立，且应当在**调用点**做精确申请，而不是改通用 helper 的下限——通用 helper 的下限对其余对象仍然正确。

这一点是配方边界，也是最容易犯的错误：把通用下限改小会影响所有对象，收益与风险都不成比例。

## 三、字节数的建模

`alloc_size_audit.py` 把通胀拆成两层：

1. **下限层**：`effective_request = max(requested, floor)`；
2. **尺寸类层**：分配器把 `effective_request` 向上取整到 size class。

两层分开报，才能说清"是库的策略浪费"还是"分配器的取整浪费"。前者可以通过源码修掉，后者只能通过减少次数或改分配器缓解。

建模结果必须与实测交叉验证。判据是 `model_error`：模型预测的每操作字节与 `alloc_probe` 实测的偏差。偏差显著时要先解释偏差（例如存在未被采样的第二分配点），而不是直接采信模型。

一个有用的换算：峰值活字节 ≈ 每批次对象数 × 每对象实际占用。它决定了工作集是否超出缓存、以及堆顶能否被 trim 收回。峰值下降通常比每操作字节下降更能改善 wall-clock，因为内核回收的成本与页数相关。

## 四、因果链验证

分配类改动最容易归因错误，因为"改了之后变快"可能来自其它因素（例如顺带减少了调用次数）。验证手段是对照实验：

- **关闭 trim**：设 `MALLOC_TRIM_THRESHOLD_=-1`，若默认与对照的差值正好等于推断的回收成本，则因果链成立；差值远小于推断时，说明瓶颈不在回收。
- **限制 arena**：`MALLOC_ARENA_MAX=1` 用来区分多 arena 的页表/锁开销。
- **替换分配器**：在 jemalloc/tcmalloc 下重测，若收益随分配器消失，说明收益来自特定分配器的回收策略，需要在报告里写明依赖。

这些手段只用于**诊断**。交付不能是"设一个环境变量"——那属于应用调优，不是源码优化，而且不可移植。

## 五、所有权与生命周期不变量

分配类改动直接触碰所有权，必须逐条核对：

- 谁申请、谁释放，是否发生变化；
- 自定义分配器（库允许替换 malloc/free）下，申请与释放是否仍同源成对；
- 对象是否可能在批次结束后被引用（延迟释放、悬垂引用、引用计数延续）；
- 跨线程释放是否仍合法（不得引入 thread-local）；
- 申请失败时的错误传播与清理路径是否保持（尤其不得调用用户 cleanup 回调）；
- 结构体布局与对外 ABI 是否变化；
- 共享对象的 refcnt 增减点与最终释放时机是否不变。

这些条目就是输出里的 `invariants_checked`。任何一条无法确认，返回 `success=false`。

## 六、验收口径

分配类改动的验收分三层，缺一层都不能算完成：

1. **字节层**：每操作申请字节、峰值活字节 —— 确定性，可作门禁；
2. **内核层**：brk/trim 次数、minor page fault 数 —— 半确定性，能直接印证因果链；
3. **时间层**：wall-clock 或 CPU 时间的 A/B —— 噪声最大，只作方向性参考。

推荐的主判据是"每操作申请字节下降倍数"与"峰值活字节下降倍数"，因为它们在相同输入下完全可复现。时间收益作为结果报告，但要注明测量环境与噪声水平。

回归门禁：其它同类接口不得劣化超过 1%；分配次数不得上升（精确申请会略微增加次数上限，但不应改变数量级）。

## 七、拒绝台账

以下情况必须记录并拒绝，而不是"先改再看"：

- 只有"看起来在分配"的推断，没有实测字节或次数；
- 需要全局池、线程本地缓存或延迟释放；
- 会破坏自定义分配器的成对约束；
- 需要改公开 ABI 或对象布局；
- 收益来自拉长对象寿命（缓存化 / 泄漏）；
- 对照实验显示成本与申请字节无关。

记录格式与机制类相同：假设、实测数字、拒绝原因。
