# 验收门：正确性 + 性能

一个函数只有在**两道门都过**之后才允许写回项目。顺序不能换：正确性不过就没有
讨论性能的资格；性能不过就不该留下这份改动。

## 一、正确性

### 参考实现从哪来

优化前先把原函数体完整复制到 `process/<fn>/ref/`，文件名 `<原文件>.<fn>.ref.c`，
函数重命名为 `<fn>_ref`，签名保持不变。项目里的原函数随后被替换成 SIMD 版本。

这样做的原因：

- 项目最终**只保留**验证过的 SIMD 代码，不保留标量版本当"后路"——后路会让代码库
  里长期存在两份逐元素等价的实现，维护成本翻倍。
- 但 A/B 必须有一份"优化前长什么样"的权威副本，否则几轮迭代后没人说得清基线是
  什么。这份副本放在结果目录里，不进项目。

如果原函数是 `static` 且被同文件多处调用，`ref/` 里要连带它依赖的静态函数一起拷
（只拷真正用到的），并在 `record.json` 的 `ref_notes` 里写明。

### 用例矩阵

每条都要跑，不能只跑"典型长度"：

| 用例 | 为什么 |
| --- | --- |
| `n = 0` | 谓词构造、空指针早退、`svwhilelt` 边界 |
| `n = 1` | 单元素路径 |
| `n = VL-1` / `VL` / `VL+1` | 尾部逻辑的全部边界 |
| `n` 为非整数倍的大值（如 4095） | 尾部与主体衔接 |
| 非对齐输入指针（`+1` 元素偏移） | 对齐优化是否越界 |
| 极值数据：`0x00/0x7F/0x80/0xFF`、`INT32_MIN/MAX` | 扩宽、饱和、舍入、符号位 |
| 真实的项目数据（若有） | 合成数据覆盖不到的分支 |

有样本文件就用样本（例如编码器的 YUV 源），截取前若干帧/若干行即可；没有就用确定性
伪随机（固定种子），保证可复现。

### 判定方式

**逐位比较**（`memcmp`），不要用容差。浮点只有在归约顺序必须改变时才允许容差，
此时必须在 `record.json` 里写清最大绝对/相对误差和理由，并在最终报告里标为
"非位精确"。

目录模式（`--ref out/ref/ --simd out/simd/`）要求两侧文件集合完全一致：任何只在
一侧存在的输出文件都会让 `compare_outputs.py` 返回 `file_set_mismatch` 并失败。
缺一侧说明那条用例根本没参与比较——"没比过"不能被记成"比过且相同"。

不一致时按这个顺序排查，不要一上来就改算法：

1. **运行时 VL 是不是 256**（`cntb`，不要用被常量折叠的 `svcntb`）。
2. **基线是不是真的跑了**（LTO 把重复调用合并掉是常见情况，见 `assets/bench/README.md`）。
3. **非对齐行距是不是真的测到了**。裸机上如果没建 MMU 恒等映射，只要行距不是 16 的
   倍数，编译器生成的 `str q0` 就会吃对齐异常，看起来像算法错。
4. 输入缓冲区有没有被上一条用例污染（每次都重新初始化）。
5. `_x` 系列的未定义 lane 有没有被读到。
6. 扩宽/窄化的操作数类型对不对。
7. 尾部谓词的 `n` 传的是元素数还是字节数。

前四条属于夹具问题，占了实际调试时间的大多数。先排除它们，再怀疑算法。

## 二、性能

### 基线是什么

**原始实现 + 项目实际编译参数**，不是 `-O0`、不是"关掉向量化的版本"。

这么定的理由：GCC 在 `-O3` 下已经会自动向量化一部分简单循环。如果基线用 `-O0`，
几乎任何手写 intrinsic 都能"加速 8 倍"，但那不是真实收益——项目本来就不是这么编的。
真实的问题是"我手写的版本，比编译器已经做的更好吗"。

如果发现 GCC 已经自动向量化且手写版本没有优势，正确答案是**放弃这个函数并记录
原因**，而不是换一个更弱的基线把数字做漂亮。

### 测量协议

同一台机器、同一个二进制、交替执行：

```
A B B A A B B A ...   至少 5 轮
```

交替的理由：机器温度、其他进程、频率状态都会漂移，连续跑 A 再连续跑 B 会把漂移
算进差值里。

取**中位数**而不是平均值（异常值影响更小），同时记录最小值和离散度。

两种计时口径，由用户在第二问里选定：

| 口径 | 对应验证方式 | 特性 |
| --- | --- | --- |
| QEMU `-icount shift=0` | `verify_method: qemu` | 按访客指令数推进，完全可复现，实质是动态指令数 |
| 墙钟（`clock_gettime` / `perf stat`） | `verify_method: native` | 含微架构效应，有抖动，需要多轮 |

**两种口径的数字不能放在同一张表里比。** 换验证方式就要重跑性能门，并在报告里写清
这是新口径的结果；把"指令数少 15%"和"墙钟快 15%"当成同一件事，是这类优化最容易
被误读的地方。

`-icount` 下三次重跑数字完全相同，一次就够；墙钟下必须多轮并看区间。

### 门控

```
speedup = median(ref_ns) / median(simd_ns)
```

- **通过**：`speedup >= 1.05`。
- **墙钟口径附加条件**：A、B 两组的中位数区间不重叠（或重叠但加速比 >= 1.10）。
  重叠说明抖动比收益大，不能下"更快"的结论。
- **未通过**：`speedup < 1.05`。此时不允许写回，回到手法选择重做。

1.05 不是随便定的：低于 5% 的差异在真实负载里会被访存、调度、缓存效应淹没，留下
一份更难维护的代码换不到可感知的收益，不划算。

`run_ab_bench.py` 会强制执行上面的条件和样本量要求：

- 有效轮数下限默认 `min(reps, max(2, ceil(reps/2)))`，可用 `--min-rounds` 覆盖；
  不足时给 `verdict: insufficient_measurements` 并以退出码 3 结束。
- 墙钟口径（`--method wall`，或 `auto` 下各轮离散度超过 0.1%）要求 A/B 的
  `[min, max]` 区间不重叠，否则加速比必须 >= 1.10 才算 `faster`。
- 任何一轮失败（超时、崩溃、没有 `TIME` 行、VL 不匹配）都不给通过结论。

### 失败了怎么办

同一函数最多试 **2 种不同手法**（例如先试谓词单循环，再试去交织 + 宽运算）。仍然
不过就：

1. 恢复项目里的原函数（用 `process/<fn>/ref/` 的内容）。
2. 在 `record.json` 里把 `status` 记为 `rejected`，写清 `reject_reason` 和两次尝试的
   实测数字。
3. 在自动模式下继续下一个函数；在指定模式下把结论交给用户决定。

失败的记录同样有价值：它回答了"这个函数不值得向量化"，避免下一轮重复投入。

### 必须记录的数字

```json
{
  "performance": {
    "harness": "bare-metal-qemu",
    "timer": "cntvct_el0",
    "deterministic": true,
    "rounds": 5,
    "ref_ns": 230471,
    "simd_ns": 230021,
    "speedup": 1.0020,
    "ref_min_ns": 230471,
    "simd_min_ns": 230021,
    "verdict": "not_faster",
    "command": "make -C ... run"
  }
}
```

缺 `command` 的记录不可复核，等于没测。

## 三、写回与回滚

- 只有 `correctness.verdict == "pass"` 且 `performance.verdict == "faster"` 的函数才
  写回项目。
- 写回后在项目里重新编译一次（用项目自己的构建方式），确认没有引入编译错误/未定义
  符号。夹具能过但项目编不过，通常是头文件、宏或 `static` 的作用域问题。
- 同一函数连续两次写回失败，直接回滚并在报告里标 `blocked`，不要继续试探。

## 四、什么情况下算"未验证"

诚实分级，不要合并成"完成"：

| 状态 | 含义 |
| --- | --- |
| `verified` | 夹具跑过、位精确、speedup >= 1.05、项目能编译、已写回 |
| `validated` | 两道门都通过，但按用户要求没写回（验证性运行 / 只读参考检出） |
| `correct_only` | 位精确但性能未提升或未达标 |
| `rejected` | 试过、失败、已回滚 |
| `unverified` | 没有可用的运行环境（缺 qemu/缺工具链/缺数据），只做了静态改写 |

`unverified` 的产物**不写回项目**，只放在 `process/<fn>/proposed/` 里，并在最终报告
里单独列出，说明缺什么才能验收。
