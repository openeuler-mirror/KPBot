# 读路径扩展曲线

> 只做测量与容量判定，**不实施**多进程改造；实施见 `agent-memory-read-scaling`。

## 步骤

1. 固定负载与核预算，按 1 / 2 / 4 / … / N 副本各跑一轮，记录：phase 时间、吞吐（q/s）、
   单核 CPU% = `(user+sys)/wall`、峰值 RSS、连接重试次数。
2. 画曲线：吞吐是否线性、单副本 CPU% 是否已达 100%、重试是否随副本数上升。
3. 定容量模型：实测每副本约吃掉 1 个核，加上服务端开销后 **容量 ≈ 核数 / 1.45**
   （固定预算下 5 副本达到 3.08×）。
4. 判断拐点：副本继续加时吞吐反降、重试激增，说明线程饿死或服务端饱和，应止损。

## 解读

| 曲线形态 | 结论 |
|---|---|
| 线性上升且单副本 < 100% | 还有余量，可继续加副本或转服务端 |
| 单副本 100%、吞吐平 | 客户端单核瓶颈，先做载荷/解码 |
| 吞吐反降 + 重试上升 | 已过拐点，减副本或先解决服务端 |
| 服务端 CPU 先满 | 服务端瓶颈，转 `graph-store-readpath-patch` |

## 输出

- 扩展曲线原始表
- 容量模型（副本数 ↔ 核预算 ↔ 吞吐）
- 下一阶段建议（多进程 / 服务端 / 先削载荷）

## 注意

- 副本数与服务端核预算必须一起规划，否则"加副本"只是在制造重试。
- 内存按副本数预留：每副本常驻内存随客户端缓存与索引规模增长。
