# 差异分类：四层误差栈的判定

## 总判据（D-1）

先问一句：**两平台的代码实现是否相同？**
- 不同 → 先对齐实现，别急着调选项。
- 相同 → 差异只能来自 编译器（L2）/ 库（L3）/ 求和顺序（L4）/ 架构语义（L3）。

同机换编译选项也会变结果（D-1b）：「同一台机器」不等于「结果必然一致」。

## 架构语义差异（D-2 / D-3）

- x86 的 x87 单元使用 **80 位扩展格式**（64 位有效位 + 15 位指数 + 1 位符号），精度控制字可选
  **24 / 53 / 64 位有效精度**三档；ARM/鲲鹏没有这条路径。没有所谓「40 位扩展精度」——
  见到 40 位请当作记录错误。
  对侧一旦走到这条路径（典型是数学库里的 `pow`/`exp` 内部用 x87 80 位算再存回 double），结果必然不同。
  **先核实是否真的走了 x87**：反汇编或接口扫描确认调用路径（SSE2/AVX 路径是 64 位标量，不会产生该差异），
  确认后再谈兜底——在目标侧用多精度库（如 MPFR）模拟，或改写算法避开。凭「x86 就是 80 位」直接归因，
  会把库实现差异误判为架构语义差异。
- **FTZ/DAZ**：非规格化数的处理**由运行时浮点控制状态决定**（x86 看 `MXCSR` 的 FTZ/DAZ 位，ARM 看 `FPCR` 的 FZ/FZ16 位），
  不是"硬件固定行为"。同一台机器上，编译器 `-ffast-math`/`-MflushZ` 之类的开关、运行时 `_MM_SET_FLUSH_ZERO_MODE`
  调用都会改变它。典型差异不是数值误差，而是**运算顺序**：

```c
float a = 1.09628081709e-33f, b = 1.07225660031e-05f;
float c = a * b;
```

| 平台 | 结果 | 过程 |
|---|---|---|
| ARM/鲲鹏 | `0` | 相乘得非规格化数 → 先 FTZ 归零 → 再舍入，仍为 0 |
| x86 | `1.17549435082e-38` | 相乘 → 先舍入到 `0x800000` → 再 FTZ，得 `0x800000` |

上面两个数值以**两端默认控制状态**（x86：FTZ/DAZ 关闭；鲲鹏：FZ 开启）为前提，换模式后结果会变。

判据与排查顺序：
1. 先记录两端的浮点控制状态（`MXCSR`/`FPCR` 值与相关编译开关），并**对齐模式**后复测。
2. 对齐后仍有差异，才是架构语义差异；再按上面两条处理（不要在模式未对齐时就宣布"接受误差"或去改算法）。
3. 这类差异只出现在极小值区间，别试图用精度选项消掉；要门就一直接受，要么在算法层归一化/加下限。

## 编译器变换（D-5）

- 版本差异：同一厂商不同版本的浮点处理不同，快速数学模式下关键指标会飘。
- 优化级别：O0 关掉全部优化，与 O3 结果差异巨大；比较必须同级。
- 浮点模型：`precise` 与 `fast` 是两个世界；`fast` 允许重结合、允许假设无 inf/NaN。
- 已知缺陷：ICC 在 `-fp-model precise -O3` 下对循环内顺序求和做重结合，与 `precise` 语义冲突（细节与受影响文件见编译器章）。

## 库实现（D-6）

- 同一函数不同实现差在末几位是常态：厂商数学库（按对侧精度做兼容）、系统 libm、开源 SLEEF 各有一套。
- 判断手段：扫二进制里的数学库接口引用（工具章 G-4），先确认「程序到底调了哪些」。
- 处理优先级：换到对侧兼容库 > 软浮点补偿 > 改写算法。

## 求和顺序（D-4 / D-7）

- 浮点加法不满足结合律：归约顺序变了，末位就变。Allreduce 是主战场。
- **进程数/线程数变化**会改网格切分与归约树形，汇总结果自然不同——这类差异不是 bug，但必须在验收单里说明「规模也变了」。

## 应用代码（D-8）

- 未定义行为：数组越界、值域越界、依赖未初始化内存、依赖 FMA 收缩后的中间精度。
- 症状：`-O0` 与 `-O3` 结果不同；换编译器才暴露；换优化等级才暴露。

## 一分钟决策树

```
结果不一致
├─ 两平台代码/配置相同？ ── 否 → 对齐实现（指纹比对）
└─ 是
   ├─ 库版本/环境/并行规模已固定，且 O0/O1 下仍不一致？ ── 否 → 编译器层（选项逐项加回）
   ├─ 单线程一致？ ── 否 → 库/架构层（接口扫描、扩展精度路径）
   ├─ 单进程一致？ ── 否 → 线程归约顺序
   └─ 多进程不一致？ → 归约算法/网格切分（并行章）
```
