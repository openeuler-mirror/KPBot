# 交付验证细则（L4-L6）— kptools-tpsplit-optimization-verify

承接 SKILL.md 的 L4-L6 总览表，展开每层的执行内容、通过标准与失败处理。前置：集群已拉起、L0-L3 拉起验证已过、网关已切流（由 `kptools-tpsplit-optimization（配套 PR #442 交付）` 完成并写入部署指南）；本 skill 只读验证，逐层执行不过不进下一层。

## L4 功能测试

- **正确性**：固定 prompt 的 completion 输出合理（不是乱码/截断）——与旧集群同 prompt 对比行为一致。**前置：部署交接中须归档脱敏固定 prompt + 生成参数（temperature/top_p/seed 等）+ 旧集群的预期响应（或解析后的行为摘要）**；仅归档性能数据而缺少行为基准时，正确性项标「未验证（缺旧集群响应基线）」，不硬比
- **边界**：`--max-model-len` 是**输入+输出 token 总预算**——按目标 tokenizer 计算模板展开后的输入长度、显式指定输出预算（如 max_tokens），使**输入+输出 ≤ max-model-len**；分开验证两例：① 总长在上限内 → 应正常出 token；② 总长越界 → 应被服务**正常拒绝**（越界拒绝 ≠ 容量故障）；仅将输入逼近上限而沿用默认输出预算、请求因总长越界被正常拒绝却被误判为容量故障——禁止此口径。并发压到 `--max-num-seqs` 确认不拒服务
- **解析器**：tool-call 与 reasoning 各发一例（旧集群用什么 parser 就测什么），确认行为与旧集群一致——**同样需要归档旧集群的同 parser 行为基准**（脱敏响应或行为摘要），缺失时标「未验证（缺旧集群 parser 行为基线）」
- 通过标准：三项全过；任一失败记录现象与参数，转 deploy（容量/参数复核），议后重新 L4

## L5 性能对比

- **对比对象**：deploy 停服前归档的旧基线（含负载/并发/计时口径：数据集、请求长度分布、并发数、压测时长、预热策略、统计窗口），从部署指南归档读取；**同口径**测新集群（同数据集、同并发、同时长、同预热、同统计窗口）
- **指标**：Prefill 吞吐、TTFT、**P-D KV 传输带宽**——带宽须指定传输侧的计数器/日志来源（Mooncake master 统计、引擎日志中的 KV 传输字节/耗时、或 /proc 级 RDMA 计数器）与单位、采样窗口；**客户端压测只记录请求与首 token 时间时，P-D 链路实际传输字节数与用时缺失、带宽不可算**——此情形将带宽标「未测（缺传输侧证据）」，不用客户端时间硬凑
- ⚠️ **历史压测数据不能直接沿用**：TP8 与 TP32 的负载模型不同；只有停服前按当时口径重采的那份基线可用。无归档基线时降级为「现状实测、不判定达标」，向用户说明，不硬凑对比
- **达标判定**：与用户事前确认的达标线（或基线的等值/上浮比例）比较；不达标时输出两种走向供用户决策——调参（候选项：max-num-batched-tokens 等，转 deploy 评估与执行）或回滚（转 deploy，按部署指南回滚章节）
- 结果呈现：新旧集群同口径指标表（含口径说明），写入验证报告 L5 章节

## L6 稳定性观察

- **窗口**：建议 ≥24h 或用户指定窗口；被动观察，不主动发压测流量
- **观察项**：KV 报错率、偶发 NPU 错误、DP 组掉员、实例重启
- **前置：核对观察分母的有效性**——窗口内**无推理流量或某实例日志中断时，"未查到致命事件"可能是无事件也可能是无数据**：先核对窗口内的请求量（proxy 日志/网关统计）、KV 传输量（master/engine 日志的字节计数）、各实例日志时间戳覆盖是否连续；分母为零或日志中断时，对应观察项标「未验证（无有效分母/覆盖中断）」，建议延长被动观察或补流量
- **已知环境偏斜列入观察**：mooncake_master 与引擎跨 python/运行时版本等环境差异——历史能跑通不代表升级后能跑通；此类异常转 deploy 回归 KV 链路（L3 判据在 deploy 侧维护）
- 通过标准：窗口内有有效分母且无致命事件、偶发事件可解释且经用户接受，才算交付完成；异常事件逐条记录（时间、现象、影响的实例）；分母无效/证据不足时**不判定交付完成**，标「未验证」并延长观察

## 失败处理与层级门禁

| 层 | 失败含义 | 处置 |
| --- | --- | --- |
| L4 | 功能/容量/参数问题 | 记录现象与参数 → 转 deploy 复核（max-model-len / max-num-seqs / max-num-batched-tokens）→ 议后重新 L4 |
| L5 | 性能不达标 | 判定 + 调参/回滚两走向 → 与用户共同决策 → 执行转 deploy |
| L6 | 稳定性异常 | 按类型分流：KV/NPU 偶发错误转 deploy 故障排查；环境偏斜类转 deploy 回归 L3；其余继续观察由用户拍板 |

任何一层失败都**不阻塞记录**：已执行层的结果照常写入验证报告，未覆盖层标「未执行」。

## 验证报告结构（固定）

```text
1. 结论（可交付 / 建议调参 / 建议回滚 / 验证未完成·暂不判定 + 一句话依据；
   结论枚举为四态：前三态须有完整证据支撑，「验证未完成·暂不判定」用于——
   缺旧基线/缺行为基准/分母无效/仅执行部分层且其余层未覆盖等证据不足场景，
   并记录缺少的证据及继续验证的条件）
2. 输入与口径（部署指南路径或「输入降级」标注、基线数据来源与口径）
3. L4 结果（正确性 / 边界 / 解析器，逐项；缺基线项标「未验证（原因）」）
4. L5 基线对比表（新旧集群同口径指标 + 达标判定；缺传输侧证据的指标标「未测」）
5. L6 观察记录（窗口、分母有效性核对、异常事件、判定；分母无效标「未验证」）
6. 风险与未测项
```
