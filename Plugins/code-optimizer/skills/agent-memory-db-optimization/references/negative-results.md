# 负结果台账与反模式（negative-results）

> 供 agent-memory-db-optimization 在阶段 4/5 按需 Read：避免重复投入已被证伪的方向，并解释跨配置反转的原因。

"试过但没用"的信息和"有效"同样重要：它能阻止下一个项目重复投入，
也能解释为什么某些数字看起来不涨。

---

## 1. 结构性无效（不是"没调好"）

| 尝试 | 结果 | 根因 | 启示 |
|---|---|---|---|
| 服务端补丁想优化写入 | **±0.1 s（0 收益）** | 四项补丁全在读路径（结果解码/相似度），写入不经过 | 先确认补丁命中的是哪个阶段，再定预期；写路径优化要另找杠杆 |
| 并行化 ingest（多进程/多线程写） | 不可行 | 会话间共享实体，判重 prompt 依赖并发交错顺序 → 缓存键不确定 → 命中率崩塌；上游要求串行写 | 写入阶段先问"这个环节是否让 LLM 参与并行化决策"，如果是，直接放弃并行 |
| 多线程做查询扩展 | 4 线程 ≈ 单线程速度 | GIL + 单事件循环，Python 侧工作全部串行 | 先测"多线程是否有效"再投入；有效的是多进程 |
| 客户端优化前测服务端补丁 | 收益 2~4%（x86_64 p1） | Amdahl：客户端占 84~89% | 服务端结论必须在最优客户端上复测 |

## 2. 跨配置反转（结论依赖并发度/架构）

| 现象 | 数据 | 结论 |
|---|---|---|
| 服务端补丁在鲲鹏几乎无效，在 x86_64 高并发下近似减半 | 鲲鹏 p5 12.96 → 12.05（−7%）；x86_64 p5 15.59 → 8.12（**−48%**） | 不能写"服务端优化收益 3%"；要写"收益随并发度与架构变化，x86_64 p5 是服务端瓶颈" |
| 第 4 个补丁收益为负 | x86_64 3.15 → 3.22 s | 在噪声带内（±0.07 s），不采纳也不否定；记账防重复 |
| 客户端优化后 L2/L3 miss 率上升 | L2D 14.2→26.0%，DRAM 归因 13.6→30.5% | 载荷变小 → 空间局部性变差，属正常迁移；不要据此回滚 |

## 3. 测量陷阱（会让"优化"看起来有效）

| 陷阱 | 表现 | 识别 |
|---|---|---|
| 脏库未清空 | 图 `235/720`、查询 hits 只有 20、时间"变快" | 每次 ingest 后校验 `(225, 492)`；清库后校验 `(0, 0)` |
| `--queries` 未真截断 | 想跑 20 条实际跑满 1986 条 | 打印实际查询数并核对；早期脚本按样本整块截断 |
| 观测工具自身开销 | py-spy + pyinstrument + nmon 同开，负载膨胀 ~66% | 纯计时阶段一律 `--no-profiling` |
| 缓存文件被写脏 | 后续运行 miss 数上升或结果漂移 | 每轮从规范副本恢复；md5 定版 |
| 服务端时间取自 `result_available_after` | 服务端"看起来"只要 0.3 ms | 用 `result_consumed_after`；两者差数倍 |
| 只绑主线程 | JVM 上千线程全机漫游，绑核"没效果" | `taskset -a -pc`；`ps -o psr -L` 抽查线程亲和 |
| 未预热 JVM | 首轮慢 40~80%，被当作基线 | 丢 2 轮完整负载 |
| wall 当判据 | x86_64 p1 wall 掉 25% 而 search 只掉 2% | 加速比只用 phase；wall 只展示 |
| 缓存键不带目标名 | LLM 与 reranker 参数撞车，串结果 | 键包含目标名 |
| 用"fill 来源"推 L3 miss | 数字自洽但与 DRAM 行重复 | 那是最初来源归属；L3 不可测就写"不可测" |

## 4. 平台能力缺失（要如实声明）

| 项 | 实测情况 | 处理 |
|---|---|---|
| x86_64 上 L3 miss 计数 | `l3_lookup_state.*` / `LLC-*` 不可用；PCM 只有来源归属 | 报告写"L3 不可测"，DRAM 用内存控制器归因，不宣称 L3 数字 |
| x86_64 上 L2I（指令 L2） | 统一 L2 缓存，无独立 L2I | 只报 L1I + 每千指令 miss |
| PMC `IC Fetch Miss Ratio` 与硬件计数比 | 0.31 vs 30.7（差 100×） | 弃用该字段，只用 refill/access 口径 |
| 分级事件不可用 | AArch64 的 `L3D_*` 缺失时只剩 DRAM 归因 | 用 `L1D_REFILL` 追最终来源，注明"仅到 DRAM 级" |
| 频率/睿频差异 | 同一 CPU 家族不同频率档位导致绝对值差 | 只比较同机相对收益；跨机比较需标注频率档位 |

## 5. 反模式

1. **先改代码再看数据**：没有"哪一层慢"的定量拆分，任何补丁都有一半概率是负收益。
2. **把单次最好结果当收益**：不丢首轮、不报标准差、不交错 A/B。
3. **只测一种架构/一种并发**：结论会在另一种配置上反转（见上表）。
4. **把配置改变报成代码优化**：绑核、池大小、预热属于"让基线正确"，
   不该算进优化收益，否则复现者按你的配置复现不出你的"收益"。
5. **用语义变化换性能**：候选集变小、字段丢失、rerank 关掉都会"变快"。
   校验和与结果指纹就是防这个的。
6. **交付不含缓存与二进制**：只给源码不给"规范缓存 + 预编译产物"，
   复现者会各自漂移出不同基线，所有对比失效。
