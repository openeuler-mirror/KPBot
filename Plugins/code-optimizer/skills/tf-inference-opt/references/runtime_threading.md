# 运行时层优化（L3）：线程池治理、直通、串行化、调度

> **何时读**：p99 差/吞吐不随核数扩展/上下文切换爆表；接入的算子库自己开线程（OMP）导致线程爆炸；想按 CPU 预算调优并行度；想减少算子间调度开销；容器里跑推理服务。

运行时层的核心认识：**线程问题需要同时检查池配置、任务粒度、阻塞等待与 CPU 预算**。一个典型 TF serving 进程里至少有：RPC 框架 worker 池、TF inter-op 池（算子间）、TF intra-op 池（算子内，Eigen）、可能还有第三方库的 OMP 线程、JIT 编译线程。若缺少统一预算和嵌套并行约束，可能出现超订。

## 1. 线程池直通（pool passthrough）

**问题模型**：若 OMP 运行时不能有效复用/限制并行团队，M 个并发 kernel 各请求 N 路并行可能放大可运行线程数，增加调度与 cache 干扰；是否创建新线程、团队如何复用，以库运行时和实测为准。

**解法**：先确认库是否提供外部池接口。闭源库若不支持，使用其公开的线程上限控制，并与请求并发联合调优；不能假设可以修改库内部运行时。支持时，库定义一个 threadpool 接口（`GetNumThreads / IsInParallel / ParallelFor`），你写一个**适配器把框架 intra-op 池包进去**：

```
class MyLibThreadPool : public MyLib::ThreadpoolIface {
  void ParallelFor(n, cost_per_unit, fn) override {
    framework_pool_->ParallelFor(n, cost_per_unit, fn);   // 直接转发
  }
  bool IsInParallel() override {
    return eigen_iface_->CurrentThreadId() != -1;
  }
};
```

- 每个库算子入口：取 `ctx->device()->tensorflow_cpu_worker_threads()->workers` → 在库调用及所有子任务结束前保持适配器存活（同步调用可栈上构造）→ `ActivateThreadpool(&tp)` → 计算 → 恢复进入前的激活态（RAII 化，嵌套调用不能只清空指针）。
- 库侧用 **thread_local 指针**保存当前激活的池：并行任务的工作线程闭包里**重新 Activate 并在退出时恢复**，把池传播进嵌套并行；同步/异步完成契约必须与适配器寿命匹配。
- **串行回退条件**（缺一不可）：池指针为空 / 已在并行区内（`IsInParallel()`，防嵌套并行死锁）/ 池线程数 ≤ 1 → 直接 `fn(0, n)` 串行执行。
- 构建上把库的线程运行时从 OMP 切到"外部线程池"模式（编译宏选择），OMP 路径保留在源码里但不再是默认。
- **cost 传递**：`ParallelFor` 的 cost_per_unit 由算子按问题规模给出（而不是写死一个大数）——框架调度器据此决定切分与是否内联；估算总成本不足以摊平调度开销的任务可在调用线程执行，省一次唤醒。

## 2. 线程数治理（先确认预算，再扫配置）

**原则：整体并行度受可用 CPU 预算约束，各池不要求数值相等。** RPC worker、请求并发、inter-op、intra-op 与库线程上限控制不同层次；分别记录后联合调优，不把总线程数或各池大小简单等同于可运行计算量。

- **CPU 预算**：读取进程所属 cgroup 及祖先约束；v1 查 quota/period，v2 查 `cpu.max`，同时记录有效 cpuset、进程 affinity、NUMA/SMT 拓扑。quota 是 CPU 时间预算（可为小数或无限制），cpuset 是可运行 CPU 集合；同时受限时以更紧约束为起点，并观察 `cpu.stat` 节流。
- **实际配置**：核查当前分支的显式参数、环境变量、自动探测与池初始化顺序。Session 路径可能由首个 Session 决定共享池，后续 Session 配置未必生效；日志打印各池实际大小、共享关系和库线程上限。RPC 框架的默认值也要按当前版本核实。
- **扫参**：固定模型、batch 与请求并发，先比较小 intra/较大 inter 与较大 intra/小 inter，再围绕赢家扫描库线程上限及 RPC worker。候选取值由可用核数和热点 shape 决定，不要求三处都等于配额；并发档位变化后复测。
- **亲和与观测**：仅在允许的 cpuset 内用 `numactl -C … -m …` 绑定 CPU/内存。记录每池 CPU 时间、上下文切换、节流和 p99；线程命名便于区分 `tf_Compute`、RPC 与库线程。
- **共享池排队**：并发请求的算子各自切成多份任务，可能因等待最慢分块而拉长 p99。独立扫描库线程上限，不能按“上限≈请求并发数”推导最优值。历史案例中从 16 路收至 2 路同时改善吞吐与 p99，但该数值只适用于当时的 shape/batch/并发。

## 3. 算子间调度开销的两个方向

高并发下，"每个就绪算子投一次线程池"的默认调度本身就是开销（任务队列往返、线程唤醒、多 session 共享 inter-op 池时互相抢占）。两个实战方向：

**方向 A：一批就绪算子单闭包串行执行**（重改造）。执行器层把一次触发产生的整批 ready 节点 move 进**单个闭包**提交一次任务，闭包内顺序执行——整批算子在同一线程跑完，消灭 N 次唤醒与队列往返。配套：算子内并行关闭（intra=1），用"算子串行"换"整图不抢池"。适合：单 session 时延敏感、或高并发下多 session 抢 inter-op 池的场景。注意这是执行器级改动，跨版本维护成本高。

**方向 B：显式串行模式下的算子内联**。历史定制通过上下文标志关闭算子内并行，并内联部分调度。仅当任务的同步、重入、控制流及栈深度契约允许时采用；inter-op=1 本身不代表应关闭 intra-op，也不能据此把通用 ThreadPool::Schedule 改成同步调用。需验证异步算子、阻塞操作和取消路径。

**候选取舍**：小 intra/较大 inter 倾向保留算子间并行，较大 intra/小 inter 倾向算子内并行。它们可作为扫参起点；最终取决于图依赖、热点粒度、请求并发和共享池，不能直接分别等同于“吞吐最优”与“时延最优”。

**动态 cost 模型**（配合调度）：执行器维护每个节点的耗时指数衰减估计（`new = ((decay-1)*old + elapsed) / decay`），据此决定节点是否"expensive"（走池）还是内联；让自定义算子把真实 cost 上报给框架（而不是让框架猜）。

## 4. 其他运行时项

- **内存归还**：推理服务启动期（模型加载/JIT 编译完）主动调分配器的 `ReleaseFreeMemory`（tcmalloc/jemalloc 都有等价接口），把加载期峰值还给 OS——容器 RSS 指标好看很多。
- **模型加载不抢推理池**：先在 Session 配置中建立专用 inter-op 池，再通过 RunOptions 选择其索引（索引 0 本身不代表新建或隔离池），避免大模型加载把在线推理线程占满。
- **XLA/子图执行**：先检查当前分支是否额外向 host 池投递任务；若考虑内联，遵守上述同步、重入和取消契约，不能仅因外层串行就改变子图异步语义。
- **NUMA**：多 socket 机器上，权重/常量的分配亲和（首次 touch 的节点）影响稳定态延迟；至少保证绑核与内存策略一致（`numactl -C … -m …`）。

## 5. 反模式

- **池中池**：库在框架的并行区内再开自己的 OMP 线程——嵌套并行 + 线程数乘法爆炸。直通 + `IsInParallel` 防护。
- **按宿主核数配线程**：容器配额才是真预算；同时检查 quota、cpuset、共享池和实际负载，避免自动探测给出超预算配置。
- **写死 cost**：`ParallelFor` 用固定大 cost，调度器无法做小任务内联决策。
- **无生效日志**：排查线程问题全靠 `top -H` 数线程——加启动日志。
- **只测吞吐不测 p99**：超订的典型症状是吞吐还行、p99 烂——指标不全就会漏诊。
- **每请求建 session 或盲目增加 session**：模型加载与池初始化会引入开销，多 session 也可能仍共享池。通常复用已加载 session，按实际池关系判断是否需要隔离。

## 实战案例摘要

此层支撑过：一个生产定制里 OMP→框架池直通的完整迁移（适配器 + thread_local 激活 + 串行回退）、异步转同步的 cost 上报改造（删掉固定 cost 与异步标志，cost 由各算子按规模传入）、brpc worker 线程默认限制（0=自动 → 16，与容器配额对齐）、TF 线程数生效日志、单线程 inter-op 的算子内联串行（几十行拿到批量调度执行器的大部分收益）、启动期内存归还。方向 A（批量调度执行器 + XLA 直通 + 线程亲和隔离）在旧版本线上验证有效，但未跟入新版本源树——重改造跨版本维护成本的活教材。
