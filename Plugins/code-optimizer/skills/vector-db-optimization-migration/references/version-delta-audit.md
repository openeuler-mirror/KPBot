# 版本差异审计

本文件给出迁移第 2 步的通用审计清单：先按类别排查源/目标版本差异，再决定处置。审计对象是“代码与构建事实”，不是版本号印象；所有结论必须用对应引擎的 source-analysis Skill 在当前 commit 重新核对。

## 1. 构建与宏

| 审计项 | 检查方法 | 迁移风险 |
| --- | --- | --- |
| CMake option 默认值与作用域 | 对比两版本 `CMakeLists.txt` 与 `option()` | 默认关闭导致“已移植但未生效” |
| 宏是否仍被编译 | grep 宏名 + 检查包围块调用者 | 死定义、空补丁 |
| 宏是否改变公共头 | 检查 `#ifdef` 是否包围类成员/虚函数 | ABI 分裂 |
| public defines / `-march` | 检查是否全项目传播 | 跨 TU 类布局错位 |
| 目标架构限制 | x86/ARM guard、SIMD 级别 | 未定义符号或静默降级 |
| LTO | 记录 `-flto` 与 `.o` 形态 | 静态反汇编假阴性 |
| 依赖默认值 | GPU、BLAS、OpenMP、Python 等 | 隐式行为变化 |

要求：每个优化保留原始 `#ifdef`；关闭宏后走目标上游原路径。不得把宏改成无条件生效。

## 2. ABI 与公共头

检查源优化是否给公共类增加成员或虚函数：

- 公共索引类、距离计算接口、结果处理器、量化器与访问表（各引擎具体类名见 adapter）；
- 公共头中的模板参数、`enum`、序列化字段。

规则：

- 任何新增数据成员或虚函数都必须让所有链接进目标库的翻译单元看到同一头文件与同一组宏。
- 用 `compile_commands.json` 核对每个相关 TU 的 `-D` 与 `-march`。
- 新增字段要考虑拷贝/移动、序列化、`reconstruct()`、派生类与 vtable。
- `strings <目标引擎动态库>` 不能证明宏已启用。

## 3. 数据结构与上游重构

目标版本可能重构了源优化依赖的数据结构。审计：

- 类型是否从 `struct` 变为抽象类层次/工厂；
- 生命周期管理是否从“每次查询重建/清零”变为池化/版本号/复用；
- 遍历、判重、候选堆、visited 的语义是否变化；
- 上游是否新增等价或更优机制。

处置原则见 `migration-contract.md` 的处置枚举。特别注意：**一个旧机制可能混合多个动机**（如“免分配”和“存储密度”），上游取代其中一个不等于整个机制都应删除，必须 `SPLIT` 后分别验证。

## 4. 分配器与内存布局

跨版本迁移常被忽略的一类差异：

- 容器底层分配器是否变化（自定义对齐分配器 vs `std::vector` 默认分配器）；
- 大块内存是否走 malloc/mmap，返回指针是否有页内偏移；
- 是否使用大页、`madvise`、NUMA 绑定；
- 向量/码字/邻居表的物理顺序与对齐；
- load 路径是否绕过运行时分配器。

影响：同一份内核代码可能因数据缓冲页内偏移、跨页数、TLB 行为而显著变慢或变快；这不是内核语义变化。

审计方法：

1. 记录索引/码字缓冲的分配路径与对齐属性；
2. 对比两版本同一数据集的布局哈希、跨页统计、`smaps`/`pagemap`；
3. 用受控副本（memcpy 到对齐/错位的新 mmap）和原位回放分离“数据缓冲”与“宿主代码”；
4. 不要只凭 QPS 或符号 profiler 下结论。

## 5. 结果处理与扫描模板

目标版本可能重构扫描器与结果收集。按以下类别审计，具体类名/模板名按引擎 adapter 展开（Faiss 示例：`ResultHandler`、`ScannerMixIn`、`SIMDResultHandler`、`SIMDLevel`、FastScan packed code、`bbs/qbs/impl`）：

- 结果处理器是纯虚接口还是 `final` 内联；
- 扫描器的模板/SIMD 分发与实际选中级别；
- 距离计算接口的模板实例化与尾调用；
- 量化码/分块扫描的 packed 布局与实现分支选择；
- 结果收集、候选保留、堆重排、refine/reorder 的位置。

审计时记录实际选中的模板/SIMD 级别与符号，不要用源码调用点代替运行时证据。

## 6. 序列化与 load/save

- 新增索引字段必须处理 save/load、版本兼容与默认值；
- load 路径可能应用重排/repack，save 路径可能不应用，两者等价性分开验证；
- load 入口（如 Faiss `read_index`、DiskANN load 路径）可能绕过运行时对齐分配器，导致“新建索引快、load 索引慢”的错觉；
- `load` 与 `save` 构建路径的行为差异必须在报告中显式声明。

## 7. 上游吸收与死宏

| 情况 | 处理 |
| --- | --- |
| 上游已用更优机制实现同一动机 | `REPLACE`/`DROP` |
| 宏只剩 CMake 开关、无源码作用点 | `DROP`，并在矩阵中标注 |
| 宏作用集在新版本变化 | `DEFER` 或 `OPT_IN`，重新做单变量门禁 |
| 源版本已回滚或来源链断裂 | 不迁入，记录缺口 |

“死定义”清理要显式记录，避免被误认为空补丁或遗漏。

## 8. 宿主差异与归因方法

当迁移后目标版本比源版本慢，先区分三类变量：

1. **内核代码**：源码、机器码、编译选项；
2. **数据缓冲**：分配器、对齐、页内偏移、大页、NUMA；
3. **宿主代码**：搜索循环、结果处理、模板形态、间接调用。

推荐证据顺序：

1. 证明工作负载位级相同（调用次数、候选数、recall、布局哈希）；
2. 隔离微基准：无宿主、真实数据，直调内核；
3. 原位回放：真实指针、真实调用序列、无宿主；
4. 受控副本：memcpy 到新鲜 mmap，改对齐/页内偏移；
5. `smaps`/`pagemap` 排除 THP、物理页、NUMA；
6. 最后才用宿主源码改写验证。

不要用负载窗口下的符号级 profiler 直接定因果；SMT 物理核计数器可能包含姊妹线程流量。
