# 收益归属判决实验 — 完整案例档案

> 配套 SKILL.md 步骤 4。核心命题：**benchmark 变快 ≠ 你以为的那个机制变快**。收益必须用"只含该机制的镜像微基"钉到机制层，否则归因错误会带偏下一步优化方向。

## 案例一：Core 瘦身的收益归属

**背景**：对 `CoreCallbackState` 做字段瘦身（缩小 per-callback 状态对象），`futures_benchmark` 的 twoThens 用例 240→216ns（+8.2%）。第一反应的归因是"类型擦除层变快了"——因为类型擦除帧（`FunctionTraits`/`callBig` 系）在生产画像中占比 3~4%，是最大的单一家族。

**判决实验**：构建只含类型擦除机制的镜像微基（运行时循环拼接 N 个 then，N 从 argv 读入——**必须运行时变量，禁止模板编译期常量**），对比优化前后该机制的帧占比：

| 量 | 优化前 | 优化后 | 判定 |
|---|---|---|---|
| twoThens 用例 | 240 ns | 216 ns | 变快 ✓ |
| 类型擦除帧占比 | 1.72% | 1.74% | **纹丝不动** |

**判决**：收益不在类型擦除机制——它在下游的**节点构造与 malloc 面**（逐节点成本约 4ns 量级）。这个判决直接改变了后续优化路线：不是继续抠 `FunctionTraits`，而是转向分配器三方对照（见 `allocator-benchmark.md`），最终 tcmalloc 在 malloc 面收割 +8%。

**反向教训**：若不做判决，"类型擦除是最大热点 + 优化后 benchmark 变快"这两个事实叠加，会得出"应该继续优化类型擦除"的错误结论——那是架构性成本，多轮火力集中于此均无产出。

## 案例二：SharedPromise 热点的真凶

**背景**：生产画像中 SharedPromise get/set 链路是 rank 侧最大热点（R1）。最初归因候选是"内部容器换 small_vector 能优化"（当时 container 替换很流行）。

**判决过程**：
1. small_vector 替换实验：**+1%（不显著，方向不明）**——判决排除容器假设
2. 帧级分析发现 R1 的成本集中在 **Core 构造的 malloc 调用**
3. 分配器对照（spGetSetOne 单读单写用例）：tcmalloc 下 85.0→78.1ns（**+8.1%**）——真凶是 malloc 面

**判决**：R1 的真凶 = Core 构造 malloc，由分配器收割。容器假设被证伪并记入负结果库。

## 镜像微基的构造纪律（复现要点）

1. **运行时循环拼接**：`int n = atoi(argv[1]); for (i<n) { f = f.then(...); }` ——编译期常量 N 会让编译器跨节点优化，实测可把 +8% 掩盖成 +0.6%
2. **只挂目标机制**：除被验证机制外不留其他 folly 调用
3. **折叠聚合按每栈样本数加权**：栈条数 ≠ 样本数。一个折叠栈可能代表几十个样本；按栈条数平均会把 1.9% 的帧算成 0.2%（10 倍误差）
4. **读法**：帧占比不变 → 收益在下游；帧占比下降 → 收益确实在该机制

## 何时必须做判决

- 优化点与热点帧**不直接对应**（如对象瘦身对类型擦除帧）
- 优化后 benchmark 变快但**幅度与热点占比不匹配**
- 多个优化点叠加后分不清各自贡献（逐点判决后再叠加，见 SKILL.md 步骤 6 的三层终验）
