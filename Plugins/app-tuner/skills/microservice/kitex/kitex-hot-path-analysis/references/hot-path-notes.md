# Kitex 热路径分析笔记（版本敏感）

> 版本敏感：以下结论需按现场读取的 Kitex、netpoll、gopkg 版本重新确认。
> 本文只记录结构性事实与分析结论，不含任何环境相关的性能数据。

## 1. 服务端链路与成本类型

| 阶段 | 成本类型 | 备注 |
|---|---|---|
| 事件循环唤醒与派发 | 系统调用 + 调度 | 每请求一次 goroutine 派发 |
| 读 meta/payload | 系统调用 | 一次或数次读取，零拷贝切分 |
| 解码 | 分配 | 结构体、列表、字符串 |
| 业务处理 | 业务 | 与框架无关 |
| 编码 | 系统调用 + 少量分配 | 一次连续分配后整体写出 |
| 回收 | 少量原子操作 | 消息与缓冲区池化 |

## 2. 已确认的结构性事实

- 默认编解码已是"单次分配 + 零拷贝读"，编解码通常不是小包场景的主成本。
- 非复用连接的客户端每次调用独占一条连接，获取/归还走同一把锁；高并发下连接数随并发增长。
- 复用连接路径按序号分片存放未完成请求，每请求涉及多次分片锁操作。
- 每请求都会经过一次 goroutine 派发；派发池与埋点包装是固定开销。
- 透传元信息在启用后会按需创建键值容器并拷贝字符串。
- 统计埋点默认关闭，注册链路追踪后自动升到详细级别。

## 3. 已验证的方向性结论（不含数值）

| 分析假设 | 结论 | 说明 |
|---|---|---|
| 换编解码实现可显著提速 | 不成立 | 默认实现已接近上限；公开的"快数倍"对比对象是 Apache Thrift |
| 详细埋点有明显开销 | 不成立 | 开销在噪声内，不应为此牺牲可观测性 |
| 连接池锁是高并发瓶颈 | 部分成立 | 并发越高越明显；低并发下可能不显著 |

## 4. 分析时的检查点

1. 先确认版本，默认值可能随版本变化。
2. 先确认是否启用复用连接、是否启用透传，这两项会改变链路。
3. 先确认埋点级别与是否有链路追踪注册。
4. 先确认目标架构上是否存在动态编解码库降级。
5. 任何结构点结论都要标注"参数能否消除"；能靠参数解决的不要进候选改造。
6. 收益必须来自本轮同口径对照，分析文档只给方向与候选。
