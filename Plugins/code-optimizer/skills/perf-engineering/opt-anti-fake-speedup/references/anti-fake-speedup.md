# 防假提速：两层铁证全量（标定案例）

## 1. 为什么需要两层

提速有两种可能：真快了，或"少干活了"。假提速的三个典型来源：

| 来源 | 表现 | 检测 |
|---|---|---|
| seed 漏写 | 检索落到空集，时延"假的低" | 顶层过滤命中数 = 0 或 < 预期 |
| 隐式早退 / 短路 | 结果少了、请求少了 | 结果条数 / 请求总数对不上 |
| 版本静默回退 | 转发变量丢失，测的是旧基线 | 运行容器确认实际 tag/image |

## 2. 第 1 层：量（干了一样多的活）

> **本 skill 招牌数字 +179.6% 的口径**：JSON 过滤基线 qa 吞吐 27.47 req/s → flatidx 76.80 req/s，
> (76.80−27.47)/27.47 = +179.58% ≈ +179.6%。基线 27.47 的逐轮值记录见 `opt-onboarding-and-baseline`
> （独立 PR 待合入），结果 76.80 见 `opt-quantify-and-decide`（独立 PR 待合入）。本节 23420/23040 是
> 重组（submodule 化）后的复验轮锚，不是 flatidx 优化对比对的原始值——两组数字勿混。

- 整体请求数逐位一致：overall retrieval **23420**、qa **23040**，与基线完全相同。
- 错误请求全为 0（否则吞吐涨可能来自报错提前返回）。
- 吞吐涨了但请求数少了几百 → 少干活，不是提速。

## 3. 第 2 层：质（每个请求干得一样重）

- 语义正确性核验：顶层 `user_id == "<trace-user>"` 计数 = 10000、空值 = 0 → 检索打在完整预热底库上。
- **过滤命中数按「同一快照」拆两项**：全库行数（81592 起点 / 82480 终点）+ 相同过滤条件基线命中数（10000）。
  只测全库行数会把"正确命中 10000"误判为失败，且漏掉"漏租户条件的全库扫描"这类假提速；两项都要对照。
- **逐查询核对结果 ID（及必要顺序）**：不同查询 top-k 结果互换后，请求数/候选数/返回条数仍能全过，
  只有按同一查询看 ID 是否与基线一致能暴露"结果串了"。近似检索约定 top-k 召回率阈值（如
  `|候选∩基线| / k ≥ 0.9`）。
- **对齐同一批查询核对返回记录的租户归属与主键**：候选版本跳过排序、直接返回前 k 条时，候选集规模/
  结果条数/请求数仍可全部一致，靠租户+主键对齐才能戳穿。
- 结果条数 / 候选集规模与基线一致。

## 4. 单一硬指标当锚

- 请求计数是跨重构最稳的锚：不随路径迁移 / submodule 化 / 版本转发改变。
- 重组后复验：计时 3 轮 QA avg 170/148/167ms、thr 78.9/80.5/79.7 r/s，请求计数 23420 完全一致。
- 版本转发失效时，运行容器确认 mem0=flatidx-v1 / milvus=top2-v2（而非 baked 默认 -v1）。
  **但"确认 tag"不够**：请求数相同 ≠ 测的是新版本，旧镜像也能跑完 23420 次。验收必须记录运行容器的
  **镜像 ID / 摘要**（`docker inspect` 的 `Image`），与预期构建比对，匹配后才用本轮结果。

## 5. 与 `opt-clean-attribution`（独立 PR 待合入）的分工

- 防假提速：证明"不是少干活"（量 + 质两层）。
- 干净归因：证明"增益/无增益能归到我的改动，而非混杂因素"（体积/.text/构建路径/单轮方差）。
- 两者正交：一个改动可能"不少干活"但仍"无法干净归因"（如 TOP1b），两者都要过。

## 6. 坑点

- **只看吞吐**：请求数降了但吞吐涨，是假提速的典型伪装。
- **只看总数不看分布**：总数对但分布偏（如都命中热门用户），仍可能是少干活的另一种形式。
- **只看返回条数不看 ID**：top-k 结果互换 / 跳过排序直接返前 k 条，返回条数仍对；按同一查询看结果 ID 才安全。
- **只看 tag 不看镜像 ID**：版本转发失效时旧镜像也能跑完同样请求数；验收到镜像 ID / 摘要与预期构建比对为止。
- **等价重构不实跑**：版本转发静默回落到默认 tag，测的就是另一个基线。
