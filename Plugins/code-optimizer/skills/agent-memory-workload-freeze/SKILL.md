# 负载口径固化

## 何时用

- 端到端时间由 LLM/embedding 调用支配，重跑差异几十个百分点；
- 准备做任何 A/B 之前，需要先把"输入"变成常量；
- 换人/换机复跑时，需要同一口径才能比较。

## 输入

| 字段 | 说明 |
|---|---|
| 写入集 | 会话/文档数量、顺序、是否可重放 |
| 查询集 | 条数、检索配方（全文/向量/混合）、候选倍数 |
| stages | 需要单独计时的阶段（ingest / search / rerank…） |
| 绑核 | 客户端与服务端是否同核、JVM 是否绑全部线程 |
| 并发度 | 串行拆分与并发压测分别用多少 |

## 步骤

1. **固定写入集与查询集**：条数写进报告；查询必须真正截断（老实现只按样本整块截断，会偷偷跑满全量）。
2. **固定绑核**：客户端与服务端绑同一组核；JVM 用 `taskset -a -pc` 绑**全部**线程，只绑主线程等于没绑。
3. **固定清库与校验**：每轮前清库并校验 `0 0`（节点/边），写入必须从空图开始，查询必须跑在"上一次 ingest 留下的图"上。
4. **固定缓存文件状态**：每轮前恢复规范缓存（运行会把新条目写回缓存），见 `llm-cache-canonicalization`。
5. **关掉 profiling 做纯计时**：py-spy + pyinstrument + nmon 同时开会把负载撑大 ~66%。
6. **测重跑波动**：先预热、**丢首轮**，再连跑 3 次，算 phase 的**标准差 / 均值**；> 2% 就回去查缓存与清库。口径与 `agent-memory-bench-matrix`（丢第 1 次热身）和 `agent-memory-runtime-config`（2 轮预热）保持一致。

## 标定案例口径

公开会话记忆基准，10 段会话 / 1986 条查询；写入集为逐段会话，查询集为固定条数的检索请求。
该规模下客户端与服务端共享同一组核，按上述口径（预热、丢首轮、看标准差）phase 波动可压到 2% 以内——换数据集时按同一结构
（写入集 / 查询集 / stages / 并发 / 绑核）重新填表，不要直接沿用条数。

## 输出

- 口径表（写入集、查询集、stages、并发、绑核、清库方式）
- 重跑波动实测值（应 < 2%）
- 需要单独计时的阶段清单

## 注意

- `wall` 含解释器启动、导入、建索引、缓存加载，固定开销会稀释后段收益（实测 x86 p1 wall 掉 25% 而 search 只掉 2%）——口径里必须区分 phase 与 wall。
- 写入通常**不可并行**：实体在会话间共享，判重依赖并发交错顺序，缓存键随之不确定。
