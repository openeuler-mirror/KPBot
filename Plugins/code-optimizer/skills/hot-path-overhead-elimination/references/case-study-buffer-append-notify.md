# 案例：缓冲区追加与通知路径的机制开销

本案例是 `hot-path-overhead-elimination` 的证据来源。它记录了一组真实改动：在一个事件缓冲区库上，六处代码改动分别对应本 Skill 的六族配方，并给出了实测数据与拒绝记录。库名与函数名只作为证据出现，配方本身不依赖它们。

## 背景

被测库为键值服务提供网络缓冲与事件通知。它的热路径有三个特征：

- 追加接口接受的载荷集中在少数几个字节数上（协议回复的固定片段）；
- 每次追加后都会调用通知派发，而绝大多数连接没有注册任何观察者；
- 缓冲区对象以"链"为单位分配，小块数据也走通用分配路径。

性能对比显示该库在 Kunpeng 目标机上明显慢于同轮对照平台，且慢在固定的机制开销上，而不是算法。

## 六族配方的落点与实测

### 1. `dominant_outcome_inline`

观察：通知派发函数约 89% 的调用命中"观察者列表为空"的早退，早退只清两个计数器。profil 显示热点集中在函数序言、保存寄存器与返回分支，而不是有效工作。

改动：把空列表判定与清零动作做成头文件内联函数，重体改名保留为 out-of-line 走慢路径。

机械核对（`codegen_overhead_probe.py --compare`）：

```
callee call sites: 2 -> 0
caller operands on the observer-list offset: 0 -> 2
```

即被调符号从热路径消失，判定谓词出现在调用方内部。

### 2. `leaf_entry_split`

观察：主导场景是 2/4/5/6 字节的无锁追加，此时不需要任何 callee-saved 寄存器；通用实现在其余场景会进入分配、重对齐与慢分支。

改动：公共入口改为 dispatcher，对主导场景走精确 guard 的叶子实现，其余场景 tail-call 到改为 `noinline` 的通用实现。guard 逐条对应通用实现的慢分支：加锁、冻结、溢出、观察者非空、末尾链不可写、剩余容量不足。

### 3. `constant_width_copy`

观察：追加长度是运行期参数，实测分布为 5 字节约一半、4 字节、6 字节、2 字节，其余长度稀少。反汇编显示这些短长度会调用通用拷贝例程，而该例程在目标架构上使用向量前缀指令，对几字节的搬运而言序言成本远高于数据搬运。

改动：按长度分类，主导长度用编译期常量宽度拷贝，其余长度继续走通用例程。

拒绝记录：在同一批实验中，"元数据缓存"类改动回退 1.99%，"只特化 5 字节"的周期数改善仅 0.3%，"表分派"为 -0.34%。三者都低于 2% 采纳门槛，记录在案。

### 4. `hot_value_first_dispatch`

观察：多宽度分派按自然顺序排列，而 5 字节占主导，每次命中都要重复分类。

改动：把 5 字节提到最前，并把 `off` 与总长度在拷贝前快照到局部变量。

实测：11 组交替采样的算术均值为追加接口 +5.65%、读行接口 +5.36%，其余三个接口在 1% 回归线内。

### 5. `absent_consumer_elision`

观察：热路径在拷贝后无条件执行 `n_add_for_cb += len` 并调用通知；没有观察者时，内联快路径立刻把计数清零，这次记账与通知完全是死代码。

改动：观察者列表为空时跳过记账与通知；建立不变量"观察者列表为空 ⇒ 两个计数器为零"，并在三个可能破坏它的写入点（移除最后一个观察者、设置回调为空、设置回调失败）修复或断言。

语义变更：移除最后一个观察者时会丢弃尚未上报的计数，使之后注册的观察者不再收到注册前的事件。这是有意的行为修正，原行为既无文档也无用途；交付时必须写在 `risk_notes` 里并配套两个回归用例（延迟回调替换、无计数继承）。

### 6. `snapshot_before_copy`

观察：拷贝写入后，编译器重新加载刚写过的字段（别名重载），形成多余 load。

改动：写前快照、写后从快照更新。实测与配方 4 合并计入了 +5.65% 的那笔。

## 平台限定与"编译器已内联"的拒绝

配方 2、3、4 的收益依赖目标架构：只有目标机反汇编仍显示"通用拷贝例程被调用、未被内联"时才成立；若编译器已经产出等价的常量宽度指令，应返回 `success=false` 并把它记进拒绝台账。因此这几族配方在源码上以 AArch64 目标为启用条件，其它目标保持原实现。

判断依据始终是目标机的反汇编，而不是对编译器行为的假设：`codegen_overhead_probe.py` 检查热路径里是否还存在对通用拷贝例程的调用。报告里必须同时写明"配方生效的架构"与"实测所用的机器"。

机制改动对应上游提交：`f78d28d2`（空回调时跳过 drain 记账）、`1ec605b5`（AArch64 drain 叶子快路径）、`6895dc75`（五字节分派让主导值走顺序路径）、`2a87765d`（五字节源加载重叠）。

| 配方 | 上游测量记录 |

| `leaf_entry_split` | evbuffer_add +18.45% |
| `hot_value_first_dispatch` | 11 组交替采样均值 add +5.65%、readln +5.36%，其余接口在 1% 回归线内 |

这些数字来自上游在 Kunpeng 目标机上的测量记录，未随本仓库提供，也未在仓库内复测；用例的验收以运行时断言为准。

机制类配方主要改善追加与读行；清空的收益来自分配路径，这正是两族配方分工的证据。

## 可复现命令

```bash
# 1) 未改动基线构建
cmake -S <src> -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# 2) 生成反汇编并核对芯片级证据
objdump -d --no-show-raw-insn build/lib/libevent_core.a > base.dump
python3 scripts/codegen_overhead_probe.py --dump base.dump --symbol <symbol> --offset <offset>
python3 scripts/codegen_overhead_probe.py --dump base.dump --compare cand.dump \
    --callee <dispatch_symbol> --symbol <symbol> --offset <offset>

# 3) 分布
python3 scripts/value_distribution.py --input sizes.txt --threshold 0.9
```

## 该案例给出的通用经验

1. 当函数体很小却排进热点榜前列时，先怀疑调用与分派机制，不要先做算法改写。
2. 主导覆盖率是最便宜的可行性判据，拿不到分布就不要做特化。
3. 快路径的 guard 必须从通用实现的慢分支枚举出来，而不是从想象的使用场景枚举出来。
4. "编译器已经做了"是常见结局；反汇编确认后拒绝，比制造改动更有价值。
5. 语义变更（如跳过记账）必须显式记录并配套回归，不能混在性能改动里悄悄交付。
