# CPU 推理与 Host 机制验证

## 选择入口

| 用户要解决的问题 | 使用入口 |
| --- | --- |
| “整理近两周 vLLM、SGLang 的 CPU 推理变化”，或“盘点某个厂商 / 模型的 Host 优化机会” | 使用 `$kpbot-training-inference-host-insights`。时间窗缩小到一天、只选一个社区或要求 HTML，都仍是社区跟踪。 |
| “核对这份报告提到的 KV 异步拷贝是否消除了 decode 主线程等待，并给出 A/B 测法” | 使用 `$kpbot-ai-host-insight`。输入可以是一条台账记录、PR、代码路径，或一个可证伪的问题（如“跨 NUMA 读取是否拖慢 CPU decode”）。 |

若只要求一期简报，由社区跟踪入口生成一份报告。若另点名一项机制要求深入验证，把该条目的证据链接交给本入口，验证结果作为该条目的专题补充。

## 从已有证据开始

1. 优先读取用户给的报告、台账或源码链接。已有社区归档时，从指定归档根（默认 `host-insights/`）读 `state.yaml` 的 `evidence` 相对路径，并从 `index.md` 定位覆盖所问窗口的往期台账。以台账和 Markdown 正文为准。HTML 可用于定位原文。引用已有记录时保留台账路径、原事件键及窗口。
2. 按社区台账的**项目、事件类型、稳定 ID**匹配，例如同一个仓库的 PR 编号、commit SHA 或 release ID。若发布说明和厂商博客都指向同一个 PR，在该 PR 的记录下补充证据链接。release 是独立事件时保留其原键并关联 PR。同键同状态只引用一次。状态或实测证据变化时列出前值、新值和来源。只有 HTML 或找不到台账时，回到一手来源核对项目、类型和 ID，标明缺失的归档信息。
3. 用用户给定的版本、窗口或 PR 的基线与变更提交做对照，记下实际查证时刻和时区。用户没有指定时间时围绕该机制查对应版本。社区归档的 `coverage_end`、`last_success_report_generated_at` 和 `pending` 仅用于交代已覆盖范围。专题查证期间保持原值。

## 把假设变成可复核的实验

- 写清命题、执行位置（CPU 计算、CPU 与加速器协作、Host 调度）和阶段（加载、prefill、decode 等）。从 [证据来源](references/sources.md) 选与命题相关的最终实现、配置和测试，固定 PR 或 SHA，定位函数、线程、数据所有权及同步点。
- 沿同一请求画出基线与改动后的执行顺序。说明哪一步会省下 CPU 周期或等待，什么结果能推翻这一判断。引述性能数字时保留硬件、软件版本、模型与精度、输入/输出长度、批量/并发、缓存和指标单位。未知条件写明未披露。
- 设计一个只改变一个变量的 A/B，对正确性、预热、重复次数和环境作相同约束。按机制选择测点，如线程阻塞与设备时间线、每 token 的 CPU 周期或远端 NUMA 读，并选一个端到端指标如 TPOT。写明接受、否定或证据不足的判定条件，将上游实测、这次实测和待测预期分别标明。

## 交付验证单

默认交付一份中文 Markdown，写清命题、对应事件和来源、基线与变更路径、对照与测点、结果和限制。用户需要 HTML 时从同一份 Markdown 派生。缺少原始测量时交付可执行的验证方案，并列出需要收集的数据。

在指定输出位置保存。沿用社区归档时，把验证单放在归档根的 `topics/<project>/<event-type>/<stable-id>/`。三个路径段取自同一条台账的项目、事件类型和稳定 ID。每段按 UTF-8 编码，原样保留小写 ASCII 字母、数字、连字符和下划线，其余字节写成大写 `%HH`。例如项目 `vllm-project/vllm` 的 `pr` 事件 `123` 归入 `topics/vllm-project%2Fvllm/pr/123/`。尚无台账记录时按一手来源确定事件键。只有性能假设、尚无稳定事件 ID 时，先在用户指定位置交付。

为文件标明验证日期。同名交付使用版本后缀。重跑先按事件键、对照版本和配置检查已有验证单。若归档沿用旧的主题目录名，也在既有验证单中查找原始事件键。证据与结论均相同则返回原件。将来源台账路径及事件键写入验证单，供下一期从同键引用。新发现注明“待周期台账核验”。专题仅写专题目录，正式 `state.yaml`、`index.md`、逐期报告和 `*-evidence.md` 由社区跟踪入口维护。
