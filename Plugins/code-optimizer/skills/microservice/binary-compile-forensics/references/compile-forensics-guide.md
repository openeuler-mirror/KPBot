# 三条证据链的原理与实测案例

## 为什么需要产物反推

构建系统的配置继承链（cmake preset → CMakeLists → toolchain file → 环境变量 →
包管理 CFLAGS）任何一层都能覆盖最终参数，且**没有任何一层能事后证明自己生效了**。
优化归因、回归排查、部署核验都吃过这个亏：配置里写着 -O3，产物里实际是 -O2——
差异不在代码，在构建。

产物是唯一不撒谎的证词。

## 链 1：编译器版本（.comment 段）

- 原理：GCC/clang 默认把版本串写进 `.comment` 段，**不需要 -g**
- 读取：`readelf -p .comment <file>`
- 判读要点：**多个版本串同时出现 = 混链构建**（部分 .o 来自不同工具链——
  实测案例：同一静态库里同时出现 GCC 12.3.1 与 GCC 10.3 串，客户侧行为
  差异追踪了一周，根因就是工具链混入）
- 失效形态：`strip`（默认不带 -s 的局部 strip）在某些发行版打包流程中会裁掉 .comment；完全 strip 的二进制可能保留 .comment（`strip -s` 不在 strip 列表内）——实测为准，无 .comment 数据时该链降级

## 链 2：参数指纹（DW_AT_producer）

- 原理：带 `-g` 构建时，DWARF 的 compile unit 里有 `DW_AT_producer` 字段，
  记录**完整编译命令参数串**（-O/-march/-mcpu/-g/-f… 全部代码生成开关）
- 读取：`readelf --debug-dump=info <file> | grep DW_AT_producer`
- 这是"现场实际参数"的**权威答案**——构建系统的任何覆盖在它面前无所遁形
- 实测案例（protobuf 库归因）：安装的 libprotobuf 优化收益与源码侧预期不符，
  配置链全部核对"正确"；DW_AT_producer 显示实际 `-O2`（发行版打包时覆盖了
  上游的 -O3）——**归因从"代码差异"改判"构建差异"，一周排查 30 分钟收敛**
- **限制**：
  - `-gno-record-gcc-switches` 下 DW_AT_producer 仍存在但不记录待核验的开关
  - debuginfo 分离（常见于发行版打包）时 DW_AT_producer 在分离包里——
    **先按 build ID 或 .gnu_debuglink 查找匹配的 debuginfo 包**，找到后从中
    读取指纹；找不到才降级。直接建议"重编"会改变正在取证的产物
  - 脚本只抽前 5 个编译单元去重——未覆盖单元的参数标为未知，结论限定于
    实际抽到的编译单元和其中明确记录的参数

## 链 3：SIMD 兜底（无 -g 时的采样）

- 原理：无 debug info 时，反汇编采样统计向量寄存器指令——SVE（z 寄存器）
  与 NEON（v 寄存器）的使用密度能判定向量代码是否真的编进去了
- 读取：`objdump -d | head -300000` 采样 + 寄存器正则计数
- 判读阈值：SVE >50 行 = 已启用；0-50 = 疑似少量（可能是 libc 内联）；
  **0 = 样本中未见（不证伪启用）**
- 实测案例（SVE 移植验证）：`-mcpu` 参数被静默丢弃后产物无任何 z 寄存器指令——
  SIMD 采样 0 行**在样本范围内**证伪了"SVE 已启用"的配置声明（此时链 2 无
  -g 不可用，链 3 是唯一证据）
- **局限**：零命中只说明"采样的前 30 万行中没有"——目标函数可能在采样范围
  之后，或允许使用 SVE 的代码只生成了标量指令。**不能以此证伪编译开关**。
  需要判定编译开关时另取参数记录（链 2 或分离 debuginfo）

## 三链交叉判读

| 情形 | 判读 |
|------|------|
| 链 2 有指纹 | 权威定论（限于实际抽到的编译单元），链 1/3 做佐证 |
| 链 2 无（debuginfo 分离）、找到分离包 | 从分离包读指纹——同上 |
| 链 2 无、链 3 有 SIMD | "参数不明但向量代码在"——够用的场景（部署核验）用它；不够的（精确归因）先找 debuginfo |
| 链 2 无、链 3 采样 0 | **样本中未见**——强疑点但非定论；判定开关另取参数记录 |
| 链 1 多版本串 | 混链构建实锤，用 `-a` 逐成员定位污染源 |
| 三条链全空 | 非 ELF 或损坏——计为"未完成取证"（不冒充成功） |

## 与相邻 skill 的协作

- `hot-library-version-gap` 先回答"跑的是哪个版本的库"，本 skill 接着回答
  "这个版本怎么编的"——两步走完成库侧归因基线
- 优化归因（`flamegraph-libopt` 家族）开工前先跑一次本 skill 固定构建基线：
  防止把构建差异误归因为代码差异（实测踩过：-886% 假回归的一半根因是
  find_package 链错库，另一半就是构建参数未确认）
