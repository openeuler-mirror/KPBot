# 测量协议：冻结负载、三段归因、扩展曲线、矩阵复测（measurement-protocol）

> 供 agent-memory-db-optimization 在阶段 1/2/5 按需 Read：先把"优化了多少"的口径钉死，再谈数字。

本文件是可执行口径。任何"优化了多少"的结论，都必须能追溯到这里的某一条协议。

## 1. 冻结确定性负载

### 1.1 缓存回放

用 `scripts/llm_replay_cache.py` 包装三类客户端：

```python
from llm_replay_cache import ReplayCache

cache = ReplayCache("cache/canon.json", mode="replay")   # CI/正式测量
llm   = cache.wrap(raw_llm,      name="llm")
emb   = cache.wrap(raw_embedder, name="embed")
rr    = cache.wrap(raw_rerank,   name="rerank")

# ... 跑基准 ...
assert cache.miss == 0, cache.stats()        # 门禁
```

要点：

- **键 = (目标名, 方法名, 参数) 的 sha256**，与 API key、base_url 无关。换 key 不会造成 miss。
- **必须带目标名**：LLM 与 reranker 常用同一个 SDK 类和同名方法，只用方法名会串味。
- **值必须可 JSON 序列化**；不可时传 `encoder/decoder`（例如 pydantic 模型 ↔ dict）。
- **缓存文件定版**：记录 md5 并随交付分发；运行会把新条目写回文件，所以每轮开始前
  从规范副本恢复（`cp -f canon.json run/llm_response_cache.json`）。
- **首跑用 `record`**：此时的数据只用于建库，不进结论表。

实测口径：4680 条缓存覆盖 10 段会话的 ingest 与 1986 条查询，`LLM Hits 312 / Misses 0`、
`Embedder Hits 568 / Misses 0`（含 20 条查询时 588）。

### 1.2 校验和

写入侧：`(节点数, 关系数)`，例如 `225 / 492`。每次 ingest 后统计，写入侧画像是
"从空图开始写 10 段会话"，同一数据集应恒等。

查询侧：结果指纹。对每条查询取 `[(uuid, round(score, 6)), ...]` 排序后拼接，再
对全部查询的指纹取 hash。两个数一起看：

- 只有性能变、图规模与指纹都不变 → 真正的零风险优化；
- 指纹变了 → 先查"候选集/字段/排序是否被改动"，不要急着庆祝数字。

### 1.3 门禁（自动重试）

```
每次 ingest：清库 → 校验 (0, 0) → 跑 → 校验 misses==0 && checksum==期望
每次 search：恢复缓存 → 跑 → 校验 misses==0
失败重试 ≤3 次，仍失败则整批作废
```

典型脏数据形态：清库"成功"但图仍是 `235 / 720`（连了别的实例/端口不一致），
此时查询变快、命中数异常（如只有 20 hits），很容易被误读成优化收益。

### 1.4 运行环境口径

| 项 | 要求 |
|---|---|
| 绑核 | 客户端与服务端同一组核；`taskset -c <list>` |
| JVM | `taskset -a -pc <list> <pid>`（**全部线程**；只绑主线程等于没绑） |
| 库状态 | ingest 从空图；search 跑在上一次 ingest 留下的图 |
| 观测 | 纯计时阶段关闭 py-spy/pyinstrument/nmon（三者同开使负载膨胀 ~66%） |
| 空闲 | profile 采样期机器空闲度 ≥ 98% |
| 预热 | JVM 需 2 轮完整负载（首轮慢 40~80%）；解释器侧首轮丢弃 |
| 日志 | 每次运行落独立目录，保留原始 CSV 与 topdown 日志 |

### 1.5 重跑波动验收

同一配置连跑 ≥3 次（丢首轮），`phase` 的标准差应 < 2%。若 > 5%，按顺序查：
缓存是否被写脏、库是否真清空、绑核是否生效、是否有他人在跑、JVM 是否未预热。

## 2. 三段归因（per-query split）

### 2.1 三个量

串行执行（`--search-concurrency 1`），对每条查询记录三段时间戳：

| 量 | 定义 |
|---|---|
| 总时间 | `Graphiti.search()` 外层墙钟 |
| DB 区间并集 | 该查询发出的所有 `execute_query` 区间之**并集**（全文 + 向量并发，两条调用的区间重叠，求和会双计） |
| 服务端时间 | Bolt SUCCESS 元数据 `result_consumed_after` |

推出：

```
框架 = 总时间 − DB 区间并集
驱动 = DB 区间并集 − Σ服务端时间
服务端 = Σ服务端时间
```

一次查询通常 2 次 DB 调用（全文检索 + 向量相似度），并发发出。

### 2.2 自证与陷阱

- **自证**：客户端优化前后，服务端绝对毫秒应基本不变。实测
  鲲鹏 7.7 → 8.5 ms，x86_64 3.3 → 3.6 ms —— 只有客户端两项在缩
  （驱动 49.9 → 12.4 ms / 35.3 → 7.9 ms）。
- **陷阱 1**：用 `result_available_after` 当服务端总时间。它只说明"开始返回得快"，
  服务端真正慢在"消费完"（本例 ~0.2~0.5 ms vs 数毫秒级 `consumed`）。
- **陷阱 2**：并发查询下测拆分。多条查询互相排队，拆分失去意义。
- **陷阱 3**：把"首跑建索引/加载缓存"混进拆分。拆分只在稳态区间做。

### 2.3 实测参考（同一优化后服务端，两种客户端）

| 机器 | 客户端 | 总 ms | 框架 | 驱动 | 服务端 |
|---|---|---|---|---|---|
| 鲲鹏 | 基线 | 59.60 | 1.15 (1.9%) | 49.93 (83.8%) | 8.52 (14.3%) |
| 鲲鹏 | 优化 | 21.06 | 0.96 (4.6%) | 12.40 (58.9%) | 7.70 (36.6%) |
| x86_64 | 基线 | 39.64 | 0.80 (2.0%) | 35.28 (89.0%) | 3.56 (9.0%) |
| x86_64 | 优化 | 11.74 | 0.58 (4.9%) | 7.85 (66.9%) | 3.31 (28.2%) |

读法：**驱动解码永远是第一嫌疑**（基线 84~89%），但它一旦被压下去，
服务端占比会翻倍（14% → 37%），下一轮该看服务端了。

## 3. 读路径扩展曲线

固定"查询集 + 同一张图"，只改副本数：

```
1 / 2 / 4 / 5 / 7 / 8 个副本，每副本 Semaphore(20) 协程并发
记录：phase 秒、qps、CPU%（单核百分比）、峰值 RSS、连接重试次数
```

实测（固定核预算，客户端 + 服务端同核）：

| 副本 | search | q/s | 加速比 | CPU% 均/峰 | 重试 |
|---|---|---|---|---|---|
| 1 | 44.13 | 45.0 | 1.00× | 190 / 240 | 0 |
| 4 | 15.47 | 128.4 | 2.85× | 594 / 669 | 0 |
| **5** | **14.33** | **138.6** | **3.08×** | 655 / 743 | 54 |
| 7 | 16.98 | 116.8 | 2.60× | 694 / 792 | 402 |
| 8 | 16.86 | 117.8 | 2.62× | 734 / 795 | 611 |

判定：

- 每副本约吃掉 1 个核，加上服务端开销 → **容量 ≈ 核数 / 1.45**。
- 超过甜点后 CPU 更高但吞吐下降 + 重试暴涨 = **服务端线程被饿死**，
  不是"再给一个核就会更快"。
- 瓶颈在客户端单核时（CPU% ~99%），先做阶段 4 的解码/水合杠杆，
  再谈副本数——否则每个副本都在重复做同样的低效工作。

## 4. 矩阵复测

### 4.1 设计

二维矩阵：客户端档位（C0…C3，开关组合）× 服务端版本（v0…v4，累积补丁），
按"客户端先做，最优客户端上再叠服务端"排成递进组：

| # | 服务端 | 客户端 | 累计优化数 |
|---|---|---|---|
| 1 | v0_orig | C0 | 0 |
| 2 | v0_orig | C1 | 1 |
| 3 | v0_orig | C2 | 2 |
| 4 | v0_orig | C3 | 3 |
| 5 | v1 | C3 | 4 |
| 6 | v2 | C3 | 5 |
| 7 | v3 | C3 | 6 |
| 8 | v4_full | C3 | 7 |

每组：6 次 ingest（每次清库）+ 6 次 search（跑在第 6 次 ingest 的图上）。
总行数 = 组数 × 2 × 6。耗时参考：x86_64 约 25 min，鲲鹏约 40 min。

### 4.2 汇总

丢弃 `run == 1`，对第 2~6 次取均值与**总体**标准差（pstdev）。加速比
`phase[#1] / phase[#8]`，分阶段、分架构。**wall 只展示，不做加速比依据**：
它被解释器启动/建索引/缓存加载主导。

### 4.3 实测参考（客户端与服务端同核预算）

```
SEARCH（1986 条查询，7 进程 × 并发 5）         x86_64            aarch64
 #  配置                                      phase   wall      phase   wall
 1  v0_orig + C0 基线                         21.86   27.49     24.97   30.53
 2  v0_orig + C1 官方 Rust 解码                9.80   15.43     11.31   17.14
 3  v0_orig + C2 时序水合下沉                   6.46   12.29      7.32   13.48
 4  v0_orig + C3 向量不回传                     5.54   11.33      6.01   12.31
 5  v1 + C3                                   3.86    9.71      4.60   10.65
 6  v2 + C3                                   3.32    9.02      4.15   10.11
 7  v3 + C3                                   3.15    8.84      3.81    9.86
 8  v4_full + C3                              3.22    8.93      3.81    9.91
    合计                                      6.8×            6.6×

INGEST（10 段会话，每次从空图开始）
 1  v0_orig + C0 基线                         15.65   16.10     16.33   16.76
 2  v0_orig + C1                               6.37    6.81      6.87    7.31
 3  v0_orig + C2                               4.80    5.13      4.91    5.35
 4  v0_orig + C3                               4.22    4.54      4.40    4.83
 5~8 （服务端影响）                           4.04~4.11       4.16~4.28
    合计                                      3.9×            3.9×
```

三点必须写进报告：

1. 服务端 4 项补丁对**写入**≈0 收益（±0.1 s），说明它们作用在读路径；
2. 服务端补丁在**客户端未优化**时几乎看不出来（Amdahl），必须放在最优客户端之后测；
3. 第 7→8 组可能持平甚至微退（实测 x86_64 3.15 → 3.22），属噪声带，不要当成"第四个补丁有害"。

## 5. 有效批次判定清单

```
[ ] CSV 行数 == 组数 × 2 × 运行次数（本例 96）
[ ] 全部 ingest 行都是 "Misses: 0 graph=225 492"
[ ] 日志无 "GIVING UP" / "CLEAR FAILED" / 连接重试风暴
[ ] 日志最后一行是完成标记
[ ] 每组都有客户端档位与绑核回显
[ ] 同一配置的 5 次 phase 标准差 < 5%（跨架构可放宽到 8%）
```

任一条不满足，整批作废；不要挑"看起来正常"的子集。
