# topdown-analysis-advisor — Topdown 分析与优化建议

交付有原始证据支持的 CPU 微架构诊断和候选优化实验。
把观测、解释、假设和验证动作分开；采集到数据不等于确认根因。
首版针对 kptools-devkit 所记录的 DevKit 文本格式，其他格式保留原件并人工解读。

## 职责与依赖

- 复用现有 kptools-devkit 的发现、部署与运行入口，不复制其二进制安装逻辑。
- 在目标环境定位该 skill 的实际目录，读取其 SKILL.md 和 topdown-guide.md。
- 本目录独立分发时不含依赖 skill；不能假设相邻目录存在。
- 离线分析不需要 DevKit 或 Linux；缺少采集环境仍可交付带缺口的报告。
- 在线依赖缺失时说明缺失项，提供采集计划；不要把未执行的命令写成实测。
- 可用时复用 kpbot-profiling-advisor 的报告与离线归档规范。
- 报告 skill 不可用时按本 skill 模板直接交付，不阻断分析。
- 不修改全局 README、注册表、已有 skill 或主流程脚本。
- 不自动修改业务代码、CPU 亲和性、内核参数、BIOS 或生产配置。
- 已授权的采集可以继续；安装、权限变更和负载启动应处于实际授权范围内。

## 工作模式

| 用户输入 | 执行路径 |
| --- | --- |
| 目标 PID、服务器或 workload，要求诊断 | 明确范围 → 环境检查 → 采集 → 分析 → 建议 |
| 已有 topdown 原始文件 | 核对来源 → 离线解析 → 分析缺口 → 报告 |
| 已有前后两组数据 | 检查可比性 → 分别解析 → 比较机制与业务指标 |
| 仅截图、片段或汇总百分比 | 保留来源限制，人工记录；必要时请求原始文本 |

没有目标时先问目标进程或输入文件；可同步准备检查清单。
对业务目标未知但数据已齐的情况，先完成描述性诊断，建议标记为待确认优先级。
不要为了填齐模板而启动无关采样。

## 工作流程

### 1. 明确测量对象

读取 [采集协议](references/collection-protocol.md)。
记录目标、业务阶段、主要目标、采样范围和允许的运行成本。
区分系统、进程、核和 cgroup；系统结果不能直接归因到某个应用。
确定分析的是持续服务、短任务还是已有日志。
在完整 app-tuner 流程内运行时继承其已确认的基线和授权。
独立专项诊断不要求启动整个 app-tuner 流程。

### 2. 检查环境并生成计划

核对架构、CPU 型号、工具版本、PMU 权限和目标存活状态。
虚拟机或容器中以实际 PMU 探测结果为准，不承诺必然可用。
先确认当前版本帮助；不要跨平台照搬 PMU 事件编码或百分比定义。
明确采集时长、窗口、scope、level 以及是否需要重复。
默认先看 Level1，再按主要信号选下钻；已有全量采集无需重采。
`-L 0` 是全部 profile 维度，不代表可移植的七层树定义。

### 3. 保存原始采集

在线采集使用 [脚本用法](references/script-usage.md) 中的 collect 子命令。
采集器调用已有 run_devkit.sh，只支持明确的 PID 或 CPU 范围。
cgroup、系统全局和启动 workload 用经核实的原生入口，遵循采集协议归档。
输出目录必须是新目录，避免覆盖既有证据。
保存 stdout、stderr、命令参数、开始/结束时间、退出状态与哈希。
采集超时或失败时保留原件，不自动无限重试。

### 4. 验收和结构化

运行 analyze，将原始文本转换为 topdown-summary.json。
脚本保留每个报告块及指标行，不把多个窗口平均成一棵树。
读 [数据约定](references/data-contract.md)，复核解析状态与原始行。
`ready_for_review` 仅表示通过格式检查，仍需人工核对目标和语义。
`needs_review` 或 `unusable` 不得被表述为已确认的瓶颈。
缺测用 null 或明确的缺口表示，不能补成零。
解析器不生成根因结论，也不推断指标分母。

### 5. 分析并补证

读取 [分析与建议规则](references/analysis-playbook.md)。
从有证据的主类别下钻，列出支持和反对当前假设的观测。
按需使用热点、SPE、带宽、NUMA、业务指标或源码进行交叉验证。
补采必须与目标和阶段相关；不同时间窗口明确标注。
无法确认时交付候选解释及能区分解释的下一步观测。
不得把 stall 周期、miss rate 和 slot 百分比混为同一口径。

### 6. 形成候选动作

每条动作包含依据、成立条件、变更变量、验证指标与停止条件。
默认只提供建议；实际优化实验单独遵循用户授权。
没有收益实测时写“待验证”，不承诺固定提速比例。
优先级综合业务影响、证据强度和实施成本，不仅按百分比排序。
没有足够证据的动作可以留空，输出有针对性的补采计划。

### 7. 交付结果

使用 [报告模板](assets/report-template.md) 编写两份相互链接的 Markdown。
原始证据放在报告目录内，以相对路径链接，便于离线移交。
有 kpbot-profiling-advisor 时将 findings 与 candidate_actions 一并交给它。
不要仅把原始 topdown 输出交给报告 skill 并期待它代做诊断。
归档器可用时按其说明生成 ZIP；不可用时交付目录即可。
检查每个结论是否能追溯到文件、报告块和行号。

## 质量检查

- 对象、时间窗口、工具版本是否有记录或明确标记未知？
- 四大类是否完整，异常百分比和缺失是否已揭示？
- 子项分母是否核实，是否误把父子项相加？
- 热点与 topdown 是否测同一个对象、同一种业务阶段？
- 根因结论是否超过数据支持的强度？
- 优化建议是否包含能证伪假设的实验？
- 业务指标和正确性约束是否进入验证方案？
- 未执行动作和历史收益是否明确标注？

## 验证与维护

在本目录运行 `node --test scripts/test/topdown.test.mjs`。
测试使用合成文本与模拟采集进程，不代表硬件兼容性认证。
新工具版本应先保存脱敏真机样本，再检查格式兼容性。
遇到未知格式保留原件和警告；不要通过宽松匹配制造貌似完整的结果。
行为评估用例见 [evals/eval_queries.json](evals/eval_queries.json)。
