# 瓶颈挖掘（阶段 2）

## 何时使用

- 已经有分相位采集数据（见 `opt-measurement-infra`，独立 PR 待合入），要回答"哪个组件、哪个进程、哪个函数慢"。
- 需要判断瓶颈性质：算力受限 / 带宽受限 / 分配 churn / I/O 等待。
- 做完一轮优化，要确认热点迁移到了哪里。

## 核心原则

1. **分层下钻：组件 → 进程 → 函数。** 先看哪个组件慢，再看哪个进程慢，最后看哪个函数慢。
2. **self vs cum 是第一判据。** `cum` 高只说明调用栈总经过这里（可能是贯穿全程的框架函数）；`self` 高才是"CPU 就在这里烧掉"。
3. **先确认谁在等、谁在算。** 等待态本身就是关键信号——把"等待者"组件直接排除，搜索空间立刻收窄一半。
4. **一个结论至少要有几条互相印证的证据**（采样栈 / 容器级指标 / 算术推算 / 请求计数），避免同一个工具的同一偏置反复背书。
5. **把热点占比翻译成物理量**，才知道"为什么慢"，才能判分叉。
6. **热点会迁移。** 优化只搬走当前瓶颈，不消灭瓶颈；每轮优化后必须重新采样。

## 步骤速览

标定案例的数字链、四类瓶颈表、多源证据与坑点**只在 `references/bottleneck-analysis.md` 一处维护**，
本节只给方法论骨架与去向：

1. **按语言选采样器分层定位**：Go=pprof、Python=py-spy、C++（Go 壳内）用 perf 原生栈（pprof 默认采不到
   cgo 之下 C++ 帧，除非程序注册 `runtime.SetCgoTraceback`）、mock/minio 看进程级 CPU/RSS → 参考排障见 references。
2. **用 self/cum 判"谁在等"**：`cum` 高 + `self` 低 = 贯穿全程的框架/等待者；`self` 高才是热点。业务 CPU
   占比要给出同窗口 CPU 时间与分母（说明采样器是否采空闲线程）→ 标定案例见 references §2。
3. **多源交叉验证**：拿不同观测面的证据互相印证（采样栈 + 容器指标 + 算术推算 + 机制切分）→ references §5。
4. **量化归因分叉**：算力利用率 = 浮点量×请求数 ÷ 核当量 ÷ 峰值；先数量级粗估当闸门，再按
   "算力/带宽/分配/IO"四类判分叉。**低利用率 ≠ 带宽受限**（依赖链/访存延迟都能造成），判带宽受限必须先
   补"实测 DRAM 带宽 vs 平台可持续带宽"对照，否则标**待验证假设** → 完整四类瓶颈表与数字链见 references §3/§4。
5. **记录测量偏置**：采集器自身开销要主动写出，并说明如何被"采集/计时分离"公平抵消 → references §6。
6. **优化后重新采样做迁移可视化**：首次诊断不要求并排火焰图（尚无"优化后"版本），复验时才要求对照采样
   确认热点迁移 → references §7。

## 门禁

- [ ] 分层到函数级，且用了正确的语言采样器
- [ ] 用 self/cum 明确了"谁在等、谁在算"，且"业务 CPU 占比"给出同窗口 CPU 时间+分母、说明采样器是否采空闲线程
- [ ] 至少 3 条来自不同观测面的证据互相印证
- [ ] 做过单位归一化 + 数量级闸门
- [ ] 已判定瓶颈类型（算力/带宽/分配/IO）；带宽受限已补实测带宽 vs 可持续带宽对照（否则标待验证）
- [ ] 记录了测量偏置及其对对比的影响
- [ ] 首次诊断不要求并排火焰图；优化后复验才要求对照采样并确认热点迁移

## 产物

- 瓶颈分析报告：分层结论 + 证据链 + 量化归因 + 瓶颈分型 + 候选方向
