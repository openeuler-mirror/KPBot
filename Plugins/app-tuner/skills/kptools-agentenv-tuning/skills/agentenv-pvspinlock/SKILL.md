# ARM Pvspinlock

## 输入与共享约定

需要 Host/Guest 关系、两侧运行内核与补丁、Hypervisor 版本、vCPU 配置、
后台负载、Guest 锁热点及 AgentENV 压测命令。
读取共享 `references/validation.md`；源码布局下为 `../../references/validation.md`。
共享优化流程见 `references/optimization-process.md`；源码布局下为
`../../references/optimization-process.md`。
环境补采使用 `scripts/collect_environment.sh`，源码布局下为
`../../scripts/collect_environment.sh`，Host 与 Guest 分别采集。

## 补丁来源

以下链接用于定位 openEuler 的相关实现，使用前核对目标分支、实际提交和依赖：

| 组件 | 补丁入口 | 核对重点 |
|---|---|---|
| kernel | <https://atomgit.com/openeuler/kernel/pull/26044/diffs> | 内核侧实现、依赖配置及 Host/Guest 配套要求 |
| QEMU | <https://atomgit.com/openeuler/qemu/pull/2008/diffs> | 对应 VMM 的能力暴露与使能方式 |
| libvirt | <https://atomgit.com/openeuler/libvirt/pull/444/diffs> | 管理层向 VMM 传递相关配置的适配 |

链接是源码线索，不证明当前系统已经包含或启用了功能。按项目实际使用的组件选择
适配范围；Firecracker 项目不能直接应用 QEMU/libvirt 补丁，也不必为了使用
PVspinlock 自动引入这些组件。

## 检查适用性

1. 确认目标是 Guest 中的自旋锁竞争。只有 mutex 等待或用户态锁热点时，
   先分析其实际路径，不据此认定 Pvspinlock 适用。
   在物理 Host 上完成采集或发现 ublk daemon 不能替代 Guest 证据；
   没有明确 Guest、匹配实现和真实负载时，只输出诊断/阻塞项，不运行替代微基准。
2. 检查 Guest 的锁等待、锁持有者抢占、vCPU runnable/运行时间、Host 调度压力。
   明确物理 CPU 是否超分配及后台负载是否可复现。
3. 获取所用 Pvspinlock 的准确实现来源、commit、配置和使能条件，
   检查 Guest/Host 的能力协商与运行时生效证据。
4. 对照实现追踪等待、释放和唤醒路径，以及禁用后回退路径。

以当前项目的实现确认等待、让出 CPU 与唤醒协议。不同内核/VMM 的使能方式不通用，
不能把其他 VMM 的配置直接套用到 Firecracker，也不能编造 CONFIG 开关或调用编号。

## 实施

### 核对实现与依赖

1. 记录当前 Host/Guest 内核、VMM 和管理层的版本、源码提交及构建配置，
   确认项目如何选择 Guest 内核、启动参数与模板。
2. 对照补丁入口取得实际差异和完整依赖，确认相关代码是否已合入当前分支；
   不重复应用已有改动，也不把网页 HTML 当补丁文件。
3. 在独立测试源码树核对适用性，可用 `git apply --check` 检查已取得的补丁。
   存在冲突或缺失接口时先完成兼容性分析，不强行忽略冲突或清理原工作区。

### 准备 Host、Guest 与 VMM 配套

1. 根据实际源码确认 Host 提供的能力、Guest 使用的锁实现及两者的协作协议。
   只更新其中一侧不足以说明功能可用。
2. 确认当前 VMM 如何请求或暴露该能力；若尚未接入，应准备相应适配，
   不把其他 VMM 的配置选项直接写入 Firecracker 配置。
3. 从实现中明确启用、禁用、默认状态及回退方式。若控制接口是 Guest 启动参数，
   切换后需重新启动 Guest；仅修改配置文件不会改变已运行内核的状态。
   对提供 `nopvspin` 接口的实现，可将其用于禁用对照，但先核实该参数的实际语义。
4. 实验性的 Host 全局默认修改必须说明影响范围并单独取得授权，
   不将其当作生产 VMM 能力协商的通用替代方案。

### 构建、部署与启动

1. 保存原内核、配置、启动项和回退步骤，按项目真实流程构建必要组件，
   记录最终配置差异、产物标识及 Host/Guest 对应关系。
2. 内核安装、Host 重启和 Guest 替换分别遵循授权；先在可恢复测试环境验证，
   不因补丁可以编译就直接替换正在使用的环境。
3. Guest 内核或启动参数变化后，重新创建匹配的测试 Guest；涉及快照恢复时，
   为相应状态准备匹配模板/快照，不将旧内存快照误当作新内核或新开关已生效。

### 核实运行状态

1. 启动后重新检查两侧运行版本、VMM 实例及 Guest 的实际启动参数。
   核对 Guest 日志、能力协商结果或实现提供的计数，不能只看源码符号和配置文件。
2. 在代表性锁争用下核查等待、让出和唤醒路径，确认没有丢失唤醒、挂起或内核异常。
3. 分别验证启用与禁用状态，确认对照真正切换了机制。无法确认时继续诊断，
   不把“配置已改”写成“优化已生效”。

缺少任一侧实现或权限时输出 `blocked` 及缺失证据。裸机或普通容器不能
替代 Guest/Host 协同验证；缺少机制时不要退化为修改用户态 spin 参数。

## 单项实验与消融

1. 根据当前业务确定沙箱规格、负载、超分水平、预热方式和采样预算，不预设固定数值。
2. 通过沙箱 ID、运行配置或串口路径核对 Firecracker PID，再识别实际 vCPU TID；
   结合 `ps -T`、`taskset -pc` 等检查线程与 pCPU 映射，区分物理核、SMT 和拓扑。
   不能只按同名进程选目标，或把进程整体 CPU mask 当作所有 vCPU 的实际绑定。
3. 若测试需要调整绑定，先保存每个目标线程的原值，按实际拓扑执行并复核，
   只修改已确认属于本轮测试的对象。
4. 在相同内核实现、规格、绑定、资源限制及背景负载下对照机制启用/禁用。
   按计划重复或交错执行；需要不同超分水平时，在每个水平内分别比较。
5. 每次启动或恢复后核对开关和目标身份，明确计时边界，并在计时后检查业务结果。
   不让一侧包含额外预热、校验或清理开销而另一侧不包含。
6. 执行项目真实负载，保存各轮原始结果、单位、失败和重试记录。
   可用机制相关微基准辅助分析，
   但结论只能覆盖实际测试的负载。
7. 多项消融使用同一业务用例，保持其他有效配置不变并说明机制依赖；
   不将其他资源变化或不同负载的收益计入该机制。

## 验证与回退

- 功能：压力下锁最终可获取、唤醒不会丢失、沙箱创建/恢复正常；检查 hang、
  soft lockup、watchdog 和内核异常。运行时跟踪需能支持等待/唤醒路径的判断。
- 性能：按相同统计规则比较项目目标指标、Guest 锁等待、调度等待及 Host CPU 开销，
  同时报告收益、退化或不确定性，不能通过选择性剔除样本制造收益。
  CPU 利用率下降不能单独证明业务性能提升。
- 空载与带负载场景分别记录，避免用不同超分配比或后台进程解释机制收益。
- 出现功能问题、性能退化或资源代价不符合目标时，按已核实的禁用路径或旧
  Guest/Host 启动项恢复，重新检查功能和原基线；需要重启时仍受相应授权约束。
- 还原本轮调整的线程绑定及配置，只清理本轮创建的沙箱、进程和测试资产，
  不对不属于本轮的实例做批量清理。

按共享结果契约记录实际负载、对照配置、收益或退化及回退结果。
附上实际采用的补丁/提交、构建身份、开关生效证据、线程映射、测试命令和原始结果路径。
未生效、未实测与实测无收益分别说明；未实测时 `gain_pct=null`，不承诺固定收益。
