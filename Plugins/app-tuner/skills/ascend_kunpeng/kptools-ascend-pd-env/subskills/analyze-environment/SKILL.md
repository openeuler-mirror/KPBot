# P/D 单环境分析

## 工作流程

1. 确认采集包、目标容器和角色。先读 `collection_meta.json`；有多个容器时，
   使用用户指定的对象，按 `folders` 映射找对象目录（旧包没有映射时核对目录与
   对象名称）。多对象包、未标角色或标为 `PD` 的包，由用户确认该对象的角色；
   整包标签只作参考。缺少元数据时，只分析能确认身份的 `inventory.json`，
   并注明缺项。分析两侧时逐份处理。
2. 读目标的 `inventory.json` 和 `SUMMARY.txt`，按需查看
   `docker_inspect_safe.json` 或随包的 `环境报告.html`。归档包先列成员再读取
   选中的普通文件，不解包到工作区。报告或摘要缺失时，以结构化结果和实际错误
   记录为准。
3. 先检查 `collection_status` 里的成功、跳过、失败和超时，再解释字段。区分
   运行进程的实际参数、Docker 配置的默认值和探针测不到的项。缺采写明原因；
   例如包列表超时时，将 vLLM 和 torch_npu 版本标为「未采到」。

| 范围 | 重点 |
|------|------|
| P / D 共用 | OS、内核、CANN/驱动、vLLM/torch_npu、实际 Python、NPU 快照、CPU/内存配额与 cpuset |
| P（Prefill） | 已采到的预填充、并发和批处理启动参数，以及 CPU/NUMA 资源限制 |
| D（Decode） | 已采到的解码并发、调度与 KV transfer 启动参数，以及内存、设备映射和亲和性 |

## 输出

每个对象各出一份分析（例如 `P-环境分析.md` 或 `D-环境分析.md`）。记录角色及
其来源、节点、容器、采集时间、采集包路径、结论状态（完成 / 部分完成 / 无法分析）
和证据位置。每条结论注明来自哪个文件和采集项，把可核实事实与待核实线索分开。
环境快照不能证明性能瓶颈；不复制完整环境变量或敏感启动参数。
