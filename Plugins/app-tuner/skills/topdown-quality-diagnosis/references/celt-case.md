# CELT 案例经验

来源：用户提供的《Opus CELT 编码 Top-down 采集范围排查案例》摘要。
这是历史案例，不是本技能的实机认证记录。
平台 HI1650V100，DevKit 26.2.RC1。
目标是 CELT 编码阶段，而旧采集覆盖整个测试框架命令。

## 已记录事实

- 原报告 Bad Speculation 13.03%，IPC 3.09。
- 独立热点报告出现 sinf64、Python 解释器及 UNKNOWN 地址。
- 旧框架包含 PCM 生成、预热、计时、校验与回解码。
- API 计时边界与进程 PMU 范围不同。
- PID 附加的一次请求为 5 秒，实际约 246 ms。
- 该次 worker 以 SIGSEGV 终止，虽已输出 PMU 计数也不是成功性能实验。
- 该版本单 PID 模式曾明确提示忽略 -r user。
- 案例没有验证 -D 的单位、支持及组合行为。

## 支持的判断

框架工作进入热点，说明需要检查采集范围。
原生持续 worker 可减少框架工作，有助于附加。
但它仍有初始化和预热，不能省略窗口验证。
按 PID 选对 worker 与 worker 运行是否完整是两项独立检查。
只有同窗完成帧数才能作每帧事件计数分母。

## 不支持的判断

不能确定 sinf64 的全部事件都来自 PCM 生成，仍需调用栈。
不能用独立热点的份额从 Top-down 13.03% 中扣减。
不能从正常的短 Demo 推导不同构建或不同阶段的优化收益。
不能将采集期开启与崩溃相关直接升级为工具缺陷。
两次不同非法访存现场不能在寄存器证据不足时合并为同根因。

## 可复用选择

完整框架适合 API 耗时及正确性验证。
持续原生 worker + 稳态窗口适合阶段 Top-down 定位。
精确边界需求可考虑程序事件控制，但必须验证会话控制范围。
不同入口产生不同证据，报告中分别说明用途。
