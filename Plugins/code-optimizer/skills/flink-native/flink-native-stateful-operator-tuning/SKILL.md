# Flink 向量化栈有状态算子性能优化

当流式有状态算子从逐行对象模型迁到向量化引擎后出现"内存爆炸"或"残余性能差距"时，
使用本 skill。核心判断：**问题极少出在计算内核本身，而在状态值的数据形态、跨语言
数据桥的传输税、以及两者的叠加**。本 skill 沉淀的是可迁移的归因与修复方法；实测
数字、批参数与内存配置必须在目标环境重新测量。

## When to use

满足以下任一条件时进入本 skill：

1. **内存形态问题**：向量化实现的状态占用比原生实现（如 Flink 原生 TopN 函数族）
   高出数倍——RSS 或堆分配计数远超预期，GC 沉重，重负载查询堆耗尽。
2. **残余差距问题**：算子执行逻辑已按原生流程重写并对齐，端到端仍差数倍，且差距
   不随算子优化收敛。
3. **新增有状态算子**：要在向量化栈上翻译/实现新的 keyed 流算子，需要知道计划节点
   契约、状态形态选型与语义对照怎么做才不踩坑。
4. **对照评估**：需要可信的 native 栈 vs 原生栈（双端 Flink）性能对比结论。

不适用的情况：

- 只允许调配置（TaskManager 内存、并行度、table.exec.\* 参数）：走 app-tuner 大数据域
  与其基准协议，不能称为源码优化。
- 纯批式算子内核（无状态、无跨语言边界）：向量化/循环展开类通用技能更对口。
- 语义兼容性调研（不打算改码）：references 的语义对照表可读，但流程不启动。

## Core findings

1. **状态值形态决定内存命运。** 向量化引擎的列式向量（RowVector 类）是"引用结构"：
   行数据分散在多个子向量、多个缓冲、多次堆分配里；把它原样存进 keyed state，一行
   数据的驻留成本是紧凑行编码的数十倍（实测案例：一行约 6.9KB、约 18 次堆分配的
   引用结构 → 约 179-280B、1 次分配的紧凑编码）。**先审形态，再谈优化。**

2. **物化次数不等于驻留行数。** "每批都会物化"不必然导致爆炸——驻留才是爆炸的
   必要条件（反例：FirstN 类算子同样每行物化、零驻留、从不爆炸）。判定顺序：
   先问"哪些行会留在状态里"，再问"留下的行以什么形态存在"。

3. **批式摊销在行级状态更新上失效。** 向量化引擎的收益模型是"按批摊薄固定开销"；
   keyed 流算子按 key 逐行进出状态，批内行通常分属不同 key——"一批数据共享一次
   状态操作"的摊销假设不成立。设计阶段应显式否决依赖共批摊销的状态布局方案。

4. **残余差距先查跨语言数据桥，再查算子。** 算子逻辑对齐后仍未收敛的差距，典型
   归属是数据桥的三类传输税（详见姊妹 skill `flink-native-jni-transport-tax`）：
   引用结构未实体化、编码税（Base64 类）、字符串拷贝链；另加小批固定开销（批
   越小、固定成本占比越高，1 行批时占比接近 100%）。

5. **性能结论必须行为冻结护航。** 任何优化前后，changelog 输出（+I/-U/+U/-D 折叠
   回最终结果集）必须与基线精确一致——多行、少行、字段不一致任一出现，性能数字
   全部作废；承诺逐条 changelog 的用例（下游按序消费/审计回溯）还须按 key 核对
   RowKind、字段与顺序（折叠终态一致不等于序列一致）。性能提升的零语义代价是
   放行条件，不是附属检查。

6. **量化收益必须带测量条件。** 本域公开数字（如"传输层单阶段消除约 87% 差距"）
   均为自测口径（nexmark 类负载、固定事件规模与并行度、blackhole sink、双端同日
   锚定）。换负载、换并行度、换数据分布必须重测；引用时标注口径。

## Methodology

按以下 6 步执行；每步有明确产物，达到能决定下一项代码修改的程度即停。

1. **冻结双端基线。** 同一查询集（nexmark 类）、同一事件规模、同一并行度、同一
   sink（blackhole 吞输出），双端（native 栈与原生栈）**同日锚定**跑基线；内存口径
   对齐——TM 堆不齐须**双端同口径重跑**、异配置轮次不进双端比值（详见
   app-tuner 侧 flink-native-bench-protocol 协议）。
   产物：基线三指标表（duration / 传输字节 / RSS 峰值）与环境口径记录。
   基准协议细节走 app-tuner 侧 `flink-native-bench-protocol`。

2. **三层拆账归因。** 把端到端差距拆到：算子层（执行逻辑 vs 原生函数族逐段对照）、
   传输层（数据桥税种清单核对）、内存层（状态形态账单——见第 3 步）。每层给出
   "本层能解释多少差距"的量化估计；一次只允许结论指向一层。
   产物：差距归属表与证据链。

3. **状态形态审计（内存层命中时）。** 取一条代表性数据，数它"住进"状态后的账单：
   引用了哪些缓冲、几次堆分配、驻留生命周期到哪结束；再数优化候选形态（紧凑行
   编码/有界缓存）的同口径账单。用"物化次数 vs 驻留行数"判定因果（Core finding 2）。
   产物：单行内存账单对照 + 驻留因果判定。

4. **语义对照冻结需求。** 原生实现的算子规格（策略分派、函数族行为、NULL/边界、
   changelog 节奏）逐项列出，标注 native 实现的对齐/偏差项——偏差是"已知差距"
   还是"必须修"，在改码前裁决（references 的语义对照表为模板）。
   产物：语义对照矩阵 + 差距处置清单。

5. **分阶段实施，逐阶段门禁。** 每阶段只动一个机制（先形态、后传输、再参数），
   独立编译部署、独立复测三指标、独立行为冻结核验；阶段收益不达预期时先核对
   归因（是否 SPEC 已裁决的预期无效——预期结果不等于优化失效）。
   产物：分阶段三指标全表 + 每阶段 changelog 一致性证据。

6. **交付与归因收束。** 分开报告：算子层收益、传输层收益、参数收益；给每仓
   改动清单与回退方式；残余差距列"归属 + 改进方案清单"，不允许"已优化"模糊
   收尾。产物：终态对照表（优化链全链路）+ 残余差距账本。

## 检查清单（内存形态修复专用）

- [ ] 状态值是否为引用结构（列向量/对象图）而非紧凑编码（行式字节/定长结构）？
- [ ] 驻留行数是否随 key 基数与时间无界增长？有界缓存（LRU 上限）是否对齐原生
      口径（如原生 topn-cache-size 类配置）？
- [ ] 物化点是否收窄到批缓冲生命周期边界之内（批结束即释放，不向状态泄漏）？
- [ ] 状态 TTL / 清理路径是否与原生语义对齐？
- [ ] 修复后单行账单（字节数 + 分配次数）是否实测复核，而非推算？
