# 新增算子语义参数的贯通改动 — 方法细节

> 来源与适用范围：本文整理自原始工程实践记录（`SKILLS_ALL.md` 汇编稿），未提供可公开引用的上游文档，也未经独立复现。文中阈值、收益倍数与机器相关数据绑定当时的生成器版本、硬件与配置，迁移到其他环境前必须重新测量。置信度：中；未覆盖范围与平台差异见正文。

## 适用背景

目标生成器有多个对外表面：配置文件与命令行、生成器的入口函数、产物导出的 C 符号、测量与校验工具、调优器，以及测试。一个语义参数只有在这六处都落地，才算真正可用。只做其中几处，会出现“命令行能传但测量工具按旧假设解释”“生成正确但基准数据异常”这类半通状态，而这类状态的排查成本通常高于把六处一次做完。

## 1. 先判断参数的归属

改动之前先回答一个问题：这个参数改变的是算子的行为，还是只改变调用方式。

改变算子行为的参数必须进入内核配置，并参与生成。缩放系数与累加系数属于这一类：它们决定存回序列是累加形式还是纯运算形式，因而改变指令序列。

只改变调用方式的参数进入运行器或工具层，不进入内核配置。例如输出指针的排布约定，若生成的序列按同一套寻址执行，那么它只是调用方与生成器之间的一致约定，不应作为内核配置项参与搜索。

判断的依据是：该参数的不同取值是否需要产生不同的指令序列。需要，则属于内核配置；不需要，则属于调用约定。归属判错会导致两种后果：把调用约定塞进内核配置，搜索空间会被无意义地放大；把行为参数留在工具层，生成物与声明不符。

## 2. 必须贯通的层

改动按下列顺序落地，顺序本身也是排查顺序。

第一层是配置。新增字段、给出默认值、写明与其他字段的约束关系。约束关系包括取值域与互斥条件，例如某系数仅在特定打包方式下有意义。

第二层是生成。入口函数接受该字段并把它转换成对序列的选择。此层必须做到：字段的组合不被接受时直接报错并指出冲突项，而不是静默降级到某条默认序列。

第三层是导出符号与接口约定。若该参数需要在运行期传入，就要有对应的入口函数，并明确参数顺序与类型。此层一旦发布便难以更改，因此需要一次定准。

第四层是命令行。参数名与默认值要和配置文件保持一致，避免出现“配置文件能设、命令行设不了”或两者默认值不同的情况。

第五层是测量与校验工具。工具按布局与语义解释输入输出，任何涉及寻址、转置、系数的新参数都要在这里同步。这一层最容易被遗漏，因为它不参与生成，改动看起来与算子无关。

第六层是调优器。新参数的候选是否进入搜索、是否与既有候选成对出现、种子是否落在合法域内，都在这层确定。

第七层是测试。测试要覆盖新旧入口在等价输入上给出相同结果，以及非法组合被拒绝。

## 3. 旧入口的兼容

新增入口时，既有入口必须保持语义等价。这条要求常被忽略，因为旧入口的签名里没有新参数，看上去无需处理。

以参考实现为例，旧入口有九个参数，没有缩放与累加系数；偏置功能通过一个编译期开关实现，实现方式是在存回时把已有的输出值与乘加结果相加。为了让旧入口在偏置构建中保持这一行为，其内部把累加系数置为一，而不是零。若顺手把旧入口改成纯运算形式，偏置构建的结果会丢掉原有的输出值，而这处差异只在带偏置的用例中体现。

由此得到一条通用做法：新入口承接全部语义，旧入口按它原本的语义映射到新入口的一组固定取值上，并在注释与测试中写明这组映射。映射关系一旦确定就不要变动，因为外部调用方按旧入口的行为编写了代码。

## 4. 默认值不改变既有产物

新增字段的默认值不得改变未启用该字段时的产物。实现上有两条要求。

其一，默认值不写入序列化配置。若序列化结果包含了新字段的默认值，那么同一份配置在改动前后会产生不同的内核标识，历史记录随之失去可比性，此前调优得到的结论无法复用。

其二，生成结果应当逐字节一致。用未启用新字段的配置生成一次，与改动前比对摘要，两者相同才说明既有路径未被触动。这条检查适合写成单元测试，成本低而覆盖面明确。

## 5. 涉及寻址的语义必须成对修改

转置布局这类参数改变的是操作数在内存中的解释方式。此时生成器与测量工具必须同时修改，因为两者各自独立地计算索引。

只改生成器会造成一种特殊现象：产物本身的数值正确，但测量工具按旧布局解释结果，于是基准数据异常；若工具还负责准备输入，它会按旧步长写入，越界或读到相邻区域，表现为偶发的大数或崩溃。

修改时有三处需要逐一核对。第一处是生成器里操作数基址的推进方向。第二处是打包路径的基址偏移，某些转置组合下打包缓冲的起始位置与不转置时不同，偏移算错会整体错位一个块。第三处是测量工具里的参考实现与容差，参考实现必须按同一布局计算。

核对方法是构造一个转置与非转置结果已知互为转置的最小形状，逐元素比对；若整体错位，说明偏移有误；若只有边界元素错，说明步长有误。

## 6. 诊断信息与失败记录

编译失败、生成失败这类异常路径容易被静默吞掉：构建结果对象里只保留成功标志，标准错误被丢弃。一旦如此，排查时会看到“失败但没有原因”。

因此在扩展接口的同时，应当把标准错误一并保留在构建结果中，并把失败条目按明确的规则处理：失败记录不写入调优历史，避免污染搜索输入；而失败原因要写入日志或记录对象，供人查看。这两件事并不矛盾，前者约束持久化的范围，后者保证信息不丢。

## 7. 验证

验证按四组组织。

第一组是新旧入口等价。对同一组等价输入，旧入口与映射后的新入口给出相同结果，覆盖默认值、非默认值与非平凡系数。

第二组是默认产物不变。未启用新字段的生成结果与改动前的摘要一致。

第三组是非法组合被拒绝。每个应当报错的组合各有一条用例，断言错误信息指出具体冲突项，而不是只断言抛出异常。

第四组是测量工具与生成器一致。用工具自带的一致性检查跑一遍全部布局组合，确认工具解释与生成物行为一致。

## 8. 约束

实现范围是单机、单线程、FP32、两种转置布局。以下情形未经验证：多线程下的布局推进；双精度；转置与其他打包方式的全部组合；跨库集成的接口稳定性。

在上述范围之外，寻址核对需要重新做一遍，不能假定本文的偏移结论成立。
