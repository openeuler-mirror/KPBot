# OpenZL 压缩内核性能优化

当目标是获得可合入 OpenZL、压缩率不变、输出逐字节一致且跨架构可复现的吞吐提升时，使用本 Skill。优化对象覆盖三层：codec 内核（`src/openzl/codecs/`、`src/openzl/fse/`）、binding/公共 API 层、benchmark 场景层（`benchmark/unitBench/`）。本 Skill 沉淀的是从一轮完整优化流水线（KV Cache BF16 路径：Encode 2.16x、Decode 3.44x，5 个提交全部通过逐字节验证）提炼的可迁移方法；所有收益数字、门限阈值、命中率都必须在目标机器与目标数据分布上重新测量。

## When to use

满足以下任一条件时进入本 Skill 流程：

1. **熵编解码内核是热点**：Huffman/FSE 的 encode/decode、直方图统计、位流读写函数在 perf 采样中占主导，需要优化查表、位操作、循环依赖或表布局。
2. **数据并行 codec 内核是热点**：bitpack/bitSplit/delta/deconstruct 等规则数据通路，需要判断手写 SIMD 是否有增量收益。
3. **需要为某类数据分布选择熵 codec**：Huffman token 打包、FSE、自动选型、multi 分块之间的吞吐/压缩率取舍。
4. **binding 或 benchmark 层出现非计算热点**：malloc 页故障、重复初始化、冗余扫描等框架开销吞噬内核收益。
5. **需要把已验证的优化跨架构移植**：aarch64 守卫的内核路径迁移到 x86 或反向，需要重新归因收益归属。

不适用的情况：

- 只要求诊断或报告：保持只读，不自动修改源码。
- 目标是压缩率提升而非吞吐：那是 codec/图结构设计问题，不是本 Skill 的内核调优。
- 引擎 graph 路径（`cgraph`/`decoder_fusion`）热点：属引擎层工程，本 Skill 只覆盖到场景层可见的内核。
- 没有代表性数据或正确性参考：先补齐（见 `openzl-bench-protocol`），不能凭合成随机数据宣称优化成功。

## Core findings

Core findings 只记录性能为什么变化、收益属于哪一层以及结论的适用边界。

1. **熵解码的瓶颈常在表访存而非指令数。** 按 tableLog 展开的解码表可达数百 KB～2MB，远超 L1D（典型 64KB）；随机 gather 使每个符号查表都在吃内存延迟。判据：IPC 显著低于机器稳态值且 L1-dcache miss 率高（实测案例 IPC 1.4、L1 miss 12.7%）。此时指令数优化（实测 -37.5% 指令/符号）收益落在噪声内，必须转向缩小热表或改善局部性。

2. **Huffman 前缀码的块恒等性质允许小根表替代大表。** 长度 L 的码字在 tableLog 位索引空间中占据 2^(tableLog-L) 个连续槽位的恒等块，块内表项相同。预计算 10-bit 根表（4KB，常驻 L1D），命中时一次 L1 查表，未命中回退全表。实测案例：命中率 96.5%（数据分布越倾斜命中率越高），Decode +132%、IPC 1.20→2.51。

3. **启用门与回退路径是特例优化的组成部分。** 根表启用需三重门：大表才值得（tableLog ≥ 16）、恒等块占比达标（实测门限 85%，O(1024) 一次性探测）、位流窗口可表达（四流 bitsConsumed ≤ 54）。不满足任一门自动回退原路径——特例快路径不得破坏通用语义。

4. **位流编码的收益来自消除冗余工作而非单条指令。** 有效组合：value-clean 前置下用快速加位（省掩码与溢出检查）；两字段查表项打包为 u32（一次 load 取双字段）；删除仅服务已死分派的冗余全趟扫描；库内 scratch arena 消除每次调用的页故障。四项合计实测 Encode +13~22.5%。

5. **展开深度受位容器宽度硬约束。** u64 位容器上 kUnroll × 最大码长 + 7 ≤ 64；超限会在 reload 前溢出（实测 3×20+7=67 越界），大于阈值档位必须强制降回安全深度或引入残差冲刷（先冲刷部分和再继续）。

6. **熵 codec 选型是数据分布的函数，不能写死。** 实测两案例方向相反：8-bit 指数流（256 符号、高倾斜）FSE 解码快 43%~63%；4-bit 指数流（16 符号）两两打包 token 后 Huffman 快近 4 倍。选型结论必须用目标分布实测（`-p` 模式切换），并区分编码方向与解码方向分别取舍。

7. **基准 harness 自身可能成为热点并污染归因。** 每迭代 malloc/free 大缓冲产生页故障（内核态 el0_da 可占 8~15%）、无预热的首轮冷启动，都会压低内核真实吞吐。先审计 harness，再测内核；缓冲复用实测带来 +50%——这部分收益属于场景层，不能计入内核优化。

8. **自动向量化对位操作/查表分支密集代码常为负收益。** SVE/SVE2 自动向量化使位拆包与 Huffman 查表代码产生大量 gather/permute/谓词开销（实测指令 +17%，净负 4~36%）。反之，纯数据并行内核（deconstruct 类）gcc -O3 已自动向量化，手写 NEON 实测持平（+3.8% 孤立、全链路 ≈0）。结论：先看反汇编确认 autovec 是否已生效，再决定是否手写。

9. **架构守卫改变收益归属。** `#if defined(__aarch64__)` 守卫内的优化在 x86 不编译，跨架构 A/B 时"另一架构无收益"可能是守卫所致而非机制失效；纯 C 优化则天然可移植（实测同批纯 C 优化三机全生效 +63~107%）。报告收益必须注明生效平台与守卫状态。

10. **无损优化的正确性门禁是逐字节一致。** 压缩率不变、输出位流与基线逐字节相同、全量 gtests 通过、零新增告警，四项缺一不可。任何"数值等价但字节不同"的改动都是格式变更，需按格式版本演进处理，不得混入性能提交。

11. **负结果与对抗审核是流程的一等产出。** 一轮完整流水线中对抗审核三次修正方向（查表掩码越界、根表命中率假设 96.5% 而非 >99%、展开溢出边界），五项候选被实测或审查否决（见 references/history-lessons.md）。指令数大降但无收益、实测回归、与 autovec 持平——这些结论避免了后续在死路上重复投入。

## Methodology

按以下 6 步执行，每步有明确产物；证据足以决定下一项修改即停止探索。

1. **冻结目标与正确性门禁。** 确定优化场景（unitBench 场景名）、数据分布（来源与熵/Top-k 统计）、基线吞吐与压缩率、门禁（逐字节 round-trip + gtests + 零新告警 + 压缩率不变）。产物：工作负载清单与基线记录（构建与运行见 `openzl-bench-protocol`）。
2. **审计 harness 并建立干净基线。** 确认场景循环无每迭代 malloc、无冷启动计入、绑核口径明确。若 harness 有缺陷先修 harness 并单独记录收益。产物：可信基线与 harness 审计结论。
3. **画像归因，区分瓶颈类别。** perf stat（IPC/branch-miss/cache-miss）+ perf record 热点 + 按需 topdown（前端/后端/退休/错误推测）。IPC 低且 L1 miss 高 → 访存类（表布局/局部性）；IPC 高但指令数多 → 计算类（指令削减/融合）；前端受限 → 分支/取指（消除分支、块恒等查表）。产物：热点表 + 瓶颈类别判定 + 理论收益上界。
4. **按类别生成候选并排序。** 访存类：根表、缩小热结构、打包字段；计算类：删冗余趟、快速位写入、循环携带变量、融合；harness 类：缓冲复用、arena。每个候选写明机制假设、启用门、预期观测变化。读 [entropy-kernel-optimizations.md](references/entropy-kernel-optimizations.md) 获取已验证技术的适用条件与门禁推导。产物：候选排名与可证伪假设。
5. **最小实现与门禁化。** 隔离副本实施最小修改；每项特例快路径配启用门与原路径回退；不改变输出位流。核对位容器宽度约束、查表掩码边界、线程安全（arena/缓冲的所有权与 NULL 回退）。产物：补丁 + 门禁条件清单。
6. **验证、跨架构复测与归因交付。** 门禁四项全过 → 单机 A/B（含反序复测）→ 需要可移植性结论时在其他架构复测（注意守卫状态）→ 分层归因报告（内核收益 / harness 收益 / 配置收益分开）。产物：对比数据、适用边界、剩余空间诚实评估。

## Codec kernel checklist

### 熵解码内核

1. 先测 IPC 与 L1 miss：访存 bound 才考虑表布局优化，计算 bound 先做指令削减。
2. 大表（tableLog ≥ 16）评估根表：O(2^rootBits) 一次性建表 + 三重门（表大小 / 恒等块占比 / 位窗口可表达），根表大小以 L1D 常驻为限（10-bit = 4KB）。
3. 位流索引计算改循环携带补码移位量（k = 容器宽 - tableLog - bitsConsumed），每符号两次变量移位降为一次；bitsConsumed 按展开块批量重建。
4. 多流（X4）结构保持位流独立，流间只做 reload 状态汇合；扩流数（X8 等）属格式变更，单列评估。

### 熵编码内核

1. 确认 ctable 规范性（Kraft 不等式/value-clean）后才可用无检查的快速加位；非规范表走通用路径。
2. 查表项字段打包（双字段 u32），消费点同步改造；保持与平台专属路径（如 avx2）的一致性。
3. 删除仅为死分派服务的预扫描/统计；分派条件收紧后重新确认无消费点。
4. 展开深度按 maxCodeLen 分档：kUnroll × maxCodeLen + 7 ≤ 64，超限档位降深度或加残差冲刷。
5. 直方图：优先展开多路独立累积（实测 4x +10.8%）；多桶拆分工作集变大可能回归，必须实测。
6. 每调用大分配（表/工作区）改调用方持有的 scratch/arena，NULL 自动回退分配，保证线程安全。

### 数据并行 codec 内核

1. 先看反汇编确认 gcc -O3 autovec 是否已覆盖；已覆盖则手写 SIMD 无增量（实测持平）。
2. 位拆包/查表/分支密集内核禁止依赖自动向量化（实测负收益），收益来自标量指令削减与表布局。
3. 内核是纯函数（不分配内存、不改全局状态），优化不破坏与 binding 的契约。

### binding / benchmark 场景层

1. 场景循环外提升到 preparation，循环内零分配；跨迭代复用缓冲需保证输出正确性不受残留数据影响。
2. 输出头部布局（元素数/类型/模式字段）变更会使新旧输出不兼容，基准对比时保持同一头部协议。
3. 熵模式切换参数（如 unitBench `-p`）encode/decode 两侧必须一致，否则 round-trip 失败。

## Anti-patterns

| # | 反模式 | 为什么错 | 正确做法 |
|---|--------|---------|---------|
| 1 | 看到指令数多就优化指令 | 熵解码常是访存 bound，指令削减收益落噪声 | 先 IPC + L1 miss 定类别 |
| 2 | 大表直接全量查表并停止优化 | 每符号吃内存延迟 | 评估根表/块恒等性质 |
| 3 | 特例快路径不设启用门 | 数据分布变化时静默错误或回退抖动 | 三重门 + 原路径回退 |
| 4 | 无视位容器宽度硬约束加深展开 | reload 前溢出，越界读表 | kUnroll × maxCodeLen + 7 ≤ 64 |
| 5 | 非规范表用快速加位 | value-clean 是其前置条件 | 门控规范性检查 |
| 6 | 熵 codec 选型写死或照搬其他数据集结论 | 选型是分布函数，两案例方向相反 | 目标分布 `-p` 全模式实测 |
| 7 | 把 harness 修复收益计入内核优化 | 归因错误，无法跨场景复现 | 分层归因，单独记录 |
| 8 | 对查表/位操作代码开 `-march` 自动向量化 | gather/谓词开销实测净负 | 标量优化 + 表布局 |
| 9 | 纯数据并行内核手写 SIMD 前不看反汇编 | autovec 可能已覆盖，手写无增量 | 先确认现有代码生成 |
| 10 | 跨架构 A/B 不核对架构守卫 | 守卫内代码未编译，误判机制失效 | 先检查守卫与编译路径 |
| 11 | 接受"数值等价"代替逐字节一致 | 位流不同即格式变更 | 门禁四项：逐字节/gtests/告警/压缩率 |
| 12 | 首个候选通过即结束 | 只证明可优化，未证明预算内最优 | 热点仍主导时再筛不同机制候选 |
| 13 | 丢弃负结果记录 | 后续在死路上重复投入 | 负结果连同证据入档 |
