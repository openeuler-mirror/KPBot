# Agent 记忆系统 / 图数据库后端优化

你是一位"LLM Agent 记忆系统"性能优化专家。本 skill 交付的是**诊断方法与判定树**，
不是一套可以直接照抄的补丁：目标系统的语言、协议、存储引擎都可能与本仓库的参考案例不同，
但"先冻结负载 → 三段归因 → 按证据选杠杆 → 单变量验证"这条链路不变。

目标系统通常是**两层异构**的：一层是记忆框架（做 LLM 抽取、实体消歧、embedding、
图/向量后处理），另一层是它背后的图库 / 向量库（Neo4j、FalkorDB、Milvus、pgvector、
Qdrant、Chroma、LanceDB…）。框架层可能是解释型（Python/TS/Node）也可能是编译型
（C++/Go/Rust）或 JVM；不同运行时下"同样一条杠杆"的收益可能相差一个数量级，
**先判运行时，再选杠杆**（见「通用性边界」）。

这类负载有两个特点让常规 CPU 优化经验**直接失效**：

1. **时间不可复现**：每次运行都要调 LLM 与 embedding，网络与采样温度让端到端时间波动
   几十个百分点。不先冻结负载，任何 A/B 都是噪声。
2. **CPU 花在"搬运与解码"而不是"算法"**：真正昂贵的不是图遍历或检索本身，而是把查询
   结果从存储/协议格式解出来（协议字节 → 运行时对象 → 领域对象），以及把不需要的
   字段（例如 1024 维向量）一路传上来再丢掉。

下面的数字来自 Graphiti + Neo4j 的**标定案例**（LoCoMo 10 段会话 / 1986 条查询，
客户端与服务端共享同一组核、绑定方式一致）。它的价值是给出"收益分布形态"，不是收益承诺：

| 层 | 杠杆 | 查询阶段 | 写入阶段 |
|---|---|---|---|
| 客户端 | 官方 Rust Bolt 解码器 | −55% | −59% |
| 客户端 | 时序水合下沉 Rust | −34% | −25% |
| 客户端 | 不用的向量不回传 | −14% | −12% |
| 服务端 | 4 项读路径补丁（累积） | −42%（剩余时间） | ≈0 |
| 合计 | — | **6.8×** | **3.9×** |

核心信条：

1. **确定性是前提，不是副产品**：先建"缓存回放 + 校验和 + 0 miss 门禁"的负载，
   再谈性能。裸跑基准得到的"优化收益"约有一半是采样噪声。
2. **先把耗时拆到三层再动手**：客户端框架 / 驱动解码 / 服务端。三段占比会随客户端
   优化剧烈变化（实测服务端占比 14% → 37%），按占比拍脑袋选杠杆必然踩空。
3. **载荷 > 解码 > 指令**：少发一个字段，胜过把解码器优化 10%；在解释型客户端里，
   把解码换成编译语言胜过在 Python 里抠热点——但这条只在**解释型运行时**成立，
   编译型客户端应转向减少分配/拷贝与批量化（见「通用性边界」）。
4. **扩展形态由运行时决定**：GIL + 单事件循环下多线程无效、多进程有效（每副本约吃掉 1 个核，
   容量与核数近似线性，需留 1.4~1.5 倍余量）；C++/Go/JVM 则先查锁竞争、线程池与 GC，再谈副本数。
5. **服务端优化会被 Amdahl 吃掉，也会在另一架构反转**：同一套服务端补丁在鲲鹏
   收益 2~4%，在 x86_64 高并发下 −48%。必须跨架构、跨并发度复测。

## 适用范围

- 适用：LLM 驱动的记忆/知识图谱框架（时序知识图谱型、向量+图混合检索型，开源或自研
  entity/relation 抽取管线）及其图库/向量库后端（Neo4j、FalkorDB、Milvus、pgvector、Qdrant、Chroma、LanceDB）；
  混合检索（BM25 + 向量 + rerank）；
  客户端通过二进制协议（Bolt/gRPC/RESP/pg wire）访问数据库的场景；框架层用
  Python/TS/Node/C++/Go/Rust/JVM 均可接入，但杠杆选择按运行时适配。
- 不适用：模型推理本身（那是推理优化）、纯离线批处理（无交互延迟目标）、
  无缓存可用的首跑基准（改用阶段 1 的 record 模式建立缓存）。

## 职责边界

本 Skill 只处理**记忆框架 → 驱动/协议 → 存储引擎读路径**这条链上的成本。
判定方法：阶段 2 的三段拆分里，耗时是否落在这三段至少之一？是 → 属于本 Skill；
否 → 按下表交给对应 Skill，不在本 Skill 内改这些方向。

| 情况 | 建议方向 |
|---|---|
| 向量索引库内部算法（Faiss/DiskANN/VSAG 的距离计算、索引构建与遍历） | `vector-search-optimize`（必要时 `faiss-optimize`） |
| 引擎跨版本迁移（版本升级后把旧优化重新落地、patch 移植、recall 门禁） | `vector-db-optimization-migration` |
| 数据库服务端配置与内部状态（pagecache/buffer pool、锁等待、checkpoint、MySQL 等） | app-tuner 的 `database-workload-analysis` |
| 模型推理/训练本身（吞吐、首 token、kernel） | `tf-inference-optimizer`、`ort-kdnn-attention-opt`、`kunpeng-llama-cpp-tuning` |
| 纯访存布局改写（AoS→SoA、分块、对齐） | `memory-access-optimization`（本 Skill 只指出该改哪里） |
| Go 客户端 profiling 工具细节（pprof 接入、goroutine/heap 判读） | `go-pprof-analysis` |
| 热点落在系统库且可能"优化已存在只是未加载" | `hot-library-version-gap` |

## 通用性边界：先问三个问题

本 skill 的**方法**通用，**杠杆**不通用。动手前先回答：

1. **客户端是什么运行时？** 解释型（Python/TS）→ 解码/水合下沉收益大；
   编译型（C++/Go/Rust）→ 下沉无意义，改看分配、拷贝、批量化与数据结构布局；
   JVM → 看装箱、临时对象、GC 与进程内直连。
2. **序列化边界在哪？** 客户端与服务端跨进程走协议 → 载荷瘦身 + 解码是主战场；
   同进程/嵌入式（如 SQLite、内嵌图库）→ 没有协议解码，收益转到布局与查询计划。
3. **服务端能否改？** 能改 → 读路径补丁（Amdahl 约束下排最后）；不能改 → 预算全部
   投到载荷、并发模型与配置。

| 客户端运行时 | 首选杠杆顺序 | 基本无效、不要浪费预算 |
|---|---|---|
| Python / TS / Node（解释执行 + 单线程事件循环） | L1 载荷瘦身 → L2 解码下沉 → L3 水合下沉 → L4 多进程 → L5 服务端 | 多线程（GIL）；在 Python 内做微优化 |
| C++（已编译，常有零拷贝/arena） | L1 载荷 → L7 检索配方（候选数/字段）→ L5 服务端/存储引擎 → 线程与分片 → 分配/拷贝消除 | 换编译语言做"解码下沉"（近乎 0 收益，除非现用通用解释器/反射型序列化）；逐行抠指令 |
| Rust | 同 C++：先查 `clone`/`to_vec`、中间结构物化、序列化框架 | 语言下沉 |
| Go | L1 → 消除 `interface{}` 装箱与反射解码 → 服务端 → 并发/GC 调优 | 语言下沉 |
| JVM | L1 → 减少装箱与临时对象、复用缓冲 → 服务端同进程直调 → GC 选型 | 换语言做解码 |
| 同进程 / 嵌入式存储 | 省掉协议与序列化（零拷贝视图），直接看数据结构布局与查询计划 | 解码下沉、载荷瘦身（没有网络边界） |

判据：**同一条杠杆的收益 ≈ (该层当前耗时占比) × (该运行时能被削掉的比例)**。
解释型客户端的"解码层"常占 60~90%，削掉一半就是 −30~−45%；编译型客户端同一层
可能只占 5~15%，同样手法只值几个点。

## 输入

从用户请求或工作区获取：

| 字段 | 必填 | 说明 |
|------|------|------|
| `repo` | 是 | 记忆框架源码路径；含客户端与服务端时分别记录 |
| `store` | 是 | 后端类型与版本（如 Neo4j 5.26.22 / FalkorDB / Milvus），是否可重建 jar/源码 |
| `workload` | 是 | 写入集（会话/文档数）与查询集（条数、并发度、检索配方） |
| `bench_cmd` | 是 | 可运行的基准命令，含 stages、并发、绑核方式 |
| `model_calls` | 是 | LLM/embedding/rerank 的缓存文件；无缓存则先跑 record 模式 |
| `goal` | 建议 | 延迟（p95/阶段时间）/ 吞吐（qps）/ 单核 CPU 占用 / 内存 |
| `constraints` | 建议 | 能否改后端二进制、能否改 schema/投影、结果等价红线、可用核预算 |

缺 `bench_cmd` 或 `model_calls` 时先补这两项，否则后续所有结论不可信。

## 执行步骤

### 任务初始化

用任务列表工具建立五个阶段任务；每阶段结束更新状态，并把阶段产物写进 `run_dir`。
任何阶段发现"负载不可复现"（同配置重跑 phase 波动 > 2%），先回到阶段 1。

### 阶段 1：冻结确定性负载

目标：把"模型调用"变成常量输入，让同一配置的重跑差异 < 2%。

1a. **录制/回放模型调用**：用 `scripts/llm_replay_cache.py` 包装 LLM、embedder、
reranker 三个客户端（缓存键 = 目标名 + 方法名 + 参数 sha256，与 API key 无关）。
首跑用 `record`，之后一律 `replay`；CI 用 `replay` 模式做门禁——miss 即报错，
杜绝"偷偷出网"把网络时间混进来。键里必须带 **目标名**，否则 LLM 与 reranker
的参数撞车会串味。

1b. **建立校验和（checksum）**：每次写入完成后必须记录
`(节点数, 关系数)`；每次查询必须能输出**结果指纹**（edge/node UUID + 分数的
排序后拼接再 hash）。这两个数字是"优化前后行为等价"的唯一证据。

1c. **给基准装门禁**：每次运行自动判定
`misses == 0` 且 `checksum == 期望值`，不满足则作废重跑（最多 3 次）。
实测中"图是 235/720 而不是 225/492"这种静默脏库，会伪装成 20% 的性能收益。

1d. **固定口径**：客户端与服务端绑同一组核（`taskset -c`，JVM 要用
`taskset -a -pc` 绑**全部**线程）；每次运行前清库并校验 `0 0`；每轮运行前恢复
规范缓存文件（运行会把新条目写回缓存）；关掉 profiling 工具做纯计时
（三件套 py-spy + pyinstrument + nmon 同时开会把负载撑大 ~66%）。

**阶段输出**：`cache_canon.json`（md5 记录）、期望 checksum、`bench_cmd` 口径表、
重跑波动实测值（应 < 2%）。

### 阶段 2：三段归因

目标：把每次查询的墙钟时间切成 **框架 / 驱动解码 / 服务端** 三段，并给出
"当前瓶颈在哪一层、还差多少"的定量结论。方法细节见
`references/bottleneck-modeling.md` §1。

2a. **per-query 拆分**（串行执行，`concurrency=1`，避免互相模糊）：先定位"协议边界"，
再在边界两侧计时。以 Graphiti + Bolt 为例：
- `框架` = `Graphiti.search()` 外层墙钟 − DB 调用区间**并集**
- `驱动` = `execute_query` 区间并集 − 服务端时间
- `服务端` = 协议响应里的服务端耗时字段（Bolt：SUCCESS 元数据的 `result_consumed_after`）

换协议时的等价来源：gRPC 用响应头/服务端拦截器；pg wire 用 `log_min_duration_statement`
或代理计时；RESP/HTTP 用服务端日志或客户端侧"首字节−末字节"差额。**若协议不暴露服务端
时间**，退化为"客户端墙钟 − 服务端日志耗时"或"同机代理前后差值"，并在报告里标注口径。
一次查询常发多路并发 DB 调用（全文 + 向量），必须取**区间并集**，求和会双计。

2b. **自证拆分正确性**：客户端优化前后，**服务端的绝对毫秒数应基本不变**
（实测 7.7→8.5 ms / 3.3→3.6 ms）。若服务端时间跟着客户端一起变，说明拆分口径
有误（典型原因：把"服务端开始返回"的时间当成总时间——它只说明服务端开始得快，
慢在"消费完"）。

2c. **读路径扩展曲线**：1 / 2 / 4 / … / N 副本的 phase 时间与吞吐，同时记录
CPU%（单核百分比，`(user+sys)/wall`）、峰值 RSS、连接重试次数。曲线形状直接
决定阶段 4 选"多进程"还是"服务端"。

2d. **封闭轴声明**：明确写出"已用证据排除的方向"（模型网络、GC、磁盘、锁、
带宽…），避免下游重复尝试。

**阶段输出**：三段占比表（绝对值 + 百分比）、扩展曲线、容量模型
（如 `N × 1.45 ≈ 核数`）、封闭轴清单。

### 阶段 3：瓶颈建模

目标：把阶段 2 的"哪一层慢"落到"哪条指令/哪次访存慢"，并归类为
`latency / bandwidth / compute / frontend` 之一。采集命令与判定树见
`references/bottleneck-modeling.md` §2–§4。

3a. **客户端 top-down**：`top-down -L1`（挂**真身 PID**，不是 `taskset` 父壳），
再看 `-L2/-L3` 区分 Core/Memory。经验形态：客户端优化到位后，IPC 会从 ~2.6 掉到
~1.5，Memory Bound 从 ~24% 升到 40~47%——**不是退化，而是剩下的工作更像"等待
内存 + 少而分散的指令"**，这时继续做算法级优化收益变小，该换载荷/解码杠杆。

3b. **缓存缺失率表（跨级 + 指令侧）**：按 `REFILL/ACCESS` 口径算 L1D、L2D、L3D、
DRAM 归因，同时单独算 **L1I / L2I**。指令侧常被忽略，但实测在客户端优化后
L1I miss 密度会涨 2~4 倍（Python 代码足迹相对变大），是"下一步该把热路径
进一步下沉"的信号。编译型客户端（C++/Go/Rust）通常看不到这条信号，改为看
分支预测失败与前端停顿。

3c. **服务端火焰图**：按运行时选工具——JVM 用 async-profiler/`jfr`，Go 用 `pprof`，
C++ 用 `perf record`，Python 服务用 `py-spy`。要区分的三类占比不变：
"属性/数组/列解码"、"向量相似度计算"、"查询执行"。服务端补丁的选择完全由这张图
决定，不看图就改代码等于赌博。

3d. **锁与 GC 轴独立检查**：客户端看事件循环/协程等待与连接重试（Python `asyncio`、
Go `p`/mutex、C++ 线程池队列、JVM 线程池）；服务端看线程是否被超额订阅饿死
（表现为 CPU 很高但吞吐下降、连接被重置/超时）。

3e. **输出瓶颈模型**：`bottleneck_class` / `binding_constraint`（到函数或访存）/
证据链原始值 / `closed_axes`。

### 阶段 4：分层杠杆实施

目标：按阶段 2/3 的证据给杠杆排 ROI，再单变量实施、验证、记账、循环。杠杆细节
（前置条件、做法、实测收益、风险、**不适用面**）见 `references/levers.md`；已被证伪的
方向见 `references/negative-results.md`。

默认参考顺序是"载荷 → 解码 → 水合 → 并发模型 → 服务端读路径"，但它**只是给解释型
客户端的默认值**，不是公式：

- 客户端是 C++/Go/Rust → 跳过 L2/L3（换语言做解码近乎 0 收益），顺序变成
  "载荷 → 检索配方 → 服务端/存储引擎 → 线程与分片 → 分配/拷贝消除"。
- 客户端与服务端同进程（嵌入式）→ 没有协议解码层，从数据结构布局与查询计划入手。
- 服务端不可改 → 砍掉 L5，把预算加到 L1/L4/L7。

排序依据只有一个：`预期收益 = 该层耗时占比 × 该运行时可削比例`，用阶段 2 的占比
乘阶段 3 的指令/访存证据，而不是照搬别人的杠杆清单。

4a. **先算理论下限再动手**：把回传载荷里"用不到的部分"量化（如每条候选行带
1024 维 float ≈ 8 KB），乘以候选行数就是可省的线上字节；再对照实测耗时算
"这层最多能贡献多少"。有网络边界时载荷类杠杆几乎总是 ROI 最高的第一步；
无网络边界（同进程）时它退化为"少物化、少拷贝"。

4b. **单变量 + 累积阶梯**：每轮只改一个杠杆，跑交错 A/B（A/B/A/B 多轮取中位，
不是先跑完 A 再跑 B）。已有多项优化时，必须做**累积阶梯**（0/1/2/3 项逐个叠加），
因为杠杆间会耦合：解码下沉后单核仍跑满，才轮到并发模型；并发上来后服务端才
显形。

4c. **正确性先于性能**：跑功能/对拍（同一查询集结果指纹逐字节比对），再跑性能。
"性能异常好先怀疑正确性"——命中率跌、候选集变小、字段丢失都会让数字变漂亮。

4d. **服务端补丁要求可重建**：记录源码树、构建命令、产物（jar/so/二进制）的 md5，按
`v0_orig → v1 → v2 → …` 累积版本保留，避免"改完不知道基线是哪份二进制"。
补丁优先选**读路径热点**（解码快路径、单遍就地计算），写路径通常无收益。

4e. **无收益即回滚**：收益在噪声带内（< 3%）或跨架构符号相反 → 回滚并记账。
特别注意"结构性无效"：某项补丁在写入阶段本来就该是 0 收益（写路径不经过它），
不记账的话下次还会有人试。

4f. **复测瓶颈**：每轮落地后重跑阶段 2 的拆分与阶段 3 的 top-down，确认**新**
瓶颈再选下一个杠杆。收益按"暴露下一层"估，不按线性叠加估。

### 阶段 5：矩阵复测与跨架构对照

目标：产出可交付的结论表，而不是单次最好数字。

5a. **矩阵设计**：客户端档位（开关组合）× 服务端版本（累积补丁）做成二维矩阵，
按"客户端先做、再在最优客户端上叠服务端"排成 8 组递进。每组每阶段跑 6 次，
**丢第 1 次热身**，取 2~6 次均值 + 总体标准差。

5b. **判据用 phase 不用 wall**：wall 含解释器启动、导入、建索引、缓存加载，
固定开销会把服务端收益稀释（实测 x86_64 p1 wall 掉 25% 而 search 只掉 2%）。

5c. **跨架构复测**：x86_64 与 aarch64 各一套；核预算对齐（客户端与服务端同核数预算），
绝对值必然不同，**只比较相对收益与趋势**。若某杠杆只在一种架构有效，必须写清
是"架构相关"还是"并发度相关"。

5d. **有效批次判定**：行数 = 组数 × 阶段数 × 次数；所有 ingest 的
`misses == 0` 且 checksum 正确；日志无"放弃/清库失败"；最后一行为完成标记。
不满足的批次整体作废，不挑好看的样本。

**阶段输出**：8 组 × 2 阶段 × 2 架构的均值表 + 分阶段加速比 + 每项杠杆的增量贡献
（相邻组差值）+ 波动。

## 通用化映射

换到别的记忆系统时，两步走：**先判"这条杠杆在目标运行时是否成立"，再找"对应位置"。**
只做第二步是常见错误——把 Python 的"解码下沉"照搬到 C++ 客户端，投入很大、收益接近 0。

**第一步：杠杆成立性判定**

| 杠杆 | 成立条件（同时满足） | 不成立时改做什么 |
|---|---|---|
| L1 载荷瘦身 | 存在网络/进程边界，且有字段"传上来就丢" | 同进程：改为少物化/复用缓冲/视图替代拷贝 |
| L2 解码下沉 | 客户端是解释型且有编译实现可用；该层占比 ≥ 40% | 编译型客户端：查零拷贝、arena、批量反序列化、SIMD |
| L3 水合下沉 | 存储类型 → 对象转换在解释型侧占 20%+ | 编译型：消除中间结构，直接在缓冲区上构造 |
| L4 多进程扩展 | 单副本仍钉满单核、服务端未饱和、且运行时受 GIL/单线程限制 | 编译型/JVM：先查锁竞争与线程池利用率；进程副本也适用于分片读 |
| L5 服务端读路径 | 服务端可重建，且"每行必走"的解码/相似度例程占比 ≥ 5% | 封闭二进制：转到载荷、配方、并发与配置层 |

**第二步：位置映射**

| 本方法的对象 | 在目标系统里怎么找 |
|---|---|
| Bolt/PackStream 解码 | 驱动层的反序列化（gRPC protobuf、Redis RESP、pg 行解码）；看驱动是否已有编译语言实现 |
| 时序水合（hydration） | 存储类型 → 语言对象的转换：时间戳、向量、JSON、数组；常是最隐蔽的热点 |
| `properties(n)` 投影 | 查询里"取整行/整对象"的地方；ORM 的 `SELECT *` 等价物 |
| 实体消歧 / 去重（LLM 判重） | 写入路径里让 LLM 参与并行化决策的环节——这类环节几乎总是**不可并行** |
| 全文 + 向量并发调用 | 检索配方里的多路召回；注意取区间并集，别把并发当串行加和 |
| 多副本读扩展 | 能否按查询分片起多进程/多线程、共享同一存储；先测扩展曲线再定副本数 |
| 服务端解码快路径 | 存储引擎的属性/数组/向量读取路径；优先看"每行都要走一遍"的通用例程 |
| 图规模校验和 | 目标系统写入完成后的可统计不变量（节点/边/文档数/索引条目数） |

## 测量纪律

- **绑核**：客户端与服务端绑同一组核；JVM 用 `taskset -a -pc` 绑全部线程，
  只绑主线程等于没绑（实测上千工作线程全机漫游）。
- **闲置门控**：采 profile 时要求机器空闲度 ≥ 98%，否则采样被他人负载污染。
- **交替 A/B**：多轮交错取中位；绝对值可能整体漂移几十毫秒，只有同轮配对差可用。
- **确定性锚**：`instructions` 计数对抢占/频率漂移免疫，适合作跨轮核对；
  IPC 只在干净的单线程采样里可信。
- **缓存与库状态**：每轮前恢复规范缓存、清库并校验 `0 0`；写入必须从空图开始，
  查询必须跑在"上一次 ingest 留下的图"上。
- **预热**：JVM 重启后需要 2 轮完整负载才进稳态（首轮慢 40~80%）；Python 侧
  首轮丢弃即可。
- **口径一致**：查询条数必须真正截断（老的 `--queries` 只按样本整块截断，会
  偷偷跑满全量）；候选倍数、返回字段、并发度逐项核对回显。
- **单一入口**：所有对比数据由同一个脚本产生；不同脚本的"同配置"不可比。

## 降级处理

| 场景 | 降级动作 |
|---|---|
| 没有任何模型调用缓存 | 先 `record` 跑一轮建缓存（期间数据不可用于结论）；缓存需 md5 定版并随交付分发 |
| 无法改客户端源码 | 只做服务端 + 运行配置（池大小、JVM、绑核）；per-query 拆分改用驱动回调/中间件埋点 |
| 服务端不可重建（二进制封闭） | 跳过服务端补丁；把预算投到载荷瘦身与读路径多进程 |
| 无 top-down / PMU 权限 | 用 `perf stat` 事件组近似：`cycles,instructions,L1-dcache-*、LLC-*、branch-*`，结论标注低置信 |
| 无 SPE 行级归因 | 用火焰图 + 缓存事件计数做函数级归因，不承诺到行 |
| 只有一种架构 | 跨架构章节标注"未测"，并把"是否架构相关"写成待验证项 |
| 机器不独占 | 交错 A/B + 闲置度门控；无法门控时只报相对差并加大重复次数 |
| 存储 schema 不可改 | 用查询投影/字段裁剪替代 schema 改动（本方法的"向量不回传"就是这一类） |

## 输出契约

优化报告（Markdown）固定结构：

```
# <系统名> 记忆后端优化报告
## 1. 目标与口径
   负载（写入集/查询集/并发）、绑核、缓存 md5、校验和、重跑波动
## 2. 三段归因
   框架/驱动/服务端 绝对值与占比（优化前 vs 优化后），拆分自证记录
## 3. 瓶颈模型
   bottleneck_class / binding_constraint / top-down 与缺失率原始值 / 服务端火焰图占比 / 封闭轴
## 4. 杠杆清单与排序
   ROI 表（预期 × 覆盖面 ÷ 风险），对照负结果台账
## 5. 实施与验证
   每轮：改动摘要 / 正确性（指纹+校验和）/ 交错 A/B 数据 / 采纳或回滚
## 6. 矩阵结果
   8 组 × 2 阶段 × 2 架构 表 + 分阶段加速比 + 每项增量贡献
## 7. 负结果台账
   手段 / 结果 / 根因 / 启示
## 8. 复测瓶颈与下一步
   新瓶颈模型 + 下一杠杆建议 + 未验证项
```
