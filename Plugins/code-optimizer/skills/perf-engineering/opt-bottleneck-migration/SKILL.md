# 热点迁移：优化只搬走瓶颈

## 何时使用

- 想判断"上一轮的优化点还能不能继续优化"。
- 一个内核被加速后仍在 profile 里占比高，要分清"已消化"vs"还能挖"。
- 下游换了实现（如 JSON 过滤 → 标量 bitmap），要判断旧路径是否已过时。

## 核心原则

1. **优化只搬走当前瓶颈、不消灭瓶颈**：加速了 A，B 就浮上来；A 从"瓶颈"变"已消化"。
2. **优化后必须重新 profile**：加速内核后，它在 profile 里的位置和性质都变了，不能沿用旧热图。
3. **"仍可见" ≠ "还能挖"**：内核被加速但仍可见，可能是"加速了扫描但没消除扫描本身"，不是新的可挖项。
4. **整条路径过时 → 收益为零**：下游换实现让旧路径消失后，继续优化该路径没有意义。

## 步骤速览

判据、过时项清单与坑点**只在 `references/bottleneck-migration.md` 一处维护**，本节给步骤名与去向：

1. **加速后重新 profile**——用"同负载下每请求扫描耗时"（cum 占比 × 每请求墙钟）判断应"减少扫描次数"还是
   "继续优化内核" → references §1。
2. **判"路径是否过时"**——下游换实现后旧帧从 profile 消失 → references §1/§2。
3. **把过时项记进"勿重造"**——历史方案按"已消化/已过时"与"可挖"分开登记 → references §2。

## 门禁

- [ ] 加速后重新 profile，未沿用旧热图
- [ ] 已落地的改动标为完成（不把"已落地"与"已消化"混为一谈）
- [ ] 用同负载下"每请求扫描耗时"判断方向（减少扫描次数 vs 继续优化内核），非只凭占比断言
- [ ] "仍可见"项被分清为已消化 vs 可挖
- [ ] 已过时路径被标注并排除出候选
- [ ] 收益为零的判断有 profile 证据支撑

## 结果（标定案例形态）

simdjson 三项优化收益分两层：**内核级 +14%（内核自测）→ milvus 负载 +10.1%（端到端）**，两数分属不同测量层、
不矛盾；加速了 JSON 扫描内核但没消除扫描本身（base-qa stage1 cum 仍 45.88%），flatidx 之后该路径过时、继续
优化收益为零。细节与证据见 `references/bottleneck-migration.md` §1。
