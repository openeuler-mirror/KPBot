# 优化方案输出契约（7 段结构）

> 本文件是向量数据库优化类 Skill（含 `vector-db-optimization-migration` 以及已安装的引擎/算法专属 Optimization Skill，如 `faiss-algorithm-optimization`、`faiss-rabitq-optimization`、`faiss-turboquant-optimization`、`faiss-ivfpq-optimization`、`faiss-ivfpqfs-optimization`、`faiss-hnsw-optimization`、`faiss-simd-optimization`、`diskann-*-optimization`）**输出优化方案时的强制输出格式**。任何面向用户或上游 Agent 的优化方案都必须按以下 7 段结构呈现，不得只给代码或只给结论。本契约与算法解耦：既有实验 verdict（accepted/rejected/inconclusive/unverified）与负向清单继续作为证据输入，不因本契约重写。

## 输出结构（7 段，缺一不可）

### 1. 优化摘要

用 1–2 句话说明本次优化做了什么，预期影响哪些索引、算子或检索路径。

### 2. 优化内容

列出本次新增或修改的优化点，按机制归类：

- 索引构建优化
- 距离计算优化
- 量化/解码优化
- 内存布局优化
- 预取/缓存优化
- 线程/绑核/并行优化
- 参数调优建议

### 3. 平台属性（每个优化点单独判定）

- **鲲鹏特有**：依赖鲲鹏平台差异化能力，如 UBMEM、KPCL、KAE、NUMA 拓扑、sysHAX、CMF 缓存管理、鲲鹏 920/TaiShan 微架构、鲲鹏编译器/工具链。
- **ARM 特有**：依赖 ARM/NEON/SVE/SVE2/ARMv8.2+ 等 ISA、ARM 内建函数、ARM 汇编、ARM 缓存层级或 ARM 微架构特征，但不一定绑定鲲鹏。
- **通用**：x86/ARM 都可能受益，不依赖特定 ISA 或平台特性。

判定规则：

- 优化依赖 NEON/SVE/SVE2、ARM 内建函数、ARM 汇编、ARM 缓存层级或 ARM 微架构特征 → **ARM 特有**。
- 优化进一步依赖鲲鹏 920、TaiShan 微架构、UBMEM、KPCL、KAE、NUMA 绑核、鲲鹏编译器/工具链等 → **鲲鹏特有**。
- 优化主要改进内存分配、批量处理、数据结构、队列/堆、分支、预取、参数配置、线程模型等 → **通用**。

混合属性（如"ARM 特有 / 通用混合"）允许，须写明哪部分属于哪类。

### 4. 优化等级 L0–L5（每个优化点单独判定）

采用鲲鹏优化分级框架：等级刻画优化所需的**改动层级与交付形态**，从 L0 零改动开箱即用到 L5 鲲鹏深度定制。等级与第 3 段平台属性是两个维度：L0–L2、L4 的优化点可为鲲鹏特有/ARM 特有/通用；L3（鲲鹏加速库）与 L5（鲲鹏定制）天然对应鲲鹏特有。

| 等级 | 类型 | 描述 |
|---|---|---|
| **L0** | 开箱基线 | 不做任何改动，开箱即用：① KAL 成果已合入原生社区，如 GmSSL、AVS3、OpenSSL、ISA-L 等鲲鹏 Native |
| **L1** | 环境优化 | 根据应用类型调整环境，保证裸算力最优，包括 BIOS、OS、虚拟化、容器等优化 |
| **L2** | 应用配置优化 | 应用配置部署优化；1、直接替换基础库：② KAL 基础库，如基础数学库、鲲鹏使能和指令加速等鲲鹏加速库 |
| **L3** | 鲲鹏库优化 | 2、使用鲲鹏加速器：② KAL-UADK、KAL-ASF 等鲲鹏软硬协同加速库；POC 现场操作，部分修改代码或二进制 |
| **L4** | 应用补丁优化 | 1、源代码修改：优化 Patch、指令集翻译等；2、二进制优化，包括 PGO、LTO、BOLT 等 |
| **L5** | 鲲鹏定制优化 | 定制源码模块/函数修改优化，需要联合设计开发；包括 ③ KAL 插件，如 SparkSQL Native 引擎、MySQL 线程池、执行计划缓存、UB 分级内存等框架深度优化 |

> ①②③ 标记 KAL 成果的接入形态：① 已合入原生社区（鲲鹏 Native）；② 需替换或接入的鲲鹏加速库；③ 框架级深度优化的 KAL 插件。

Faiss 场景判定规则（示例；其他引擎按相同 L0–L5 层级映射到本引擎的构建/参数/源码改动）：

- 不改 FAISS 源码与环境，仅依赖已合入社区/基础库的鲲鹏 Native 成果 → **L0**（基线参照，通常作为收益对比基准而非主动优化点）。
- BIOS/OS/虚拟化/容器、NUMA 拓扑与绑核等环境层调整，不触及 FAISS 本体 → **L1**。
- nprobe、efSearch、nlist、k_factor、nbits、线程数等参数与部署配置调优，或直接替换基础库（基础数学库、鲲鹏使能与指令加速等 KAL 基础库）→ **L2**。
- 接入鲲鹏软硬协同加速库（KAL-UADK、KAL-ASF 等），部分修改代码或二进制，POC 现场操作 → **L3**。
- FAISS 源码修改（SIMD kernel、算法专用路径、内存布局、批量处理等优化 Patch，含指令集翻译）或 PGO/LTO/BOLT 等二进制优化 → **L4**。
- 依赖 UBMEM/KPCL 等鲲鹏平台能力对模块/函数做深度定制改造，需联合设计开发（如向量内存分级、远端访问路径重构）→ **L5**。

判定要求：

- 不能只给等级，必须写出"为什么是这个等级"。
- 一个优化点同时涉及多个等级时（如源码 Patch 之外还需参数调优），以主要改动机制所在等级为主等级，并在备注中说明次要等级。
- 如果优化需要客户额外配置参数（L2）、环境调整（L1）、加速库接入（L3）、平台能力接入或联合设计开发（L5），必须明确写出来。

### 5. 是否开箱即用（每个优化点单独判定）

- **可直接生效**：编译/部署后无需客户改参数即可受益。
- **条件生效**：需要满足维度、batch、metric、nprobe、efSearch、线程数、NUMA 绑核等条件。
- **需客户配置**：需要客户显式选择参数、平台能力或部署方式。
- **需平台适配**：需要鲲鹏/ARM 平台识别、编译选项或底层能力接入。

### 6. 预期收益与风险

- 可能提升：QPS、延迟、召回率、内存占用、构建时间、缓存命中率等。
- 潜在风险：召回率下降、兼容性变化、编译依赖增加、平台限制、参数敏感等。

### 7. 验证建议

给出可执行的验证方向，例如：优化前后 QPS / p95 延迟对比、Recall@k 是否下降、NEON/SVE 路径是否真正命中、绑核/NUMA/线程数是否影响收益，并给出建议测试的索引类型（Faiss 如 IVFFlat、IVFPQ、HNSW、IVFPQFS、PQFS；DiskANN 按 Vamana/量化配置；其他引擎按实际索引类型）。

## 与既有证据协议的衔接

- **收益数字必须带证据标记**，沿用本 Skill 库标记体系：`[experiment]`（实测，须引用实验代号与数据集）/ `[inference]`（基于热点或调用链推断）/ `[unverified]`（未验证）。禁止把预期收益写成已验证收益。
- **推荐项不得违反负向清单**：已被 rejected 的方向（见各算法 `*-experiments.md` 与 `*-optimization-candidates.md`）不得作为优化内容输出，除非给出明确的新适用条件。
- **等级 ≠ verdict**：L0–L5 描述优化的改动层级与交付形态；accepted/rejected/inconclusive/unverified 描述实验结论。两者独立，均须标注。
- **两套格式各司其职**：本文件约束"优化方案的呈现"；实验后的结论记录继续用 `candidate-evaluation.md` 的结论格式写入各 `*-experiments.md` ledger。
- 涉及 SIMD 内核的平台属性/等级判定，须以实际符号反汇编或 sampled symbol 证据为准，不凭源码声明（沿用各 Skill 硬约束）。
- 平台属性为混合时（如内核 ARM 特有 + 门控逻辑通用），分别注明。

## 输出示例格式（每优化点紧凑呈现，可嵌入第 2 段之后的逐点详情）

```text
优化点：HNSW 距离计算 NEON/SVE 向量化
平台属性：ARM 特有
优化等级：L4（源码修改：优化 Patch；含 ARM 指令级实现）
是否开箱即用：条件生效，需 ARM 平台并启用 NEON/SVE 编译路径
预期收益：降低距离计算延迟，提升 HNSW 检索吞吐
风险：非 ARM 平台无法使用该路径；SVE 需确认编译器和硬件支持
验证建议：在 ARM 平台上对比 FP32 HNSW 检索延迟与召回率，确认向量化路径命中
```

```text
优化点：IVFPQ 解码查表优化
平台属性：ARM 特有 / 通用混合
优化等级：L4（源码修改：算法专用查表与解码优化 Patch）
是否开箱即用：条件生效，依赖 PQ 参数、维度、metric 和 batch 大小
预期收益：降低 IVFPQ 查询延迟
风险：不同 nbits/M/维度下收益可能不同
验证建议：针对 IVFPQ 索引测试不同 nprobe 和 batch 下的 QPS 与 Recall
```

```text
优化点：减少临时内存分配和 memcpy
平台属性：通用
优化等级：L4（源码修改：通用实现优化 Patch）
是否开箱即用：可直接生效
预期收益：降低查询开销，提升高并发场景稳定性
风险：需验证内存生命周期，避免悬空引用
验证建议：压测高 QPS 场景，观察延迟尾部和内存分配变化
```

```text
优化点：nprobe / efSearch / 线程数调优
平台属性：通用
优化等级：L2（应用配置优化：不改核心实现的参数调优）
是否开箱即用：需客户配置
预期收益：在召回率约束下优化延迟和吞吐
风险：参数不当可能导致召回下降或资源占用升高
验证建议：使用固定数据集做参数 sweep，记录 Recall@k、p95 延迟和 QPS
```

## 适用范围

- **适用**：任何向量数据库/检索库优化方案的规划与呈现——新增候选提案、实验结果汇报、优化建议清单、跨版本迁移方案，无论由哪个 Agent/模型（OpenCode、Claude、openai.yaml agent）产出。
- **不适用**：纯源码问答、perf 数据解读、构建/测试操作指引——这些按各自 Skill 原有格式输出。
