# LZ4 压缩候选查找优化

## 说明与范围

仅调整压缩器找到候选的位置，保留真正的匹配验证、编码格式和解码语义。先确认热点来自实际 LZ4；输入文件是 Snappy Parquet，并不排除中间 Shuffle 使用 LZ4 Frame。

## 输入

| 输入 | 核对内容 |
| --- | --- |
| 加载与调用 | 实际压缩库、提交/补丁、Block/Frame、字典模式及 Shuffle 调用链 |
| 候选分支 | 表类型、架构门控、哈希公式、参与字节数、实际机器加载宽度及尾部限制 |
| 兼容材料 | 原/候选压缩与解压库、完全相同的原始字节、错误语义和固定随机种子 |
| 指标 | 各表模式命中、压缩/解压耗时、压缩字节、内存及完整查询基线 |

## 实施步骤

### 1. 确认压缩热点和模式

从加载库与调用栈确认 LZ4_hashPosition 等候选查找热点，区分文件 codec 和 Shuffle codec。记录 byU16 等实际表模式，不能把某分支经验外推到所有 LZ4 调用。

### 2. 限定架构、表及实际读取范围

只在已证明适用的分支改变哈希输入。五字节参与哈希可能由八字节加载实现；检查输入上界、最后一次加载位置、字节序和非对齐约定。尾部不足时沿原安全路径。

### 3. 保持候选之后的匹配校验

例如 ABCDX 与 ABCDY 前四字节相同，第五字节可以分散候选索引。但哈希只是候选定位，不可跳过最小匹配、offset、窗口和尾部校验，也不能要求原/候选选择相同位置。

### 4. 运行真实四向兼容矩阵

固定相同原始序列化字节，执行原压原解、原压候解、候压原解、候压候解。逐组检查解码状态、长度和逐字节相等；压缩流允许改变，只有传输契约要求时才核对压缩流逐字节一致。

### 5. 扩展模式与失败输入

按实际使用覆盖 Block/Frame、字典、块大小、短输入、不可压与高重复样本及尾部。Frame 核对头、块链接、校验和和截断；Sanitizer 双边同种子失败仍是未解决失败。

### 6. 同时比较速度与压缩率

测候选查找、压缩、解压、输出字节及峰值内存；压缩率退化可能抵消 CPU 收益。用于 Shuffle 时再重建列比较行值/NULL/顺序，并按单项开关做端到端配对。

## 约束与回退

- 局部哈希分支优化不修改 LZ4 格式，也不取消候选后的真实匹配验证。
- 实际加载宽度与参与哈希字节数分别核对；模式/架构不符或尾部不安全时保留原分支。
- 三组解码成功不能代替完整四向矩阵；双边失败不能作为兼容性通过。

## 交付与验收

交付库指纹、候选表模式、加载边界、失败样本与四向矩阵。记录 `模式 | 候选路径命中 | 原始/压缩字节 | 压缩/解压耗时 | 四向状态/长度/字节 | 查询秒数`。

实现与证据细节见 [实施参考](references/implementation.md)。

## 本地用例与验证边界

从 Skill 根目录运行 `python3 cases/hash-candidate-contract/run.py`，按 `cases/hash-candidate-contract/case.yaml` 校验结果。使用 `python3 -O cases/hash-candidate-contract/run.py` 或 `PYTHONOPTIMIZE=1` 重跑，结果应一致。用例通过普通布尔检查决定 `success` 和非零失败退出码。

用例验证候选哈希/加载分派和兼容证据判定模型；没有执行真实 LZ4、Frame、字典或 Sanitizer。 未完成的目标端证据标为 `awaiting_target_evidence`。触发与边界评估规格见 [evals/evals.json](evals/evals.json)，规格不等于已执行模型评测。
