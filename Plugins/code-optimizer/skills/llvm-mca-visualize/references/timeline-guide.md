# llvm-mca -timeline 解读参考

本文件解释 `llvm-mca-visualize` 采集的 `-timeline` 输出及相关可视化视图如何解读。分析流水时序图、向用户解释图上的阶段/重叠/谷底时阅读本文件。

## 页面结构（双 Tab）

- **全局（不随 Tab 切换）**：标题/meta/KPI；**Dispatch 等待统计**（GROUP/SCHEDQ/RAT/RCU/LQ/SQ 聚合计数，说明哪类结构限制发射）；瓶颈归因与关键路径。
- **Tab A：指令流水时序图（默认）**：按迭代分组（`==== 第 N 次迭代 ====`），≥3 次迭代时默认折叠前两组；行=该迭代的 ISA 指令（`it4 #0`），右侧标注 `uOps=N · 端口占用`；逐周期色块；下方为逐周期执行占用曲线。**不拆 uop 行**（MCA 不导出 uop 时刻）。
- **Tab B：端口资源热力图（辅助）**：有真实占用的端口单元 + 逐资源端口压力条形图；数据来自 patched llvm-mca `-issue-trace`（逐迭代真实 issue）。
- `--view all|timeline|resource`：all=双 Tab；timeline=仅 A；resource=仅 B。
- **前置条件**：真实端口数据需要打过 `IssueTraceView` 补丁的 llvm-mca（`-issue-trace`），通过 `--mca-bin` 或 `MCA_BIN` 指定；补丁源码在 `scripts/llvm-mca-issue-trace/`，构建方法见 `SKILL.md`。未提供时脚本直接报错，不做近似。

> **等待原因限制**：`-timeline` 只有一种等待符 `=`，**MCA 不区分"等寄存器(RAW/LCD)"与"等资源(端口排队)"**，因此图上等待段统一用灰色并标注"原因未知"。判断依赖 vs 资源：结合关键路径（红色虚线框）与顶部 Dispatch 统计（SCHEDQ/RAT/RCU/LQ/SQ）。

## -timeline 是什么

`llvm-mca -timeline` 是 MCA 的一条视图：对每条指令，按周期列出它处于哪个流水阶段（发射/等待执行/执行/退休）。它把"谁在哪个周期占用了流水"画成一张横轴为周期的表，是构建流水时序图的数据来源。`--json` 只有聚合指标（IPC、资源压力等），**没有逐周期的每条指令时序**，所以可视化必须采集 `-timeline`。

## 阶段字符图例

| 字符 | 阶段 | 含义 | 图例颜色 |
|------|------|------|---------|
| `D` | dispatch 发射 | 指令进入调度器 | 蓝 `#4c6ef5` |
| `e` | executing 执行中 | 正在执行单元上运行 | 绿 `#2f9e44` |
| `E` | executed 执行完 | 执行完毕、等待退休 | 绿 `#2f9e44` |
| `R` | retired 退休 | 结果写回、指令退役 | 橙 `#f08c00` |
| `-` | retire_wait 退休等待 | 执行完到退休之间的等待 | 黄 `#ffe066` |
| `=` | wait 等待 | 已发射但未执行（等数据/资源） | 灰 `#adb5bd` |
| `.` | idle 空闲 | 该周期该指令尚未开始（或迭代间隙） | 透明 |

> 实测（LLVM 17 / openEuler）：退休字符是**大写 `R`**（不是小写 `r`），且执行完（`E`）到退休（`R`）之间会用 `-` 标出退休等待段。脚本按图例段自适应，这里统一记录。

> 字符集随 LLVM 版本可能略有差异。脚本会从 timeline 尾部的 `Legend:` 段自动适配，无法解析时明确报错，不会画错图。

## 指令流水时序图怎么看

横轴是周期，纵轴每一行是一条指令（按 index）。每个周期格子的颜色表示该指令此刻所处的阶段。关键路径指令会叠加红色虚线框。

- **单条指令**：从左到右依次应看到 `D`(蓝) → 可能有 `=`(灰) → `e`/`E`(绿) → `r`(橙)。
  - 蓝色到绿色之间的**灰色段越长** → 该指令等待越久，是"在排队等数据或等端口"的直接证据。
  - 绿色段长度 = 执行实际占用的周期数（× 指令延迟特性）。
- **指令之间**：
  - 多条指令的绿色段在相邻行重叠 → 说明并行执行的指令多，流水被填满。
  - 全是灰色等待(=`而绿色很少 → 执行单元没闲着的问题不大，反而是**依赖链**在卡（后一条必须等前一条结果）。
  - 大量格子"同时"都是某同一种颜色但其它端口颜色稀缺 → 端口争用。

**典型瓶颈判读**：
- 同一列上绿色高度 = 该周期同时执行的指令数，若长期贴着"指令行数"不放 → 后端已满，是资源吞吐瓶颈。
- 某一行灰色段很长且后一个绿色段随之后移 → 该指令在关键的 loop-carried 依赖链上。

## 逐周期执行占用怎么看

纵轴=每周期处于执行中(e/E)的指令数，横轴=周期。这是流水图里"绿色总量"随周期的折线/面积。

- **饱满平台期**：曲线到达并平贴在上限（=指令行数）→ 执行单元被充分占用。
- **锯齿/周期性谷底**：曲线周期性回落到低位 → 每个迭代开始都有一段"没活干"的间隙，指向依赖等待或 dispatch 缺口（也是 loop-carried 依赖的典型特征）。
- **整体偏低**：执行占用长期低 → 可能是前端/dispatch 卡住、依赖链太长，或（真实场景下）cache 停顿——注意 MCA 不建模内存，见局限。

## 跨迭代重叠与 loop-carried 依赖

**默认口径**：`--iterations 1` 时只仿真并画第 0 次迭代这一趟的 D/等待/执行/退休结构（单趟，KPI 含流水填充/排空，非稳态）；**只要 timeline 解析到多次迭代，脚本自动跳过 iter0（热身）并渲染其余全部**（`--start-iteration`/`--show-iterations` 默认自动，显式传值优先）。

- 想看**稳态吞吐/瓶颈**：`--iterations 100`（KPI 变稳态，timeline 自动跳过 iter0）。
- 想控制迭代数与窗口：`--iterations 30 --timeline-max-iterations 6` → 解析出 0..5，自动渲染 **1..5**；`--timeline-max-iterations` 会同时把 `--timeline-max-cycles` 设为 0（不限），避免 MCA 默认 80 周期截断。也可显式给 `--timeline-max-cycles N`。
- 想看**指定迭代**：`--start-iteration 2 --show-iterations 1` 画单独一次稳态迭代；显式 `--start-iteration 0 --show-iterations 2` 看跨迭代重叠。

> 注意对 **loop-carried 依赖**的循环：MCA 窗口内"发射比退休快"，越靠后的迭代在调度器里排队等待越久（wait 递增），窗口内未必达到"发射被限流"的完全稳态；此时以 KPI 的 `周期/迭代` 为稳态结论。

- 迭代 n 的最后几条指令尚未退休、迭代 n+1 的指令就已发射 → 说明流水这种迭代边界被有效利用（good pipelining）。
- 若两次迭代之间出现明确的**空档**（一行尾部空闲、下一迭代要等上一迭代某条指令退休才动）→ 存在跨迭代依赖（如 post-index 地址更新 `ldr q0, [x0], #16` 下一轮的 ldr 依赖 x0；或循环携带累加）。这种 loop-carried 依赖通常是收益最大的优化目标（拆分累加器、多路指针推进）。

## 资源×周期视图（--view resource）

纵轴为**有真实占用的端口单元**，横轴为周期。占用来自 **patched llvm-mca 的 `-issue-trace`**（`IssueTraceView`）：每条指令**每次迭代**在哪个 cycle issue、实际落到哪个单元、占多少 cycle。

- **只显示有占用的端口行**：空白端口隐藏（备注给出实际行数）；hover 含**迭代号 + 指令 + issue cycle + 该次占用的第 k/N 周期**。
- **单元集是精确的**：`ldr q,[x0],#16` 会同时点亮 load 单元与整数/地址单元（如 `LD.x` + `S*/SM*`），这正反映"取数 + 地址更新"多个 uOp。
- **颜色 = 端口类型**（Load 蓝 / Store 橙 / Vector-FP 绿 / Scalar 青 / Mul 紫 / Branch 红），纵轴行名也标同色，图带类型图例。
- **运算类别描述（`ops`）**：出现在单元格/行名/图例悬停，以及 JSON 的 `resources_detail[].ops`。
- **每格 = 该周期被占用 1 次**：色块长度 = 该次 issue 的连续占用周期数；同周期并发占用才累加（正常为 1）。**不要**把长度为 N 的块读成“每格 N 周期”。
- **压力条口径**：`pressure` 单位是 **cycles/迭代**，不是百分比；单单元上限 = `cycles_per_iteration`，利用率 = `pressure / cycles_per_iteration`（示例：12.3 cycles/iter，S1 3.00 ≈ 24%）。条形长度按最大值归一化，比较时看数值。
- **限制**：ILP/延迟中的指令不会显示端口占用（这是真实的：它尚未 issue）；该视图需要 patched llvm-mca，`--parse` 离线模式不可用。
- **数据校验**：单迭代时逐 `(指令, 单元)` cycles 与 `ResourcePressureInfo` 完全一致；30 迭代按迭代平均后同样一致（见验证脚本）。

## 与 llvm-mca-analysis 的分工

| 能力 | llvm-mca-analysis | llvm-mca-visualize（本 Skill） |
|------|-------------------|-------------------------------|
| 聚合瓶颈归因（资源压力 vs 数据依赖） | ✅ 文本/JSON | ✅（顶部 KPI 卡，同源数据） |
| 逐资源端口压力 | ✅ 文本 | ✅ 条形图 |
| 关键依赖序列 critical_chain | ✅ 文本 | ✅ 列表 + 图上红色虚线框 |
| **逐周期指令流水时序** | ❌（不采 -timeline） | ✅ 时序图 + 逐周期执行占用 |

两者可互接：`llvm-mca-visualize --json` 输出 JSON，`.timeline` 是结构化时序数据；`llvm-mca-analysis` 的输出可作瓶颈文本来源。一般流程：先用 `llvm-mca-analysis` 拿一句话归因，再用本 Skill 看图定位具体指令/周期。

## 局限与准确性

1. **不建模 cache/内存层级**：load/store 在 MCA 里只有执行延迟，没有 cache miss。访存密集代码的时序图会显得比实测"填得更满"。图上显示充分流水但实测慢 → 用 perf/SPE 查内存。
2. **不跟随控制流**：MCA 把输入当直线序列。带分支/尾部的函数级分析是近似的；循环稳态分析请用 `asm` 模式抽循环体。
3. **依赖调度模型质量**：结果取决于 LLVM 调度模型对该 uarch 的刻画精度，hip 系列模型由 HiSilicon 贡献仍有简化。把 MCA 当"纸面预估（paper prediction）"，与硅片实测（silicon）对照。不同 uarch 的模型差异巨大，**uarch 一定要指定对**。
4. **不建模前端**：fetch/decode/分支预测不在 MCA 范围。若流水图上后端满但实测前端卡，可能是前端问题，MCA 看不见。
5. **timeline 图例随版本变**：脚本自适应 + 失败即报错，不会出伪图。
