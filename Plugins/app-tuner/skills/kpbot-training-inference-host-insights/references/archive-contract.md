# 归档与运行连续性

## 首次运行

使用用户指定的输出目录，默认在当前工作区创建 `host-insights/`。目录为空时以研究启动时间为截止，检查此前七天。无需历史报告、调度器或笔记软件。

在输出目录按年份保存同一批次的 `<YYYY-MM-DD-HHmm>.md`、`<YYYY-MM-DD-HHmm>.html` 与 `<YYYY-MM-DD-HHmm>-evidence.md`。如有重名，整批使用同一个版本后缀。用根目录的 `index.md` 记录窗口、指向三份产物的相对链接和 0–5 项有证据的发现。零发现时写明已查范围与缺口。仅在用户指定既有 Obsidian Vault 时沿用其布局及双链约定。

## 窗口、缺口与去重

在输出根目录的 `state.yaml` 记录最近一次成功归档的状态。示例中，报告已交付，但 vLLM 的 PR 来源仍有一个未完成的窗口。

```yaml
last_success_report_generated_at: '2026-01-08T09:15:00+08:00'
coverage_end: '2026-01-08T09:00:00+08:00'
evidence: '2026/2026-01-08-0900-evidence.md'
pending:
  - source: github/vllm-project/vllm/pulls
    start_exclusive: '2026-01-01T09:00:00+08:00'
    end_inclusive: '2026-01-08T09:00:00+08:00'
    cursor: null
```

1. 先按来源回补每个 pending 窗口。使用保存的分页游标；游标缺失、过期或不能保证顺序时，重查整个缺失窗口。回补结果按原窗口筛选，即使早于全局水位也要入账，标注“历史补漏”。
2. 再查上期制作尾窗（上期覆盖截止至生成时间）和本期正式窗口（上次成功生成时间至本次启动时间），均采用左开右闭边界。证据台账区分事件时间、实际检索时间及精度，按项目、事件类型和稳定 ID（PR 编号、SHA、release ID 等）与已归档台账去重。相同事件的状态变化记录更新时间。
3. 为每个未查完的来源保存其窗口及下一页游标，包括本期新增缺口；原有缺口继续保留。仅在完整检查该窗口的全部页面且回补证据成功归档后清除对应条目。其他来源成功或全局水位推进均不能清除它。

## 专题验证单

专题验证单与周期台账共用事件键。按归档根的 `topics/<project>/<event-type>/<stable-id>/` 写入或查找验证单。三个路径段取自同一条台账的项目、事件类型和稳定 ID。每段按 UTF-8 编码，原样保留小写 ASCII 字母、数字、连字符和下划线，其余字节写成大写 `%HH`。例如 `vllm-project/vllm` 的 `pr` 事件 `123` 对应 `topics/vllm-project%2Fvllm/pr/123/`。从台账复用原值，发布或提交等不同类型即使 ID 相同也分开归档。验证单注明原始事件键、来源台账和日期。读取旧归档时，若按上述路径找不到验证单，再从既有专题的正文按原始事件键匹配。周期报告核对事件键后引用验证单，专题写入不更新周期水位。

## 提交本次归档

先完成并校验 Markdown、派生 HTML、证据与索引，再通过同目录临时文件替换 state.yaml，一次写入新水位和全部剩余缺口。部分来源失败仍可交付，报告须标明覆盖限制。全部来源失败或写入中断时保留旧状态，下次按旧窗口重试并检查已有产物。已完整检查且零发现可计为成功；专题增补、范围调整或修改技能均不推进周期水位。
