# 生成器接入多线程运行时的约束 — 方法细节

> 来源与适用范围：本文整理自原始工程实践记录（`SKILLS_ALL.md` 汇编稿），未提供可公开引用的上游文档，也未经独立复现。文中阈值、收益倍数与机器相关数据绑定当时的生成器版本、硬件与配置，迁移到其他环境前必须重新测量。置信度：中；未覆盖范围与平台差异见正文。

## 适用背景

目标生成器接受形状与配置，发出 C++ 与汇编，编译成动态库供运行时调用。加入多线程支持之前，一份产物只按单线程的方式执行，配置中的线程数只是一个被记录的值。

引入多线程时，需要回答四个问题：线程数在何时确定；运行时给的线程数少于预期时怎么办；哪些状态必须按线程隔离；生成的 C++ 与汇编是否需要不同的编译选项。这四个问题都有明确答案，且答案之间相互牵连，单独处理其中一项往往会在另一处暴露问题。

## 1. 线程数的确定时机

线程数应当在生成期确定，并随产物一起固定，不在运行期传入。

理由是调优的对象是一个组合：线程数与分块方式共同决定分区的划分、每线程的工作量与打包缓冲的大小。若线程数可以在运行期改变，产物的行为就与调优时的条件脱钩，调优得到的最优点不再对应实际执行的形态。一份库通吃所有核数的想法在表面上节省了构建次数，代价是调优结论失去意义。

由此得到两个配套要求。其一，切换线程数意味着重新生成并重新编译，这条要求应当写进构建流程，而不是留给调用方在运行期试探。其二，线程数为一的构建不含并行区，直接串行执行。保留这条路径的理由不是性能，而是口径：单线程与多线程的计时、正确性、数值一致性都按不同前提判定，若线程数为一的产物仍带并行区，两类结论会混在一起，无法区分是算法差异还是运行时差异。

## 2. 运行时的契约

生成的算子自己开启并行区，并假定运行时提供一个与生成时声明相同的线程团队。这个假定必须被检查，而不是被默认。

有三条常见途径会让实际团队小于请求值：运行时的动态调整机制按当前负载缩减线程数；环境变量设置了线程数上限；外层已经处于并行区，内层并行被串行化。

团队小于预期时，算子应当打印原因并终止，而不是继续执行。理由在于这里的降级是隐形的：结果仍然正确，只是每线程负责的区域变大，性能随之下滑，而这种下滑不会被任何断言捕获，只会表现为“多线程没有效果”。一旦这类结论进入调优流程，调优器会把线程数这一维判为无效，进而在后续所有形状上都选单线程，这个错误会扩散到整个搜索空间。

打印原因这一步不能省略。终止而不给出原因，会让使用者误以为是资源不足或驱动问题；给出触发条件，才能让人确认是环境变量还是嵌套并行导致。

## 3. 按线程隔离的状态

并行区内每个线程负责分区的一部分，下列状态必须按线程隔离，否则会互相覆盖。

打包缓冲必须私有。若多个线程共用一块打包区，一个线程写入的中间结果会被另一个线程覆盖，症状是偶发的数值错误，且与线程调度的时序有关。

性能计数的槽位必须是按线程索引的固定数组。若在每次提交时动态分配或追加，提交路径上会出现分配开销，且不同线程的记录可能写进同一位置，症状是统计结果对不上总时长。固定数组在生成期按最大线程数确定长度，各线程按下标写入，提交时不发生分配。

分区方式应当采用闭式公式直接算出每个线程的起止，而不是让线程之间协商或动态领取任务。闭式划分的结果只取决于线程数与形状，可复现，也便于在测试中逐线程核对覆盖范围是否恰好覆盖整体且互不重叠。

## 4. 编译与链接的拆分

生成的 C++ 与汇编应当使用不同的编译选项，并分别交给合适的编译器。

C++ 部分承担分区、打包与调度，只用到基础向量扩展，因此可以使用较低的指令集目标。汇编部分包含专用矩阵指令，必须使用完整的目标架构，并交给支持该架构的汇编器。

这样拆分有实际的工具链原因：部分编译器版本完全不支持专用矩阵指令对应的架构，也无法解析相应的汇编；而 C++ 部分若一并要求高版本架构，会连带失败。把汇编单独交给支持它的汇编器，C++ 部分就能使用通用编译器。

链接器的选择影响首次并行的开销。以 GNU 运行时为例，其并行区的首次初始化在参考实测的目标机器上约为数毫秒；而若干基于 LLVM 的运行时在同一台机器上首次初始化需要数秒，并在初始化期间触发大量文件系统访问，原因是它们要枚举整机的拓扑信息以支持亲和性设置。对于被测算子而言，这段开销与计算无关，属于纯粹的运行时启动成本。

另有一处接口细节：部分工具链在引入标准并行头文件时会与向量扩展头文件冲突，因此线程号与团队规模这类运行时函数宜直接声明原型，而不是包含该头文件。

## 5. 计时前必须完成预热

多线程内核的首次调用要付出一次性成本：创建线程池、唤醒处于低功耗状态的核。参考实测在目标机器上测得首次调用约为一秒，而稳态每次几毫秒。

若计时循环不做预热，这段一次性成本会摊入均值。以重复三次为例，均值会从几毫秒抬到数百毫秒，对应的算力从数百 GFLOPS 掉到个位数。这个失真足以让调优器得出错误结论：它会认为所有多线程候选都很慢，于是稳定地选择单线程。

因此预热是接入多线程的必要步骤，而不是可选的优化。预热次数按一次性成本的量级确定，取一到两次即可覆盖线程池创建与核唤醒。

修改预热默认值时，需要同步检查仓库中随包发布的全部配置文件。若配置文件里仍写着预热为零，默认值的修改不会生效，而这类遗漏不会报错，只会让计时继续失真。

## 6. 验证

验证分四层，逐层排除不同类型的缺陷。

第一层是线程数为一的回归。单线程产物的生成结果应当与接入前逐字节一致，说明多线程的代码路径没有侵入串行路径。

第二层是团队规模契约。构造线程数上限受限的场景，确认算子打印原因并终止，而不是降级执行。

第三层是覆盖与互不重叠。对若干个形状与线程数组合，核对各线程的起止区间恰好覆盖整体且两两不交。这一层用纯计算即可完成，不必上机。

第四层是数值与规模的交叉。同一形状在不同线程数下的结果应当一致；若不一致，优先检查打包缓冲是否私有，其次检查分区是否有重叠。

## 7. 约束

验证范围是目标架构上的单机多核执行，线程数在生成期固定。以下情形未经验证：跨节点执行；运行期动态改变线程数；与外部并行区嵌套；亲和性与内存绑定的完整策略。

这些情形下分区方式与首层开销的结论需要重新测量，不能直接沿用本文数据。
