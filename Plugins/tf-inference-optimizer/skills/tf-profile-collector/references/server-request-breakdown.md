# 服务端请求耗时分解日志（应用层逐请求埋点）

## 定位

服务端预测程序（如 `predictor_server` 等业务预测服务）自带的**逐请求耗时分解埋点日志**，直接测量每个请求各阶段的耗时（无需相减推算）。它能揭示请求的完整生命周期分解（请求解析 → 预测 → 解压 → 响应序列化），快速判断瓶颈在「框架层（请求解析/序列化）」还是「模型层（TF 预测）」。

这是**请求级**的黄金数据，与 trace（op 级）、perf（微架构级）互补，构成三层画像：

| 层级 | 手段 | 回答 |
|---|---|---|
| 请求级 | 服务端耗时埋点日志 | 框架层 vs 模型层，哪个阶段是瓶颈 |
| op 级 | trace | 哪个 op 热 |
| 微架构级 | perf / topdown | 为什么热 |

## 前提（非所有场景都有）

- 此日志是**特定服务自带的埋点**，不是所有服务都有（不确定是否为 TF 原生）。**必须在环境验证阶段确认目标服务是否存在此类埋点**，以及日志文件位置、字段名。
- 若无此埋点，跳过本采集，不得硬套或臆造字段。

## 采集方法

1. 在环境验证阶段确认：目标服务是否输出「逐请求耗时分解」埋点，日志文件路径 + 字段名。
2. 定位日志文件，读取逐请求分解字段，聚合统计各阶段平均耗时与占比。

## 典型字段（举例，字段名因服务而异，需按实际日志确认）

```json
{
  "p_total_cost": 2641,        // 总耗时
  "p_parse_packet_cost": 1851, // 请求解析（protobuf 反序列化 + feature convertor）
  "p_predict_cost": 567,       // TF 预测（session.run）
  "uncompress_cost": 182,      // 解压
  "p_pack_reply_cost": 1,      // 响应序列化
  "request_packet_size": 229724 // 请求包大小（字节）
}
```

> 不同服务的字段名、拆分粒度不同，务必先读实际日志确认，不套用上述字段名。

## 分析

各阶段耗时占比 → 定位头号瓶颈阶段：

- **请求解析占比高**（如 ~68%）→ 瓶颈在服务端预处理（protobuf 反序列化 + feature convertor），不是 TF 计算。优化方向应转向「优化服务端解析 / 缩减请求包 / 优化解压」，而非继续优化算子。
- **预测占比高** → 瓶颈在 TF 计算，回到 trace / perf 深入算子。
- **序列化/解压占比可忽略** → 不要在这些阶段浪费优化投入。

## 与其它手段交叉验证

- 请求级（埋点日志）× op 级（trace）× 微架构级（perf）三层互相印证，避免偏角度。
- 瓶颈定位类结论强制两维印证：如「请求解析是瓶颈」应同时有埋点日志（解析占比）+ 端到端 benchmark（P99 与预测耗时的差）印证，而非仅凭单一口径。
