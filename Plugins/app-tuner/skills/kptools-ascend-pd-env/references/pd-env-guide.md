# vLLM-Ascend P/D 环境采集与对比指南

> 配套 skill：`kptools-ascend-pd-env`。本文解释采了什么、字段怎么读、
> 跨机跨时间怎么用、出问题怎么查。

---

## 1. 为什么要比环境

P/D 分离部署里 Prefill 和 Decode 跑在不同容器、经常在不同机器上。两侧环境漂移的
典型后果不是报错，而是：

- **CANN / 驱动 / torch_npu 版本不一致** → 算子行为或精度差异，偶发 HCCL 超时
- **HCCL 环境变量不一致**（`HCCL_*`、`ASCEND_*`）→ 建链失败或带宽上不去
- **cpuset / cgroup 配额不一致** → 一侧 Host 侧成为瓶颈，吞吐被拖住
- **vLLM 启动参数不一致**（`--max-num-seqs`、`--block-size`、KV transfer 配置）→
  两侧容量不匹配，排队堆在一侧
- **Python 解释器不是同一个**（venv vs 系统 Python）→ 装的包和实际跑的包对不上

这些都是「两边一比就看出来、单看一边看不出来」的问题，所以本 skill 的默认动作是对比。

## 2. 12 个采集项

容器内的探针按下表顺序执行，每项单独计时、单独超时、单独兜底，结果按行流式输出。
一项卡住或失败不影响其他项，失败原因会写进结果，不会变成空白。

| 采集项 | 采什么 | 超时 | 取不到时 |
|--------|--------|------|----------|
| `system` | `/etc/os-release`、`uname`、glibc 版本、CPU 核数、内存 | 15s | 标记失败并记原因 |
| `kernel` | 内核版本与相关参数 | 15s | 同上 |
| `cgroup` | CPU 配额、内存上限、cpuset、cgroup v1/v2 | 15s | 同上 |
| `tools` | gcc / python / pip 等位置与版本 | 15s | 缺哪个记哪个 |
| `npu_smi` | NPU 设备列表与状态 | 25s | 非昇腾机器标记**跳过** |
| `lscpu` | CPU 架构与拓扑 | 15s | 标记失败并记原因 |
| `numa` | NUMA 节点与距离 | 15s | 同上 |
| `ascend_versions` | CANN / 驱动 / 固件版本文件 | 15s | 没有 Ascend 目录时**跳过** |
| `ascend_dirs` | Ascend 安装目录结构 | 15s | 同上 |
| `git` | 仓库 commit 与 dirty 状态 | 10s | 不是仓库时**跳过** |
| `processes` | 进程命令行、可执行文件、cwd、环境变量（最多 40 个进程） | 15s | 读不到的进程单独标注 |
| `python_profiles` | 解释器身份、`sys.prefix`、包清单（最多 4 个画像） | 20s/60s | 画像失败单独标注 |

单容器总预算 300s，整体超时也会把已采到的项写出来。

**只读范围**：不安装任何软件、不连网、不改容器、不重启服务。git 项用
`--no-optional-locks` + `GIT_OPTIONAL_LOCKS=0`，并且不执行会写 `.git/index` 的
`describe --dirty`，而是先 `status --porcelain` 再自己补 `-dirty` 后缀。

**包清单来源**按 `importlib.metadata` → `pip list --format=json` → `pip freeze`
依次降级，报告里会标出实际用的是哪一种。三种都失败时对比会提示
「包列表未采到，包差异不可信」，不要把「核心包无差异」当成结论。

**解释器识别**以进程 `argv[0]` 优先于 `/proc/PID/exe`：venv 的 python 是指向系统
解释器的符号链接，只看 `exe` 会把 venv 认成系统环境，`pyvenv.cfg` 也就找不到了。

## 3. 对比怎么做

每份采集摊平成「分类 + 项目名 + 取值」的可比较项，所有环境并排成一张矩阵，再两两成组比较。

### 分类

| 分类 | 内容 | 是否性能相关 |
|------|------|-------------|
| `基础信息` | OS、内核、glibc、CPU、内存、CANN/驱动版本、Python 身份 | 按项目名匹配 |
| `启动参数` | 进程完整命令行拆出来的参数 | 整类都算 |
| `核心包` | vllm、torch、torch_npu、transformers 等 | 整类都算 |
| `其他包` | 其余 pip 包 | 按项目名匹配 |
| `进程环境变量` | 进程实际生效的环境变量 | 按项目名匹配 |
| `Docker配置环境变量` | 容器定义里的环境变量 | 按项目名匹配 |

按项目名匹配的关键词包括 HCCL、ASCEND、NUMA、cpuset、thread、cache、batch、block
等。报告里性能相关差异单独计数，排在前面。

### 状态

| 状态 | 含义 |
|------|------|
| `相同` / `全部相同` | 所有环境这一项取值一致 |
| `不同` / `存在差异` | 取值不一致，报告里高亮 |
| `仅X有` | 只有某个环境有这一项（单边存在算差异，不是忽略） |
| `均缺失` | 所有环境都没采到这一项 |
| `无法比较` | 某个环境的这一项采集失败，两侧取值无法放在一起判断，不计入差异 |

### 列名

列名取采集包里的容器名。两个包里有同名容器时自动加包名区分，例如
`vllm-p(机器A)` 和 `vllm-p(机器B)`。

## 4. 跨机器、跨时间怎么比

采集包是自包含的：一个目录 + 一个同名 `.tar.gz`，拷到任何有 python3 的机器上都能读。

**跨机器**（A、B 两台都有容器）：

```bash
# 在 A 上
bash scripts/collect.sh vllm-p --role P --out ./A-env
# 在 B 上
bash scripts/collect.sh vllm-d --role D --out ./B-env
# 把 A-env/采集.tar.gz 和 B-env/采集.tar.gz 拷到一起，在任一台机器上
bash scripts/collect.sh ./A采集.tar.gz ./B采集.tar.gz --out ./对比结果
```

**跨时间**（升级前后、改配置前后）：

```bash
# 升级前采一次留着
bash scripts/collect.sh vllm-p --out ./升级前
# 升级后现采 + 拿旧包一起比
bash scripts/collect.sh vllm-p ./升级前/采集.tar.gz --out ./升级后对比
```

**多于两个**：给几个就比几个，两两成组，报告里每组一行小结。

采集包可以是目录，也可以是 .tar.gz。解包时拒绝绝对路径、`..`、符号链接，
并有单文件 512MB / 总量 2GB 的上限，避免恶意构造的采集包写满磁盘。

采集被硬杀掉、`collection_meta.json` 没来得及写的残缺目录，只要里面有
`inventory.json` 也能按「不完整的包」读进来，报告里标注不完整。

## 5. 退出码

| 码 | 含义 |
|----|------|
| 0 | 成功。只采一个容器、没有可对比的第二个环境，也算成功，产物是 `采集/环境报告.html` |
| 1 | 参数错误、输出目录非空；或给的采集包有没读进来的，而还剩环境可报（报告只含读进来的那些） |
| 2 | 环境不可用：没有 python3，或要采本机容器却连不上 docker（这时什么都不写，不会留下空报告） |
| 3 | 没有任何对象采集成功；采集包全都读不出来；或给的对象本身就凑不出两个环境 |
| 130 | 被 Ctrl-C 中断；已采到的部分、摘要、报告都会落盘 |

失败提示走 stderr 且排在成功汇总之前，`> 文件 2>&1` 或 `2>&1 | head` 时顺序不变。

1 和 3 的分界在于是否还有可报的环境：给两个包、坏了一个，剩下那个还能出单环境说明 → 1；
两个都坏、或本来就只有一个环境 → 3。采本机容器 + 一个坏包也是 1，因为单环境报告确实生成了。

## 6. 故障排查

| 现象 | 查什么 |
|------|--------|
| 退出 2，说连不上 docker | dockerd 没起、`DOCKER_HOST` 不对、或当前用户不在 docker 组。只对比已有采集包时不需要 docker |
| 提示「X 是本地已存在的目录，已按采集包处理」 | 工作目录里有和容器同名的目录（日志目录、上次的产物），把容器名抢走了；换个工作目录再跑 |
| 某容器只有 docker inspect 层面的信息 | 容器里没有 Python。`--python` 指定路径，或确认镜像确实没装 |
| `python_profiles` 失败 | 容器内 Python 版本低于 3.6，或进程读不到（跨 uid） |
| 包列表来源是 `pip freeze` | `importlib.metadata` 和 `pip list` 都失败了，包版本可能不全 |
| `npu_smi` 跳过 | 这台机器上没有 npu-smi，正常现象；真机上跳过要查驱动 |
| `git` 跳过 | 采集路径不是 git 仓库 |
| 对比显示「无法比较」很多项 | 另一侧采集失败了，先看 `采集/SUMMARY.txt` 的原因 |
| 对比显示「仅X有」很多项 | 两侧确实只有一边设置了这些项，常见于环境变量和启动参数 |
| 对比 note 里有「包列表未采到」 | 包差异不可信，不要据此下结论 |
| Python 画像采集失败 | 基础信息里与 Python 解释器相关的行可能显示为差异，以 `采集/SUMMARY.txt` 里的采集项状态为准 |
| 某项显示超时 | 容器负载高或命令卡住。超时是内部固定值，重跑一次；持续超时说明容器里那个命令本身有问题 |
| 采集被 Ctrl-C | 探针在容器内按进程组清理，不会留下孤儿进程；已采到的部分已落盘 |

## 7. 安全与数据

**取值口径**：一律原样记录，不做遮盖，`SUMMARY.txt` 末尾的说明和这一条一致。采集结果里会包含完整的环境变量、启动参数和路径，
其中可能有内部地址、token 或口令。采集包按内部资料保管，对外分享前请自查。

输出目录建的时候就是 `0700`，采集过程中有锁文件防止两个采集写同一个目录。
