# 采集范围与在线流程

## 测量契约

先用一句话定义分析对象，例如“稳态 CELT 编码 API 的流水线开销”。
分别填写以下三个范围，不用进程名代替阶段证明。

| 维度 | 核实内容 | 常见误差 |
|---|---|---|
| 进程 | PID/TID、exe、启动时间、子进程和线程覆盖 | Python 父进程或 verify_worker |
| 时间 | 准备、预热、目标循环、验证、清理 | 延长 repeats 同时重复非目标工作 |
| 事件 | 事件定义、用户/内核、缩放和聚合 | 请求 user 实际被忽略 |

记录输入哈希、配置、构建/库标识和 CPU。
构建标识不同可能正是 A/B 变量，不应要求两组构建完全相同。
但必须知道每组用了哪个构建，以及除目标改动外哪些条件被冻结。

## 环境与能力

保存 DevKit 版本、top-down help、CPU 型号、内核及虚拟化信息。
不要把文档中的“无虚拟机限制”解释为任何虚拟机都能访问 PMU。
以当前事件实际可用性为准，区分权限、未映射、事件不支持。
对于未验证参数，先查看本机帮助和试采日志。
先读已有环境诊断结果，避免重复采集相同信息。

若已安装 kptools-devkit，复用其 discover/run 入口。
离线包只有本技能，不能假设相邻目录一定存在。
找不到工具时先报告能力缺口，不伪造采集。
不在诊断中自动写 sysctl、改变服务配置或启用特权容器。

## 选择采集策略

### 完整命令

适用于完整任务诊断或初步范围排查。
保存工具对父子进程和退出的行为证据。
不要因命令包含 taskset 就假设只采到了业务函数。
框架自己的验证、PCM 生成和计时调用可能仍在目标进程内。

### 原生 worker 与 PID

用于可持续的目标阶段。
先确认 worker 独立运行成功，再附加。
PID 的 exe 和启动时间应在采集前后核对。
附加后进程退出，不能把同号新进程当成原目标。
线程型工作负载须确认工具包含哪些线程及新建线程。
检查 worker 内是否仍有逐帧时钟、校验和回解码。

### 延迟与固定窗口

核实当前版本 -D/-d 的单位、模式与组合支持。
用阶段标记确定稳态，不把固定延迟本身当作稳态证据。
目标阶段应覆盖整个窗口，并为启动抖动保留余量。
音频素材 22 秒不代表程序执行 22 秒。
记录实际窗口；若目标提前完成，解释其对目标的影响。

### 程序区间控制

仅当边界精度确有需要且用户允许插桩时采用。
预热与缓冲准备在启用事件之前完成。
整个目标块启停一次，避免逐帧控制开销主导测量。
记录该事件会话的 enabled/running 时间。
自行管理的事件不会自动开启或关闭外部 DevKit 的事件。
未取得对应平台事件与公式，不宣称基础 perf 事件复现了 DevKit Top-down。

## 状态记录

工具 stdout/stderr 分别保留，或用明确的合并日志。
管道应保存工具退出码，不能用 tee 的退出码代替。
wait 只能等待当前 shell 的子进程；外部服务通过监控证据验收。
目标收到信号时保存原始状态表示，如 -11 或 shell 的 139。
记录到的非零状态足以阻止正式比较，不必先归因根因。

短任务：检查最终退出及实际完成量。
服务：检查窗口内健康、进度与窗口后存活。
健康检查不能只证明 PID 存在而不证明业务仍有进展。
任务窗口结束后仍继续运行时，等待短任务最终状态再定稿。

## 重复与有界复采

三次独立运行只是起点，不能替代离散程度分析。
时间子报告不是三次独立运行。
频率、温度、负载和阶段漂移需要单独记录。
默认最多两轮修正复采，每轮只改变一个主要变量。
已达到用户时间预算时交付剩余不确定性。
硬故障停止普通重试，不靠更长窗口掩盖。

## 采集计划最少内容

- 目标阶段及三维范围。
- 当前工具与平台证据。
- 命令、工作量、预热和 CPU。
- 预期窗口与实际窗口记录方式。
- 工具和负载状态记录方式。
- 重复次数、资源预算和停止条件。
- 每轮将区分的假设。
- 成功、受限、失败时分别交付什么。
