# 环境和性能波动

## 先约定口径

测量前记录重复次数或预算、统计量和异常规则。
采用框架已有统计流程时记录其定义与版本。
报告工具中的 minimum_blocks 是项目声明的最少完整配对块数。
工具要求至少两块以避免单次值直接形成方向判断。
实际所需样本量由场景噪声、成本和目标精度决定。

## 可观察的干扰

| 来源 | 可以收集的证据 | 处理方法 |
|---|---|---|
| 同机任务争用 | 进程列表、负载、CPU 利用率 | 在约定资源下复测 |
| 频率与温度变化 | 频率、温度、限频记录 | 保持同等预热并记录状态 |
| NUMA 与线程变化 | 亲和性、线程数、内存节点 | 核对冻结配置 |
| 缓存与数据状态 | 预热记录、数据版本、缓存策略 | 按同一复位规则采样 |
| 网络或存储扰动 | 请求错误、延迟、队列、吞吐 | 单列受影响的窗口 |
| JIT、后台压缩或 GC | 编译、压缩、回收日志 | 检查是否为业务负载本身的一部分 |

框架可以观测的内容优先复用。
信息不可获取时记录观测缺口。
性能优化自身改变频率、GC 或缓存行为时，这可能属于优化机制。
因此环境审查需区分外部条件变化与优化引起的运行行为变化。

## 自对照

可对原版执行与候选对照相同的采样协议。
双方使用同一配置，以估计协议本身产生的相对变化。
自对照使用同一业务场景、机器和输入。
保留每个块的原值和相对变化。

noise.floor_pct 表示事先声明方法得到的噪声参考幅度。
可采用自对照绝对变化的约定分位数或保守范围。
选择方法及数据依据写入 noise.evidence 指向的记录。
噪声参考幅度是经验依据，其含义由采样协议决定。
工具不会为它自动赋予置信水平。

## 判断小幅变化

观察正向和负向变化时采用相同标准。
若收益绝对值落在噪声参考幅度内，标明可能存在波动。
若各块方向跨零，保守地保留方向未定。
若有效样本不足，先标明样本不足。
缺少自对照或其他可审查波动证据时写明依据不足。

工具的保守判读适合初步报告。
项目若有更完整的预声明统计分析，可以附上方法和结果。
原始数据、排除规则及独立采样单位均需可追溯。
人工补充判断时明确引用的证据，保留机器生成观察值。

## 复测策略

优先检查是否存在可恢复的环境偏离。
随后在同一窗口增加平衡重复。
避免只在好看的运行结果出现后停止。
预先设定最大预算或采样停止条件。
在预算内分批运行时，记录每批的采样计划和结果。

环境持续漂移时可缩短配对间隔。
部署成本高时使用可比的分块设计，并记录批次效应。
实际框架无法交错时披露顺序限制。
长时间只测一方产生的时间趋势需单独分析。

## 与业务门槛的关系

方向可辨但收益太小，记录未达到用户业务门槛。
方向未定时，业务是否接受还需用户的风险与收益标准。
主指标提升而错误率或 P99 回退时并列报告。
各指标的方向、门槛和统计口径独立记录。
若用户指定硬约束，最终验收检查全部约束。

## 现有技能联动

通过名称查找当前环境已安装的相应技能。
从其实际资源根读取文件，避免依赖原仓库的绝对位置。
优先复用已有记录和分析脚本。

- verify-optimization 可核对正确性、系统证据和测量是否完整。
- vector-experiment-methodology 适用于向量检索的条件冻结与漂移分析。
- kernel-paired-benchmark 适用于短算子的同进程自对照与平衡顺序。

联动只引入适用于当前问题的方法。
本次用户的框架、负载和验收口径保持在实验清单中。
局部算子的噪声证据只用于解释局部结果。
业务端到端结论仍需要完整业务测量的波动依据。
