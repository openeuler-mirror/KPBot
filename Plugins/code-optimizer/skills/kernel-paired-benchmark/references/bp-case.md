# BP 全位宽实例

本实例来自 Lance 的 Kunpeng 950 位打包解码实验。此前分开运行原版和候选时，部分位宽的收益幅度变化较大，因此增加同进程配对测量。

## 当时测了什么

同一个 Rust 程序包含原版与 NEON 解包路径。每个位宽准备一份压缩输入和一块输出缓冲区，两种实现按相同地址反复解包，每次输出 1024 个整数。

计时包含解包调用、公共入口检查和循环开销。打包、头部解析、输出分配、预热及结果校验放在外部。这个边界对应内核解包性能。

u32 遍历 W0 到 W32，其中 W0、W32 使用原版回退，W1 到 W31 检查 NEON 命中。u64 对应 W0 到 W64，零位宽和满位宽同样作为回退点。两种类型分别建立矩阵。

每个位宽、每次进程分别做 AA、BB、AB，每类 21 组，共 63 组、252 段计时。原版批次从小到大校准至约 10ms，三类实验共享同一迭代次数，每段前有 64 次未计时预热。

当时的自对照门槛为中位数在 [0.97, 1.03]，P10 至少 0.95，P90 至多 1.05。三个独立进程采用升序、降序和种子 2384 的乱序。测量绑定 CPU8、NUMA0，监控放在 CPU0，同时观察 CPU9 负载。频率策略为 performance，并保留运行频率采样。

这些参数应按目标机器和所需分辨能力调整。核编号、组数、校准时长和门槛都不是硬件通用常数。

## 这次经验改变了什么判断

自对照通过后，各个位宽的原版/候选比值更便于解释，但进程间幅度仍有变化。例如 u32 W1 三轮配对加速比约为 1.953、2.024、1.554。它们支持该负载下收益方向一致，无法据此保证所有运行都达到同一幅度。

回退点始终展示。候选优化生效与否应由入口审计、特性探测及实际调用证据确认，不能由加速比大小猜测。

原实验三轮汇总使用算术平均，配对分位数采用线性插值。迁移该实例时保留原定义，或从原始组数据生成另一个明确命名的统计口径。

## 如何复用

先把当前项目的两个真实入口接到同一测试程序，保留语义和正常分派。再依据 [执行步骤](../SKILL.md) 建立矩阵，按 [数据格式](protocol.md) 保存原始记录。

编解码器常见矩阵包括类型、位宽、块长、尾段、对齐和数据分布。业务实际只覆盖部分参数时，完整矩阵用于发现回退，业务分布用于估计实际收益。是否计入分配和解析，由所测问题决定。

本目录附有 [W1 历史测量摘录](../assets/bp-w1-evidence.json)，包含三个进程各 21 个配对比值、原归档文件名、日期和 SHA-256。`cases/protocol-contract/run.py` 从这些比值重新计算上述三个中位数。

摘录用于核对本文数字，未附完整四段计时、机器日志和构建产物，因而不能单独复现机器上的收益。该历史实验的参数与当前项目适用性仍需独立验证。发布时若要宣称硬件复现完成，应一并提供可分发的测试程序、构建身份和完整原始记录。
