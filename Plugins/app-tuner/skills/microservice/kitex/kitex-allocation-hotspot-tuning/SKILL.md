# Kitex 分配热点削减

本 skill 只回答"每请求分配从哪来、先削哪一个"。GC 参数与并行度在 `go-runtime-tuning`；编解码实现选择在 `kitex-thrift-codec-selection`；协议与元信息取舍在 `kitex-transport-protocol-selection`。

## 何时触发

- 每请求分配偏高（可从堆采样换算），堆增长快、GC 频繁。
- 分配热点集中在字符串/二进制解码、上下文链、透传元信息或请求响应结构。
- 放宽 GC 只能缓解不能解决，或内存预算不允许放宽。

## 输入

- 堆采样（按分配空间与分配对象数各看一次）。
- 每请求字节数、GC 次数与停顿、RSS。
- 请求形态：payload 大小、列表长度、是否有大量透传 header。

## 范围

- 覆盖：请求路径上的分配来源识别、优先级排序与业务侧削减。
- 不覆盖：GC 参数与并行度、协议选型、框架源码改造。

## 出处

- 编解码与元信息的分配点：`pkg/remote/codec/thrift/`、`gopkg/protocol/ttheader/`（版本以现场读取为准）。
- 采样方法：Go 官方 pprof 文档（`heap`、`alloc_space`、`alloc_objects`）。

## 命中验证与越界验证

- 命中：问"堆增长快但内存预算不能放宽，怎么查"，应答"先看分配空间与分配对象数两份采样，再按来源排序削减"。
- 越界：问"GC 百分比设多少"，应答属于运行时参数，转 `go-runtime-tuning`。

## 分配来源清单（按经验优先级）

| 来源 | 典型表现 | 削减方向 |
|---|---|---|
| 字符串/二进制解码 | 大字符串或二进制字段占分配大头 | 复用 payload、减小字段、按需返回字段 |
| 请求/响应结构与列表 | 每次调用新建结构体、切片增长 | 复用请求对象、预估切片容量、避免深拷贝 |
| 上下文链 | 每层中间件都往 context 写值 | 减少中间件层级、避免每请求新建公共值 |
| 透传元信息 | header 键值多、字符串拷贝多 | 精简透传键值（协议层见 `kitex-transport-protocol-selection`） |
| 缓冲区池未命中 | 池命中率低、反复新建 | 固定 payload 规模、避免极不规则的请求大小 |

## 执行步骤

1. **量化**：用分配空间与分配对象数两份采样交叉看，算出每请求字节数与对象数，同时记录 GC 次数与 P99。
2. **排序**：优先处理"占比高且可复用"的来源；占比高但属于业务语义（如必须返回大字段）的先不动。
3. **削分配**：从业务侧可改的部分入手（复用请求对象、限制返回字段、精简透传 header、固定 payload 规模）；不改框架源码。
4. **再谈 GC**：削减后再看 GC 频率，参数调整交给 `go-runtime-tuning`。
5. **验证**：每请求字节数、GC 次数、P99 三项同时看；只降分配不看延迟不算完成。

## 判断要点

- 单点占比过小的热点不值得做侵入性改造；先确认它在两份采样中都稳定出现。
- 常见分配大头是"返回值里的字符串/二进制"与"每请求新建的结构体/列表"，两者都在业务侧可控。
- 透传元信息的开销随键值数量与长度增长，能用协议层精简的不要靠代码优化补偿。
- 缓冲区池命中率与请求大小分布强相关；极不规则的 payload 会让池效果变差，这属于形态问题而非实现问题。

## 回退

- 业务侧改动：恢复原请求构造/返回字段。
- 池与缓冲参数：恢复原值。
- 任何改动都要能单独回退，不与 GC 参数或协议改动混在同一轮。

## 输出

- 输出分配来源排序、削减建议与验证口径；不产出文件。

## 与相邻技能的边界

- GC 参数与并行度：唯一归属 `go-runtime-tuning`，本 skill 只处理分配来源。
- 透传 header：是否透传、透传哪些键由 `kitex-transport-protocol-selection` 决定；本 skill 只评估其分配代价。
- 编解码实现：是否更换由 `kitex-thrift-codec-selection` 决定；本 skill 只处理更换之后的剩余分配。
- 框架源码：不改；候选改造见 `kitex-hot-path-analysis`，落地由 code-optimizer 承接。
- 本 skill 可独立调用，不依赖 `WORKFLOW.md` 的中间产物。
