# 传输协议选型检查表

## 1. 需求 → 协议

| 需求 | Framed | TTHeader | gRPC |
|---|---|---|---|
| 同语言、无透传 | 推荐 | 不需要 | 不需要 |
| 需要透传链路/租户/泳道信息 | 不支持 | 推荐 | 可用但成本更高 |
| 跨语言（非 Go 上游） | 需自定义 | 视对端支持 | 推荐 |
| 流式调用 | 不支持 | 部分能力 | 推荐 |
| 服务网格/代理识别 | 需额外约定 | 推荐 | 推荐 |
| 最小延迟与最小分配 | 推荐 | 次之 | 最差 |

## 2. 成本构成

- **Framed**：仅长度前缀，服务端按长度切包，无头部解析。
- **TTHeader**：每次请求解析头部并构造整型/字符串键值容器；字符串值需要拷贝。键值数量与长度直接决定分配量。
- **gRPC**：每次请求构造头部字段列表并做头部压缩，经过控制帧队列与流控状态机；即使空负载也比 Thrift 路径重。

## 3. 元信息精简清单

1. 只透传真正需要的键（链路、租户、压测标记等）。
2. 合并同类项，避免一个语义拆成多个键。
3. 缩短值长度；不要在 header 里放大块 JSON。
4. 高频公共值考虑放连接级或进程级，而不是每请求透传。
5. 定期清理历史遗留 header，尤其是已废弃的调试字段。

## 4. 泛化调用在 ARM64

- 动态编解码/泛化调用库通常只为 x86 提供加速实现，ARM64 走降级路径并打印告警。
- 优先用静态生成代码；必须泛化调用时，单独压测并与静态方案对比。
- 泛化调用的分配与 CPU 往往同时上升，不要只看 QPS。

## 5. 回归清单

- 超时与重试语义是否变化（尤其切换复用连接后）。
- 错误返回与异常路径是否仍能携带足够信息。
- 可选字段、嵌套结构、列表/映射的兼容性。
- 流式与单向调用。
- 两侧版本与协议选项一致。

## 6. 判定方法

- 逐项对比同一负载下 Framed 与目标协议的 QPS、P99 与每请求分配，三项同时看。
- TTHeader 额外统计透传键值数量与总长度，确认成本与 header 规模相关。
- gRPC 额外关注头部构造与流控相关帧的占比，判断成本是否属于协议固有。
- 任何结论都必须来自本轮同口径对照，不能引用外部基准。
