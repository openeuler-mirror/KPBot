# Kitex 版本升级审计

本 skill 只回答"升级会改变什么、怎么验证、怎么回退"，不做具体调优参数推荐。

## 何时触发

- 计划从旧版本升级到新版本。
- 升级后出现行为变化、性能下降或配置不生效。
- 需要确认文档里的老建议在新版本是否仍成立。

## 范围

- 覆盖：版本差异审计、配置显式化、升级前后对照与回退。
- 不覆盖：具体调优参数、性能收益承诺。

## 出处

- 默认值与选项：目标版本的 `pkg/rpcinfo/rpcconfig.go`、`internal/client/option.go`、`internal/server/option.go`，以及仓库变更记录。
- 依赖配套：目标版本的 `go.mod`。

## 命中验证与越界验证

- 命中：问"升级后配置看起来没生效"，应答"查默认值变更、废弃选项、依赖版本"的顺序。
- 越界：问"升级后该调哪个参数"，应答属于专项调优，转对应 skill。

## 必须在升级前确认的项

| 项 | 为什么要确认 |
|---|---|
| 默认传输协议 | 新版本曾把默认值从"带缓冲"改为 Framed，未显式配置的服务行为会变 |
| 默认编解码 | 默认可能仍是 fastcodec；自定义 codec 的优先级与回退顺序需确认 |
| 依赖版本耦合 | 网络库、序列化库、工具链与 Kitex 版本存在配套关系，混用会出现隐性降级 |
| 废弃选项 | 老选项可能被忽略或语义变化，配置"看起来生效"但实际没生效 |
| ARM64 支持缺口 | 部分动态编解码/泛化调用库只对 x86 提供加速实现 |
| 埋点默认值 | 注册链路追踪后埋点级别会自动升高，影响可观测性与开销 |

## 执行步骤

1. **冻结现状**：记录版本、显式配置项、默认值来源、关键依赖版本，并跑一轮基线（口径见 `microservice-ab-testing`）。
2. **列差异**：从变更记录与默认值代码确认差异，只保留与当前服务相关的项。
3. **显式化配置**：把依赖默认值的选项改为显式配置，避免升级后行为漂移。
4. **分步升级**：先升级依赖与工具链并重编译，确认功能等价，再评估性能；不要与调优混在同一轮。
5. **对照验证**：功能回归（错误码、可选字段、流式、单向）+ 性能对照（QPS/P50/P99/CPU/分配）。
6. **记录回退路径**：版本、配置、生成代码三者要能一起回退。

## 常见回归形态

- 吞吐或延迟变化，但配置未变：多为默认值或依赖版本变化。
- 某项配置不再生效：废弃选项或默认值优先级变化。
- ARM64 上特定能力变慢：加速路径缺失，需改用静态生成代码或换实现。
- 埋点开销突然上升：自动升级到更详细的级别。

## 输出

- 差异清单（与本服务相关）。
- 需要显式化的配置项。
- 回归结论：等价 / 有差异需适配 / 不建议升级。
- 回退步骤。

## 与相邻技能的边界

- 升级与调优分开：本 skill 只做差异审计与回归，不推荐具体调优参数；参数在 `kitex-transport-tuning`、`kitex-transport-protocol-selection`、`go-runtime-tuning` 等专项技能。
- 升级可能改变默认协议或默认并行度，发现这类变化时只输出"需要显式化配置"，具体取舍由对应专项技能决定。
- 本 skill 可独立调用，不依赖 `WORKFLOW.md` 的中间产物。
