# 跨版本移植形态前提核对清单

> 配套 SKILL.md 步骤 3。核心命题：**上游优化自带形态前提（shape premise），移植前必须逐项核对**——形态不合时整体移植实测 -22%，只取语义收益的自设计 +5.6%。

## 核对表（37.x → 4.25.x 实测）

| 上游优化 | 隐含前提 | heap/小消息/浅树形态下的后果 | 实测 | 结论 |
|---|---|---|---|---|
| 三段批量 MapMergeFrom（phase-1 批量分配节点） | arena 连续 bump 分配，n 次分配 O(1) 摊销 | 批量分配退化为 n 次 malloc，同时付出双倍 src 遍历 | merge 段 -22% | ❌ 放弃整体移植 |
| destruction 循环预取（ClearTable next-node + repeated Destroy lookahead） | destroy 是 miss-bound（深树大消息） | rank 形态 destroy：64MB cache 污染仅 +1.5%——非 miss-bound，预取只增加指令 | -1.2~1.4% | ❌ 放弃 |
| 数据预取 API（MaybePrefetch 系） | （改名型） | — | 4.25.8 已有同度实现（`MaybePrefetchForwards`，CACHELINE×16，同算法同状态机） | ⚠️ 先查本地版本，常是改名而非新增 |
| miss 路径逐元素拷贝构造 | 无形态前提（局部语义收益） | 任意形态可用；保留 element-wise 单遍避免上游方案的形态假设 | merge 段 +5.6% | ✅ 可移植（自设计实现） |
| 合并前一次性表 reserve | 扩容链成本显著 | 短 key rehash 实测 ~0.2µs/merge，先验估计高估 50 倍 | 增量 +0.46% | ✅ 可移植（低收益，先测后做） |

## 判断流程

1. **列出上游优化的机制**（它靠什么省时间：批量分配摊销？预取隐藏延迟？拷贝消除？）
2. **推断机制的隐含前提**（机制成立需要什么条件：连续分配？miss-bound？深度遍历？）
3. **核对生产实际形态**（heap 还是 arena？分配器痕迹 `je_*`/`malloc`？消息尺寸？树深度？）
4. **前提不符 → 弃整体移植**；机制无前提 → 提取语义收益，用自设计实现（element-wise 单遍、无批量假设）
5. **可迁移项也必须先过 A/B**：<5% 预估增量的优化实测后才允许进入实现评审（resize 案例：先验 25~35%，实测 0.46%）

## 通用规律

**新版本（37.x）的优化普遍针对 arena/大消息/深树形态**（上游默认负载在演化）；**旧版本生产负载常是 heap/小消息/浅树**。跨版本移植第一问永远是"形态对齐吗"——这一问的价值已在两个方向上验证：不合形态的整体移植 -22%，合形态的语义提取 +5.6%。

## 验收矩阵（移植类改动）

- 语义正确性：`DebugString()` 全量比对（**绝不能用 `SerializeAsString()`**——map entry 顺序未指定，不同构造路径合法输出本就不同）
- A/B：5 轮交替协议（见 `alternating-ab-protocol` skill 的 scripts/alternating_ab.sh），方向一致性 N/N
- 形态记录：记录本次负载的形态特征（分配器/尺寸/深度），负结果连同形态入档（见 `negative-results.md`）——同一优化换个形态可能翻正
