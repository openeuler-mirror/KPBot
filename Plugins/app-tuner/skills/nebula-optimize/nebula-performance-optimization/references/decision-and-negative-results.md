# 决策矩阵、负结果与实验台账

## 1. 先判断“值不值得做”

在动手前回答：

1. 瓶颈证据是什么？（进程/线程/函数/机制，不能只说“慢”）
2. 这个杠杆能直接影响该机制吗？
3. 预期收益量级？部署/配置是否已经做过？
4. 正确性风险/回滚成本？
5. 是否有同口径基线可对比？

如果 1/2/5 答不上来，先回 `nebula-hotspot-analysis`，不要开始改。

## 2. 决策矩阵

| 证据 | 杠杆 | 预期量级 | 风险 | 验证 |
|------|------|---------|------|------|
| Go1 futex 59%，graphd CPU 高 | 多 graphd/少 worker | +30–50% QPS | 中（端口/资源） | Go1 A/B + futex 迁移 |
| Go2/3 storaged RocksDB 高 | 多 storaged/读池 | +10–30% | 中（磁盘/内存） | Go2/3 A/B |
| FSP BFS 哈希/字符串高 | flat_map/SSO/拷贝消除 | +10–15% | 中高（语义） | FSP 逐路径比对 |
| 内存分配 20–40% | 对象池/复用/SSO | +5–10% | 中 | 微基准 + 端到端 |
| nGQL 解析 22% | 批量/预编译 | +10–15% | 低中 | Insert A/B |
| WAL fsync/compaction | WAL/compaction/磁盘/批量 | +5–20% | 中高（数据安全） | Insert A/B + 恢复演练 |
| 读路径整体 | LSE/LTO/jemalloc | 0–17% | 低中（ABI） | 五场景 A/B |
| 混合负载利用率低 | 浮动部署 | +10–30% | 低（布局） | 五场景 A/B |
| 单场景点查延迟 | 固定绑核（收益区间按线程级 1:1 口径；进程级口径见 config-tuning.md §2.3） | +10–20% | 低（弹性） | Go1 A/B |
| 数据模型不合理 | 改 VID/分区/索引 | 大 | 高（重导入） | 新 Space 验证 |

## 3. 负结果清单（不要再重复）

| 尝试 | 结果 | 根因 |
|------|------|------|
| `-mtune=neoverse-n2` | Go1 -2.5% | 热点在 futex/jemalloc，非指令调度 |
| `-mtune=tsv110` | 全场景 -1%~-3.2% | 鲲鹏 950 流水线不同 |
| `-march=...+crc` | 链接失败 | F14 模式与预编译 folly 不匹配 |
| `-fno-plt`/`-Bsymbolic`/`-fvisibility=hidden` | 链接失败 | 符号可见性冲突 |
| third-party `-O3` | 无显著收益 | autoconf 库已充分优化 |
| 全量第三方升级 2021→2025 | 读路径≈0 | 收益主要来自 Nebula 补丁 |
| 关闭 `query_concurrently` | -0.8% | 单跳无收益，增加调度 |
| `wal_sync=false`（3.8.0 上游默认；对照 true） | Insert -23.6% | compaction 增加 |
| write_buffer 256MB | Insert -25.4% | 大 buffer 增加 flush 延迟 |
| standalone worker 96→48 | -14.3% | 400 并发下 worker 不足 |
| 固定绑核用于混合负载 | 进程级 -14%~-29%；线程级 1:1 -36%~-51%（双口径，与 config-tuning.md §2.3 同源） | 静态核不足 |
| 线程级 1:1 绑核 | 全场景负收益 | 突发负载核搁浅 |
| NEON 判等用 `vmaxvq==0` | QPS 虚高 +126% | 误判 VID 相等，少做工作；正确性否决 |
| `std::move(const Edge&)` | 无收益 | 退化为拷贝 |
| 单做 Edge 移动 | FSP 几乎无变化 | 短 SSO 字符串移动≈拷贝 |
| schema 返回引用 | 未实施 | 虚函数接口影响 10+ 文件 |

## 4. 反模式

| 反模式 | 问题 |
|--------|------|
| 没有基线就调参 | 无法判断收益/回滚 |
| 同时改多个参数/补丁 | 无法归因 |
| 只看 QPS 不看成功率/延迟 | 可能用错误换吞吐 |
| 用一个场景的提升代表整体 | 掩盖其他场景回退 |
| 用微基准替代端到端 | 函数快但系统瓶颈在别处 |
| 负收益后叠加第二个变量“补救” | 归因彻底失效 |
| 把部署问题当源码问题 | 例如 futex 队列，改业务代码无用 |
| 把 I/O 问题当 CPU 问题 | 加 worker/CPU 无效 |
| 不做正确性验证就上性能测试 | 可能“更快地算错” |
| 生产直接试高风险参数 | WAL/副本/数据格式可能丢数据 |
| 不记录二进制/环境身份 | 无法复现 |

## 5. 停止条件

出现以下任一，停止继续优化并回到分析：

- 正确性失败（语义/路径/计数/写回读）。
- 连续两个杠杆无显著收益（<5%）。
- 收益只在一个场景，其他场景劣化。
- 环境不可控（其他租户、频率、数据未重置）。
- 优化进入第三方框架深层（改造成本/风险超过收益）。
- 用户未确认高风险变更（WAL/副本/数据格式/生产窗口）。

“到这里性价比不高”本身是有效结论，应记录并停止。

## 7. 归因检查

在宣布“有效”前，问：

- 两腿是否只差一个变量？
- 数据/缓存/compaction 是否重置/预热一致？
- 客户端是否先瓶颈？
- 成功率是否 100%（读场景）？
- 收益是否 >5% 且可复现？
- 其他场景是否不劣化？
- 热点是否按预期迁移（机制证据）？

任何一项答不上来，结论只能标“待确认”。

## 8. 边界与移交

| 问题 | 交给 |
|------|------|
| OS governor/THP/大页/irqbalance/ulimit | `kpbot-app-tuner` 的 `os-optimization` |
| BIOS SMT/C-State/NUMA/内存频率 | `bios-optimization` |
| 网卡队列/RSS/RPS/中断 | `network-optimization` |
| 绑核/NUMA 布局/线程亲和 | `cpu-affinity-optimization` |
| 通用 C/C++ 向量化/循环/汇编 | `kpbot-code-optimizer` |
| 压测口径/正确性/A/B | `nebula-test-verification` |
| 热点采集/归因 | `nebula-hotspot-analysis` |
| 部署/编译/数据导入 | `nebula-build-deployment` |

Nebula 专属的 Key/容器/Value/迭代器/schema 改动留在本 skill；不要把所有性能问题都归到
“源码优化”。
