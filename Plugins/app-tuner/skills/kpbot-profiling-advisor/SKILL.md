# KPBot 最终性能报告

面向两类阅读任务：工程师先通过《01-Profiling.md》理解应用怎样完成一次工作、时间与资源花在哪里，再通过《02-优化建议.md》决定先验证什么、何时继续或停止。两份文档分别写明应用、运行标识、必要配置和分析范围，开头相互链接。已有采样足以支持整理时直接使用。正文省去无采样基线表、环境清单与流程审计。

## 从实际运行产物组稿

从用户指定的运行目录或已归档的 skill 输出开始。按运行清单、任务包或结果里的路径定位文件。下表给出 KPBot 的常见入口；独立运行的 skill 也可直接提供自己的 CSV、trace、火焰图、分析日志或优化结果。

| 输入 | 读取和关联方式 | 写入报告 |
| --- | --- | --- |
| 采样或分析 skill 的结果 | 从 `performance_signal_summary.json` 或专项输出的 `findings` 出发，沿 `evidence_sources` 回到采样命令、原始计数、调用栈或 trace。用 `snapshot_metadata.json` 或本次采集记录核对运行标识、目标与窗口。 | 将可核实的观测写入 Profiling。来源记录为失败、降级或缺测时，只在影响解读的条目说明缺口，附实际日志。 |
| 优化 skill 的建议 | 读取 `candidate-skill-results/<subskill>.json` 中的 `subskill_name`、`findings` 和 `candidate_actions`，按 `action_id` 对照 `candidate_pool.json`。专项独立运行时，沿用其报告中的动作、前提和依据。 | 按原建议提炼动作、优先级、验证方案和回退条件。相同实验可合并，保留各来源 skill 和动作标识；互斥方案分别列出。 |
| 优化 skill 的验证结果 | 用运行标识、来源 skill 和动作标识关联 `rounds/round_N_summary.json` 及原始 A/B 数据。核对前后指标、正确性、执行状态和回退记录。 | 有可比实测时写明命中的结果分支和实际处置；未执行的动作标为“待验证”。已拒绝、已回退或无法独立归因的结果保留原状态及原因。 |

每条的“证据”或“依据”注明来源 skill，链接其实际输出及所引用的原件；同一文件已包含两者时只链接一次。缺少来源标识时据实写“来源未记录”，保留文件、命令和运行范围。跨轮历史资料单独标注配置与日期，摘要和原件冲突时指出差异，将待核实的数字留作缺口。字段和目录示例见[专项输出约定](../kpbot-app-tuner/references/subagent-orchestration.md)。

能力目录、skill 说明、经验库及示例用于理解现有产物。入选候选 skill 列表只代表已路由；实际条目取自已收到的采样结果或优化动作。有采样而无优化输出时，建议文档注明“本轮尚无优化 skill 输出”；仅有优化输出时，沿其证据引用定位采样，无法取得的原件标为缺失。报告整合阶段不代跑采样或调优。

## 章节与呈现

Profiling 沿用已有章节和证据锚点，新报告按“工作单位与测量范围 → 成本集中处 → 硬件机制 → 系统资源 → 归因边界 → 历史对照”组织。《02-优化建议.md》开头用一段话定义工作单位（例如一个请求或一个推理批次）、主要目标（吞吐、尾延迟或资源成本）和约束。正文以瓶颈方向为章、具体动作为条。重排已有建议时保留条目锚点，同步更新编号与引用。

### Profiling：一项采样分析，一个结果

保留已有章节和编号，以实际分析能力命名条目，例如 CPU 火焰图、热点函数、Top-down、缓存、TLB、SPE 或算子耗时。将已收到的采样结果按[能力对照表](references/capability-map.md)归类，逐项填写[采样条目模板](assets/profiling-item.md)。

- `result` 写最重要的实测结果，给出单位、采样对象和比较口径。共享的模型配置、运行标识和窗口可在文首写一次；单实例诊断、不同事件轮次或历史构建的差异在相应条目标明。
- `interpretation` 解释数字怎样回答本项问题。按需要列出算子排名、缓存层级、延迟分位数或跨轮结果的小表，再用一段话解释其中有区分度的差异和归因边界。例如，算子累计耗时接近时，结合调用次数区分高频小操作和少次昂贵操作；存在并行重叠时，交代累计耗时与墙钟时间各自代表什么。
- `sources` 链接足以复算或定位该结果的本地原件。火焰图同时提供事件、主要调用链及 SVG，注明函数自身占比或含子调用占比。Top-down 槽位数据缺失时注明缺口，已测的 stall 周期按自身分母呈现。静态模拟和实测分别标注。

交付前逐条复读：只看该条正文，工程师能否说出**测了谁、如何得到这个数、它支持什么判断、还有什么无法确定**？若只剩一个百分比或函数名，从原件补入对应的计数、对照或调用关系。证据不足时写明缺少哪项观测及其影响。优化动作归入第二份文档。

### 优化建议：一项动作，一组验证分支

先问：在当前并发和负载下，完成一单位工作需要做多少计算、移动多少数据，哪些环节在关键路径上等待？吞吐关注哪种资源先饱和，尾延迟关注哪些依赖和排队延长了单次完成时间。按优化 skill 的动作直接要改变的成本归类。以下方向供选择，有实际候选或验证记录才开章。

| 瓶颈方向 | 用什么证据区分机制 | 可归入本章的已有动作 |
| --- | --- | --- |
| 内存容量、带宽与访存延迟 | 容量看工作集、缺页与回收；带宽看每批搬运字节和实测可持续带宽；延迟看依赖访存、SPE 延迟、缓存及 TLB walk。单凭 LLC miss 比率无法确认带宽饱和。 | 减少拷贝、复用缓冲、调整数据布局、分块或 NUMA 放置 |
| 计算量与处理器执行效率 | 看热点算子在关键路径上的耗时、每批运算量及执行指令。结合内核路由、向量利用率或指令流水线证据，区分冗余计算和内核执行效率。 | 消除重复运算、替换计算内核、向量化或优化指令路径 |
| 并行、调度与同步等待 | 看关键任务、线程等待栈、锁竞争、负载不均及每单位工作 CPU 时间。忙等占比高时，还要区分调度开销和等待慢任务。 | 调整并行度、实例布局、任务粒度或同步策略 |
| 存储、网络与外部服务 | 分解请求链路上的传输、设备服务和排队时间，将慢请求与同窗 I/O、重传或下游等待关联。 | 合并 I/O、减少往返、调整并发或批处理 |

同一技术可以改变不同成本。例如算子融合消除中间张量写回时归入内存方向，消除重复计算时归入计算方向。每个动作只在主机制下完整列一次，相关章节可交叉引用。多种原因均可能成立时写明“待区分”，给出能区分它们的观测或对照；若已有候选但连主机制也无法判断，可集中列入“待定位”。章节按对业务目标的影响和证据强度排序。

每章开头用一两句话写出该方向的关键观测及瓶颈判断的验证状态。章内按优先级列出实际动作，逐项套用[建议条目模板](assets/optimization-item.md)。区分“机制是否成立”与“动作是否有效”：已测到访存长尾仍可对应一个待验证的布局方案。已采纳、暂缓、已回退等动作状态随条目标记，保留来源 skill 的实际决定。

- `rationale` 引出具体采样或历史对照，说明其适用范围、待区分的原因，以及该动作成立的条件。给出热点占比时要写清分母；引用已验证收益时标出当时的配置。暂缓项说明缺少什么证据。
- `experiment` 指定对象、变更变量、应固定的条件，以及怎样同时观察机制指标、业务主指标和正确性。已有实验写实际结果和适用性；尚待验证的预期使用条件语气。配对、噪声与回退的共同口径可引用首章。
- `branches` 用“可观测结果 → 下一步”列出真正会改变决定的分支。从来源 skill 的验证和回退计划提炼分支；未给出判据时注明待补项。例如等待减少且吞吐提高时复验并确定配置；只有每千样本 CPU 成本下降时，按资源目标决定采用与否；若业务目标仍是吞吐，则转查关键路径。关键指标持平或约束退化时写清何时停止或恢复哪个配置。
- `evidence` 链接对应的 Profiling 条目和本轮或历史原件。局部指标已改善、端到端收益待复验时，两种状态分别写明。

## 离线交付与复核

从本技能目录运行随附的归档脚本，将示例中的 `run/` 替换为实际报告目录。结构化输入字段见[应用调优报告字段约定](../kpbot-app-tuner/references/report-schema.md)。可以直接编写两份 Markdown，或分别用已有生成器渲染。为每个章节与信息点设置可见编号，为跨文档引用加稳定锚点，例如在发现前写 `<a id="p-wait"></a>`，在建议中写 `[图级等待](01-Profiling.md#p-wait)`。把两份文档放在同一目录；Profiling 的开头须有到优化建议的本地链接，归档器会递归收集另一份文档及双方引用的原始证据。

```bash
python3 scripts/archive_report.py --report run/01-Profiling.md --output run/最终报告.zip
```

交付两份 Markdown 和一个 ZIP。解压后检查两份文档各自可读、编号连续、跨文档条目定位正确、采样和图可离线打开，运行 `sha256sum -c SHA256SUMS.txt` 核验同目录文件。优先实验应当能回答“什么结果会让我改变决定”；将只写了“继续优化”的分支改成具体动作。
