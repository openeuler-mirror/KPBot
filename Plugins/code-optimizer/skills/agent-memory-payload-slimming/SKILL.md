# L1 载荷瘦身

## 前置条件

端到端追踪确认某字段"传上来就被丢弃"：在结果解析处下断点/打印，看 `attributes` 里哪些键
被构造后又 `pop` 掉，并确认代码里真的从不从该 map 读它（专用 loader / 按需查询除外）。

## 做法（不改 schema，只改查询投影）

图查询语言没有"删键"，但 map 投影可以用常量覆盖：

```cypher
-- 之前：properties(n) -> 每行带 1024 维向量（约 8 KB）
WITH n{.*, name_embedding: []} AS attributes
```

关系同理（`e{.*, fact_embedding: []}`）。保留 map 类型与全部动态属性，只把大字段置空列表；
解析端本来就会丢弃它，行为不变。用环境变量开关（默认关）便于 A/B。

## 实测（标定案例）

| 阶段 | x86_64 | 鲲鹏 |
|---|---|---|
| 检索 | 6.46 → 5.54 s（−14%） | 7.32 → 6.01 s（−18%） |
| 写入 | 4.80 → 4.22 s（−12%） | 4.91 → 4.40 s（−10%） |

结果指纹与图规模逐字节不变。

## 风险

- 若某条冷路径真的从 `attributes` 读向量，会拿到 `[]` → 报错或静默降级；
- 上线前全仓搜索该键的读取点，开关化 + 全量对拍。

## 不适用于

客户端与服务端同进程/共享内存（不存在"上行"）——此时改做"少物化、复用缓冲、视图替代拷贝"，
量化口径从"线上字节"换成"每行拷贝字节数"。

## 分别估算传输量与时间

- **传输量**：可省字节 = 每行大字段字节 × 候选行数 × 查询数（单位只到字节，不折算时间）；
- **时间收益上限** = 该阶段耗时占比 × 该阶段可消除的时间比例。后者与协议、驱动实现相关，通常无法从字节数推导——未知时标"待测"，用 A/B 实测填。

不要把"字节数 × 耗时占比"当时间（量纲不成立）。
