# kptools-kvc-crosscheck-analyzer：跨源总量对账

## 定位

本技能是 KVC 分析层的汇总枢纽。上游采集与分析（RoCE 计数器、offload 双写日志、master 记账、池侧快照）各自给出一个总量数字，本技能把它们放进同一张对账矩阵交叉验证，回答四个问题：

1. 每传输段实际多大（量级区间：下界/上界）
2. 各源总量之间对不对得上（双写对账、P/D 对称性）
3. 线上放大几倍（口径统一后的倍数）
4. 哪些传输模型假设被实测排除

本技能只消费现成数字，不做数据采集与日志解析。缺哪个源就在矩阵里如实标注"缺失"，不要用推导值冒充实测值——对账的价值恰恰在于实测数之间互证。

## 四源输入

| 源 | 口径 | 锚例 |
| --- | --- | --- |
| RoCE 计数器 | 窗口差分实收 | 601GB / 83.2GB |
| offload_watch | P/D 落盘双写 | P 351.3GB + D 352.9GB = 704GB |
| master 记账 | SSD Storage 累计 | 655.86GiB |
| 池计账 | ΔMem/ΔKeys | 2.61GB/请求（230 key × 11.4MB） |

四个源测的是同一次传输的不同侧面，各有盲区：RoCE 含重传与非 KVC 流量（毛量偏大）；offload 是落盘量不含 wire 开销（净量近似）；master 是记账口径（含持久化语义）；池侧只看驻留不看传输。正因为单源都有盲区，交叉才有信息量。

锚例来自真实实测，当量级先验用（不是硬性预期）：新的对账结果若与锚例差出一个数量级，先怀疑口径与单位，再怀疑物理。锚例数字本身也按各自轮次的段数口径得出——套用到新数据时必须用新数据的实际段数重算，不能照抄锚例结果。

## 分析项

六项按序执行，每项给出判定依据与锚例。

### 1. 每传输段量级区间

- 下界 = P offload 对账：351.3GB ÷ 段数。offload 是 KV 数据落盘量，不含协议头与重传，是净数据量的近似，**但"不含协议头/重传"不保证它一定是下界**：同一份 KV 被落盘两次、线上只传一次时，落盘字节会大于线上净量——先确认落盘数据与本轮请求/段/key 的对应关系与去重口径（双写目录是否按请求唯一命名、有无覆盖/重复落盘），关系未核实（检视意见）时保留对照值并**标明下界未知**（锚例轮次 351.3GB ÷ 512 段 = 0.686 ≈ 0.69GB/段，与 evals/ 期望输出同口径，容差 ±0.02——此前写 0.61 系 #496 抄录残留，0.61×512=312.3 无任何口径可推导）。
- 上界 = RoCE 实收 ÷ 段数：601GB ÷ 512 段 = 1.17GB/段。wire 实收含一切开销，故为上界。**前提：RoCE 覆盖完整**——计数只覆盖一张网卡或部分窗口时实收偏低，会把上界估小；覆盖未证实（未核对请求集、方向、全部链路、窗口）时，该上界与后续模型排除一并标为**无法判定**（见分析项 2）。

结论报区间不报单点：真实每段净量落在两者之间；区间宽度本身就是信息（协议头 / 重传 / 混入流量的总占比）。任一侧前提未核实时，区间降级为"已知对照值，界未证实"。

### 2. 排除法上界检验

对每个候选传输模型假设，算出它要求的 wire 总量，与 RoCE 实收对比：

- 锚例：假设"TP 全量复制"→ 每段 2.44GB → 512 段需 wire ≈1.25TB（2.44 × 512 = 1249.28GB；所需 wire 的**下界向下取整**——排除是单向判定，下界向上取整会让 1.2493–1.25TB 边界带的数据从"相容"误翻成"排除"）；实测仅 601GB → 排除该假设（锚例差 2 倍，不受取整影响）。

排除法是单向判定，输出三态：

- 实收 < 假设所需 wire → **排除**（量不够，假设不成立）——**前提是 RoCE 覆盖已证实**：计数只覆盖一张网卡、部分测试窗口或部分链路时，即使模型成立实收也可能低于所需字节，覆盖未核实（请求集 / 方向 / 全部链路 / 窗口逐项核对）时排除判定降级为**无法判定**（检视意见）
- 实收 ≥ 假设所需 wire → **相容**（不等于证实，只说数据不与假设矛盾）
- 证据不足（缺段数或假设参数，或 RoCE 覆盖未证实）→ **无法判定**

不要把"相容"表述为"验证成立"。

### 3. 线上放大倍数

放大倍数 = 线上传输量 ÷ 池计账量。锚例：P tx 5.56GB/请求 ÷ 池 2.61GB/请求 ≈ 2.1×。

**分子口径**：线上传输量取引擎侧 P tx（锚例口径）。RoCE 计数器是独立的 wire 源，不是引擎计数的上限；引擎 tx 全程总量与 RoCE 窗口实收出现差额（锚例 1423GB vs 601GB）属计量点与窗口覆盖差异，必须列入开放项，不得以"物理不可能"为由剔除任何一源。

**基数口径必须统一**——这是本技能最高频的错误来源。实测教训：分母取"量子口径"时，同一批数据得 4.5–5.7×；统一为池 key 口径（230 key）后，两轮独立实测同为 ~2×。倍数差异完全来自分母口径，不是物理现象。

执行纪律：

1. 报任何倍数之前，先写明分子与分母各自的口径（哪个源、什么单位、什么计数对象：请求 / key / 段 / 量子）。
2. 分子分母口径不一致时，先换算再相除。
3. 换算不了的（缺换算所需的计数），报区间并标注"口径不可统一，倍数仅供参考"。
4. **有限倍数区间只在有独立上下界时输出**（检视意见）：只知道每请求传输量与每 key 驻留量、缺每请求的 key 数及其范围时，无法算出有依据的区间——保留两源原值，标明"倍数区间无法计算"，并列出缺少的计数（每请求 key 数 / key 大小分布 / 副本数）；靠单点相除得出的"区间"是伪区间，不得输出。

### 4. P/D 对称性

P tx ≈ D rx 是健康基线（锚例 5.56 ≈ 5.50，偏差 <2%）。两侧显著不等（如 >10%）指向单侧异常——单侧重传、统计窗口错位、计量点不在同一路径。此时把单侧异常单列为待查项，不要摊进放大倍数里稀释结论。

### 5. 双写对账

双写总量 ÷ 请求数，与池 key 口径对比。锚例：704GB ÷ 256 请求 = 2.75GB/请求 ≈ 池侧 2.61GB/请求。两者接近**只说明总量相容**——等大的 key A 落盘两次、B 没落盘时，差异在总字节数中恰好抵消，即使双写总额与池驻留总额完全相同也无法排除重复或丢失（检视意见）。判断重复或丢失须按同一窗口的**请求、key、副本逐项核对**（key 级清单/计数对账），只有 key 级明细可得时才下"一致"结论；只有总额时，结论限定为"总量相容，key 级分布未核"。

### 6. 窗口放大拆解

逐项列明窗口口径差异，常见三类：

- 客户端失败但服务端全传（流式传输下客户端 ok=0 ≠ 服务端没传）
- 名义 token 数 vs 实测 token 数
- block 对齐带来的尾部放大

每项给出能解释的量级；对完后剩余无法解释的差额标注"开放项"，不要硬塞进已知解释——开放项是下一轮采集的输入。

## 陷阱

四个高频错误，全部来自实测教训，出现任何一个都足以让对账结论失效：

1. **基数口径不统一直接报倍数**（最高频）。同一批数据，分母从池 key 口径换成量子口径，倍数从 ~2× 变 4.5–5.7×，结论完全反转。见分析项 3 的执行纪律。
2. **GiB / GB 混算**。655.86GiB ≠ 655.86GB，差约 7%。对账矩阵里每个数字必须带单位，比较前先换算（1 GiB = 1.0737 GB）。锚例中 master 记账 655.86GiB 换算后 ≈704GB，恰好与 offload 双写总量 704GB 对上——这正是单位统一后两源互证的实例，不换算就会误判为"对不上"。
3. **客户端 ok=0 就断定服务端没传**。流式传输 bug 教训：客户端失败/计数为零不代表服务端没发。"传没传"只由服务侧与 wire 侧证据（RoCE 实收、master 记账）判定；客户端状态只用于解释窗口口径差异。
4. **源间对不上就静默剔除输入源**。用户给出的实测数（如引擎 P tx）除非有独立证据证明其口径错误，否则必须进入对账；引擎 tx 与 RoCE 实收对不上时，张力进开放项（候选：重传多计、多网卡窗口未覆盖、统计窗口错位），不能因为"超过 wire 实收"就判其为污染数据剔除。剔除任何输入必须写明理由与证据，并在报告中保留原值。
